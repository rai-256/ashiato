# collection-coverage Specification

## Purpose
収集が「動いていたか」を日ごとに残す。記録が無い日について、収集が止まっていたのか、
動いていたが出来事が無かったのかを後から区別できるようにする。
欠損の意味は**その時点で残さないと復元できない**ため、記録の格納と同じ関門で書く。

## Requirements

### Requirement: 稼働記録は新しく入った記録だけを数える

WHEN 記録を格納する THE SYSTEM SHALL その日のその論理ソースが稼働していたことを記録する。
THE SYSTEM SHALL 稼働記録の件数を、**新しく入った記録の数**とし、重複として弾いた分を数えない。
THE SYSTEM SHALL 重複だけが届いた日についても、稼働していたことは記録する。
THE SYSTEM SHALL この「日」を、記録の出来事時刻を **`Asia/Tokyo` に固定して**区切ったものとする。
THE SYSTEM SHALL 記録に付いたタイムゾーンで日を区切らない。

導出元: FR-33, NFR-13。ST01 の design D13。深掘り Q2。

部分失敗のときに成功分を再送するので、**重複の到着は常態**になる。重複まで数えると
件数が実態から離れ、稼働状況の画面がその値を読んだときに誤る。
一方で行そのものを立てないと、「欠損」と「重複だけ届いた」が区別できなくなる。

日の区切りを固定するのは、**NFR-13 の分母がぶれるため**。記録ごとのタイムゾーンで切ると
東西の移動で 1 年が 364 日にも 366 日にもなり、NFR-13 の分母がぶれる。
`Asia/Tokyo` は本人が選んだ（深掘り Q2）。当初の実装は UTC 固定だった。

#### Scenario: 重複は件数に加えない

- **WHEN** 同じ記録を 2 回送る
- **THEN** その日の稼働記録の件数は 1 である
- **AND** その日が稼働していたことは記録されている

#### Scenario: 日本時間の 0 時を境に別の日になる

- **WHEN** 出来事時刻が `2026-03-01T14:59:59Z` の記録と `2026-03-01T15:00:01Z` の記録を格納する
- **THEN** 前者は `2026-03-01` の稼働記録に、後者は `2026-03-02` の稼働記録に入る

#### Scenario: 記録のタイムゾーンが違っても日の区切りは動かない

- **WHEN** 記録に付いたタイムゾーンが `America/New_York` の記録を、出来事時刻 `2026-03-01T15:00:01Z` で格納する
- **THEN** その記録は `2026-03-02` の稼働記録に入る

### Requirement: 収集側は想定間隔ごとに生存信号を送り、取得できる状態かを併せて報告する

WHILE あるソースの収集が有効である THE SYSTEM SHALL そのソースに登録された想定間隔ごとに送られる生存信号を受け付ける。
THE SYSTEM SHALL 生存信号に、そのソースを**取得できる状態か**（権限・センサ・接続）を含めることを要求する。
**ただしメディアのソース（`c01-photo` / `c01-screenshot` / `c01-image` / `c01-video`）の取得できる状態かは接続を含めないものとして受け、送る契機の時点で接続があったかを、取得できる状態かとは別の欄で受けて残す。**
THE SYSTEM SHALL 接続の有無の欄を持たない生存信号も受け付け、その信号の接続の有無を「分からない」として残す。
THE SYSTEM SHALL 取得できない状態を報告する生存信号について、**何が満たされていないか**を残す。
THE SYSTEM SHALL 生存信号に、**前回の生存信号からの取得の試行回数と成功回数**を含めることを要求する。
THE SYSTEM SHALL 記録が 1 件も届かない日についても、生存信号が届いていればその日の稼働を残す。
THE SYSTEM SHALL 登録簿に無いソースからの生存信号を拒否する。

導出元: FR-78。深掘り Q1, Q5。ST09 の深掘り Q10、整合の確認 2026-10-17 の C7。

FR-33 は記録を生成したときにしか書かないので、**記録が 0 件の日は行が無いだけ**になり、
扉 #14 が求める「動きが無かったのか / 収集が壊れていたのか」を区別できない。区別は遡って作れない。

取得可否を併せて載せるのは、**収集プロセスが生きたまま取れていない**状態があるため。
Android は長期間使っていないアプリの権限を自動で剥がし、位置の権限が剥がれると
プロセスは動いたまま記録が 0 件になる。稼働だけを送っていると、壊れているのに「動いていた」と残る。

**メディアのソースの接続の有無を別の欄に残すのは ST09 の深掘り Q10**（FR-78 ★ 2026-10-17）。圏外の日に撮った写真は後で届くので、
接続を取得可否に混ぜると利用が主語のソースでその日が達成日から落ちる。接続を外すだけだと圏外だったことが行に残らず、後から数え直せない。

#### Scenario: 記録が 0 件でも生存信号があれば稼働が残る

- **WHEN** ある日にそのソースの記録が 1 件も届かず、生存信号だけが届く
- **THEN** 稼働状況を引くと、その日のそのソースが稼働していたことが返る
- **AND** その日の記録の件数は 0 である

#### Scenario: 想定間隔より細かい空きが取得率として残る

- **WHEN** 前回の信号からの間に取得を 360 回試みて 230 回成功したことを示す生存信号が届く
- **THEN** 稼働状況を引くと、その区間の試行回数と成功回数が返る
- **AND** その区間は収集側が生きていたものとして扱われる

#### Scenario: 信号が来ない区間は取得率では埋まらない

- **WHEN** ある区間について生存信号が 1 件も届かない
- **THEN** 稼働状況を引いても、その区間の取得率は返らない
- **AND** 収集側が生きていたことを示すものが無い

#### Scenario: 取得できない状態が理由とともに残る

- **WHEN** 位置の権限が無いことを報告する生存信号が届く
- **THEN** 稼働状況を引くと、その日の状態が「動いていたが取れない状態だった」として返る
- **AND** 何が満たされていないか（権限）が返る

#### Scenario: 登録簿に無いソースの生存信号は拒否される

- **WHEN** ソース登録簿に無い論理ソース名で生存信号を送る
- **THEN** 要求は拒否され、生存信号は残らない

#### Scenario: 圏外の写真の生存信号は取れる状態のまま接続が無かったことが残る

- **WHEN** 取得できる状態で、接続が無かったことを別の欄に持つ写真の生存信号が届く
- **THEN** 稼働状況を引くと、その日の写真の状態は「動いていた・記録なし」で、「動いていたが取れない状態だった」ではない
- **AND** その生存信号の行に、接続が無かったことが残っている

#### Scenario: 接続の有無の欄を持たない生存信号も受け付ける

- **WHEN** 接続の有無の欄を持たない位置の生存信号が届く
- **THEN** その生存信号は受け付けられ、行の接続の有無は「分からない」である

### Requirement: 生存信号の受け口は複数件をまとめて受け取り、1 件ごとの結果を返す

THE SYSTEM SHALL 生存信号の受け口が、複数件を 1 回の要求でまとめて受け取れるようにする。
THE SYSTEM SHALL 1 件だけを裸で送る要求も受け取る。
THE SYSTEM SHALL 一部が不正でも、正しい分は受け付ける。
THE SYSTEM SHALL 1 件も受け付けなかったときにだけ、要求そのものを拒否する。
THE SYSTEM SHALL 拒否の応答に、受け取った値や内部の詳細を含めない。
THE SYSTEM SHALL 取得できない状態を報告しながら**何が満たされていないかを持たない**生存信号を、
受け付けない。
THE SYSTEM SHALL 取得の試行回数または成功回数を持たない生存信号を、受け付けない。
THE SYSTEM SHALL 成功回数が試行回数を超える生存信号を、受け付けない。

導出元: FR-78。ST01 が `record-envelope` に置いた取り込み口と同じ形に揃える。

収集側は部分失敗の後で再送するので、1 件ずつの受け口だと再送のたびに要求数が膨らむ。
理由を持たない「取れない」を断るのは、**それが状態③の証拠にならない**ため ——
「取れない状態だった」とだけ残っても、権限なのかセンサなのか接続なのかが分からなければ、
扉 #14 が求めた区別に届かない。

#### Scenario: 複数件を 1 回で受け取る

- **WHEN** 生存信号を 3 件まとめて 1 回で送る
- **THEN** 3 件とも受け付けられ、1 件ごとの結果が返る

#### Scenario: 一部が不正でも正しい分は受け付けられる

- **WHEN** 3 件のうち 1 件が登録簿に無いソースで、2 件は正しい
- **THEN** 正しい 2 件は受け付けられ、不正な 1 件だけが拒否される

#### Scenario: 1 件も受け付けなかったときだけ要求が拒否される

- **WHEN** 送った生存信号がすべて拒否される
- **THEN** 要求そのものが拒否される

#### Scenario: 拒否の応答に受け取った値が含まれない

- **WHEN** 登録簿に無いソース名で生存信号を送る
- **THEN** 応答に、送ったソース名も内部の詳細も含まれていない

#### Scenario: 理由の無い「取れない」は受け付けられない

- **WHEN** 取得できない状態を示しながら、何が満たされていないかを持たない生存信号を送る
- **THEN** その生存信号は拒否される

#### Scenario: 取得の回数を持たない信号は受け付けられない

- **WHEN** 取得の試行回数を持たない生存信号を送る
- **THEN** その生存信号は拒否される

#### Scenario: 成功が試行を超える信号は受け付けられない

- **WHEN** 試行回数 10・成功回数 11 の生存信号を送る
- **THEN** その生存信号は拒否される

### Requirement: 生存信号は一次記録と同じ保護を受ける

THE SYSTEM SHALL 受け付けた生存信号を後から書き換えない。
THE SYSTEM SHALL 同じ生存信号が複数回届いたとき、行を 1 つだけ残す。
THE SYSTEM SHALL 生存信号について、収集側から受け取った原文をそのまま残す。
THE SYSTEM SHALL 生存信号の受信時刻を**時刻として**（日に丸めずに）残す。
THE SYSTEM SHALL 生存信号に利用者識別子を持たせる。

導出元: FR-78, FR-29, FR-30。深掘り Q13, Q14。

生存信号は「動いていた・記録なし」と「動いていたが取れない状態だった」の**唯一の証拠**で、
扉 #14 が「後から区別する唯一の手段」と呼んだ当のものにあたる。だから証拠として扱う。
収集側は部分失敗の後で再送する（「重複の到着は常態」）ので、冪等キーが無いと再送のたびに行が増える。

受信時刻を丸めないのは、**日境界の決定を行に焼き込まないため**。丸めると
`Asia/Tokyo` という選択が過去の行に固定され、後から引き直せなくなる。

#### Scenario: 同じ生存信号を 2 回送っても 1 行

- **WHEN** 同じ冪等キーの生存信号を 2 回送る
- **THEN** 残る生存信号は 1 行である

#### Scenario: 格納された生存信号は書き換えられない

- **WHEN** 格納済みの生存信号を更新しようとする
- **THEN** その操作は拒否される

#### Scenario: 受信時刻が時刻のまま残る

- **WHEN** 生存信号を格納する
- **THEN** その行は日付ではなく時刻を保持しており、日は集計時に `Asia/Tokyo` で引かれる

### Requirement: ソースごとに収集を開始した日が残る

THE SYSTEM SHALL 各ソースについて、収集を開始した日を
**そのソースのいちばん古い記録が作られた日**（生存信号なら発信された日）として残す。
THE SYSTEM SHALL 記録も生存信号も 1 件も無いソースを、まだ開始していないものとして扱う。
THE SYSTEM SHALL 収集開始日より古い記録が後から届いたとき、**収集開始日をその日まで遡らせる**（メディアのソースを除く）。
THE SYSTEM SHALL 収集開始日が遡ったとき、その日以降の状態と達成の判定を引き直せるようにする。
THE SYSTEM SHALL 収集開始日より前の日を、そのソースについて「導入前」として扱う。
THE SYSTEM SHALL 収集開始日より前の日を、NFR-13 の分母に数えない。
THE SYSTEM SHALL **登録簿にそのソースの行ができた日より前に発信された生存信号**を、
収集開始日の計算から除く。**生存信号そのものは受け取り、保存する。**
THE SYSTEM SHALL **記録**については、その時刻が登録簿に行ができた日より前であっても、
収集開始日の計算に用いる。
THE SYSTEM SHALL 引き継ぎ元のあるソースについて、**引き継ぎの鎖の根の収集開始日**を
そのソースの収集開始日とする。
THE SYSTEM SHALL **アプリ利用の集計（`c01-app-usage-rollup`）の収集開始日を、同じ携帯のアプリ利用（`c01-app-usage`）の収集開始日とする**。
THE SYSTEM SHALL 集計の記録が届いても（重複した記録の到着を含む）、集計の収集開始日を集計の記録の日へ動かさない。
THE SYSTEM SHALL **メディアのソース（`c01-photo` / `c01-screenshot` / `c01-image` / `c01-video`）の収集開始日を、そのソースの生存信号のうち登録簿に行ができた日以降でいちばん古いものが発信された日**（`Asia/Tokyo`）とする。
THE SYSTEM SHALL メディアのソースの記録が届いても（撮影の時刻が収集開始日より前でも、重複した記録の到着でも）、収集開始日を記録の日へ動かさない。
THE SYSTEM SHALL メディアのソースに生存信号が 1 件も無いうちは、記録があってもまだ開始していないものとして扱う。

導出元: FR-79, FR-61。深掘り 第 4 回 Q11, 第 5 回 Q22, 第 6 回 Q24, 第 7 回 Q26,
第 8 回 Q29, Q31。ST14 の深掘り Q8、申し送り st06 R7、整合の確認 C6。ST09 の深掘り Q13、整合の確認 2026-10-17 の C3 / C4 / C5 / K1。

**登録簿に行ができた日より前を外すのは本人の決定**（第 8 回 Q29）——
端末の時計が狂った生存信号が 1 件届くと収集開始日がその日まで落ちるが、
**収集開始日は前にしか動かない**（第 7 回 Q26）ので、正しい日を送り直しても戻らない。
実測では 1999 年に落ち、成功条件 1 が「**確定・未達**」で固まった。
**捨てるのではなく、計算から外す** —— 本人の答えは「受けるが、収集開始日の計算から外す」。

**閾値が掛かるのは生存信号だけ**（第 9 回 Q32）。生存信号の発信時刻は**端末の時計そのもの**だが、
記録の時刻は**出来事が起きた時刻**で、古いことに正当な理由がある ——
端末にある写真は撮影時刻が何年も前、ブラウザ履歴は導入時点で過去ぶんが取れる、
Takeout 系は過去 1 年ぶんをまとめて流し込む。
記録にも掛けていたときは、**登録簿に行を足してから過去ぶんを流し込む運用で、
記録が何万件あっても全日が「導入前」**になった（実測）。

**集計だけを例外にするのは ST14 の深掘り Q8 の本人の決定**（FR-79 ★ 2026-10-13）。
集計は最初の取り込みで**導入の 1〜2 年前の箱から入る**ので、「いちばん古い記録の日」のままだと導入前の 1〜2 年が格子に②/⑥で並ぶ。
集計は「過去の分をまとめて取った」もので、収集が始まったのは導入の日。重複した記録の到着でも当て直さないのは、
アプリを入れ直して端末の台帳が消え、同じ箱を送り直したときに開始日が戻らないようにするため。
ブラウザ履歴・Takeout 系の遡り（第 9 回 Q32）は変えない。

**メディアのソースを最初の生存信号の日にするのは ST09 の深掘り Q13 の本人の決定**（FR-79 ★ 2026-10-17。ST02 の第 9 回 Q32 の「写真の遡りは変えない」を覆す）。
ST09 の Q3 で導入前の写真を全部取り込むので、「いちばん古い記録の日」のままだと収集開始日がいちばん古い撮影日（時計の狂った 1 枚なら 2000 年）まで遡り、
成功条件 1 の写真の窓が導入より前に置かれて未達で確定する。過去の写真は「過去の分をまとめて取った」もので、集計と同じ形。
記録の時刻はどれも撮影と保存の時刻で「見始めた日」を持たないので、生存信号から決める（整合の確認 C4）。生存信号は書き換え禁止なので、ここから計算し直せ、
入れ直しても、いちばん古い生存信号の日のまま後ろへ動かない。見始めた日より前の記録のある日の見え方は「ソース × 日 の状態」の例外が持つ。

**引き継ぎの鎖から引くのも本人の決定**（第 8 回 Q31）——
ソースを分けて古い名前を退役させたとき、新しい名前が収集開始日を自分の登録日から
数え直すと、**名前を分けた日に成功条件 1 の窓が振り出しに戻る**。
1 年の連続性は成功条件 1 そのものなので、鎖の根から引く。

**登録簿に登録した日ではない**（第 5 回 Q22）—— ウィンドウとブラウザ履歴は PC 側の収集が
まだ存在せず、登録だけ先にあると**作っていないのに計測が始まる**。

**受け取った日でもない**（第 6 回 Q24）—— 圏外で溜めて送ると受信は数日後になり、
**記録が実際にある日が「導入前」になって NFR-13 の分母からも落ちる**。

**後から古い記録が届けば遡る**（第 7 回 Q26）。圏外での保持があるので
**いちばん古い記録が最初に届くとは限らない**。遡らせないと同じ誤りが残る。
窓の起点も一緒に動くが、**動くのは入力であって判定式ではない** ——
式が同じなら、同じ入力から必ず同じ答えが出る。

これが無いと、「記録も生存信号も無い日」が**まだ始めていなかった**のか
**収集が壊れていた**のかを区別できず、稼働状況の画面は導入前の期間がすべて不明で埋まる。
**day one から持たないと後から作れない。**

#### Scenario: 収集開始日より前は導入前になる

- **WHEN** あるソースの収集開始日が `2026-04-01` で、`2026-03-20` の状態を引く
- **THEN** その日の状態は「導入前」である

#### Scenario: 1 件も届いていないソースは開始していない

- **WHEN** 登録簿にあるが記録も生存信号も 1 件も届いていないソースの状態を引く
- **THEN** どの日も「導入前」であり、「途絶」になる日は無い

#### Scenario: 最初の信号が発信された日が開始日になる

- **WHEN** あるソースの最初の生存信号が `2026-04-01`（`Asia/Tokyo`）に発信される
- **THEN** そのソースの収集開始日は `2026-04-01` である
- **AND** `2026-03-31` 以前はすべて「導入前」である

#### Scenario: 溜めてから送っても開始日は取得した日になる

- **WHEN** `2026-04-01` から `2026-04-03` に取得した記録を、まとめて `2026-04-03` に送る
- **THEN** そのソースの収集開始日は `2026-04-01` である
- **AND** `2026-04-01` の状態は「導入前」ではない

#### Scenario: 後から古い記録が届くと開始日が遡る

- **WHEN** 収集開始日が `2026-04-05` のソース（メディアのソースでない）に、`2026-04-01` に取得した記録が後から届く
- **THEN** そのソースの収集開始日は `2026-04-01` に変わる
- **AND** `2026-04-01` の状態は「導入前」ではなくなる

#### Scenario: 開始日が遡ると達成の判定も引き直される

- **WHEN** 収集開始日が遡る
- **AND** そのソースの達成を引き直す
- **THEN** 分母は遡った開始日から数え直されている

### Requirement: 記録も生存信号も来ない期間は途絶として残る

IF あるソースについて、そのソースに登録された想定間隔を超えて**観測の記録**（格子で数えない記録を除いた記録。「取りこぼしの主張と時計の測定は稼働状況の記録として数えない」）も生存信号も届かない
THEN THE SYSTEM SHALL その期間を「途絶」として稼働記録に残す。
THE SYSTEM SHALL この判定を、収集側からの報告を待たずに**受け手の側で**行う。
THE SYSTEM SHALL 途絶の判定を、収集開始日以降かつ意図的な停止でない期間についてのみ行う。

### Requirement: 意図的な停止と破棄は時刻の範囲で残る

WHEN 利用者が収集を停止する THE SYSTEM SHALL 停止したソースと**期間を時刻の範囲として**残す。
IF 端末内の保持の上限を超えて記録を破棄する THEN THE SYSTEM SHALL
破棄した**期間を時刻の範囲として**と、破棄した件数を残す。
THE SYSTEM SHALL 端末からの破棄について、**どの端末が・なぜ捨てたか**と、**出来事の時刻の 1 時間ごとの件数**を残す。
THE SYSTEM SHALL 破棄の範囲を**始まりを含み終わりを含まない区間**として残し、1 件だけの破棄も範囲として残せるようにする。
THE SYSTEM SHALL これらを自由文ではなく、機械が範囲として読める形で残す。

導出元: FR-34, FR-9。深掘り Q3。

当初の `core.coverage` は (ソース, 日, 状態) が主キーで、期間は `note` の自由文しか持てず、
FR-34 の「期間」も FR-9 の「破棄した期間と件数」も満たしていなかった。
**粗く記録した過去は後から細かくできない。**

> **2026-09-14 の追加（ST04 の深掘り C8 / C12、独立レビュー R1 / R3 / R4）。**
> 端末・理由・時間ごとの件数は、**捨てた時点を過ぎると端末にも残らない**ので、受け手が行として持つ。
> 範囲と総件数だけでは、取得が一様でないので日ごとの件数を割り戻せない。
> 1 件の破棄は始まりと終わりが同じ時刻になり、始まりより終わりを後に求める範囲の制約に拒まれていた（実測）。

#### Scenario: 半日の停止が時刻の範囲で残る

- **THEN** その停止は開始時刻と終了時刻を持つ範囲として残っている

- **THEN** その破棄は、終わりが始まりより後の範囲として残っている

### Requirement: ソース × 日 の状態は 8 つのいずれかに決まる

THE SYSTEM SHALL 各ソースの各日について、次の 8 つのいずれか 1 つの状態を返す ——
「記録あり」「動いていた・記録なし」「動いていたが取れない状態だった」「意図的な停止」
「破棄された期間」「途絶」「導入前」「**退役**」。
THE SYSTEM SHALL 複数の条件が同時に成り立つ日について、次の順に評価し、
最初に当たったものをその日の状態とする ——
(1) 収集開始日より前（まだ開始していなければ全日）なら「導入前」（**ただしメディアのソース（`c01-photo` / `c01-screenshot` / `c01-image` / `c01-video`）は、その日に観測の記録が 1 件以上あれば「記録あり」**）、
(2) **登録簿の退役した日より後なら「退役」**、
(3) その日を丸ごと覆う破棄があれば「破棄された期間」、
(4) その日を丸ごと覆う意図的な停止があれば「意図的な停止」、
(5) 観測の記録が 1 件以上あれば「記録あり」、
(6) **端末が取りこぼしとして残した期間がその日に重なれば「動いていたが取れない状態だった」**、
(7) 取得できる状態の生存信号があれば「動いていた・記録なし」、
(8) 生存信号があれば（すべて取得できない状態なら）「動いていたが取れない状態だった」、
(9) 直前の観測の記録・生存信号からの経過が想定間隔を超えていれば「途絶」、
(10) そうでなければ「動いていた・記録なし」。
THE SYSTEM SHALL (10) で「動いていた・記録なし」とするのは、
**その日をまたぐ前後の観測の記録または生存信号が想定間隔以内にある**ときに限る。
THE SYSTEM SHALL 「観測の記録が 1 件以上ある」を、**その日に出来事の時刻が属する記録のうち、格子で数えない記録（「取りこぼしの主張と時計の測定は稼働状況の記録として数えない」）を除いたものがあること**
として判定する（稼働記録の件数ではなく、記録そのものから引く）。
THE SYSTEM SHALL 1 日を丸ごと覆わない停止・破棄について、その日の状態を決めさせない。
THE SYSTEM SHALL 「その日を丸ごと覆う破棄」を、**同じソースの破棄の範囲のうち、重なるもの・端が接するものを合わせた範囲**で判定する。
THE SYSTEM SHALL メディアのソースの、端末から消えた事実の記録（気づいた時刻の 1 件）を観測の記録に数える。
THE SYSTEM SHALL メディアのソースの収集開始日より前の「記録あり」の日を、達成（NFR-13）の分母と分子と、途絶の判定に入れない。
THE SYSTEM SHALL 同じ入力に対して同じ状態を返す。

深掘り Q1, Q5, 第 4 回 Q11, 第 5 回 Q19, 第 8 回 Q31。ST14 の深掘り Q7 / C9、整合の確認 C6。ST09 の深掘り Q13、整合の確認 2026-10-17 の C3。

**⑧「退役」を⑦「導入前」の直後に見るのは、両方が同じ型だから** ——
「その日はこのソースの収集期間の外」。`retired_on` は `collection_started_on` の対で、
**日付であって真偽値ではない**（ST03 の R56。真偽値だと「いま退役しているか」しか問えず、
**退役より前に起きた本物の途絶まで遡って消える**）。
判定は **「退役した日より後」** —— 退役した日そのものはまだ収集していたので、その日は本来の状態で出る。

**メディアのソースだけ (1) に例外を置くのは ST09 の深掘り Q13 で本人が読んだ見え方**（FR-79 ★ 2026-10-17）。
収集開始日を見始めた日にしても、取り込んだ過去の写真は格子の過去の日に記録として見える。窓と途絶の判定には入れないので、成功条件 1 の写真の窓は導入の日から始まる。

**「記録あり」を記録そのものから引くのは ST03 の R57。**
稼働記録の件数（その日に新しく入った記録の数）で決めていたときは、
ST03 が外部サービスからの更新経路を開けて**出来事の時刻が別の日へ動いた瞬間**、
記録の無い日が「記録あり」・記録のある日が「途絶」になった（ST03 の実測）。
稼働記録の表は「新しく入った記録だけを数える」を満たし続けるが、**状態の出どころではない**。

**取りこぼしの期間を生存信号より先に見るのは ST14 の深掘り Q7 の本人の決定**（申し送り st06 R5）。
アプリ利用は取得元（OS）が 10 日で消すので、収集が生きていて取得できる状態の生存信号も届いているのに、イベントだけが取れない形が起きる。
(7) を先に見ると、その日は「動いていた・記録なし」（使っていなかった）と区別がつかない。
取りこぼしの期間を主張する記録そのものは観測ではないので (5) に数えない —— 以前の評価の順（記録が 1 件でもあれば①）では、
「取れなかった」と主張する 1 件がその日を①に塗っていた（整合の確認 C6）。

**破棄の範囲を合わせてから丸ごと判定する**のは 2026-09-14 の追加（ST04 の深掘り C13、独立レビュー R5）。
端末は、1 度でも送ろうとした破棄の報告を書き換えず、その後の破棄を別の報告にする。
1 本ずつ見ると、2 本に割れた破棄はどちらもその日を丸ごと覆わず、⑤「破棄された期間」が立たない。
端末は続けて捨てた範囲を隙間なくつなぐので、**端が接するものだけ**を合わせる（離れた破棄を近さで合わせない）。
導出の規則なので、範囲が残っていれば引き直せる（design の D 番号に反転条件）。

**停止と破棄を記録より先に見るのは本人の決定**（第 5 回 Q19）——
「なぜこの日はデータが少ないのか」に画面が先に答える。1 日を丸ごと止めた日に記録が一部
残っていても、その日は「意図的な停止」として見える。

扉 #14 が稼働記録に求めた区別は「動きが無かったのか / 収集が壊れていたのか /
自分で止めたのか / バッファから破棄されたのか」の 4 つで、
3 つの表示ではそのうち「動きが無かった」と「壊れていた」を分けられない。
**③は生存信号か取りこぼしの期間が無ければ作れず、⑥は受け手の能動的な検知でしか作れず、
⑦は収集開始日を day one から持たないと作れない。**
**②はその日の生存信号があるか、前後を想定間隔以内の記録・生存信号に挟まれているときに立つ** ——
想定間隔が長いソース（ブラウザ履歴 24 時間、Takeout 系 60 日）では信号の無い日が間に挟まるので、
その日を⑥「途絶」にすると正常な運用が異常に見える。

#### Scenario: 丸ごと覆う停止も破棄も無い日に記録があれば記録あり

- **WHEN** ある日にそのソースの記録が 1 件以上ある
- **AND** その日を丸ごと覆う停止も破棄も無い
- **THEN** その日の状態は「記録あり」である

#### Scenario: 丸ごと覆う停止は記録より優先される

- **WHEN** 1 日を丸ごと覆う停止がある日に、そのソースの記録も 1 件以上ある
- **THEN** その日の状態は「意図的な停止」である

#### Scenario: 破棄は停止より優先される

- **THEN** その日の状態は「破棄された期間」である

#### Scenario: 生存信号だけなら動いていた・記録なし

> **2026-09-14 の追加（ST04 の深掘り Q3。proto で本人が選んだ）。**
> 丸ごと覆わない破棄は状態を決めないので、印が無いと**長い圏外の両端の日と、上限を小さくして溢れさせた日の破棄が画面から消える**。
> 印は形で持たせる（色を意味の担い手にしない）。**期間と件数は週の詳細だけ**に書き、ソースの見出しの下の一覧は作らない ——
> 一覧の行を足さないので、開いた直後の高さ（5 ソースで 997 px。proto の実測）は変わらず、ひとスクロールの予算に効かない。
> 印の色は段ごとに変える（「記録あり」と「動いていた・記録なし」の上は最も暗い段、「それ以外」の上は控えめな文字の明るさ）——
> 1 色だと「それ以外」の段の上で 1:1 になり見えない。

**「スクロールせずに 5 本」は現物の高さで成り立たなかった**（第 8 回 Q30）。
第 7 回 Q28 の根拠にした 600 px は `5 ソース × 5 行 × 24 px` で**セルだけを積んだ勘定**で、
見出し・余白・「1 年ぶんを見る」のボタン・達成の表を数えていない。
実際に宣言されている箱を積むと **約 1,491 px**（実測）。
本人の答えは「**同時に見える」を 1 スクロール以内に緩める**」で、
第 7 回 Q28（開いた直後は直近 4〜5 週だけ）と NFR-19（週の帯 24 px）は動かさない。

**ひとスクロールは 2 画面ぶん**とする —— 基準の画面は **360 × 640 CSS px**
（NFR-19 が幅に使っている小さい端末に、その端末の高さを合わせたもの）。
開いた直後に 1 画面ぶんが見え、1 回スクロールすると残りが見える。

**退役したソースを後ろに置いて畳むのは ST03 の R63** —— ST03 の運用では退役は 1 本きりではなく
増えるので、退役した格子が上に並ぶと **Must の 5 本が 1 画面から押し出される**。

1 年を見せるのは、完了の判定が「1 か月放置した後に開くと、欠けた日が一目で分かる」であるため。
直近 14 日では 1 か月の放置を見せられない。

**色を意味の担い手にしない。** ソースの区別は各格子に添えたソース名の文字が担う
（`ui-direction.md` の宿題 1 —— 6 色の輝度差が最小 1.009:1 で、グレースケールと 2 型色覚では
区別できない）。

**格子が 3 段までなのは、明度だけでは 7 段を分けられないため**（第 5 回 Q21）。
WCAG SC 1.4.11 は隣接する色に 3:1 を求めるが、7 段を隣接 3:1 で並べると 3^6 = **729:1** が要る。
**sRGB の理論最大は 21:1** で、21:1 を 6 等分しても隣接 1.661:1 にしかならない。
3 段なら 3:1 × 3:1 = 9:1 で収まる。8 状態の区別は**週を選んだときの文字**が担う。

**縦長にするのは NFR-19 のため**（第 6 回 Q25）。横長（週 = 列）だと 1 ソースが 53 列になり、
360 px 幅では週の帯が 6 px で 24 px を割る。縦長なら週の帯は幅いっぱいを取れる。
**新しい週を上**にするのは、開いた直後に出る直近 4〜5 週が新しい側になるようにするため。
完了の判定「1 か月放置した後に開くと欠けた日が一目で分かる」を満たすのは
**初期表示を直近 4〜5 週に絞ること**（第 7 回 Q28）で、
**週の向きだけでは 2 本目以降のソースに届かない**（1 本目の下に 53 行ぶんの距離がある）。

セルを表示専用にするのは、**1 週 7 日を横に並べても 1 セルが 24 px に満たない場合がある**ため。
選ぶ単位を週にすれば、セルの大きさに関わらず NFR-19 を満たせる。

### Requirement: 稼働記録と登録簿は利用者識別子を持つ

THE SYSTEM SHALL 稼働記録・ソース登録簿・生存信号・停止・破棄のいずれの表にも、
利用者識別子の列を持たせる。

導出元: FR-29。扉 #9。

FR-29 は「**すべてのテーブル**に」と定めており、扉 #9 は「単一利用者でも day one から持つ」で
決着している。現在は `core.event` にしか列が無い。ST02 が `core.coverage` を作り直すので、
**列を足す最も安い機会がここ**にあたる。

- **THEN** いずれにも利用者識別子の列がある

### Requirement: 破棄の報告の受け口は複数件をまとめて受け取り、1 件ごとの結果を返す

THE SYSTEM SHALL 端末からの破棄の報告を受け取る口を持ち、複数件を 1 回の要求でまとめて受け取れるようにする。
THE SYSTEM SHALL 1 件だけを裸で送る要求も受け取る。
THE SYSTEM SHALL 一部が不正でも、正しい分は受け付ける。
THE SYSTEM SHALL 1 件も受け付けなかったときにだけ、要求そのものを拒否する。
THE SYSTEM SHALL 拒否の応答に、受け取った値や内部の詳細を含めない。
THE SYSTEM SHALL 理由を持たない、または理由が 4 つ（90 日を超えた / 2 GB を超えた / 置き場に書けなかった / 置き場の行が読めなかった）のどれでもない破棄の報告を受け付けない。
THE SYSTEM SHALL 端末識別子を持たない破棄の報告を受け付けない。
THE SYSTEM SHALL 件数が 0 以下の破棄の報告を受け付けない。
THE SYSTEM SHALL 範囲を持つのに、終わりが始まりより後でない破棄の報告を受け付けない。
THE SYSTEM SHALL 時間ごとの件数の合計が報告の件数と一致しない破棄の報告を受け付けない。
THE SYSTEM SHALL 時間ごとの件数に、報告の範囲と重ならない時間を持つ破棄の報告を受け付けない。
THE SYSTEM SHALL 理由が「置き場の行が読めなかった」または「置き場に書けなかった」の報告に限り、範囲と時間ごとの件数を**両方とも**持たないことを許す。
THE SYSTEM SHALL それ以外の理由で、範囲か時間ごとの件数を欠く破棄の報告を受け付けない。

導出元: FR-9, FR-33。ST04 の深掘り C2, C8, C9, C12。生存信号の受け口（FR-78）と同じ形に揃える。

いま稼働記録には破棄の置き場（ST02）があるが、**端末から送る口が無い**。
端末は部分失敗の後で再送するので、生存信号と同じくまとめて受け取り、1 件ごとの結果を返す。
**端末は断られた報告を捨てずに送り直す**（証拠を捨てると扉 #14 の区別が遡って作れない）。
断る条件は形の不正と、登録簿に無いソース（登録簿を直せば次の送り直しで通る。取り込み口と同じ扱い）に限る。
形の不正で断られた報告は端末に残り続けるので、端末は断られない形でしか報告を作らない（`device-collection` の破棄の報告の要件）。

### Requirement: 破棄の報告は一次記録と同じ保護を受ける

THE SYSTEM SHALL 受け付けた破棄の報告を後から書き換えない。
THE SYSTEM SHALL 同じ破棄の報告が複数回届いたとき、1 つだけ残す。
THE SYSTEM SHALL 破棄の報告について、端末が報告に載せた原文の文字列を、1 バイトも変えずに読み戻せる形で残す。
THE SYSTEM SHALL 原文と報告の欄の食い違いを受け付けの条件にしない（欄を集計に使い、原文は証拠として残す。生存信号と同じ扱い）。
THE SYSTEM SHALL 破棄の報告の受信時刻を**時刻として**（日に丸めずに）残す。
THE SYSTEM SHALL 破棄の報告に利用者識別子を持たせる。

導出元: FR-9, FR-29, FR-30。扉 #14。ST04 の深掘り C8（独立レビュー R1）。

破棄の報告は「バッファから破棄されたのか」の**唯一の証拠**で、生存信号（FR-78）と同じ理由で証拠として扱う。
端末は 1 度送ろうとした報告を書き換えずに再送するので、冪等でないと再送のたびに件数が二重に数えられる。

#### Scenario: 同じ破棄の報告を 2 回送っても 1 つ

- **WHEN** 同じ冪等キーの破棄の報告を 2 回送る
- **THEN** 残る破棄の報告は 1 つである

#### Scenario: 格納された破棄の報告は書き換えられない

- **WHEN** 格納済みの破棄の報告を更新しようとする
- **THEN** その操作は拒否される

- **WHEN** 原文にキーの順序・空白・数値の表記を含む破棄の報告を格納する
- **THEN** 読み戻した原文の文字列は、送った原文の文字列とバイト単位で一致する

#### Scenario: 破棄の報告の受信時刻が時刻のまま残る

- **WHEN** 破棄の報告を格納する
- **THEN** その行は日付ではなく時刻として受信時刻を保持している

### Requirement: 稼働状況の応答は日ごとの破棄の件数と時刻の範囲を持つ

THE SYSTEM SHALL 稼働状況の応答の各ソース × 日に、その日（`Asia/Tokyo`）に属する**破棄の件数**を含める。
THE SYSTEM SHALL その日に重なる破棄の範囲（重なるもの・端が接するものを合わせた後）を、**その日の中で切った時刻の区間**として含める。
THE SYSTEM SHALL 区間の時刻を `Asia/Tokyo` の時と分で表し、日の終わりまで続く区間の終わりを `24:00` とする。
THE SYSTEM SHALL 区間ごとの件数を、その区間と重なる時間の件数の合計とする。
THE SYSTEM SHALL 1 つの時間が同じ日の 2 つ以上の区間と重なるときは、その時間の件数を**最も早い区間にだけ**数える（区間の件数の合計がその日の件数を超えない）。
THE SYSTEM SHALL 範囲を持たない破棄（置き場の行が読めなかった分など）を、どの日の件数にも入れない。

導出元: FR-9, FR-54。ST04 の深掘り Q3（効く先）/ C12 / C13。

画面の印と週の詳細の文字（「うち N 件を破棄（時刻〜時刻）」）は、この応答だけを材料にする。

> **2026-09-15 の追加（ST04 の実装レビュー R6。design D19（仮））。** 1 件ずつの破棄が同じ時間に 2 つの離れた区間を作ると、
> 「重なる時間の合計」を字義どおりに当てると同じ件数が 2 つの区間に二重に出て、区間の合計がその日の件数を超えていた。
> 最も早い区間にだけ数え、件数が 0 になった区間と、時間ごとの件数を持たない ST02 の破棄の範囲は、件数を添えずに時刻だけを出す。
件数を時間ごとに持つ（C12）ので、日をまたぐ範囲も日ごとに正しい件数で切れる。

#### Scenario: 日をまたぐ破棄は日ごとに切られる

- **WHEN** `2026-05-01 22:00` から `2026-05-02 03:00`（`Asia/Tokyo`）までの破棄があり、22 時台と 23 時台に 60 件ずつ、0〜2 時台に 60 件ずつある
- **THEN** `2026-05-01` の応答は件数 120 と区間 `22:00〜24:00` を持つ
- **AND** `2026-05-02` の応答は件数 180 と区間 `00:00〜03:00` を持つ

#### Scenario: 同じ時間に重なる 2 つの区間では前の区間にだけ数える

- **WHEN** `10:00:00` の 1 件と `10:30:00` の 1 件が別々の破棄として届き、10 時台に 2 件ある
- **THEN** その日の応答は件数 2 と、区間 `10:00〜10:01`（件数 2）・`10:30〜10:31`（件数 0）を持つ

#### Scenario: 範囲を持たない破棄は日の件数に入らない

- **WHEN** 置き場の行が読めなかった件数 2 の破棄の報告だけがある
- **THEN** どの日の応答も破棄の件数 0 で、区間を持たない

#### Scenario: 同じ報告を 2 回受けても日の件数は 1 回ぶん

- **WHEN** 10:00 から 13:00 までの 180 件の破棄の報告を 2 回受ける
- **THEN** その日の応答の破棄の件数は 180 である

### Requirement: 途切れの判定の対象は登録簿の印と記録の出どころで決まる

THE SYSTEM SHALL 登録簿の各ソースに「途切れの判定の対象か」の印を持たせ、**既定を「対象」**とする。
THE SYSTEM SHALL 次のソースを途切れの判定から外す ——
(1) 印が「対象外」のソース、
(2) **収集した記録（出どころが「収集した」）を 1 件も持たず**、本人が書いた記録（出どころが「本人が書いた」）か導出した記録（出どころが「導出した」）を持つソース、
(3) 退役した日以降のソース（退役した日そのものを含む）、
(4) 収集開始日を持たないソース、
(5) いまを覆う意図的な停止があるソース。
THE SYSTEM SHALL 携帯端末の時計の測定（`c01-clock`）・アプリ利用の集計（`c01-app-usage-rollup`）・滞在（`s01-stay`）・個人属性（`s01-attribute`）に「対象外」の印を付けて登録簿に入れる。
THE SYSTEM SHALL 新しく登録されたソースを、印を付けない限り判定の対象として扱う。
THE SYSTEM SHALL 引き継ぎ元のあるソースについて、引き継いだ収集開始日（「ソースごとに収集を開始した日が残る」）を (4) の収集開始日として扱い、引き継いだ日（登録簿に行ができた時刻）を最後に生きていた時刻の下限にする。

導出元: FR-35, FR-25, FR-54, FR-61, FR-34, FR-79。ST14 の深掘り C1 / C2 / Q6、整合の確認（`docs/audit/2026-10-13-st14-consistency.md`）C3。

**本人が書いたソースを外すのは、書かない日は壊れていないから**（FR-35 ★ 2026-10-07）。書いていない日は FR-57 で見え、書き忘れは FR-43 が促す。
外し方を**記録の出どころという分類**で決めるのは、名前を列挙すると、場所の登録（`s01-place`）や衛星が本人の代わりに書く記録のように後から増えるソースを取りこぼすため（整合の確認 C3）。
**収集した記録を 1 件でも持つソースは外さない**（spec-review R2）—— 取り込み口はどのソースにも「本人が書いた」の記録を受け付けるので、「1 件でも持てば外す」だと、収集のソースに 1 件混ざっただけで永久に鳴らなくなる。
**既定を「対象」にするのは厳しい側**（C1。独立レビュー R7）—— 既定が「対象外」だと、印を付け忘れた新しい収集のソースが黙って外れ、壊れても鳴らない。
`c01-clock` は位置の生存信号が携帯の稼働を持つので外す（Q6）。集計は 1 日に 1 回ほど OS の箱を取り直すもので、生きているかは同じ携帯のアプリ利用の生存信号が持つ。

#### Scenario: 新しく登録したソースは判定の対象になる

- **WHEN** 印を指定せずに新しいソースを登録簿に入れ、そのソースの記録が届いた後、想定間隔の 3 倍を超えて何も来ない
- **THEN** そのソースは途切れとして判定される

#### Scenario: 対象外の印のソースは途切れにならない

- **WHEN** 「対象外」の印を付けたソースについて、最後の記録から想定間隔の 3 倍を超えて何も来ない
- **THEN** そのソースは途切れとして判定されない

#### Scenario: 本人が書いた記録のソースは印が無くても途切れにならない

- **WHEN** 印が「対象」のソースに出どころが「本人が書いた」の記録が 1 件あり、最後の記録から想定間隔の 3 倍を超えて何も来ない
- **THEN** そのソースは途切れとして判定されない

#### Scenario: 収集した記録と本人が書いた記録が混ざったソースは判定の対象のまま

- **WHEN** 位置に収集した記録と出どころが「本人が書いた」の記録が 1 件ずつあり、最後の記録から 18 時間 1 分経っても何も来ない
- **THEN** 位置は途切れとして判定される

#### Scenario: 導出した記録のソースは途切れにならない

- **WHEN** 出どころが「導出した」の記録を持つソースについて、最後の記録から想定間隔の 3 倍を超えて何も来ない
- **THEN** そのソースは途切れとして判定されない

#### Scenario: 時計の測定と集計と滞在と個人属性は対象外で登録されている

- **WHEN** 登録簿の `c01-clock` / `c01-app-usage-rollup` / `s01-stay` / `s01-attribute` の印を読む
- **THEN** 4 つとも「対象外」である
- **AND** `c01-location` / `c01-app-usage` / `c01-photo` / `c02-window` / `c02-browser-history` / 書庫の各ソース / `s01-archive-inbox` は「対象」である

#### Scenario: 退役した日からは途切れにならない

- **WHEN** `2026-05-10` に退役したソースについて、`2026-05-10` に判定する
- **THEN** そのソースは途切れとして判定されない

#### Scenario: 収集を始めていないソースは途切れにならない

- **WHEN** 登録簿にあるが記録も生存信号も 1 件も届いていないソースを判定する
- **THEN** そのソースは途切れとして判定されない

#### Scenario: 引き継いだソースは届く前から判定の対象になる

- **WHEN** 収集開始日を持つソースを引き継いだ新しいソースに、まだ記録も生存信号も届かないまま、引き継いだ日から想定間隔の 3 倍を超える
- **THEN** 新しいソースは途切れとして判定される

#### Scenario: 停止している間は途切れにならない

- **WHEN** いまを覆う意図的な停止があるソースについて、最後の記録から想定間隔の 3 倍を超えて何も来ない
- **THEN** そのソースは途切れとして判定されない

### Requirement: 途切れは最後に生きていた時刻から想定間隔の 3 倍で判定する

THE SYSTEM SHALL 端末から来るソースの「最後に生きていた時刻」を、**観測の記録の出来事の時刻**と**取得できる状態の生存信号の発信時刻**のうち新しいほうとする。
THE SYSTEM SHALL 取得できない状態を報告する生存信号を「最後に生きていた時刻」に数えない。
THE SYSTEM SHALL 次の、途切れの判定で観測ではないとする記録（FR-35 の列挙）を「最後に生きていた時刻」に数えない ——
アプリ利用の取りこぼしの期間の主張（`c01-app-usage` の種類 `gap`）、PC の時計の測定（`c02-window` の種類 `clock-skew`）、
離席（同 `idle`）、PC が止まっていた期間（同 `powered-off`）、除外の印（同 `excluded`）。
THE SYSTEM SHALL 意図的な停止が終わった時刻を、それより前の「最後に生きていた時刻」の代わりに数える。
THE SYSTEM SHALL 出来事の時刻・発信時刻がいまの時刻より後の記録・生存信号を、**その記録・信号を受け取った時刻**で数える。
IF いまの時刻から「最後に生きていた時刻」を引いた経過が、そのソースの想定間隔の 3 倍を超える THEN THE SYSTEM SHALL そのソースを途切れと判定する。
THE SYSTEM SHALL PC を閉じていた時間も経過に数える。
THE SYSTEM SHALL 削除済みの記録も「最後に生きていた時刻」に数える（削除は観測した事実を消さない）。
THE SYSTEM SHALL 破棄の報告を「最後に生きていた時刻」にも途切れの判定にも数えない。
THE SYSTEM SHALL サーバ自身が作るソース（書庫の取り込み器）の「最後に生きていた時刻」を、取得できる状態の生存信号の発信時刻とする。
THE SYSTEM SHALL 判定を引くたびに導き、判定の結果を判定の材料として行に焼き込まない。

導出元: FR-35, FR-78, FR-7, FR-81, FR-82, FR-83, FR-85。ST14 の深掘り Q2 / Q3 / C9 / C12、整合の確認 C4 / C10。

**取れない状態の生存信号を数えないのは本人の決定**（Q2）—— 逐語の「最後の生存信号から」のままでは、権限が剥がれても生存信号は届き続けるので**永久に鳴らない**。
FR-78 が「壊れているのに動いていたと残る」と名指しした当の状態にあたる。
**観測ではない記録を数えないのは**、PC が 1 時間ごとに時計の測定の記録を残すため（C9）—— 数えると、窓が読めなくなった PC が毎時「生きている」になり、鳴らない。
**端末で作られた時刻で測る**のは格子と同じ時刻を見るため（Q3）。届いた時刻で測ると、圏外で溜めて送った記録が途切れを隠す。
未来の時刻を受け取った時刻に置き換えるのは、時計の狂った端末の 1 件が途切れを何年も隠さないようにするため（いまに丸めると、その 1 件が届いた後ずっと「いま生きている」になる）。
PC を閉じていた時間を数えるのは ST07 の深掘り Q8 の本人の判断（C12）。
破棄の報告で鳴らさないのは、端末が上限の 7 日前に自分で知らせるから（FR-9。C8）。破棄の報告は端末が生きていた証拠でもあるが、記録が捨てられた事実であって取れている証拠ではないので、生きていた時刻にも数えない。
判定を行に焼かないのは、想定間隔を変えたら判定もそのまま変わるようにするため（稼働状況と同じ。ST02 の design D6）。

#### Scenario: 位置の記録が 18 時間を超えて来ないと途切れになる

- **WHEN** 想定間隔 6 時間の位置について、最後の記録の出来事の時刻が 18 時間 1 分前で、その後に生存信号も無い
- **THEN** 位置は途切れとして判定される

#### Scenario: 18 時間ちょうどでは途切れにならない

- **WHEN** 想定間隔 6 時間の位置について、最後の記録の出来事の時刻がちょうど 18 時間前である
- **THEN** 位置は途切れとして判定されない

#### Scenario: 取得できる状態の生存信号があれば記録が無くても途切れにならない

- **WHEN** 写真の最後の記録が 10 日前で、取得できる状態の生存信号が 1 時間前に発信されている
- **THEN** 写真は途切れとして判定されない

#### Scenario: 取れない状態の生存信号だけが届き続けると途切れになる

- **WHEN** 位置の最後の記録と最後の取得できる状態の生存信号が 19 時間前で、その後は権限が無いことを報告する生存信号だけが 6 時間ごとに届いている
- **THEN** 位置は途切れとして判定される

#### Scenario: 時計の測定だけが届き続けても途切れになる

- **WHEN** ウィンドウの最後の前景の記録と最後の取得できる状態の生存信号が 19 時間前で、その後は時計の測定の記録だけが 1 時間ごとに届いている
- **THEN** ウィンドウは途切れとして判定される

#### Scenario: 取りこぼしの期間の主張は生きていた時刻に数えない

- **WHEN** アプリ利用の最後のイベントの記録と最後の取得できる状態の生存信号が 19 時間前で、その後に取りこぼしの期間を主張する記録が 1 件届いている
- **THEN** アプリ利用は途切れとして判定される

#### Scenario: 離席と停止と除外の印は生きていた時刻に数えない

- **WHEN** ウィンドウの最後の前景の記録と最後の取得できる状態の生存信号が 19 時間前で、その後に離席・PC が止まっていた期間・除外の印の記録が 1 件ずつ届いている

#### Scenario: 溜めてから送った記録は出来事の時刻で測る

#### Scenario: 削除済みの記録も生きていた時刻に数える

- **THEN** 位置は途切れとして判定されない

#### Scenario: 破棄の報告は生きていた時刻に数えない

- **THEN** 位置は途切れとして判定される

- **THEN** 位置は途切れとして判定されない

- **THEN** 取り込み器は途切れとして判定される

#### Scenario: 想定間隔を変えると判定も変わる

- **WHEN** 最後の記録が 2 日前のソースの想定間隔を 1 日から 6 時間に変える
- **THEN** そのソースは途切れとして判定される

### Requirement: 書庫のソースは最後の書庫から登録簿の日数で途切れとする

THE SYSTEM SHALL 登録簿に、ソースごとの「通知までの日数」を持たせる（持たないソースは想定間隔の 3 倍で判定する）。
THE SYSTEM SHALL 書庫の各ソースの通知までの日数を **75 日**として登録簿に入れる。
THE SYSTEM SHALL 通知までの日数を持つソースの「最後に生きていた時刻」を、**そのソースを運んだ書庫のうち最も新しく作られた書庫の作られた時刻**とする（その書庫で新しく入った記録が 0 件でもよい）。
THE SYSTEM SHALL 書庫の作られた時刻を持たない書庫について、置き場で見つけた時刻を作られた時刻として数える。
THE SYSTEM SHALL 形の確認を待っている書庫を、そのソースを運んだ書庫に数えない。
THE SYSTEM SHALL そのソースの項目を 1 件も持たない書庫（製品のファイルがあっても項目が 0 件のもの）を、そのソースを運んだ書庫に数えない。
IF 記録があるのに、そのソースを運んだ書庫が台帳に 1 件も無い THEN THE SYSTEM SHALL そのソースの記録のうち最も新しく届いた記録の届いた時刻を、最後の書庫の作られた時刻の代わりに数える。
IF いまの時刻から最後の書庫の作られた時刻を引いた経過が、通知までの日数を超える THEN THE SYSTEM SHALL そのソースを途切れと判定する。
THE SYSTEM SHALL 書庫のソースの格子の「途絶」を、今までどおり**最後の記録から想定間隔（60 日）**で判定する（通知とは測り方が違う）。
THE SYSTEM SHALL 本人が変えた通知までの日数を、移行を当て直しても戻さない。

導出元: FR-35, FR-16, FR-80, EXT-B, EXT-E。ST14 の深掘り Q9 / Q3 / C3、整合の確認 C5 / C8 / C9。

**75 日は本人の決定**（Q9。A —— 遅く鳴らすと取り逃した期間が取れなくなる）。
Takeout 系の 60 日 × 3 = 180 日では、鳴った時点で PC の手元の Chrome なら直近 90 日しか残っていない（EXT-E）。75 日は 2 か月の周期に 15 日の遅れを許し、90 日より前に鳴る。
予約エクスポートが 1 年で止まる（EXT-B）ことに気づく手段もこの通知になる。
Takeout が書き出す Chrome の履歴の保持は一次情報がまだ無く、本物の書庫で 75 日より短いと分かったら日数を縮める（FR-35 ★ C8）。
**書き出しの事実で測る**のは、出来事の時刻で測ると、その製品を使わなかった期間が途切れに見えるから（Q3）。
「運んだ最後の書庫」は台帳でそのソースを運んだ書庫のうち最も新しく作られたもので、FR-16 の最終日を運んだ書庫（最も新しい出来事を運んだ書庫）とは別物（整合の確認 C9）。
形の確認を待っている書庫は、まだ何も格納していないので数えない（確認を済ませないと 75 日で鳴る）。
項目が 0 件の書庫を数えないのは厳しい側（design D24（仮））—— 書き出しの範囲の誤りで中身が空の書庫を「書き出した」と数えると、取れていないのに鳴らない。
台帳より前に入った記録（台帳の行を残せなかった経路も含む）は、届いた時刻を書き出しの時刻の代わりにする —— 書き出しの時刻が分からないまま、すぐ鳴らすのも永久に鳴らさないのも事実と合わない。
格子は出来事の空きを見せ、通知は書き出しを忘れたことだけを知らせる。使わなかった製品は格子で「途絶」に見えても鳴らない（FR-35 ★ C5）。

#### Scenario: 最後の書庫から 75 日を過ぎると書庫のソースが途切れになる

- **WHEN** 視聴履歴を運んだ最後の書庫が 75 日と 1 時間前に作られ、その後に視聴履歴を運んだ書庫が無い
- **THEN** 視聴履歴は途切れとして判定される

#### Scenario: 2 か月ごとの書き出しでは書庫のソースは途切れにならない

- **WHEN** 視聴履歴を運んだ書庫が 60 日ごとに置かれ、最後の書庫が 60 日前に作られた
- **THEN** 視聴履歴は途切れとして判定されない

#### Scenario: 新しい行の無い書庫でも最後の書庫は進む

- **WHEN** 視聴履歴を運んだ書庫が 80 日前に作られ、10 日前に作られた書庫が視聴履歴を運んだが、入った記録は 0 件で既にあった記録だけだった
- **THEN** 視聴履歴は途切れとして判定されない

#### Scenario: 後の書庫が古い出来事を運ばなくても最後の書庫で測る

- **WHEN** 視聴履歴の最も新しい出来事を運んだ書庫が 80 日前に作られ、10 日前に作られた書庫が視聴履歴のより古い期間だけを運んだ
- **THEN** 視聴履歴は途切れとして判定されない

#### Scenario: 使わなかった製品は途切れにならない

- **WHEN** 視聴履歴の最後の記録の出来事が 70 日前で、視聴履歴を運んだ最後の書庫が 5 日前に作られた
- **THEN** 視聴履歴は途切れとして判定されない

#### Scenario: 使わなかった製品は格子では途絶に見える

- **WHEN** 視聴履歴の最後の記録の出来事が 70 日前で、視聴履歴を運んだ最後の書庫が 5 日前に作られた
- **THEN** 最後の記録から 61 日目の日の格子の状態は「途絶」である

#### Scenario: 形の確認を待っている書庫は最後の書庫に数えない

- **WHEN** 視聴履歴を運んだ最後の読み終えた書庫が 76 日前に作られ、5 日前に置いた書庫が形の確認を待っている
- **THEN** 視聴履歴は途切れとして判定される

#### Scenario: 作られた時刻の無い書庫は見つけた時刻で測る

- **WHEN** 視聴履歴を運んだ最後の書庫が作られた時刻を持たず、置き場で見つけた時刻が 76 日前である
- **THEN** 視聴履歴は途切れとして判定される

#### Scenario: 項目が 0 件の書庫では最後の書庫は進まない

- **WHEN** 視聴履歴を運んだ最後の書庫が 76 日前に作られ、5 日前に作られた書庫は視聴履歴のファイルを持つが項目が 0 件だった
- **THEN** 視聴履歴は途切れとして判定される

#### Scenario: 運んだ書庫が台帳に無いソースは届いた時刻で測る

- **WHEN** 視聴履歴の記録が 10 日前に届いていて、視聴履歴を運んだ書庫が台帳に 1 件も無い
- **THEN** 視聴履歴は途切れとして判定されない

#### Scenario: 実行時に足された製品のソースも 75 日で登録される

- **WHEN** 取り込み器が、登録簿に無いマイアクティビティの製品のソースを書庫から見つけて登録する
- **THEN** そのソースの通知までの日数は 75 日である

#### Scenario: 書庫のソースは 75 日で登録されている

- **WHEN** 登録簿の書庫の各ソースの通知までの日数を読む
- **THEN** どれも 75 日である
- **AND** 書庫以外のソースは通知までの日数を持たない

#### Scenario: 本人が変えた通知までの日数は移行を当て直しても戻らない

- **WHEN** 視聴履歴の通知までの日数を 60 日に変えた後に、移行を当て直す
- **THEN** 視聴履歴の通知までの日数は 60 日のままである

### Requirement: 途切れの判定は問い合わせの口から読める

THE SYSTEM SHALL 途切れと判定したソースの一覧を返す口を持つ。
THE SYSTEM SHALL その口に、途切れ 1 回ごとの識別子・ソースの表示名・論理ソース名・最後に生きていた時刻だけを返させ、**記録の中身を返さない**。
THE SYSTEM SHALL 判定した時刻を一緒に返す。
THE SYSTEM SHALL その口を、**収集アプリの資格情報でも画面の資格情報でも**読めるようにする。
THE SYSTEM SHALL 資格情報の無い問い合わせを断る。
WHILE サーバが起動してから判定を待つ時間（30 分）が経っていない THE SYSTEM SHALL 途切れの一覧を返さず、判定を待っていることを返す。
THE SYSTEM SHALL 同じ途切れが続く間、同じ識別子を返す。
THE SYSTEM SHALL 端末識別子の無い問い合わせにも判定を返す（画面などから読むため）。
THE SYSTEM SHALL 途切れの一覧を表示名の順（同じなら論理ソース名の順）で返す。

導出元: FR-35, PERM-10。ST14 の深掘り C4 / C5 / C7、整合の確認 C1。

**判定はサーバの 1 か所**（C4）—— 端末ごとに判定すると、端末によって鳴る・鳴らないが分かれる。
**返すのは表示名と最後の時刻だけ**（C5）—— 通知はロック画面に出る。
**収集アプリの資格情報で読める**のは、止まった端末の途切れを別の端末が知らせるため（Q1）。収集アプリの資格情報を「送るだけ」に締める ST44 は、この口を例外に残す（`docs/handoff/ST44.md`）。
**起動直後に判定しない**のは、端末が溜めた分を送り直す前に判定すると、サーバを起動し直すたびに鳴るから（C7）。待つ間に「途切れ無し」を返すと、端末が出ている通知を消してしまう。

#### Scenario: 途切れたソースの表示名と最後に生きていた時刻が返る

- **WHEN** 位置が途切れている状態で途切れの判定を問い合わせる
- **THEN** 位置の表示名・論理ソース名・最後に生きていた時刻・途切れの識別子が返る
- **AND** 判定した時刻が返る

#### Scenario: 途切れの応答に記録の中身が含まれない

- **WHEN** 緯度と経度を持つ位置の記録があるソースが途切れている状態で途切れの判定を問い合わせる
- **THEN** 応答に記録の緯度・経度・本文・原文が含まれていない

#### Scenario: 収集アプリの資格情報で途切れの判定が読める

- **WHEN** 収集アプリの資格情報で途切れの判定を問い合わせる
- **THEN** 要求は受け付けられ、判定が返る

#### Scenario: 画面の資格情報で途切れの判定が読める

- **WHEN** 画面のログインの資格情報で途切れの判定を問い合わせる
- **THEN** 要求は受け付けられ、判定が返る

#### Scenario: 資格情報の無い途切れの問い合わせは断られる

- **WHEN** 資格情報を持たずに途切れの判定を問い合わせる
- **THEN** 要求は断られ、判定は返らない

#### Scenario: 起動して 30 分の間は判定を待っていると返る

- **WHEN** 位置の最後の記録が 2 日前の状態でサーバを起動し、10 分後に途切れの判定を問い合わせる
- **THEN** 途切れの一覧は返らず、判定を待っていることが返る

#### Scenario: 起動して 30 分が経つと判定が返る

- **WHEN** 位置の最後の記録が 2 日前の状態でサーバを起動し、31 分後に途切れの判定を問い合わせる
- **THEN** 位置が途切れとして返る

#### Scenario: 途切れが続く間は同じ識別子が返る

- **WHEN** 位置が途切れたまま、途切れの判定を 2 回問い合わせる
- **THEN** 2 回とも位置の途切れの識別子は同じである

#### Scenario: 端末識別子の無い問い合わせにも判定が返る

- **WHEN** 位置が途切れている状態で、端末識別子を添えずに途切れの判定を問い合わせる
- **THEN** 位置が途切れとして返る

#### Scenario: 途切れの一覧は表示名の順に返る

- **WHEN** 表示名が「写真」と「位置」の 2 つのソースが途切れている状態で途切れの判定を問い合わせる
- **THEN** 一覧は表示名の順に並んでいる

#### Scenario: 途切れが無ければ空の一覧が返る

- **WHEN** どのソースも途切れていない状態で途切れの判定を問い合わせる
- **THEN** 途切れの一覧は空で返る

### Requirement: 途切れと戻りと届けたことは追記のみの台帳に残る

WHEN 途切れの判定を引いて、新しく途切れたソースがある THE SYSTEM SHALL そのソースの途切れが始まったことを、最後に生きていた時刻と判定した時刻とともに台帳に 1 行足す。
WHEN 途切れの判定を引いて、台帳で途切れが続いているソースが途切れでなくなった THE SYSTEM SHALL そのソースが戻ったことを、判定した時刻とともに台帳に 1 行足す。
WHEN 端末が自分の識別子を添えて途切れの判定を問い合わせる THE SYSTEM SHALL その端末にその途切れを初めて返したことを台帳に 1 行足す（同じ端末に同じ途切れを 2 回目以降に返しても足さない）。
THE SYSTEM SHALL 端末識別子の無い問い合わせについて、届けたことを台帳に残さない。
WHILE 判定を待っていると返す間 THE SYSTEM SHALL 台帳に何も書かない。
THE SYSTEM SHALL 台帳の行を書き換えさせず、消させない。
THE SYSTEM SHALL 台帳に利用者識別子を持たせ、記録の中身を載せない。
THE SYSTEM SHALL 途切れの識別子を、その途切れが始まった台帳の行から決める。

導出元: FR-35, FR-29。ST14 の深掘り C6。

後から「いつ途切れ、いつ端末に返したか」を数えるため（C6。`delivered` は「サーバが端末に返した」で、「端末で出せた・気づけた」とは読まない。Q-R16）。判定は引くたびに導くので、台帳が無いと、途切れが始まった・戻った・端末に返したの事実が残らない。
台帳は判定の材料ではない —— 判定の結果は台帳を読まずに記録・生存信号・書庫から出る。台帳は「途切れの識別子を続けて同じにする」ことと、事実を残すことにだけ使う。

#### Scenario: 新しく途切れると台帳に始まりが 1 行残る

- **WHEN** 位置が途切れた状態で途切れの判定を 2 回問い合わせる
- **THEN** 台帳に位置の途切れの始まりが 1 行だけ残っている
- **AND** その行は最後に生きていた時刻と判定した時刻を持つ

#### Scenario: 戻ると台帳に戻りが 1 行残る

- **WHEN** 途切れていた位置の記録が届いた後に途切れの判定を問い合わせる
- **THEN** 台帳に位置が戻ったことが 1 行残っている

#### Scenario: 戻ったソースは応答の一覧から消える

- **WHEN** 途切れていた位置の記録が届いた後に途切れの判定を問い合わせる
- **THEN** 応答の途切れの一覧に位置は無い

#### Scenario: 戻った後にまた途切れると別の識別子になる

- **WHEN** 位置が途切れ、戻り、また途切れた後に途切れの判定を問い合わせる
- **THEN** 位置の途切れの識別子は、1 回目の途切れの識別子と違う

#### Scenario: 端末に初めて返した途切れが台帳に残る

- **WHEN** 端末 A が自分の識別子を添えて途切れの判定を 2 回問い合わせ、端末 B が 1 回問い合わせる
- **THEN** 台帳に位置の途切れを端末 A に返したことが 1 行、端末 B に返したことが 1 行残っている

#### Scenario: 端末識別子の無い問い合わせは届けたことを残さない

- **WHEN** 位置が途切れている状態で、端末識別子を添えずに途切れの判定を問い合わせる
- **THEN** 台帳に位置の途切れを届けた行は無い

#### Scenario: 判定を待つ間は台帳に書かない

- **WHEN** 位置の最後の記録が 2 日前の状態でサーバを起動し、10 分後に端末が途切れの判定を問い合わせる
- **THEN** 台帳に行は増えていない

#### Scenario: 途切れの台帳の行は書き換えられない

- **WHEN** 途切れの台帳の行を更新または削除しようとする
- **THEN** その操作は拒否される

#### Scenario: 途切れの台帳に記録の中身が載らない

- **WHEN** 途切れの台帳の列を調べる
- **THEN** 記録の本文・原文・座標の列は無く、利用者識別子の列がある

### Requirement: 携帯と PC の収集アプリが途切れを OS の通知で知らせる

THE SYSTEM SHALL 携帯の収集アプリに、位置の生存信号を送る契機（6 時間ごと。起動時の 1 回を含む）で、**端末で 1 回だけ**途切れの判定を問い合わせさせる（ソースの数だけ問い合わせない）。
THE SYSTEM SHALL PC の収集アプリに、時計の測定の契機（1 時間ごと）で途切れの判定を問い合わせさせる。
THE SYSTEM SHALL 収集アプリに、問い合わせに自分の端末識別子を添えさせる。
WHEN 途切れの一覧に、その端末がまだ音を鳴らしていない途切れが 1 つでもある THE SYSTEM SHALL その端末に、途切れているソースすべての表示名を並べた通知を**音つきで 1 通**出させる。
WHEN 途切れの一覧が、その端末が音を鳴らした途切れだけから成る THE SYSTEM SHALL その端末に、通知を**音を鳴らさずに**一覧の中身へ差し替えさせる（出ていなければ音を鳴らさずに出す）。
WHEN 途切れの一覧が空になる THE SYSTEM SHALL その端末に、出ている途切れの通知を黙って消させる。
WHILE サーバに届かない、または判定を待っていると返る THE SYSTEM SHALL 収集アプリに、出ている途切れの通知を変えさせない。
THE SYSTEM SHALL 途切れの通知の文面を、ソースの表示名と最後に生きていた日時だけで組ませる（記録の中身を載せない）。
THE SYSTEM SHALL 途切れの通知を、携帯では他の通知と別の通知チャネルで出させる。
THE SYSTEM SHALL PC で音を鳴らさずに差し替えるとき、画面の端に通知を出さず、通知の一覧の中身だけを差し替えさせる。
THE SYSTEM SHALL 収集アプリに、音を鳴らした途切れを、収集アプリを起動し直しても覚えさせる。
IF 収集アプリが OS の通知を出せない（通知の権限が無い・差出人を登録できない） THEN THE SYSTEM SHALL 収集アプリに、通知を諦めたことをログに残させ、収集と送信を続けさせる。
THE SYSTEM SHALL 途切れを、外の中継（メール・チャット・プッシュ通知の中継）を通して知らせない。

導出元: FR-35。ST14 の深掘り Q1 / Q4 / Q5 / C5 / C11、整合の確認 C15。

**2 台が知らせるのは本人の決定**（Q1）—— 止まった端末は自分の途切れを知らせられないので、携帯と PC が互いの途切れを知らせる。外の push は文面を外に出す（exported）ので作らない。
**音は端末ごとに 1 回**（Q4。整合の確認 C15）—— 同じ途切れで携帯と PC が 1 回ずつ鳴りうる。鳴り続ける通知は切られ、切られた通知は 1 年の途中で気づく手段を失わせる（FR-35 ★ 2026-09-10）。
**1 通にまとめ、新しい途切れでだけ鳴らす**（Q5）—— 同時に途切れたソースの数だけ鳴らさない。
**問い合わせを今ある契機に相乗りする**（C11）—— 電池のために新しく起きる仕組みを足さない。携帯で鳴るのは止まってから 18〜24 時間後になる。
サーバに届かない間に通知を消すと、途切れが続いているのに消える。
**PC の差し替えで画面の端に出さない**のは、PC は 1 時間ごとに問い合わせるので、途切れが続く間に毎時表示されると「鳴り続ける通知」と同じになるから（spec-review R5）。
**鳴らした途切れを起動し直しても覚える**のは、Android は前景サービスでもプロセスを落として起動し直すので、覚えが記憶の中だけだと同じ途切れで何度も鳴るから（Q4。spec-review R6）。

#### Scenario: 新しい途切れで音つきの通知が 1 通出る

- **WHEN** 通知の出ていない端末が、位置が途切れていると返る問い合わせを受け取る
- **THEN** 位置の表示名を持つ途切れの通知が音つきで 1 通出る

#### Scenario: 新しく途切れたソースが増えたときだけまた鳴る

- **WHEN** 位置の途切れで音を鳴らした端末が、位置と写真が途切れていると返る問い合わせを受け取る
- **THEN** 位置と写真の表示名を並べた途切れの通知が音つきで出る

#### Scenario: 途切れたソースが減ると音を鳴らさずに差し替わる

- **WHEN** 位置と写真の途切れで音を鳴らした端末が、写真だけが途切れていると返る問い合わせを受け取る

#### Scenario: 戻ると通知が黙って消える

- **WHEN** 途切れの通知を出している端末が、途切れが無いと返る問い合わせを受け取る
- **THEN** 途切れの通知は消え、音は鳴らない

#### Scenario: サーバに届かない間は通知が変わらない

- **WHEN** 途切れの通知を出している端末が、サーバに届かずに問い合わせに失敗する
- **THEN** 途切れの通知は出たままで、音は鳴らない

#### Scenario: 判定を待っている間は通知が変わらない

- **WHEN** 途切れの通知を出している端末が、判定を待っていると返る問い合わせを受け取る
- **THEN** 途切れの通知は出たままで、音は鳴らない

#### Scenario: 同じ途切れでも端末ごとに 1 回鳴る

- **WHEN** 携帯の端末と PC の端末が、それぞれ初めて位置の途切れを受け取る
- **THEN** 携帯と PC のそれぞれで音つきの途切れの通知が 1 通出る

#### Scenario: 途切れの通知に記録の中身が載らない

- **WHEN** 位置が途切れていると返る問い合わせを受けて通知を出す
- **THEN** 通知の題と本文は、位置の表示名と最後に生きていた日時と定まった文言だけから成る

#### Scenario: 携帯は生存信号の契機で問い合わせる

- **WHEN** 携帯の収集アプリが位置の生存信号を送る契機に達する
- **THEN** 途切れの判定の問い合わせが端末識別子を添えて 1 回送られる

#### Scenario: ソースが複数あっても携帯の問い合わせは契機ごとに 1 回

- **WHEN** 位置・アプリ利用・写真の生存信号の契機が同じ時刻に重なる
- **THEN** 途切れの判定の問い合わせは 1 回だけ送られる

#### Scenario: 収集アプリを起動し直しても同じ途切れでは鳴らない

- **WHEN** 位置の途切れで音を鳴らした収集アプリを起動し直し、同じ途切れの識別子で位置が途切れていると返る問い合わせを受け取る
- **THEN** 途切れの通知は音を鳴らさずに出ている

#### Scenario: 通知を出せなくても収集は止まらない

- **WHEN** 通知の権限が無い状態で、位置が途切れていると返る問い合わせを受け取る
- **THEN** 通知は出ず、通知を諦めたことがログに残り、記録と生存信号の送信は続いている

#### Scenario: PC は時計の測定の契機で問い合わせる

- **WHEN** PC の収集アプリが時計の測定の契機に達する
- **THEN** 途切れの判定の問い合わせが端末識別子を添えて 1 回送られる

#### Scenario: 携帯の途切れの通知は専用のチャネルで出る

- **WHEN** 携帯で途切れの通知を出す
- **THEN** その通知は、常駐の通知とも未送信の保持の通知とも違う、途切れの通知チャネルで出ている

#### Scenario: PC の途切れの通知は Windows の通知として出る

- **WHEN** PC の収集アプリが位置が途切れていると返る問い合わせを受け取る
- **THEN** Windows の通知の履歴に、位置の表示名を持つ途切れの通知が 1 件ある

#### Scenario: PC の音なしの差し替えは画面の端に出ない

- **WHEN** 位置の途切れで音を鳴らした PC の収集アプリが、次の契機で同じ途切れを受け取る
- **THEN** 差し替えた通知は画面の端に出ない設定で、通知の履歴の中身だけが差し替わっている

### Requirement: 取りこぼしの主張と時計の測定は稼働状況の記録として数えない

THE SYSTEM SHALL 稼働状況の日の状態と達成日を数えるとき、次の、格子で観測ではないとする記録（FR-54 の列挙。以下「格子で数えない記録」）を「記録」に数えない ——
アプリ利用の取りこぼしの期間の主張（`c01-app-usage` の種類 `gap`）と、PC の時計の測定（`c02-window` の種類 `clock-skew`）。
THE SYSTEM SHALL この除外を、「記録あり」の判定・途絶の判定の前後の記録・達成日の「記録が 1 件以上ある日」のすべてに当てる。
THE SYSTEM SHALL 格子で数えない記録そのものは格納し、読み出せるままにする（捨てない）。
THE SYSTEM SHALL 稼働記録の件数（新しく入った記録の数）には、格子で数えない記録も今までどおり数える。

導出元: FR-54, FR-7, FR-85。ST14 の深掘り C9、申し送り st05 R6 / st06 R5、整合の確認 C13。

数えると、**何も取れていない日が主張の 1 件で「記録あり」に塗られる**（FR-54 ★ 2026-10-13）。
PC は窓が読めなかった日も 1 時間ごとに時計の測定を残し（FR-7 ★ 2026-09-15）、携帯は取得元に残っていなかった期間を 1 件の記録として残す（FR-85）。
格子から外すのはこの 2 つの種類だけ（FR-54 ★ の列挙。整合の確認 C13）。離席・止まっていた期間・除外の印は、**PC の収集がその日に動いていた**証拠なので（離席の出入りは入力を見ている収集が書き、止まっていた期間の始まりは PC がまだ動いていた時刻、除外は前景を読んで外したもの）、格子では今までどおり数える
（途切れの判定では数えない —— 「途切れは最後に生きていた時刻から想定間隔の 3 倍で判定する」。窓が読めなくなった PC でも離席の出入りは書かれるので、途切れを隠す。design D22（仮））。
稼働記録の件数は「新しく入った記録だけを数える」の表で、状態の出どころではない（ST03 の R57）。

#### Scenario: 時計の測定しか無い日は記録ありにならない

- **WHEN** ある日にウィンドウの記録が時計の測定だけで、取得できない状態の生存信号がある
- **THEN** その日のウィンドウの状態は「動いていたが取れない状態だった」である

#### Scenario: 時計の測定しか無く生存信号も無い日は途絶になりうる

- **WHEN** 想定間隔 6 時間のウィンドウについて、ある日とその前後 1 日に時計の測定の記録しか無く、生存信号も無い
- **THEN** その日のウィンドウの状態は「途絶」である

#### Scenario: 前景の記録がある日は時計の測定があっても記録あり

- **WHEN** ある日にウィンドウの前景の記録が 1 件と時計の測定の記録が 24 件ある
- **THEN** その日のウィンドウの状態は「記録あり」である

#### Scenario: 格子で数えない記録も読み出せる

- **WHEN** 時計の測定の記録を格納した後に記録を読み出す
- **THEN** その記録は読み出せる

#### Scenario: 格子で数えない記録も稼働記録の件数には入る

- **WHEN** ある日にウィンドウの時計の測定の記録を 3 件格納する
- **THEN** その日のウィンドウの稼働記録の件数は 3 である

### Requirement: 取りこぼしの期間は週の文字に理由と期間で出る

THE SYSTEM SHALL 稼働状況の応答の各日に、その日に重なる取りこぼしの期間（`c01-app-usage` の種類 `gap` の記録の始まりと終わり）を、理由とともに持たせる。
THE SYSTEM SHALL 取りこぼしの期間の重なりを、始まりを含み終わりを含まない区間と、`Asia/Tokyo` の日で判定する。
WHEN 利用者が週を選ぶ THE SYSTEM SHALL その 7 日のうち取りこぼしの期間が重なる日について、状態の名前に添えて、理由ごとに次の文字と期間を出す ——
取得元に残っていなかった期間（理由 `retention`）は「取得元に残っていない（期間）」、
時計の食い違いで問い合わせを諦めた期間（理由 `clock_skew_abandoned`）は「時計のずれで取れていない（期間）」（1 日の画面（ST25）と同じ言葉。design D23（仮））。
THE SYSTEM SHALL 期間を、取りこぼしの期間の始まりと終わりの `Asia/Tokyo` の日時（`YYYY-MM-DD HH:MM〜YYYY-MM-DD HH:MM`）で出す。
THE SYSTEM SHALL 2 つの理由を 1 つの文字に畳まない。
THE SYSTEM SHALL 知らない理由の取りこぼしの期間を、理由の文字を付けずに「取りこぼし（期間）」と出す。

導出元: FR-54, FR-85。ST14 の深掘り Q7、申し送り st06 R5 / R26、整合の確認 C12。

**理由を分けるのは扉 #14 の材料だから**（申し送り st06 R26）—— 取得元が消したのか（`retention`）、端末が問い合わせなかったのか（`clock_skew_abandoned`。取得元にはまだ残っていたかもしれない）。
8 つの状態は増やさない（FR-54 ★）。状態は③に畳み、違いは文字が担う。
期間を日時で出すのは、取りこぼしの期間が日をまたいで 10 日ほどに及ぶことがあり、日の中の時刻だけでは始まりと終わりが読めないため。

#### Scenario: 取得元に残っていない期間が週の文字に出る

- **WHEN** アプリ利用に、理由が取得元に残っていなかった、`2026-09-01T08:00+09:00` から `2026-09-03T08:00+09:00` までの取りこぼしの期間がある週を選ぶ
- **THEN** `2026-09-02` の行に「動いていたが取れない状態だった」と「取得元に残っていない（2026-09-01 08:00〜2026-09-03 08:00）」が出る

#### Scenario: 時計のずれで取れていない期間は別の文字で出る

- **WHEN** アプリ利用に、理由が時計の食い違いで問い合わせを諦めた、`2026-09-01T08:00+09:00` から `2026-09-03T08:00+09:00` までの取りこぼしの期間がある週を選ぶ
- **THEN** `2026-09-02` の行に「時計のずれで取れていない（2026-09-01 08:00〜2026-09-03 08:00）」が出る
- **AND** 「取得元に残っていない」は出ない

#### Scenario: 2 つの理由が同じ日に重なると 2 つとも出る

- **WHEN** 同じ日に、理由の違う 2 つの取りこぼしの期間が重なる週を選ぶ
- **THEN** その日の行に「取得元に残っていない（…）」と「時計のずれで取れていない（…）」が 1 つずつ出る

#### Scenario: 終わりの時刻ちょうどの日には重ならない

- **WHEN** アプリ利用の取りこぼしの期間が `2026-09-01T08:00+09:00` から `2026-09-03T00:00+09:00` までである
- **THEN** 稼働状況の応答の `2026-09-03` の日は、その取りこぼしの期間を持たない

#### Scenario: UTC の真夜中に終わる取りこぼしは日本時間のその日に重なる

- **WHEN** アプリ利用の取りこぼしの期間が `2026-09-01T08:00+09:00` から `2026-09-03T00:00Z`（日本時間 `2026-09-03 09:00`）までである
- **THEN** 稼働状況の応答の `2026-09-03` の日は、その取りこぼしの期間を持つ

#### Scenario: 稼働状況の応答の日が取りこぼしの期間と理由を持つ

- **WHEN** 取りこぼしの期間が重なる日を含む期間の稼働状況を引く
- **THEN** その日に、取りこぼしの期間の始まり・終わり・理由が返る

#### Scenario: 知らない理由の取りこぼしは理由の文字を付けずに出る

- **WHEN** 理由が `unknown_reason` の取りこぼしの期間がある週を選ぶ
- **THEN** その日の行に「取りこぼし（…）」が出る

### Requirement: アプリ利用の集計は格子に出る

THE SYSTEM SHALL アプリ利用の集計（`c01-app-usage-rollup`）を、稼働状況の格子のソースの 1 つとして出す。
THE SYSTEM SHALL 集計の格子を、**Must の 5 ソースより後ろ、書庫のソースより前**に置く。
THE SYSTEM SHALL 集計の格子を、開いた直後から直近 4 週の行を出した状態で置く。
THE SYSTEM SHALL 集計を成功条件 1 の達成に数えない。
THE SYSTEM SHALL 集計の格子を足しても、Must の 5 ソースの格子の高さの予算（「稼働状況は 1 年を週に畳んだ格子で見える」）を超えないようにする。

導出元: FR-54, FR-79, NFR-13。ST14 の深掘り Q8、申し送り st06 R7。

集計の値は ST06 の下流から既に入っているが、口（`must_sources()` の 5 本と書庫）に入らず誰にも見えていなかった（申し送り st06 R7）。
Must の 5 本の後ろに置くのは、Must の 5 本の連なりとひとスクロールの予算を変えないため（design D10（仮））。

#### Scenario: 集計の格子が Must の後ろで書庫の前に出る

- **WHEN** 集計の記録と書庫のソースがある状態で稼働状況の画面を開く
- **THEN** 格子は上から Must の 5 ソース・集計・書庫のソースの順に並ぶ

#### Scenario: 集計は達成に数えられない

- **WHEN** 達成の判定を引く
- **THEN** 集計の論理ソースは 5 本の中に無い

#### Scenario: 集計の格子を足しても Must の 5 本はひとスクロール以内

- **WHEN** 集計の記録がある状態で、幅 360 CSS px・高さ 640 CSS px で稼働状況の画面を開く
- **THEN** Must の 5 ソースは集計より前にあり、その最後の格子の下端は、箱が最も低いときの下端から箱の高さの上限 160 CSS px を超えて下がらない

#### Scenario: 集計の格子は開いた直後から直近 4 週を出す

- **WHEN** 集計の記録がある状態で稼働状況の画面を開く
- **THEN** 集計の格子は、押さなくても直近 4 週の行を出している

### Requirement: 稼働状況の画面は OS の明暗に追従する

THE SYSTEM SHALL 稼働状況の画面の明暗を、OS の明暗の設定に追従させる。
IF OS の明暗の設定を取得できない THEN THE SYSTEM SHALL 稼働状況の画面をダークで出す。
THE SYSTEM SHALL ライトとダークのどちらでも、格子の隣り合う 2 段の相対輝度比を 3:1 以上、破棄の印とセルの比を 3:1 以上、本文と背景のコントラスト比を 4.5:1 以上にする。

導出元: NFR-17, NFR-18, NFR-23。申し送り st25 Q5。

画面は 2026-10-12 の表面の作り直しで既に追従しているが、正典（この capability）に要件が無かった。
画面の下限は画面を持つ Story が自分の画面について満たす（INDEX の訂正 2026-09-15）。ST25 の深掘り Q5 で本人が「稼働状況は ST14 へ」を選んだ。

#### Scenario: OS がライトなら稼働状況もライトで出る

- **WHEN** OS の明暗の設定がライトの状態で稼働状況の画面を開く
- **THEN** 画面の背景はライトの面の色である

#### Scenario: OS がダークなら稼働状況もダークで出る

- **WHEN** OS の明暗の設定がダークの状態で稼働状況の画面を開く
- **THEN** 画面の背景はダークの面の色である

#### Scenario: 明暗の設定が取れなければダークで出る

- **WHEN** OS の明暗の設定を取得できない状態で稼働状況の画面を開く
- **THEN** 画面の背景はダークの面の色である

#### Scenario: ライトでも格子の 3 段と印と文字が下限を満たす

- **WHEN** OS の明暗の設定がライトの状態で、格子の 3 段・破棄の印・本文の色を測る
- **THEN** 隣り合う 2 段の比と印とセルの比はいずれも 3:1 以上、本文と背景の比は 4.5:1 以上である
