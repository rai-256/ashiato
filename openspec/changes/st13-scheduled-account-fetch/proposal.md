## Why

FR-15 は「C-03 が各ソースに登録された取得契機で新着を取りに行き、取得間隔は登録簿が持つ」と言うが、**要件の中に API で定期取得できるアカウント系のソースは 1 つも無い**
（Google の Data Portability API は日本で提供されていない。テストの OAuth は 7 日で切れる。YouTube の視聴履歴の API は無い。前提は `premises.md`）。
いま登録簿は取り方も取得の間隔も持たず、取り込み器の見回りの間隔は環境変数（`ASHIATO_ARCHIVE_SCAN_SEC`）にある。

この Story は、**後のソースが登録簿に 1 行足すだけで乗れる定期取得の枠**と、**ソースごとの取り方と間隔を登録簿で持って画面で見せること**を作り、
NFR-12（Google 系の手作業は 2 か月に 1 回まで・他のソースは手作業ゼロ）を崩しているものを直す。崩しているのは 2 つ:
ST12 の取り込み器が手作業を増やす・画面を誤らせる不具合（申し送り R25 / R34 / M7 / M8）と、携帯の収集アプリが数か月で Android に休止させられて権限を剥がされること。

## What Changes

**深掘りの第 1 回（6 問）はまだ答えが無い。この版は全問を推奨の答えで書いた**（2026-10-20 の先読みの流れ。`deep.md` の `（答え待ち・推奨: …）`）。
本人の答えが推奨と違えば `spec --answers` が該当する Q だけを書き直す。

- **登録簿がソースごとに取り方と取得の間隔を持つ**（Q1 推奨・FR-15）。取り方は 端末 / PC / 書庫 / サーバ / 定期取得 の 5 つ。
  間隔はサーバが回すもの（取り込み器の見回り・定期取得）だけが従う値で、端末と PC の行は端末が決める値を写して見せる。想定間隔（FR-35）とは別の列で、想定間隔より長い取得の間隔は断る
- **取り込み器の見回りの間隔を登録簿から読む**（Q1 推奨）。環境変数 `ASHIATO_ARCHIVE_SCAN_SEC` は読まず、設定されていれば起動を断る（値が 2 か所にあると、どちらが効いているか分からない）
- **定期取得の枠を置く**（Q1 推奨）。取り方が「定期取得」のソースを、起動の直後に 1 回、その後は登録簿の間隔ごとに取りに行く。いまは 0 本で、0 本でも動く。
  前回の時刻を DB に持たず、単調な時計で待つ（時計が戻った・進んだ・止まっていた、のどれでも起動の直後の 1 回で追いつく）
- **ST12 の取り込み器の 4 つを直す**（Q2 推奨: R25・R34・M7・M8）:
  台帳の「読んだ」行と論理ソースごとの行を 1 つのトランザクションで書く（記録は 1 件ずつのまま。ST12 の D4 に触らない）/
  専用のフォルダが無くても（無ければ作り）、片方の置き場が読めなくてももう片方を読む / 読み終えた・中身が変わった書庫の失敗の回数を 0 に戻す /
  ファイルを読めない I/O の失敗を「形が対応していない」と呼ばない
- **S-7 設定に「ソース」節を足す**（Q3 推奨の形・Q6 推奨）。登録簿の全ソースを取り方でまとめて並べ、読むだけ。書庫のソースは間隔の代わりに「手作業・2 か月ごと」と通知までの残り日数を出す。
  定期取得の節は空でも出し、無いことを文字で言う
- **携帯の収集アプリが休止の対象から外れるよう、初回に 1 回頼む**（Q4 推奨）。外れているかを生存信号の原文に載せ、S-7 の端末の節に外れていないことを出す
- **形の確認の印は CLI のまま**（Q5 推奨）、**間隔は画面から変えない**（Q6 推奨）。どちらも spec の振る舞いを足さず、design の（仮）と反転条件に残す
- FR-15 に「いま定期取得するソースは無い」を ★ で足すのは、答えを受けた record の段（要件の改訂は record が行う）

**BREAKING**: 環境変数 `ASHIATO_ARCHIVE_SCAN_SEC` を設定したまま起動すると断る（値は登録簿の `s01-archive-inbox` の取得の間隔へ移す）。
`/ingest`・`/heartbeat`・`/archives/status`・`/coverage` の形は変えない。新しい読み出しの口 `GET /sources` を足す。

## Capabilities

### New Capabilities

無し。

### Modified Capabilities

- **`external-ingestion`** —— 登録簿の取り方と取得の間隔・見回りの間隔を登録簿から読むこと・定期取得の枠・Google 系の手作業の範囲・S-7 のソースの一覧を足し（ADDED）、
  ST12 の Requirement のうち「取り込み待ち置き場に置かれた書庫を読む」（R34・M8）・「取り込み器は自分の論理ソースに 1 日 1 回の生存信号を送る」（R34。起動時にフォルダを作るので、読めない場合の Scenario の条件を直す）・「1 件が読めなくても書庫の残りを読む」（M7）・「置いた書庫ごとに追記のみの台帳が残る」（R25）を `MODIFIED` する
- **`device-collection`** —— 携帯の収集アプリが休止の対象から外れるよう頼み、外れているかを生存信号の原文に載せる Requirement を足す（ADDED。Q4 推奨）

**capability の割当を 1 本足す**: `docs/stories/INDEX.md` の表で ST13 は `external-ingestion` だけだったが、Q4（推奨）の振る舞いは C-01 の中にあり `device-collection` に属する。
INDEX の `device-collection` の行に ST13 を足し、訂正の節に理由を書いた。Q4 で「別の Story に送る」「防がない」が選ばれたら、`spec --answers` がこの割当と Requirement を外す。

S-7 のソースの一覧は全ソース（端末・PC を含む）を並べるが、置き場は `external-ingestion` にした。FR-15（登録簿の取得間隔）は ST13 の要件で、
`collection-coverage` に置くと走っている ST09 と同じ capability を触る（INDEX の ST12 の前例と同じ判断）。

### 走っている Story との重なり

- **ST09（`device-collection` / `collection-coverage` / `data-durability`。下流）**: ST09 は `device-collection` の「端末は想定間隔ごとに生存信号を送る」を `MODIFIED` している。
  ST13 はその Requirement を `MODIFIED` せず、**別の ADDED の Requirement** で休止の除外を足し、状態は生存信号の**原文**に載せる（`/heartbeat` の欄を足さない。ST09 は欄 `network` を足す）。
  `MainActivity` の初回の流れと `Heartbeat.kt` は ST09 も触る。ST13 は main の形で書き、ST09 が先に main に入ったら rebase で解く（ST09 の未確認の実装を取り込まない。design D12）。
  ST13 は既に上流にいるので、INDEX の割当を足しても `衝突待ち` にはならない
- `collection-coverage` / `data-durability` には触らない（書き出しの分類に載る新しい表は無い。列は `core.source` に足すだけで、`core.source` の書き出しの扱いは変わらない）
