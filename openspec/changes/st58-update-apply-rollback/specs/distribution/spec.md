## ADDED Requirements

### Requirement: 携帯の収集アプリは、「更新あり」を押すと新しい版を落として照らし、Android のインストール画面を開く

WHEN 本人が携帯の収集アプリの最初の画面の「更新あり」の行を押す THE SYSTEM SHALL 見つけた最新の版の携帯の APK を落とし、版の一覧の指紋と照らしてから（「収集アプリは、押したときだけ配布物を落とし…」）、Android のインストール画面を開く。
WHEN 本人が携帯の更新の通知を押す THE SYSTEM SHALL 最初の画面を開き、「更新あり」の行を押したときと同じに落とし始める。
THE SYSTEM SHALL 入れ替えるかどうかを本人に任せる（インストール画面で本人が入れるまで、入っている版のまま動き続ける）。
IF アプリに「提供元不明のアプリ」が許されていない THEN THE SYSTEM SHALL 落とす前にその許可の画面を開き、行に「許可した後に、もう一度押してください」と出す。
THE SYSTEM SHALL 落とした APK をアプリの専用の置き場（バックアップと端末の移し替えから外す置き場）に置き、インストール画面を閉じた後か、次にアプリを開いたときに消す。
IF 落とせない・指紋が無い・指紋が合わない THEN THE SYSTEM SHALL インストール画面を開かず、行に「入れられませんでした（<理由>）」を出す。

導出元: FR-114。深掘り Q2（推奨: アプリが落として、Android のインストール画面を開く）。premises P5・P9。
古い版への入れ直しと、別の鍵で署名した APK は Android 自身が断る（P5）。入れる権限（`REQUEST_INSTALL_PACKAGES`）は、本人が許すまで何も入れられない。

#### Scenario: 携帯の更新ありの行を押すと、指紋の合う APK でインストール画面が開く

- **GIVEN** 「提供元不明のアプリ」が許された、版 `0.4.0` の携帯の収集アプリと、`0.5.0` の APK とその指紋を返す手元の受け手（試験の配布元）
- **WHEN** 最初の画面の「更新あり 0.5.0」の行を押す
- **THEN** 落とした APK の SHA-256 は受け手の指紋と同じで、その APK を入れる Android のインストール画面が開く

#### Scenario: 携帯の更新の通知を押すと、落とし始める

- **GIVEN** 「提供元不明のアプリ」が許された、版 `0.4.0` の携帯の収集アプリ
- **WHEN** 「新しい版 0.5.0 が出ています」の通知を押す
- **THEN** 最初の画面が開き、受け手への APK の要求が 1 回出る

#### Scenario: 携帯は指紋の合わない APK でインストール画面を開かない

- **GIVEN** 版の一覧の指紋と中身の違う APK を返す受け手
- **WHEN** 「更新あり 0.5.0」の行を押す
- **THEN** インストール画面は開かず、行に「入れられませんでした」が出て、落とした APK は置き場に残らない

#### Scenario: 携帯は提供元不明のアプリが許されていなければ、許可の画面を開く

- **GIVEN** 「提供元不明のアプリ」が許されていない携帯の収集アプリ
- **WHEN** 「更新あり 0.5.0」の行を押す
- **THEN** 「提供元不明のアプリ」の許可の画面が開き、受け手への APK の要求は 0 件で、行に「許可した後に、もう一度押してください」が出る

#### Scenario: 携帯でインストール画面を取り消すと、入っている版のまま動き続ける

- **GIVEN** インストール画面が開いている、版 `0.4.0` の携帯の収集アプリ
- **WHEN** インストール画面を取り消す
- **THEN** アプリの版は `0.4.0` のままで、収集のサービスは動き続け、落とした APK は置き場に残らない

#### Scenario: 携帯は入れ終えた後に APK を置き場に残さない

- **WHEN** インストール画面で入れ終え、新しい版のアプリを開く
- **THEN** 落とした APK の置き場は空である

### Requirement: 携帯の収集アプリは、更新で入れ替わった後、開かなくても収集を再開する

WHEN 携帯の収集アプリが更新で入れ替わり、送り先が設定してある THE SYSTEM SHALL 本人がアプリを開かなくても、収集のサービスを起こして収集を再開する。
IF 裏の位置の権限が許されておらず、裏から収集のサービスを起こせない THEN THE SYSTEM SHALL 「更新の後に収集が止まっています。開いてください」の通知を 1 回出す（通知の権限も無い端末では、今と同じく開くまで止まる）。
THE SYSTEM SHALL 送り先が設定されていない端末では、更新の後に収集のサービスを起こさない。

導出元: FR-114（更新を入れる）。申し送り st51-update-history R10（更新の後に自分で起き直さない）。defaults.md P1（design D10（仮））。review/deep.md R11。premises P6・P7（確かさ 2。計測テストで 4 に上げる）。
更新を入れたのに収集が止まったままだと、開くまで記録も生存信号も無い。

#### Scenario: 携帯は更新の後、開かなくても収集を再開する

- **GIVEN** 送り先が設定され、裏の位置の権限が許された携帯の収集アプリ（エミュレータ）
- **WHEN** 同じ鍵で署名した新しい版の APK を `adb install -r` で入れ、アプリを開かずに 30 秒待つ
- **THEN** 収集のサービスが動いていて、新しい版の生存信号が未送信に積まれる

#### Scenario: 携帯は裏の位置の権限が無ければ、更新の後に開くよう通知する

- **GIVEN** 送り先が設定され、裏の位置の権限が許されていない携帯の収集アプリ
- **WHEN** 新しい版の APK を `adb install -r` で入れる
- **THEN** 「更新の後に収集が止まっています。開いてください」の通知が 1 回出る

#### Scenario: 送り先の無い携帯は、更新の後に収集を起こさない

- **GIVEN** 送り先が設定されていない携帯の収集アプリ
- **WHEN** 新しい版の APK を `adb install -r` で入れる
- **THEN** 収集のサービスは動いていない

### Requirement: PC の収集アプリは、本人が確かめてから自分を新しい版に入れ替え、動き出さなければ前の版に戻す

WHEN 本人が PC の収集アプリの「新しい版」の通知を押す、または `update` の口を使う THE SYSTEM SHALL 窓を開き、入っている版と見つけた最新の版を示して「入れ替えますか [y/N]」と聞く。
WHEN 本人が `y` と答える THE SYSTEM SHALL 配布物を落として指紋を照らし（「収集アプリは、押したときだけ配布物を落とし…」）、前の版の実行ファイルを残したまま、新しい版に入れ替えて起こす。
THE SYSTEM SHALL 入れ替えの間に、前の版と新しい版が同時に収集しない。
THE SYSTEM SHALL 入れ替えた新しい版を、窓を閉じても止まらない形で起こす。
THE SYSTEM SHALL 新しい版に、動き出したと書く前に手元の置き場（未送信・設定・確かめた記録）の形を変えさせない（前の版に戻しても、前の版が未送信を読める）。
THE SYSTEM SHALL 新しい版が動き出した（新しい版が 1 分以内に動き出したことを置き場に書いた）ことを確かめてから、自動起動の台本を新しい版に向ける。
IF 新しい版が 1 分以内に動き出さない THEN THE SYSTEM SHALL 前の版に戻して起こし直し、自動起動の台本を前の版に向けたままにし、「新しい版 <版> が動き出さなかったので、<前の版> に戻しました」を通知する。
IF 本人が `y` 以外で答える、または見つけた最新の版が入っている版より新しくない THEN THE SYSTEM SHALL 何も替えない（後者は窓に「入っている版が最新です」と出す）。
THE SYSTEM SHALL 入れ替えの前に積んだ未送信を消さず、入れ替えた後の版が続きから送る。
THE SYSTEM SHALL 新しい版を起こす子のプロセスを、時刻サーバの検査（`tools/check-no-time-server.sh`）が許す決まった 1 つの形だけにする。

導出元: FR-114（Windows で入れる操作を開き、入れるのは本人）。深掘り Q1（推奨: 収集アプリが自分で落として入れ替える）。FR-114 ★ 2026-10-25（時刻サーバの検査の許可の形）。申し送り ST52 D5・R14（PC の後戻り。自動の戻しは「新しい版の後に前の版を動かす」場面で、未送信は行ごとの送信契約の版で守る）・defaults.md C7。premises P15・P16・P23・P24（design D12（仮）。動いている実行ファイルの名前は変えないので P4 に依らない）。
入れ替えている数秒と、新しい版が動き出さなかったときに前の版へ戻るまでの間は、窓・入力・アドレスバーの記録が取れない（Q1 の不可逆）。未送信は行ごとに焼いた送信契約の版で送るので、古い版へ戻しても古い形で送らない（`contract.rs`・`outbox.rs`）。

#### Scenario: PC は新しい版の通知を押すと、入れ替えの窓を開く

- **GIVEN** 見つけた最新の版 `0.5.0` を持つ、版 `0.4.0` の PC の収集アプリ
- **WHEN** 「新しい版 0.5.0 が出ています」の通知を押す
- **THEN** 窓が開き、`0.4.0` と `0.5.0` と「入れ替えますか [y/N]」が出る

#### Scenario: PC は y で新しい版に入れ替え、前の版の実行ファイルを残す

- **GIVEN** 版 `0.4.0` の PC の収集アプリと、`0.5.0` の配布物とその指紋を返す手元の受け手（試験の配布元）
- **WHEN** `update` の口で `y` と答える
- **THEN** 1 分以内に版 `0.5.0` の収集アプリが動いていて、版 `0.4.0` の実行ファイルは元の場所に残り、`0.4.0` の収集アプリは動いていない

#### Scenario: PC は新しい版が動き出してから、自動起動の台本を新しい版に向ける

- **GIVEN** 新しい版が動き出す前に止める差し込み（試験の組み立て）
- **WHEN** `update` の口で `y` と答え、新しい版の起動を待つ間に自動起動の台本を読む
- **THEN** 台本は前の版の実行ファイルを指していて、新しい版が動き出したことを書いた後に読むと新しい版を指す

#### Scenario: PC は新しい版が 1 分以内に動き出さなければ、前の版に戻して起こし直す

- **GIVEN** 起きてすぐに落ちる新しい版の配布物（試験の配布元）
- **WHEN** `update` の口で `y` と答え、1 分待つ
- **THEN** 版 `0.4.0` の収集アプリが動いていて、自動起動の台本は `0.4.0` を指し、「新しい版 0.5.0 が動き出さなかったので、0.4.0 に戻しました」の通知が 1 回出る

#### Scenario: PC は y 以外の答えでは何も替えない

- **WHEN** `update` の口で空の答え（Enter だけ）と `n` を返す
- **THEN** 受け手への配布物の要求は 0 件で、実行ファイルと自動起動の台本は答える前と同じ

#### Scenario: PC は入っている版より新しくない版を入れない

- **GIVEN** 見つけた最新の版が `0.4.0` の、版 `0.4.0` の PC の収集アプリ
- **WHEN** `update` の口を使う
- **THEN** 窓に「入っている版が最新です」が出て、受け手への配布物の要求は 0 件である

#### Scenario: PC は入れ替えの前に積んだ未送信を、入れ替えた後に送る

- **GIVEN** 送り先のサーバが止まっていて、未送信が 3 件ある版 `0.4.0` の PC の収集アプリ
- **WHEN** `0.5.0` に入れ替えた後にサーバを起こす
- **THEN** 3 件はどれもサーバに入り、未送信は空になる

#### Scenario: PC は前の版に戻しても、新しい版が積んだ未送信を消さない

- **GIVEN** 新しい版が動き出す前に、送信契約の版を 1 つ上げた形の行を 1 件積んで止まる差し込み（試験の組み立て）と、前の版が積んだ未送信 2 件
- **WHEN** 新しい版が 1 分以内に動き出さずに前の版へ戻った後、サーバを起こす
- **THEN** 前の版が積んだ 2 件はサーバに入り、新しい版の行は未送信に残り、前の版は自分の知らない送信契約の版の行を送らない

#### Scenario: PC は入れ替えの間、前の版と新しい版が同時に記録を積まない

- **WHEN** `update` の口で `y` と答え、入れ替えの前後 2 分の収集アプリのプロセスと、受け手が受けた記録を読む
- **THEN** 収集アプリのプロセスが同時に 2 つ動いた時は無く、受け手が受けた記録に、2 つの版が同じ時刻に積んだ行は無い

#### Scenario: PC は窓を閉じた後も、入れ替えた新しい版が動き続ける

- **WHEN** `update` の口で `y` と答え、入れ替えが済んだ後に窓を閉じ、1 分待つ
- **THEN** 版 `0.5.0` の収集アプリが動いている

#### Scenario: PC は指紋の合わない配布物で入れ替えない

- **GIVEN** 版の一覧の指紋と中身の違う配布物を返す受け手
- **WHEN** `update` の口で `y` と答える
- **THEN** 窓に「入れられませんでした」が出て、実行ファイルと自動起動の台本は答える前と同じで、版 `0.4.0` の収集アプリが動いている

#### Scenario: 時刻サーバの検査は、入れ替えた新しい版を起こす形を許し、ほかの子のプロセスを許さない

- **WHEN** `tools/check-no-time-server.sh` と `tools/check-no-time-server.sh --self-test` を走らせる
- **THEN** どちらも rc=0 で、自己検査は入れ替えた新しい版を起こす決まった形を通し、名前を引数に取る形と `w32tm /resync` を落とす

### Requirement: 収集アプリは、押したときだけ配布物を落とし、版の一覧の指紋と照らす

WHEN 本人が更新を入れる操作をする（携帯の行・PC の `y`）THE SYSTEM SHALL そのときだけ、版の一覧を更新の確認と同じ決まった形（「更新を確かめる問い合わせは、版の一覧を取る決まった形だけを配布元へ送る」）で取り直し、自分の部品の配布物の場所と指紋（`digest`）を読む。
THE SYSTEM SHALL 配布物を `https://github.com/rai-256/ashiato/releases/download/` の下からだけ落とし、転送（3xx）は `https://release-assets.githubusercontent.com/` へのものだけを追い、ほかの宛先・ほかの道への転送は「落とせない」として扱う。
THE SYSTEM SHALL 配布物を落とす要求を、方法 `GET`・本文なしにし、見出しを更新の確認と同じ 5 つの名前の内側にし、自分の版番号・端末の機種・OS の版・端末や利用者の識別子・資格情報・記録を入れない。
THE SYSTEM SHALL 落とした配布物の SHA-256 が、版の一覧の答えの指紋（`sha256:<64 桁の 16 進>`）と同じときだけ入れ、指紋の無い配布物は入れない。
THE SYSTEM SHALL 押す前に配布物を落とさない。
THE SYSTEM SHALL 押したときの取り直しを、24 時間ごとの確かめの数えと確かめた記録に入れない。
THE SYSTEM SHALL 宛先の差し替えを、更新の確認と同じく試験の組み立てだけで読む（配る組み立ては差し替えを持たない）。

導出元: FR-114・FR-116（記録を外へ出さない）。深掘り Q1・Q2（どの道でも指紋と照らしてから入れる）。defaults.md C9。premises P2・P3。
配布物を落とすと、どの版を落としたかと元の IP と時刻が配布元に見える。押したときだけに限り、中身は配布物の取得だけにする（ST57 の確かめと同じ扱い）。

#### Scenario: 押す前は配布物を落とさない

- **GIVEN** 「更新あり 0.5.0」を出している、携帯と PC の収集アプリ
- **WHEN** 24 時間ずつ時計を進めて確かめを 2 回迎える
- **THEN** 受け手への要求は版の一覧の取得だけで、配布物の要求は 0 件である

#### Scenario: 配布物は決まった 2 つの宛先からだけ落とす

- **GIVEN** 配布物の要求に、決まった宛先の外（試験の別の受け手）への転送を返す受け手
- **WHEN** 携帯と PC の収集アプリで更新を入れる操作をする
- **THEN** 別の受け手への要求は 0 件で、どちらも「落とせない」を理由に入れない

#### Scenario: 指紋の無い配布物は入れない

- **GIVEN** 版の一覧の答えの配布物に `digest` が無い受け手
- **WHEN** 携帯と PC の収集アプリで更新を入れる操作をする
- **THEN** どちらも入れず、PC の実行ファイルは前と同じで、携帯のインストール画面は開かない

#### Scenario: 落とす要求は自分の版も端末の情報も持たない

- **WHEN** 携帯と PC の収集アプリで更新を入れる操作をし、受け手が受けた要求を読む
- **THEN** どの要求も方法 `GET`・本文なしで、見出しは 5 つの名前の内側にあり、道と見出しのどこにも収集アプリの版番号・端末の機種・識別子が無い

#### Scenario: 押したときの取り直しは、確かめの数えを動かさない

- **GIVEN** 最後に確かめてから 2 時間の PC の収集アプリ
- **WHEN** 更新を入れる操作をし、確かめた記録と最後に確かめた時刻を読む
- **THEN** 確かめた記録の行の数と最後に確かめた時刻は、操作の前と同じである

### Requirement: サーバのインストーラは、入っている版と違う版で走らせると、サーバを止めてから更新の手順を進める

WHEN サーバのインストーラが、プログラムの置き場に自分と違う版のサーバがあるインストールの上で走る THE SYSTEM SHALL 管理者の確認を 1 回出し、次の順で更新する:
(1) 「更新の途中」の印を書く（前の版・新しい版・この回の退避の置き場・進んだ段）、(2) サーバと更新係のサービスを止め、サーバのサービスの開始の種類を「無効」にする、(3) プログラムの置き場を前の版の退け先（`<プログラムの置き場>\previous`）へ退ける、
(4) 新しい版の配布物で置き換える、(5) 新しい版の `ashiato-server migrate` で、この回のための空の置き場に退避を取ってから移行を当てる、(6) 新しい版のサーバを起こす、
(7) サーバが待ち受けを開いたら、まず「待ち受けを確かめた」を印に書いてから、サーバのサービスの開始の種類を「自動」に戻し、「アプリと機能」の版を新しい版にし、更新係を（切ってなければ）起こし、印を消す。
THE SYSTEM SHALL 移行の前の退避を取る前に、サーバのサービスを止めておく（退避の後に前の版が受け取った記録を、戻しが捨てない）。
THE SYSTEM SHALL 更新の手順で、DB の秘密・設定（`server.json`・`owner.json`）・画面の合言葉・更新係の置き場を書き換えない（新しい版が要る鍵を足すことだけを許す）。
WHEN 入っている版と自分の版が同じ THE SYSTEM SHALL 更新の手順に入らず、走らせ直し（「インストールを走らせ直すと…」）として振る舞う。
THE SYSTEM SHALL 「更新の途中」の印と更新の記録を、状態の置き場の中の、管理者と SYSTEM だけが書ける置き場（`<状態の置き場>\update`）に置く（サーバと DB のサービスのアカウントは読めるが書けない）。
THE SYSTEM SHALL 開発版のインストーラには開発版の置き場だけを、それ以外のインストーラには正式版の置き場だけを更新させる。
THE SYSTEM SHALL この更新の手順を Windows のサーバにだけ持たせる（Linux のサーバの更新と戻しは、Linux の入れ方を持つ Story が扱う）。

導出元: FR-114（S-01 の更新の手順。手動で始める）・FR-119。申し送り st48 R21（新しい版の migrate の前に古いサーバを止める）・ST55 D14（配置の正本・正式版と開発版を混同しない）。defaults.md C1・C6・C8（design D1・D6・D8）。premises P10・P11・P14・P19。review/deep.md R2・R10。
今のインストーラは、別の版のファイルがあれば何も替えずに止まる（P10）。前の版を退けておかないと、FR-119 の「前の版の S-01 で起動し直す」ができない（P11）。

#### Scenario: 新しい版のインストーラで走らせると、移行を当てて新しい版のサーバが起きる

- **GIVEN** 版 `0.4.0` のサーバを入れ、記録の件数を控えたインストール
- **WHEN** 版 `0.5.0` の配る zip のインストーラを走らせる
- **THEN** rc=0 で、`/healthz` は 200 で答え、サーバの版は `0.5.0`、記録の件数は控えと同じで、前の版の退け先に `0.4.0` のサーバがあり、サービス `ashiato-server` の開始の種類は「自動」、更新の途中の印は無い

#### Scenario: 更新の移行の間、サーバは待ち受けない

- **GIVEN** 版 `0.4.0` のサーバを入れたインストールと、移行の段で止まって待つ差し込み（試験の組み立て）を持つ版 `0.5.0` のインストーラ
- **WHEN** インストーラを走らせ、移行の段で待っている間に、サーバの番号へ繋ぐ
- **THEN** 繋がらず、サービス `ashiato-server` は実行中でなく、開始の種類は「無効」である

#### Scenario: 更新しても、秘密と設定と画面の合言葉は変わらない

- **GIVEN** 版 `0.4.0` のインストールの設定のファイル（`server.json`・`owner.json`）の指紋を控えた
- **WHEN** 版 `0.5.0` のインストーラで更新する
- **THEN** 2 つの設定のファイルの指紋は控えと同じで、更新の前の画面の合言葉でログインできる

#### Scenario: 同じ版で走らせ直すと、更新の手順に入らない

- **WHEN** 入っている版と同じ版のインストーラを走らせる
- **THEN** 前の版の退け先は作られず、移行の前の退避の置き場の中身は走らせる前と同じである

#### Scenario: サーバのアカウントは、更新の途中の印を書けない

- **WHEN** 更新の印の置き場の ACL を読む
- **THEN** 書ける主体は Administrators と SYSTEM だけで、サーバと DB のサービスのアカウントは読むことだけができる

#### Scenario: 開発版のインストーラは、正式版のインストールを更新しない

- **GIVEN** 正式版の `0.4.0` だけを入れた PC
- **WHEN** 開発版のインストーラを走らせる
- **THEN** 正式版のプログラムの置き場と DB と記録の件数は走らせる前と同じである

#### Scenario: 正式版のインストーラは、開発版のインストールを更新しない

- **GIVEN** 開発版だけを入れた PC
- **WHEN** 正式版のインストーラを走らせる
- **THEN** 開発版のプログラムの置き場と DB と記録の件数は走らせる前と同じである

### Requirement: 更新の移行が落ち、この回の退避があれば、退避から DB を戻して前の版で起こし直す

IF 更新の手順の新しい版の `migrate` が終了コード 0・2・3・4 以外（移行の失敗の 1、落ちた・止められた）で終わり、この回のために渡した空の置き場に、取り終えた退避（退避を取り終えたときにだけ付く名前のファイル）がある THEN THE SYSTEM SHALL 退避を別の名前の DB に入れ、入り終えてから元の DB と名前を入れ替え、プログラムの置き場を前の版に戻し、前の版のサーバで起こし直す。
THE SYSTEM SHALL 戻すものを、DB・プログラムの置き場（サーバ・更新係・同梱の PostgreSQL）・「アプリと機能」の版にし、設定と更新係の置き場は戻さない。
THE SYSTEM SHALL 落ちた DB を、元の DB と入れ替えた後に `ashiato_failed_<時刻>` の名前で残し、次に更新が通ったときに消す。
THE SYSTEM SHALL 戻しを、DB の管理者でない表の所有者の役割で行う。
THE SYSTEM SHALL 戻した後の前の版のサーバに、更新の前と同じ記録・同じ版の記録・同じ役割の検査で起きさせる。
THE SYSTEM SHALL 戻した後、更新の確認を切っていなければ、前の版の更新係のサービスを起こす。

導出元: FR-119。深掘り（ST58）Q5。申し送り st48 R21・st54 D3（戻すのは終了コード 1 の回だけ）。defaults.md C2・C3・C6（design D2・D3・D6）。premises P12・P13・P18・P20。review/deep.md R1。
途中の版で落ちると、それより前の版は当たったまま残る（P13）。前の版のサーバは「DB が新しい」で起きないので、戻さないとどちらの版も動かない。別の名前の DB に入れてから入れ替えるので、戻しの途中で止まっても元の DB は壊れない。

#### Scenario: 更新の移行が落ちると、退避から DB を戻し、前の版のサーバが起きる

- **GIVEN** 版 `0.4.0` のサーバを入れ、記録の件数と版の記録を控えたインストールと、必ず落ちる移行を末尾に足した版 `0.5.0` のインストーラ（試験の組み立て）
- **WHEN** インストーラを走らせる
- **THEN** rc≠0 で、`/healthz` は 200 で答え、サーバの版は `0.4.0`、記録の件数と版の記録は控えと同じで、`ashiato_failed_` で始まる名前の DB が 1 つある

#### Scenario: 戻した後、更新の間に溜まった未送信が入る

- **GIVEN** 移行が落ちて前の版に戻したインストール
- **WHEN** 収集アプリの資格情報で記録を 1 件送る
- **THEN** 送った記録はサーバに入り、DB の記録の件数が 1 増える

#### Scenario: 戻した後の「アプリと機能」の版とプログラムの置き場は前の版

- **WHEN** 移行が落ちて前の版に戻したインストールの「アプリと機能」の版と、プログラムの置き場のサーバ・更新係の版を読む
- **THEN** どれも `0.4.0` で、前の版の退け先と前の版の置き場の中身の指紋は同じである

#### Scenario: 戻しは DB の管理者の役割を使わない

- **WHEN** 移行が落ちて戻したときに、インストーラが起こした命令の記録（試験の組み立て）を読む
- **THEN** DB へ繋いだ命令の役割はどれも `ashiato_owner` で、DB の管理者の役割 `ashiato` で繋いだ命令は無い

#### Scenario: 戻した後、切っていない更新係は動いている

- **WHEN** 更新の確認を切っていないインストールで、移行が落ちて前の版に戻した後に、サービス `ashiato-updater` を読む
- **THEN** 実行中で、開始の種類は「自動」で、その実行ファイルの版は前の版である

### Requirement: この回の退避が無いとき・移行の失敗でない終わり方では、DB を戻さずに前の版で起こし直す

IF 新しい版の `migrate` が終了コード 2（DB の接続先が手元でない）・3（DB に知らない版がある・版の記録を読めない）・4（系統が違う）で終わる、または 0 以外で終わってもこの回の置き場に取り終えた退避が無い THEN THE SYSTEM SHALL DB を戻さず、プログラムの置き場を前の版に戻し、前の版のサーバで起こし直す。
THE SYSTEM SHALL この回に取ったと特定できない退避（前の回の退避・いちばん新しい名前のファイル）と、取り終えていない退避（書きかけ）を、戻しに使わない。

導出元: FR-119。申し送り st48 R21（終了コード 3 の回は退避が無い）・st54 D3（終了コード 4 も）・ST55 D14。defaults.md C2（design D2）。premises P18。review/deep.md R1・R4。
`rc≠0` を一律に移行の失敗と扱って、いちばん新しい退避を戻すと、前の回の退避（それ以後の記録を含まない）を戻しうる。時計が戻ったときと 2 回目の試みでも同じ。

#### Scenario: DB に新しい版の知らない版があると、戻さずに前の版のまま起きる

- **GIVEN** 版 `0.5.0` が知らない版を当てた DB の上の、版 `0.4.1` のインストール（試験の組み立てで版の記録に版を足した）
- **WHEN** 版 `0.5.0` のインストーラを走らせる
- **THEN** rc≠0 で、`ashiato_failed_` で始まる DB も戻しの DB も無く、記録の件数は走らせる前と同じで、版 `0.4.1` のサーバが `/healthz` に 200 で答える

#### Scenario: 系統が違う DB には、戻さずに前の版のまま起きる

- **GIVEN** 系統の違う DB の上のインストール（試験の組み立ての差し込み）
- **WHEN** 新しい版のインストーラを走らせる
- **THEN** rc≠0 で、DB は戻されず、前の版のサーバが `/healthz` に 200 で答える

#### Scenario: 退避の前に落ちた回は、前の回の退避を戻さない

- **GIVEN** 移行の前の退避の置き場に前の回の退避があるインストールと、退避を取る前に終了コード 1 で落ちる差し込み（試験の組み立て）
- **WHEN** 新しい版のインストーラを走らせる
- **THEN** rc≠0 で、DB は戻されず（`ashiato_failed_` で始まる DB が無い）、記録の件数は走らせる前と同じで、前の版のサーバが起きる

#### Scenario: 書きかけの退避は戻さない

- **GIVEN** 退避を書いている途中で `migrate` を止める差し込み（試験の組み立て）
- **WHEN** 新しい版のインストーラを走らせる
- **THEN** rc≠0 で、DB は戻されず（`ashiato_failed_` で始まる DB が無い）、記録の件数は走らせる前と同じで、前の版のサーバが起きる

### Requirement: 新しい版のサーバが待ち受けを開く前に落ちたら戻し、開いた後は戻さない

IF 移行が通った後、新しい版のサーバが 180 秒以内に待ち受けを開かない THEN THE SYSTEM SHALL 移行が落ちたときと同じに、この回の退避から DB を戻し、プログラムの置き場を前の版に戻し、前の版のサーバで起こし直す。
WHEN 新しい版のサーバが待ち受けを開いた THE SYSTEM SHALL それ以後に新しい版が落ちても、手順がそこで止まって走らせ直しても、DB を戻さない（受け取った記録を捨てない）。

導出元: FR-119（★ Q5 で「移行は通ったが、新しい版が待ち受けを開く前に落ちた」を含める。record の段で要件へ戻す）。深掘り Q5（推奨: 待ち受けを開いた後は戻さない）。premises P13。review/deep.md R4。
待ち受けを開く前は、新しい版は記録を 1 件も受け取っていないので、戻しても失う記録は無い。開いた後に戻すと、新しい版が受け取って 200 を返した記録（収集アプリは未送信から消している）を捨てる。

#### Scenario: 新しい版のサーバが待ち受けを開かなければ、戻して前の版で起きる

- **GIVEN** 起きてすぐに落ちる新しい版のサーバ（試験の組み立ての差し込み）
- **WHEN** 新しい版のインストーラを走らせる
- **THEN** rc≠0 で、サーバの版は前の版、記録の件数と版の記録は走らせる前と同じで、`/healthz` は 200 で答える

#### Scenario: 待ち受けを開いた後に新しい版が落ちても、DB は戻さない

- **GIVEN** 待ち受けを開いた 5 秒後に落ちる新しい版のサーバ（試験の組み立ての差し込み）
- **WHEN** 新しい版のインストーラを走らせ、終わった後に版の記録を読む
- **THEN** インストーラは rc=0 で終わり、版の記録に新しい版の移行があり、`ashiato_failed_` で始まる DB は無い

### Requirement: 更新や戻しが途中で止まっても、サーバは半端な DB で起きず、走らせ直すと前の版へ戻し終えてからやり直す

THE SYSTEM SHALL 更新の手順の間、サーバのサービスの開始の種類を「無効」にしておき、新しい版の待ち受けを確かめた後か、前の版で起こし直すときにだけ「自動」に戻す。
WHEN 「更新の途中」の印が残ったインストールの上で、ST58 以後のどちらかの版のインストーラを走らせる THE SYSTEM SHALL まず前の版へ戻し終え（この回の移行を始めていて、この回の取り終えた退避があれば DB も戻す）、自分の版が前の版と違えば、更新の手順を初めからやり直す。
IF 印の段が「待ち受けを確かめた」である THEN THE SYSTEM SHALL 走らせ直しでも `rollback` の口でも DB とプログラムの置き場を戻さず、更新の手順の (7) の残りを進めて終える。
IF 戻しそのものが落ちる THEN THE SYSTEM SHALL サーバを止めたまま（開始の種類「無効」）、この回の退避の場所と、戻しをやり直す口（`ashiato-setup.exe rollback`）を示して止まる。
WHEN 本人が `rollback` の口を使う THE SYSTEM SHALL 管理者の確認を 1 回出し、印に従って前の版へ戻し終え、前の版のサーバで起こし直す。
IF 「更新の途中」の印が無い THEN THE SYSTEM SHALL `rollback` の口で何も替えず、「戻すものはありません」を示す。

導出元: FR-119。深掘り Q5（推奨: 更新の間はサーバが自分で起きないようにし、印を見てやり直す）。premises P19（サービスは「自動」で、落ちれば 10 秒後に起こし直す）。review/deep.md R3・R4。
途中で電源が落ちると、PC の起動のときにサーバが半分戻った DB で起き、受け取った記録を続きの戻しが捨てうる（Q5 の不可逆）。開始の種類を「無効」にしておけば、印を見て戻すまで起きない。

#### Scenario: 更新の途中で止まると、サービスは自分で起きない

- **GIVEN** 移行の後・新しい版のサーバを起こす前に止まる差し込み（試験の組み立て）
- **WHEN** 新しい版のインストーラを走らせ、止まった後に `sc start ashiato-server` を試みる
- **THEN** サービス `ashiato-server` の開始の種類は「無効」で、開始は断られ、更新の途中の印が残っている

#### Scenario: 移行の後に止まった更新は、走らせ直すと戻してからやり直し、新しい版で起きる

- **GIVEN** 移行の後に止まった更新（前の版 `0.4.0`・新しい版 `0.5.0`）
- **WHEN** 差し込みを外して、版 `0.5.0` のインストーラをもう一度走らせる
- **THEN** rc=0 で、サーバの版は `0.5.0`、記録の件数は更新の前と同じで、更新の途中の印は無い

#### Scenario: 移行の後に止まった更新は、前の版のインストーラで走らせ直すと前の版で起きる

- **GIVEN** 移行の後に止まった更新（前の版 `0.4.0`・新しい版 `0.5.0`。どちらも ST58 以後の組み立て）
- **WHEN** 版 `0.4.0` のインストーラを走らせる
- **THEN** rc=0 で、サーバの版は `0.4.0`、記録の件数と版の記録は更新の前と同じで、開始の種類は「自動」、更新の途中の印は無い

#### Scenario: 待ち受けを開いた後に止まった更新は、走らせ直しても DB を戻さない

- **GIVEN** 新しい版の待ち受けを確かめた直後に止まる差し込み（試験の組み立て）で止まった更新と、その後に新しい版が受け取った記録 1 件
- **WHEN** 差し込みを外して、前の版と新しい版のどちらかのインストーラを走らせる
- **THEN** rc=0 で、サーバの版は新しい版、受け取った 1 件は DB にあり、`ashiato_failed_` で始まる DB は無く、開始の種類は「自動」、更新の途中の印は無い

#### Scenario: 戻しが落ちると、サーバを止めたまま、退避の場所とやり直しの口を示す

- **GIVEN** 戻しの段で落ちる差し込み（試験の組み立て）と、必ず落ちる移行
- **WHEN** 新しい版のインストーラを走らせる
- **THEN** rc≠0 で、出力にこの回の退避の場所と `ashiato-setup.exe rollback` があり、サービス `ashiato-server` は実行中でなく開始の種類は「無効」で、元の名前の DB は消えていない

#### Scenario: 戻しをやり直す口で、前の版で起きる

- **GIVEN** 戻しが落ちて止まったインストール
- **WHEN** 差し込みを外して `ashiato-setup.exe rollback` を走らせる
- **THEN** rc=0 で、サーバの版は前の版、記録の件数と版の記録は更新の前と同じで、更新の途中の印は無い

#### Scenario: 印が無ければ、戻しの口は何も替えない

- **WHEN** 更新の途中の印の無いインストールで `ashiato-setup.exe rollback` を走らせる
- **THEN** 「戻すものはありません」が出て、プログラムの置き場と DB は走らせる前と同じである

### Requirement: 更新が入らなかったことを、インストーラの窓と状態の置き場の更新の記録に残す

WHEN 更新の手順が退避から戻した、または DB を戻さずに前の版で起こし直した THE SYSTEM SHALL インストーラの窓に、戻したか入らなかったか・新しい版・前の版・理由を出し、rc≠0 で終わる。
THE SYSTEM SHALL 理由を、移行が落ちたなら落ちた版の名前と SQLSTATE とその短い説明、移行の前に止まったなら止まった種別とその短い説明にし、DB の誤りの本文を出さない。短い説明は次の表にする（文は design D15（仮））:

| 種別・SQLSTATE の級 | 短い説明 |
|---|---|
| `db_ahead` | DB に新しい版の知らない版がある |
| `ledger_unreadable` | 版の記録を読めない |
| `channel_mismatch` | DB の系統が違う |
| `db_not_loopback` | DB の接続先が手元でない |
| `backup_failed` | 移行の前の退避に失敗した |
| `connect_failed` | DB に繋げない |
| `server_not_listening` | 新しい版のサーバが起きない |
| `aborted` | 移行が途中で終わった |
| `pg_major_mismatch` | 同梱の PostgreSQL の大きい版が違う |
| SQLSTATE `23…` | 制約に反した |
| SQLSTATE `42…` | 定義が当たらない |
| SQLSTATE `53…` | 資源が足りない |
| SQLSTATE `57…` | 止められた |
| SQLSTATE `08…` | 繋がらない |
| ほかの SQLSTATE | DB の誤り |

THE SYSTEM SHALL 更新の記録の 1 行を、欄 `at`（時刻）・`result`（`applied`・`rolled_back`・`not_applied` のどれか）・`to_version`（新しい版）・`from_version`（前の版）・`reason`（`kind`・`failed_version`・`sqlstate`。通った行は `null`）で持つ。
THE SYSTEM SHALL 同じ中身（時刻・結果・新しい版・前の版・理由）を、状態の置き場の更新の記録（`<状態の置き場>\update\outcomes.jsonl`）に 1 行足す（DB の外。戻した DB の形に依らずに残る）。
WHEN 更新が通る THE SYSTEM SHALL 通ったことを同じ記録に 1 行足す。

導出元: FR-120（★ Q4 で「入らなかった」も知らせる。record の段で要件へ戻す）。深掘り Q4（推奨: インストーラの窓と、画面の帯に出す）。申し送り st51 R1。premises P17。review/deep.md R4。
窓を閉じると窓の文は消える。画面の帯（「画面は、サーバの…帯に出し…」）はこの記録を読む。戻した DB が前の版の形だと更新の履歴が「戻した」を受け付けないことがあるので、元の記録は DB の外に置く。

#### Scenario: 移行が落ちて戻すと、窓に戻したことと版と理由が出る

- **GIVEN** 版 `0.4.0` のインストールと、値 `st58-secret-value` を持つ行を重ねて SQLSTATE `23505` で落ちる移行を足した版 `0.5.0` のインストーラ（試験の組み立て）
- **WHEN** インストーラを走らせる
- **THEN** 出力に「0.4.0 に戻しました」・`0.5.0`・落ちた版の名前・`23505`・「制約に反した」があり、更新の記録の最後の行は結果 `rolled_back` で同じ版と理由を持つ
- **AND** 出力・更新の記録・控え・インストーラとサーバのログのどれにも `st58-secret-value` が無い

#### Scenario: 移行の前に止まると、窓に入らなかったことと種別が出る

- **GIVEN** DB に新しい版の知らない版があるインストール
- **WHEN** 新しい版のインストーラを走らせる
- **THEN** 出力に「入りませんでした」・`db_ahead` の短い説明・前の版で動いていることがあり、更新の記録の最後の行は結果 `not_applied` で種別 `db_ahead` を持つ

#### Scenario: 更新が通ると、更新の記録に通った行が足される

- **WHEN** 新しい版のインストーラで更新が通る
- **THEN** 更新の記録の最後の行は結果 `applied` で、新しい版と前の版を持つ

### Requirement: 戻したことを、更新の履歴に「落ちた試みの結果」と「戻した」の 2 行で残す

WHEN 移行が落ちて退避から DB を戻した THE SYSTEM SHALL 前の版のサーバを起こす前に、更新の履歴に 2 行を足す:
「落ちた試みの結果」（きっかけ `migrate`・時刻は戻した時・前の版と今の版は戻した DB の試みの行と同じ・移行の結果は `failed`・落ちた版の名前と SQLSTATE（取れなければ空））と、
「戻した」（きっかけ `migrate`・時刻は戻した時・前の版は落ちた新しい版・今の版は戻した先の前の版・移行の結果 `rolled_back`・当てた版は空・落ちた版の名前と SQLSTATE は空）。
WHEN 移行は通ったが新しい版のサーバが待ち受けを開かずに退避から DB を戻した THE SYSTEM SHALL 「落ちた試みの結果」の代わりに、この回の移行の結果の行（移行の結果 `applied`・当てた版の名前）を時刻を戻した時にして足し、続けて「戻した」の行を足す。
THE SYSTEM SHALL 戻した DB に残っている試みの行を書き直さない。
IF 戻した DB の更新の履歴が `rolled_back` を受け付けない、または表が無い（ST58 の移行・ST51 の移行を持たない版へ戻した）THEN THE SYSTEM SHALL 2 行を状態の置き場の控え（`<状態の置き場>\update\history-pending.jsonl`）に書き、次に `rolled_back` を知る版への更新が通ったとき（新しい版の待ち受けを確かめた後）に、更新の手順が控えた時刻のまま表へ足し、写したことを控えに印す（同じ控えを 2 度写さない）。

導出元: FR-120・FR-121。深掘り Q6（推奨: `outcome` に `rolled_back` を足す。書けない回は状態の置き場に控え、次に通った移行が表へ写す）。申し送り st51 R1。premises P17。review/deep.md R5。
戻した DB には試みの行だけが残る（結果の行は退避より後に書いたので戻すと消える）。戻した後に、落ちた版と SQLSTATE を書き直さないと、書き出しから理由が分からない。書き出しを読む側は `outcome = rolled_back` で「戻した」を読む（一度出た行は書き直せない）。

#### Scenario: 戻すと、更新の履歴に落ちた試みの結果と戻したの 2 行が足される

- **GIVEN** `rolled_back` を知る版 `0.4.0` のインストールと、SQLSTATE `23505` で落ちる移行を足した版 `0.5.0` のインストーラ
- **WHEN** インストーラを走らせて戻した後に、更新の履歴を書いた順に読む
- **THEN** 最後の 3 行は、試み（`attempted`・今の版 `0.5.0`）・落ちた試みの結果（`failed`・今の版 `0.5.0`・落ちた版の名前・`23505`）・戻した（`rolled_back`・前の版 `0.5.0`・今の版 `0.4.0`）の順である

#### Scenario: rolled_back を受け付けない DB に戻すと控えに書き、次に通った移行が表へ写す

- **GIVEN** 更新の履歴が `rolled_back` を受け付けない形の DB（ST58 の移行の前まで当てた）と、落ちた試みの結果と戻したの 2 行を持つ控え
- **WHEN** `rolled_back` を知る版への更新が通り、更新の手順が控えを写す
- **THEN** 更新の履歴に控えの 2 行が控えた時刻のまま足され、控えの行には写した印が付き、もう一度写しても行は増えない

#### Scenario: 戻しても、試みの行は書き直さない

- **WHEN** 戻した後に、戻す前の DB にあった試みの行と、戻した後の同じ `seq` の行を比べる
- **THEN** 2 つの行は全列が同じである

#### Scenario: 待ち受けを開かずに戻すと、更新の履歴に当てた結果と戻したの 2 行が足される

- **GIVEN** `rolled_back` を知る版 `0.4.0` のインストールと、起きてすぐに落ちる新しい版 `0.5.0` のサーバ（試験の組み立て）
- **WHEN** インストーラを走らせて戻した後に、更新の履歴を書いた順に読む
- **THEN** 最後の 3 行は、試み（`attempted`）・当てた結果（`applied`・当てた版の名前）・戻した（`rolled_back`・前の版 `0.5.0`・今の版 `0.4.0`）の順である

### Requirement: 移行の前の退避は、更新が通ったらその回の 1 つだけを残す

WHEN 更新の手順で新しい版のサーバが待ち受けを開いた THE SYSTEM SHALL 移行の前の退避の置き場（`<状態の置き場>\backups\pre-migrate`）の中で、この回の退避の 1 つだけを残し、それより前の退避（前の回の置き場と、ST58 より前の版がじかに置いた退避）を消す。
THE SYSTEM SHALL 戻した回・入らなかった回には、退避を消さない。
THE SYSTEM SHALL 前の回に残した落ちた DB（`ashiato_failed_<時刻>`）を、更新が通ったときに消す。

導出元: FR-119（退避は FR-66 とは別）。深掘り Q7（推奨: 更新が通ったら、その回の 1 つだけを残す）。review/deep.md R6。
更新のたびに DB 全体の写しが 1 つ増え、記録の削除が写しに届かない。戻すのに要るのはその回の退避だけで、毎日の拠点内のバックアップ（FR-66。30 日残す）は別にある。2 つ前より古い更新の前の写しは無くなる（Q7 の不可逆）。

#### Scenario: 更新が通ると、移行の前の退避は直前の 1 つだけになる

- **GIVEN** 移行の前の退避の置き場に、前の版が置いた退避が 2 つあるインストール
- **WHEN** 新しい版のインストーラで更新が通る
- **THEN** 移行の前の退避の置き場の退避は 1 つで、それはこの回の置き場の中にある

#### Scenario: 戻した回は退避を消さない

- **GIVEN** 移行の前の退避の置き場に、前の版が置いた退避が 2 つあるインストール
- **WHEN** 必ず落ちる移行を足した新しい版のインストーラを走らせて戻す
- **THEN** 前の 2 つの退避と、この回の退避が残っている

#### Scenario: 更新が通ると、前の回に残した落ちた DB を消す

- **GIVEN** 前の回に戻して `ashiato_failed_` で始まる DB が 1 つ残ったインストール
- **WHEN** 新しい版のインストーラで更新が通る
- **THEN** `ashiato_failed_` で始まる DB は無い

### Requirement: 同梱の PostgreSQL の大きい版が違う配布物では、何も替えずに止まる

IF 更新の配布物に入っている PostgreSQL の大きい版が、入っている DB の置き場の大きい版と違う THEN THE SYSTEM SHALL サービス・プログラムの置き場・DB に何も触れず（印も前の版の退け先も作らず）、更新の記録に結果 `not_applied`・種別 `pg_major_mismatch` の 1 行だけを足し、大きい版が違うこととその 2 つの版を示して rc≠0 で止まる。
THE SYSTEM SHALL 大きい版が同じで小さい版が違う PostgreSQL は、プログラムの置き場と一緒に入れ替え、戻すときは一緒に前の版に戻す。

導出元: FR-119。defaults.md C5（design D5）。review/deep.md R8。
DB の置き場は大きい版を名前に持つ（`db\17`）。大きい版が違う配布物で入れ替えると、空の DB を新しく作り、記録のある DB を置いたまま空の DB に繋ぎうる。大きい版を上げる道（`pg_upgrade`）は、大きい版を上げる Story が扱う。

#### Scenario: 大きい版の違う PostgreSQL を持つ配布物では、何も替えずに止まる

- **GIVEN** 同梱の PostgreSQL の大きい版を `18` と申告する差し込み（試験の組み立て）を持つ新しい版のインストーラ
- **WHEN** 版 `0.4.0` のインストールの上で走らせる
- **THEN** rc≠0 で、出力に `17` と `18` があり、更新の途中の印も前の版の退け先も無く、サービス `ashiato-server` は実行中で開始の種類は「自動」で、更新の記録の最後の行は結果 `not_applied`・種別 `pg_major_mismatch` である

### Requirement: 切った更新の確認は、更新でも戻しでも切ったままで、戻した後も新しい版を「更新あり」に出す

THE SYSTEM SHALL サーバの更新係の切った印（`enabled: false`）・PC の収集アプリの `update-check off`・携帯の収集アプリの端末ごとのスイッチを、更新でも戻しでも書き換えない。
THE SYSTEM SHALL 切ってあるサーバの更新係を、更新の手順の最後に起こさない（開始の種類「無効」のまま）。
WHEN 前の版に戻した後に、更新の確認が有効である THE SYSTEM SHALL 戻した新しい版をまた「更新あり」に出し、同じ版をもう一度入れられるようにする。

導出元: FR-114。申し送り ST57（更新の確認を切った設定は、更新で戻さない・前の版へ戻したときの更新係）。defaults.md C4（design D4）。review/deep.md R7。

#### Scenario: サーバの切った更新の確認は、更新でも戻しでも切ったまま

- **GIVEN** `update-check off` で切った版 `0.4.0` のインストール
- **WHEN** 版 `0.5.0` のインストーラで更新し、続けて必ず落ちる移行を足した版 `0.6.0` のインストーラで戻す
- **THEN** どちらの後も、切った印は `enabled: false` で、サービス `ashiato-updater` の開始の種類は「無効」である

#### Scenario: PC の切った更新の確認は、入れ替えても切ったまま

- **GIVEN** `update-check off` で切った版 `0.4.0` の PC の収集アプリ
- **WHEN** `update` の口で `0.5.0` に入れ替える
- **THEN** 入れ替えた後の `update-check` の状態は切ったままで、受け手への版の一覧の要求は増えない

#### Scenario: 携帯の切った更新の確認は、入れ替えても切ったまま

- **GIVEN** 設定の画面で更新の確認を切った携帯の収集アプリ（エミュレータ）
- **WHEN** 新しい版の APK を `adb install -r` で入れる
- **THEN** 入れた後の設定の画面のスイッチは切ったままである

#### Scenario: 戻した後も、新しい版を更新ありに出す

- **GIVEN** 更新係の結果が見つけた最新の版 `0.5.0` を持ち、`0.5.0` の移行が落ちて `0.4.0` に戻したインストール
- **WHEN** ログインして `GET /update-status` を求める
- **THEN** `state` は `available` で、`latest` は `0.5.0`、`installed` は `0.4.0` である
## MODIFIED Requirements

### Requirement: インストーラは DB の 3 つの役割を作り、インストールのときだけ移行を当てる

WHEN インストーラが DB を初めて作る THE SYSTEM SHALL 管理者・表の所有者・実行時の 3 つの役割を作り、表の所有を表の所有者へ移し、実行時の役割から管理者と所有者の権限を外す（開発の DB の役割と同じ形）。
WHEN インストーラが走る THE SYSTEM SHALL サーバの移行（`ashiato-server migrate`）を表の所有者で当て、移行の前の退避を状態の置き場の `backups\pre-migrate` に、同梱の `pg_dump` で取る（更新の手順では、その下のこの回のための空の置き場に取る）。
IF 初めてのインストール（前の版の無いインストール）で移行が失敗する THEN THE SYSTEM SHALL サーバのサービスを開始せず、移行の失敗とログの場所を示して止まる。
IF 更新の手順で移行が失敗する THEN THE SYSTEM SHALL 「更新の移行が落ち、この回の退避があれば…」と「この回の退避が無いとき…」に従って前の版で起こし直す。
THE SYSTEM SHALL サーバのサービスが起きるたびには移行を当てない（移行を当てるのはインストールと更新のときだけ）。
THE SYSTEM SHALL 移行の前の退避の置き場と `pg_dump` を、作業の場所や PATH に頼らず、絶対の場所で渡す。

導出元: FR-108・FR-109。C7 / C11 / review/deep.md R7。申し送り K1（`migrate_backup.rs` の既定は作業の場所からの相対で、サービスの作業の場所は `C:\Windows\System32`）。
版の食い違いは、サーバが起動の時に止める（ST48。正典 distribution）。
★ ST58: 更新の手順でも移行を当て、退避はこの回のための置き場に取る。移行の失敗で止まるのは初めてのインストールだけで、更新では前の版へ戻す（FR-119。design D1・D2）。

#### Scenario: 配る形に移行を当ててサーバが起きる

- **WHEN** 配る zip からインストールする
- **THEN** 記録の DB の版の記録に、サーバが知っている全部の移行の版が並び、サーバは実行時の役割の検査を通って起き、`/healthz` に 200 で答える

#### Scenario: 実行時の役割は管理者でも表の所有者でもない

- **WHEN** インストールした後に、実行時の役割 `ashiato_app` の属性と、記録の表の所有者を読む
- **THEN** `ashiato_app` は管理者でなく、どの役割も継がず、記録の表の所有者は `ashiato_owner` である

#### Scenario: 移行の前の退避は状態の置き場に、同梱の pg_dump で取られる

- **WHEN** 移行の前の退避の置き場の指定と PATH の `pg_dump` を持たない環境でインストールする
- **THEN** 退避のファイルが `C:\ProgramData\ashiato\backups\pre-migrate` の下にでき、`C:\Windows\System32` の下には何もできない

#### Scenario: 移行が失敗すると、サーバのサービスを開始せずに止まる

- **WHEN** 当たらない移行を差し込んだ配布物（試験の組み立ての差し込み）で、前の版の無い PC に初めてインストールする
- **THEN** インストーラは rc≠0 で移行の失敗とログの場所を示して止まり、`ashiato-server` は実行中でない

#### Scenario: サービスの起動では移行を当てない

- **WHEN** インストールした後に、版の記録の行の数を数え、`ashiato-server` を止めて開始し、もう一度数える
- **THEN** 2 つの数は同じである

### Requirement: インストールを走らせ直すと足りないものだけを足し、既にある DB・秘密・設定を上書きしない

WHEN 入っている版と同じ版のインストーラをもう一度走らせる THE SYSTEM SHALL 既にある DB・秘密・設定・画面の合言葉を上書きせず、足りないもの（サービス・置き場・権限・プログラム）だけを足す。
WHEN 入っている版と違う版のインストーラを走らせる THE SYSTEM SHALL 何も替えずに止まるのではなく、更新の手順（「サーバのインストーラは、入っている版と違う版で走らせると…」）に入る。
WHEN 「更新の途中」の印が残ったインストールの上で走らせる THE SYSTEM SHALL 走らせ直しの段より先に、前の版へ戻し終える（「更新や戻しが途中で止まっても…」）。
WHEN 更新係の無い前のインストールの上で走らせ直す THE SYSTEM SHALL 更新係のサービスと置き場と権限を足し、更新の確認を有効にする。
THE SYSTEM SHALL 走らせ直しで、更新係の切った印（`enabled: false`）と確かめた記録を上書きせず、切ってある確認を入れ直さない。
THE SYSTEM SHALL 秘密を設定に書き終えてから DB を作る（途中で落ちても「秘密はあるのに DB が無い」側に倒れ、走らせ直しで DB を作れる）。
IF DB はあるのに秘密が無い THEN THE SYSTEM SHALL 何も書き換えず、DB と秘密が食い違っていることと状態の置き場の場所と、出口のインストーラの `repair` の口を示して止まる。
WHEN 前のインストールが画面の合言葉を決める前に終わっていた THE SYSTEM SHALL 走らせ直しで、画面の合言葉を決める段からやり直す。

導出元: FR-108・FR-110・FR-111。C10 / review/deep.md R5。
★ ST57: 更新係を足す・切った確認を戻さない（聞かない既定 C7）。
★ ST58: 違う版のインストーラは更新の手順に入る（今までは別の版のファイルがあれば何も替えずに止まった。premises P10）。同じ版の走らせ直しは変えない。
上書きすると DB に繋げなくなり、収集アプリの資格情報も切れる。DB があるのに秘密が無いまま止まっている間、携帯の未送信は上限（90 日・2 GB。FR-9）に向かって溜まるので、記録を残したまま戻る出口を `repair` の口に置く（design D10・D27。深掘り Q8）。

#### Scenario: 走らせ直しても秘密と DB は変わらない

- **WHEN** インストールした後に、設定のファイルの指紋と記録の件数を控え、インストーラをもう一度走らせる
- **THEN** 設定のファイルの指紋と記録の件数は控えと同じで、2 つのサービスは実行中である

#### Scenario: DB を作る途中で落ちても、走らせ直しで DB ができる

- **WHEN** DB を作る段で止まる差し込み（試験の組み立ての差し込み）でインストーラを走らせ、差し込みを外してもう一度走らせる
- **THEN** 2 回目で DB ができ、1 回目に作った秘密でサーバが起きる

#### Scenario: DB はあるのに秘密が無いと、何も書き換えずに止まる

- **WHEN** インストールした後に設定のファイルを退け、インストーラをもう一度走らせる
- **THEN** インストーラは rc≠0 で DB と秘密の食い違いと状態の置き場の場所と `repair` の口を示して止まり、DB の置き場の中身と記録の件数は変わらない

#### Scenario: 合言葉を決める前に閉じたら、走らせ直しで合言葉の段からやり直す

- **WHEN** 画面の合言葉を決める段でインストーラを閉じ、もう一度走らせる
- **THEN** 2 回目は DB と秘密を作り直さずに、画面の合言葉を決める段を出す

#### Scenario: 更新係の無いインストールを走らせ直すと、更新係が足される

- **GIVEN** 更新係のサービスと置き場の無い、前の版のインストール（試験の組み立ての差し込みで更新係を消した形）
- **WHEN** インストーラをもう一度走らせる
- **THEN** サービス `ashiato-updater` が開始の種類「自動」で登録され、更新係の置き場ができ、DB と設定のファイルの指紋は控えと同じである
