## R40. Q17 で「通す」と決めた 3 つのうち 2 つは Q21 で対象が消え、残る「本文の消去」が 0004 の迂回をそのまま開ける

- 成果物: openspec/changes/st03-idempotent-ingest/deep-questions-r4.json（新規）
- 根拠: Q21 の答え（履歴は自分の感度と削除の印を持たない）で、履歴表に `sensitivity` も
  `deleted_at` も無い。**Q17 の選択肢 1 が「通す」と書いた「削除の印・感度」には当てる先が無く**、
  残る正当な書き換えは「本文の消去」（FR-51 / ST23）だけになる。
  実験 T3（実測）—— ① `BEGIN; INSERT INTO core.event_version …; UPDATE core.event SET raw='{"t":"tampered"}' …; COMMIT;`
  ② `UPDATE core.event_version SET raw='', payload='{}';`（Q17 が通すと決めた操作そのもの）
  → **`event = {"t":"tampered"} / version 1,2 = 空`**。原文は 1 本も残らない。
  DB には「本人が消すと決めた」か「攻撃者が消した」かを見分ける材料が無い。
  実験 Z1 は「親が削除済みのときだけ消去を通す」という絞りが**効く**ことを示すが、
  実験 Z3（実測）—— 書き換え → **親を論理削除** → 履歴を消去 → **`deleted_at=NULL` で削除を取り消す**
  → **改竄した本文が生きた行として残り、原文は消える**。論理削除の付け外しは
  `migrations/0002_immutable_collected.sql:10`（「論理削除は通す」）が両方向に開けている。
  `migrations/0004_immutable_origin.sql:5-13` が記録した 3 手の迂回と同じ形が、履歴側で復活している
- kind: irreversible
- 処置: escalated — Q23。本文の消去を DB が改竄とどう見分けるかを 1 問にした。選択肢 2（親が削除済みのときだけ）には「削除の取り消しを塞がないと 4 手が残る＝塞ぐと取り消せない削除になる」を代償として書いた
- 提案: 「**履歴の本文の消去（FR-51）を、DB がどうやって改竄と見分けるか**」を 1 問にする。
  選択肢は (a) FR-51 が残す消去の台帳（「削除した事実・時刻・件数・範囲」）の行が同じ
  トランザクションにあるときだけ通す（**Q10 とまったく同じ形**。ST03 で台帳の形を決めることになる）、
  (b) 親が削除済みのときだけ通す（**併せて論理削除の取り消しを塞がないと 4 手が残る** —— 実験 Z3）、
  (c) 見分けない（Q17 の「原文を失わない」は約束だけになる）。
  併せて、`deep.md` に Q17 の答えを書くときは「削除の印・感度」を落とす（対象が無い）。

## R43. 外部識別子を記録ごとに持たないソースでは、外部での更新が行を増やす —— ST03 自身の完了の判定 2 がそのクラスで成り立たない
