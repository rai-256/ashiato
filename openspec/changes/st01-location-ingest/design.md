## Context

製造準備 B で縦串（ダミー 1 件 → 保存 → 取り出し）が通っており、次のものは**すでに在る**:

| 在るもの | 場所 |
|---|---|
| エンベロープの表と登録簿・稼働記録 | `migrations/0001_envelope.sql` |
| 取り込み口・読み出し口・資格情報の検査 | `crates/server/src/lib.rs` |
| 送信の形と冪等キー | `crates/server/src/ingest.rs` / `docs/collector-contract.md` |
| Android のビルド（**位置取得は無い**） | `collector-android/` |

制約: サーバは Rust、C-01 は Kotlin、C-02 は Rust（製造準備 A-1）。
**同じ 1 件を Kotlin と Rust のどちらが送っても同じ結果になること**を B の縦串が確かめている。
運用コストは 0 を目指す（全部ローカル）。開発は週 15 時間。

## Goals / Non-Goals

**Goals:**

- 位置の実データが端末から D-01 まで届き、エンベロープの欄がすべて埋まる
- 記録が**後から足せないもの**（原文・時刻 2 本・地域・出自・版・単位）を day one から持つ
- 不変条件をサーバ側の 1 か所に集め、収集側の実装が 2 つに分かれても守られる

**Non-Goals:**

- **圏外でのバッファと保持の上限** —— ST04。ここでは「失敗したら未送信のまま残す」だけ
- **稼働記録の可視化** —— ST02。ここでは既存の更新処理をそのまま通す
- **冪等の一般則（`external_id` による重複判定）** —— ST03
- **端末時計のずれの測定** —— ST05
- **画面での閲覧** —— ST25

## Decisions

### D1. 冪等キーを安定なハッシュへ差し替える（BREAKING）

現在の `content_hash` は `std::collections::hash_map::DefaultHasher` を使っている。

```rust
let mut h = std::collections::hash_map::DefaultHasher::new();
```

**Rust の標準ライブラリは `DefaultHasher` の出力が版をまたいで安定であることを保証していない。**
これは DB に永続化して再送判定に使う鍵の性質と両立しない —— コンパイラを上げた日に、
**同じ原文が別の鍵になり、全件が重複として二重に入る**。

→ **SHA-256 を採る。** 追加依存は `sha2` 1 本。BLAKE3 のほうが速いが、
毎秒 1/60 件の頻度で速度は問題にならず、SHA-256 のほうが**他言語の実装を確かめやすい**
（Kotlin 側が同じ鍵を再現できるかを検証する場面がある）。

代替案: `DefaultHasher` のまま「版を上げない」と決める → **却下**。
依存更新は月 1 回まとめて上げる方針（製造準備 A-4）と正面から衝突する。

既存データへの影響: **縦串のダミーのみ**なので失われるものは無い。

### D2. NFC 正規化はサーバ側の取り込み口 1 か所で行う

収集側（Kotlin / Rust）に置くと、**片方が忘れた瞬間に混在が始まる**。
混在は後から直せない（扉 #16）。

正規化の対象は `payload` と `raw` の**両方の文字列**。
`raw` を正規化することは「原文をそのまま残す」（FR-18）と一見ぶつかるが、
**扉 #16 が「値の形」を NFC に決めている**ので、こちらが優先する。
バイト列としての原本が要る記録（写真など）は `raw` ではなく別の置き場を使う（FR-4 / ST09）。

→ 実装は `unicode-normalization` crate。JSON の文字列だけを再帰的に走査する。

### D3. 「収集した」記録の書き換え禁止は DB で強制する

アプリ層のチェックでは、**同じ PC で動く第三者製プラグイン**（PERM-8 が既定を最も厳しい側に
置いている前提）や、psql を直接叩く運用が素通りする。

→ `core.event` に `BEFORE UPDATE` トリガを置き、`origin = 'collected'` の行の
`raw` / `payload` / `event_time` の変更を拒否する。`deleted_at` / `deleted_by` の更新は通す
（論理削除は FR-50 で認められている）。

代替案: 権限で `UPDATE` を落とす → **却下**。論理削除が通らなくなる。

### D4. 単位系と座標系を要求の欄に足す

いまは DB の DEFAULT（`si` / `EPSG:4326`）任せで、**収集側が指定する経路が無い**。
FR-28 は「持たせる」だけでなく、後から別の測地系のソースが入ったときに
**既存分と区別できること**が目的なので、送り手が言えないと意味が薄い。

→ `IngestRequest` に `unit_system: Option<String>` / `crs: Option<String>` を足し、
省略時はサーバ側で既定を入れる。`docs/collector-contract.md` と `docs/openapi.json` を更新する。

### D5. `origin` の検査をアプリ層に上げる

いまは DB の `CHECK` だけなので、不正値は `internal()` を通って **500** になる。
呼び出し側から見ると「自分の要求が悪い」と分からない。

→ 受け取り時に列挙で検査して **400**。応答本文には受け取った値を載せない
（`internal()` が既にそうしているのと同じ理由 —— 値が呼び出し元に反射する）。

### D6. 端末識別子は自前で採番して端末に保存する

Android の `ANDROID_ID` は初期化でリセットされ、かつ**端末をまたいで追跡できる値**でもある。

→ 初回起動時に UUID を 1 つ生成し、アプリの保存領域に置く。以後それを送る。
アプリを消して入れ直すと変わるが、**それは「別の端末」として扱ってよい**
（記録が消えるわけではなく、以後の記録が別の端末識別子を持つだけ）。

### D7. 位置取得は前景サービスで行う

Android は継続的な位置取得を前景サービスなしには許さない（常時通知が出る）。

→ 前景サービス + `FusedLocationProviderClient` の定期取得。60 秒間隔は FR-1 が定めている。
通知が常時出るのは**利用者が本人 1 名**なので受け入れる。

### D8. 利用者識別子は環境変数で 1 つ固定する

PERM-1 が「利用者を 1 名として運用」と定めている。

→ `.env` の `ASHIATO_USER_ID`（UUID）をサーバと収集側の両方が使う。
`.env.example` に雛形を置く。DB に利用者表を作るのは、利用者が 2 名になったときでよい
（列は day one から持っているので、後から表を足しても既存行は埋まっている —— 扉 #9 の狙い）。

## Risks / Trade-offs

| リスク | 緩和 |
|---|---|
| **60 秒間隔の位置取得が電池を食う** | FR-1 が間隔を定めているので、まず要件どおり作って実測する。実測してから要件へ戻す（間隔は可逆な決定） |
| **`raw` の正規化が「原文そのまま」と衝突して見える** | D2 に判断の根拠を書いた。バイト列の原本が要る記録は別経路（ST09） |
| **前景サービスの常時通知が邪魔になる** | 本人 1 名なので受け入れる。嫌なら間隔を延ばす（可逆） |
| **Android の実機確認が CI で回らない** | 完了の判定に「実機を持って外を歩く」が入っている。CI はビルドと単体までを見る |
| **SHA-256 への差し替えを Kotlin 側が再現できるか** | 鍵の算出は**サーバ側だけ**が行う。収集側は鍵を作らない（現在の設計どおり） |

## Open Questions

- **水平精度の下限を設けるか。** 精度が 1km の記録も残すか、捨てるか。
  → **残す方針で進める**（捨てると後から復元できない。精度の欄があるので後から絞れる）。
  実データを見てから要件へ戻す。**specs にも tasks にも影響しない**ので後回しにできる
- **稼働記録の日付境界を UTC のままにするか、`tz_id` を見るか。** 現在の実装は UTC 固定。
  → **ST02（収集が動いていたかが日単位で見える）の担当**。そこで決める
