## Purpose

記録が「後から足せないもの」を失わずに保存されることを保証する。原文・出来事の時刻と格納の時刻・
地域・出自・スキーマ版・単位と座標系・利用者を、すべての記録が day one から持つ。
書き込みの受け入れ条件（登録簿・資格情報・値の妥当性）もこの capability に属する。

## ADDED Requirements

### Requirement: 記録は取得元から受け取った原文を失わない

THE SYSTEM SHALL 記録を格納するとき、取得元から受け取った原文をそのまま 1 つの欄に保存する。
THE SYSTEM SHALL 原文を**構造として解釈し直さない** —— 受け取った並び・表記・重複を保ったまま保存する。
THE SYSTEM SHALL 「収集した」に分類された記録の原文と解析済みの内容を、格納後に書き換えない。

導出元: FR-18, FR-30。扉 #7（原文をそのまま残すか。決着済 —— 残す）。
原文を捨てると、解析の誤りに後から気付いても**元に戻せない**。

> **2 行目は 2026-09-08 の追加（深掘り 第 2 回）。** 原文を JSON 型で保存すると、
> 格納するのは「受け取ったもの」ではなく「**構造として同じもの**」になる。実測: `jsonb` は
> キー順を変え（`{"b":1,"a":2}` → `{"a":2,"b":1}`）、重複キーを落とし、
> 数値表記を展開する（`1e2` → `100`）。
> **深掘り 第 1 回で原文の NFC 正規化を拒んだ理由（署名の検証・外部との照合）は、
> 型が正規化する限り達成できない。** 保存する型は文字列でなければならない。

#### Scenario: 原文がそのまま残る

- **WHEN** 取得元から受け取った内容を 1 件格納する
- **THEN** 格納された記録の原文の欄が、受け取った内容とバイト単位で一致する

#### Scenario: 並び・重複・表記が保たれる

- **WHEN** キーの並びが辞書順でなく、重複キーを含み、指数表記の数値を含む原文を送る
- **THEN** 保存された原文は、並び・重複・表記のすべてが送ったままである

#### Scenario: 収集した記録は書き換えられない

- **WHEN** 「収集した」に分類された記録の原文または解析済みの内容を更新しようとする
- **THEN** 更新は拒否され、記録は変わらない

### Requirement: 記録は 2 つの時刻と地域を持つ

THE SYSTEM SHALL すべての記録に「出来事が起きた時刻」と「格納された時刻」の 2 つを持たせる。
THE SYSTEM SHALL 出来事が起きた時刻に、UTC からのずれ（分）とタイムゾーン識別子の両方を持たせる。

導出元: FR-19, FR-20。扉 #6（決着済）。
片方しか持たないと「いつ起きたか」と「いつ届いたか」を後から区別できない。
ずれだけでは夏時間の切り替えを再現できず、識別子だけでは当時のずれが分からない。

#### Scenario: 2 つの時刻が両方埋まる

- **WHEN** 記録を 1 件格納する
- **THEN** 出来事が起きた時刻と格納された時刻の両方が埋まっている
- **AND** UTC からのずれとタイムゾーン識別子の両方が埋まっている

#### Scenario: 時刻の欄が欠けた要求は拒否される

- **WHEN** 出来事が起きた時刻・UTC からのずれ・タイムゾーン識別子のいずれかを欠いた要求を受け取る
- **THEN** 要求は 400 で拒否され、記録は格納されない

### Requirement: 記録は出自を特定できる

THE SYSTEM SHALL すべての記録に、収集側で生成した一意な識別子を持たせる。
THE SYSTEM SHALL すべての記録に、どの論理ソース・どの端末が生成したかを持たせる。
THE SYSTEM SHALL すべての記録を「収集した」「本人が書いた」「派生させた」のいずれかに分類する。
THE SYSTEM SHALL すべての記録に利用者識別子を持たせ、利用者を 1 名として運用する。

導出元: FR-21, FR-24, FR-25, FR-29, PERM-1。扉 #8, #9, #13（いずれも決着済）。
由来が混ざると、AI が推定した値と本人が書いた値を区別できなくなり、成功条件 2 を壊す。

#### Scenario: 出自の欄がすべて埋まる

- **WHEN** 記録を 1 件格納する
- **THEN** 収集側の識別子・論理ソース・端末識別子・由来の分類・利用者識別子がすべて埋まっている

#### Scenario: 分類にない値は拒否される

- **WHEN** 由来の分類が「収集した」「本人が書いた」「派生させた」のいずれでもない要求を受け取る
- **THEN** 要求は 400 で拒否される
- **AND** 応答に内部の詳細（表名・接続先・受け取った値）が含まれない

### Requirement: 記録は解釈に必要な版と単位を持つ

THE SYSTEM SHALL すべての記録に、それが書かれた時点のスキーマ版を持たせる。
THE SYSTEM SHALL 数値を持つ記録に、単位系と座標系の識別子を持たせる。
THE SYSTEM SHALL 単位系と座標系を収集側が要求で指定できるようにし、省略時は既定値を用いる。

導出元: FR-26, FR-28。扉 #10, #11（いずれも決着済）。
版を持たないと、解釈の規則を変えたときに過去の記録をどう読むべきか判らなくなる。
座標系を持たないと、別の測地系のソースが後から入ったとき既存分と区別できない。

#### Scenario: 版と単位が埋まる

- **WHEN** 記録を 1 件格納する
- **THEN** スキーマ版・単位系・座標系がすべて埋まっている

#### Scenario: 収集側が座標系を指定できる

- **WHEN** 既定と異なる座標系を指定した要求を受け取る
- **THEN** 指定された座標系が記録に保存される

### Requirement: 解析済みの文字列は NFC に正規化され、原文は手を加えられない

THE SYSTEM SHALL 解析済みの内容に含まれる文字列を、格納するとき Unicode NFC に正規化する。
THE SYSTEM SHALL 正規化を取り込み口の 1 か所で行い、収集側の実装に依存しない。
THE SYSTEM SHALL 原文に対しては正規化を含むいかなる変換も行わず、受け取ったまま保存する。

導出元: FR-27（NFC）, FR-18（原文をそのまま）。扉 #16（NFC に統一）。

**FR-18 と扉 #16 は衝突する。本人の判断で FR-18 を優先し、正規化の対象を解析済みの内容に限る**
（2026-09-08、ST01 の深掘り）。理由: 原文のバイト列は**一度変換すると二度と戻らない**のに対し、
原文を後から正規化することはいつでもできる。外部サービスとの照合や署名の検証が
将来必要になったとき、変換済みの原文では確かめられない。
検索・照合は解析済みの側で行うので、混在の実害は解析済みが NFC であれば防げる。

#### Scenario: 解析済みの文字列は合成済みで保存される

- **WHEN** 解析済みの内容に NFD（分解済み）の濁点を含む文字列を入れて送る
- **THEN** 保存された解析済みの文字列は NFC（合成済み）になっている

#### Scenario: 原文は受け取ったまま保存される

- **WHEN** 原文の中に NFD の文字列を含む要求を送る
- **THEN** 保存された原文はバイト単位で送られたものと一致する
- **AND** 原文の中の文字列は NFD のままである

### Requirement: 登録簿に無いソースは受け付けない

THE SYSTEM SHALL 登録簿に登録された論理ソースからの記録だけを受け付ける。
THE SYSTEM SHALL 新しいソースの追加を、登録簿への 1 行の追加だけで完了させ、API の変更を要求しない。

導出元: FR-61。
API を変えずにソースを増やせることが、プラグイン機構（FR-77）の前提になる。

#### Scenario: 未登録のソースは拒否される

- **WHEN** 登録簿に無い論理ソースを名乗る要求を受け取る
- **THEN** 要求は 400 で拒否され、記録は格納されない

#### Scenario: 登録するだけで受け付けられる

- **WHEN** 登録簿に新しい論理ソースを 1 行追加する
- **THEN** API のコードを変更せずに、そのソースからの記録が受け付けられる

### Requirement: 取り込み口は複数件をまとめて受け取り、1 件ごとの結果を返す

THE SYSTEM SHALL 取り込み口で、記録の配列を 1 回の要求として受け取る。
THE SYSTEM SHALL 記録 1 件だけを配列に包まずに送った要求も、長さ 1 の配列として受け取る。
THE SYSTEM SHALL 応答を、要求に並んだ順の**1 件ごとの結果**として返す。
THE SYSTEM SHALL 1 件でも格納したとき 200 を返し、**1 件も受け付けなかったときだけ** 400 を返す。
THE SYSTEM SHALL 要求の一部が不正でも、正しい分を格納する。

導出元: FR-10, FR-22。design D12 / D13 / D14。

**この 3 つは実装で決まったが、仕様に属する** —— 呼び出し側は状態符号ではなく
1 件ごとの結果を見て「何を未送信から取り除くか」を決める。ここが決まっていないと、
部分失敗のときに成功分まで再送されるか、失敗分が黙って捨てられる。
`design.md` にだけ書くと archive で正典から落ちるので、ここに置く。

#### Scenario: 複数件を 1 回で受け取る

- **WHEN** 記録 3 件の配列を 1 回の要求で送る
- **THEN** 3 件すべてが格納される
- **AND** 応答は送った順に並ぶ 3 件ぶんの結果である

#### Scenario: 1 件だけの裸の要求も受け取る

- **WHEN** 配列に包まずに記録 1 件を送る
- **THEN** 長さ 1 の配列として受け取られ、応答は 1 件ぶんの結果の配列である

#### Scenario: 一部が不正でも正しい分は格納される

- **WHEN** 3 件のうち 1 件が不正な要求を送る
- **THEN** 正しい 2 件は格納され、応答のその 2 件は受理を示す
- **AND** 不正な 1 件は受理されなかったことを示す
- **AND** 状態符号は 200 である

#### Scenario: 1 件も受け付けなかったときだけ 400

- **WHEN** 送ったすべてが不正な要求を送る
- **THEN** 状態符号は 400 である

### Requirement: すべての API 要求は資格情報を要求する

THE SYSTEM SHALL すべての API 要求に、呼び出し元を識別できる資格情報を要求する。
THE SYSTEM SHALL 資格情報を欠くか一致しない要求を 401 で拒否する。
THE SYSTEM SHALL 資格情報の比較を、一致した長さから内容が推測されない方法で行う。

導出元: PERM-10。
PERM-7（外部からの到達を Tailscale 網内に限る）は**網の外を止めるだけ**で、
**同じ PC の中から呼ぶものを何も止めない**。第三者製のプラグインは同じ PC で動く。

#### Scenario: 資格情報が無いと拒否される

- **WHEN** 資格情報を付けずに取り込み口または読み出し口を呼ぶ
- **THEN** 401 で拒否される

#### Scenario: 同じ PC の別プロセスからでも拒否される

- **WHEN** 同じ PC 上の別プロセスが資格情報を付けずに呼ぶ
- **THEN** 401 で拒否される
