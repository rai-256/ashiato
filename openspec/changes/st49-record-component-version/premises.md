# ST49 の前提（外の形式・既存の振る舞い）

ST49 の決定は外のサービスの形式には依らない。依るのは**この repo の収集アプリとサーバの今の振る舞い**（溜め方・送り方・資格情報の区別・版の置き場）で、
どれも `file:line` で辿れる。

**失われるもの（`loss`）のある問いが載る前提**: Q1 は 4・5、Q2 は 6・11、Q3 は 12、Q4 は 7・13。4 は走らせて確かめた（4）。5 は走っている ST48 の仮の決定で、
Q1 の推奨はそれに依らない（ST48 の D8 が否になっても、記録に残す印の中身は Q1 の答えで決まる。そろえるのは値の形だけ —— C11）。
6・7・11・12・13 は「どこで書くか」の前提で、外れても**失う側の選択が変わらない**（失わない側の推奨は、書く場所が増えるだけ）。確かさ 2〜3 のまま tasks の試験で 4 に上げる。
1〜3 は C4・C9 の実装の前提で、どの問いにも載らない（失わない側 —— 今の版を付けない・読み飛ばしても入る —— を C で既に選んでいる）。

### 確かさを上げる先（spec の段で tasks の検証にする）

- 1・2: 版の欄の無い**今の形の未送信の行**を材料に置き、更新後の収集アプリが読み戻して送ると、版が空（不明）で届く試験（C-01 は Robolectric、C-02 は `#[cfg(test)]`）。既定を今の版にすると落ちる
- 3: 版の欄つきの要求を、版の列を持たない S-01 の形で読んでも受け付ける試験（serde の読み飛ばしを固定する）
- 6: 画面のログインで送った要求に収集アプリの版の欄を書いても、記録には S-01 の版だけが入る試験

## 聞かずに決めるもの（C。spec の段で design の D にする）

- **C1** 版は記録の**送信要求の 1 件ごと**の欄で申告する（まとめ送りの見出しや HTTP のヘッダにしない）。見出しにすると「送った時の版」になり、C7 の取り違えが戻る（前提 1）
- **C2** 版の値は**文字列のまま**持ち、形を検査しない・断らない。収集アプリの申告が空・形が違っても記録は受け付ける（断ると収集アプリは FR-10 で捨てる。FR-124）。空文字は「不明」（null）として持つ
- **C3** 版の欄は**内容の鍵（`content_hash`）・破棄の報告の鍵（`logical_source + raw`）に混ぜない**。版を `raw` にも入れない（別の欄にする）。混ぜると同じ記録が版ごとに別の行になり、重複の判定が変わる（壊してはいけない「同じ記録を何度送っても増えない」）。
  同じ内容が別の版から 2 度届いたら、先に入った行の版が残る（後の到着は重複で、行も版も変わらない）
- **C4** 版を持たない記録は「不明」（null）のまま持つ。**後から推定で埋めない**（取り込みの時刻から版を当て推量すると、本物の版と区別できなくなる）。
  ST49 より前に入った記録と、更新の前に溜まって更新の後に届いた未送信がこれに当たる。収集アプリは溜めた行を読み戻すとき、欄が無ければ**今の版を入れない**（前提 2）
- **C5**（design D1（仮）・D2（仮））版は**今の中身を作った部品の版**を指す。中身が入れ替わるときは版も一緒に動かし、前の値を前の版の表（`core.event_version`・その読み口・書き出しの前の版の表）に写す —— `schema_version` と同じ扱い（前提 10・11）:
  外部サービス由来の更新（FR-22。C-02 のブラウザ履歴の読み直しを含む）は、届いた要求の収集アプリの版と受け取った S-01 の版に変える。滞在の作り直しで原文が変わったときは作り直した S-01 の版に変える（前提 8 の `push_version` に列を足す）。
  印だけの書き換えと、変わらなかった滞在は元の版のまま。前の版の表の列が本表と揃うことを試験で固定する（足し忘れると更新のたびに前の値が消える）
- **C6**（説明の書き分けは design D4）版の列は書き出し（ST33）の記録の表と前の版の表に、説明つきで足す。今の列は消さず・名前を変えない。
  説明は書き分ける: 収集アプリの版（と画面の版）は「部品の申告（S-01 は確かめていない）」、S-01 の版は「S-01 が自分で入れた」（FR-123 が衛星を外す理由「確かめられない」は収集アプリの版にも当たる。外に出た説明は直せない）
- **C7** 収集アプリの版を信じるのは API の合言葉の要求だけ。画面のログインの要求が収集アプリの版の欄を書いてきても、収集アプリの版としては使わない（前提 6）。衛星の資格情報の要求（ST29 が足す）にも収集アプリの版を付けない（FR-123 の★ Q13）。
  判定は `ingest_request` の呼び出し元（HTTP の認可の判定か、S-01 の中の格納か）から渡す（書庫の格納には HTTP の判定が無い。`lib.rs:537-540`）
- **C8** 版の列は書き換えの門（FR-30）の**外**に置く。収集アプリの申告値（`device_id`・`tz_*`）を門の外に置いた先例（`gates.sql:66-70`）と同じで、誤った印（C10 で防ぐが、古い組み立てに残る）を直す余地を残す。
  版は内容の鍵の入力ではない。代わりに、列を書き換えるのは C5 の経路（前の版を残す）だけにする
- **C9** 版の変化の検知（FR-121。生存信号で申告する）と送信契約の版（FR-124 / FR-130）は持たない（ST51・ST50）。ST49 が足す欄は任意の欄で、今の収集アプリ・今の S-01 との組み合わせで記録は失われない（前提 3）。
  **代償**: 扉 32 の期限（配布の経路に切り替える日）の前は、S-01 より先に収集アプリを入れ替えた間に送った記録の版と、収集アプリを古い版へ戻した間に送った未送信の版は落ちる（古い側が欄を読み飛ばす。記録は 200 で入り、収集アプリは未送信から消す）。
  失わない側として、収集アプリの溜めは読み戻した行の知らない欄を捨てずにそのまま送る形にする（以後の版を戻しても欄が落ちない。design D3（仮））。ST49 より前の版へ戻した間の脱落は直せない。
  期限の後は ST50（FR-125 / FR-130）が止める。S-01 を先に・収集アプリを後に入れ替える順を tasks に置くか、ST50 を requires に入れるかは spec の段で決める
- **C10** 組み立ての印は**組み立てのたびに作り直す**。S-01・C-02 の `build.rs` は git の HEAD と参照先（worktree では `git rev-parse --git-dir` の先）の変化で作り直し、C-01 の gradle は構成キャッシュに印を載せない。
  ST48 の D8（「HEAD の変化では作り直さない」）は DB の台帳の診断の材料なので許したが、記録の版は**後から直せない記録に焼き込む**ので、古い印を許さない。印を取れなければ `unknown`
- **C11** 印の値の形は ST48 の台帳（`build_version`・`build_commit`）とそろえる（commit は 40 桁。短縮しない）。ST48 の D8 が否になったら、印の作り方だけを ST49 が持ち、形は変えない
- **C12** 選び出す口（画面や API の絞り込み）はこの Story では作らない。版は書き出し（C6）と D-01 の問い合わせで選べる。後から作っても失うものは無い（review/deep.md R12）
- **C13** 生存信号（`core.heartbeat`）には版を付けない。動いている版の申告は ST51（FR-121）が生存信号に足す
- **C14** 走っている ST41（同じ `INSERT`・`IngestRequest`・`EVENT_COLUMNS` に列を足し、`core.event_live` の `SELECT *` を作り直す）・ST23（`ingest_request` に呼び出し元の引数を足す）・ST48（移行を当て直さない）と同じ箇所を触る。
  ST49 の移行で `core.event_live` と前の版の読み口を作り直す。触る順は spec の段で tasks に書く（proposal の Impact）
