# ST09 設計 — 写真と動画をメタごと取り込み、写真は原本も置く

## Context

- `collector-android` は ST01 / ST04 / ST05 / ST06 / ST17 で、位置・アプリ利用・集計・時計の 4 本のソースを持ち、未送信の置き場（`SegmentStore`。1 件 1 行の JSON、
  端末に積んでから 90 日かつ全ソースで 2 GB）・破棄の報告（`DropLedger`）・ソースごとの生存信号（`SourceCadence` / `HeartbeatEmitter`）が揃っている。
  **端末の写真の一覧（MediaStore）も EXIF もまだ読んでいない。** `ACCESS_MEDIA_LOCATION` と `READ_MEDIA_IMAGES` は宣言済み、`READ_MEDIA_VIDEO` は未宣言（premises.md P10）
- 取得可否は `Capability.of(permission, sensor, network)` で、接続を全ソースの取得可否に混ぜている（`Heartbeat.kt`。整合の確認 K2）
- `crates/server` は `/ingest`（JSON の配列。axum の既定で 1 回 2 MB まで。P9）・`/heartbeat`・`/drops` を持ち、登録簿 `core.source` に `c01-photo` の行がある
  （想定間隔 21600 秒。`migrations/202609111111_coverage_rebuild.sql`）。`touch_started_on` は記録が届くたびに収集開始日を前へ動かす（K1）
- 書き出し（ST33）は `export/excluded.rs` の一覧でソースを分類し、分類の無い表・列・ソースで止まる。`c01-photo` は「時刻 1 点」「緯度経度を持つ」に載っている
- 深掘りで本人が決めたこと（Q1〜Q17）は `deep.md`。**ここで決めるのは、その決定を実装に落とすときの技術判断だけ**で、観測可能な振る舞いは
  `specs/` に置いてある（`design.md` に置くと `openspec archive` で正典から落ちるため）

外の形式の前提は `premises.md`（P1〜P14）。確かさ 2 以下の前提は、下流の最初の計測テスト（Task 2）で 4 まで上げ、外れたら止める。

## Goals / Non-Goals

**Goals**
- 端末から消えた後は取れないもの（過去の写真・画像の原本・動画のメタ・消えた事実）を、取れるうちに残す
- 写真の原本が ST04 の未送信の 2 GB を食い潰さない（「壊してはいけないもの」）
- 書き換え禁止の記録に、後で並びや採り方を変えると書き換えになる値（D-02 の場所）を持たない

**Non-Goals**
- **写真を画面に出す・写真を 1 件消す口**（Q17。新しい Story として /requirements から足す）。1 日の画面（ST25 / ST22 の画面）にも写真を足さない
- **原本の欠け・量を稼働状況の画面に出す**。ST09 は画面を持たない（ブリーフの面）。読み出しの口（D12）だけを足し、見せ方は ST31 / ST10 か画面の Story が決める
- **週次の突き合わせ（FR-72）** は ST10。**バックアップ（FR-66 / FR-67）と拠点外（NFR-9）** は ST30 / ST31（`docs/handoff/ST10.md` / `ST31.md`）
- **衛星と AI の読み出しで撮影位置を抜く門** は ST45 / ST38（`docs/handoff/ST45.md`）。**種類（FR-88 / FR-102）の欄** は ST38（D19）
- **文字抽出のエンジンと結果を書く処理**（ST35）。表だけを空で作る（D17）
- **本文の消去（FR-51）を D-02 に及ぼす** のは ST23（deep.md の R8）
- アプリ利用の取得可否から接続を外すこと（整合の確認 C6。変えるなら ST09 の外の change で本人に問う）

## Decisions

### D1. 端末の写真の一覧を読む 1 つの読み手が、4 つの論理ソースの記録を作る

- 読み手（`MediaScanner`）は MediaStore の画像と動画の表を、端末のすべての置き場（`MediaStore.getExternalVolumeNames`）について読む。
  論理ソースは D3 で決める。位置とは別のスレッドで走り、位置の 60 秒の取得を止めない
- 契機は 3 つ（Q11（B）/ C14）:
  1. **保存の知らせ**: 画像と動画の表に `ContentObserver` を張り、知らせを受けたら **10 秒待って**（続けて来た知らせを 1 回にまとめる）変わった分を読む
  2. **6 時間の見直し**: 置き場ごとの世代の数（`MediaStore.getGeneration`）が前回から変わったかを聞き、変わった分（`GENERATION_MODIFIED` が前回より大きい行）を読む
  3. **1 日 1 回の全部の突き合わせ**: 世代の数に頼らず、一覧の全部の行を見分けの台帳（D2）と突き合わせる。**前回の全部の突き合わせから 24 時間**で行い、
     前回の時刻が今より先なら（時計が戻った）すぐ行う。一覧の版（`MediaStore.getVersion`）が変わったと分かったときもすぐ行う
- **1 回の契機で読むのは 200 件まで**（仮）。残りは同じ契機の続きとして続けて読み、1 件ずつ記録を未送信に積む（初回の過去ぶんで数万件を一度にメモリに持たない）
- **（仮）反転条件**: 知らせを受ける形が電池を目に見えて食うと分かったら、知らせを外して 1 時間ごとの見直しにする（deep.md Q11 の反転条件。記録の形は変わらない）

### D2. 見分けの台帳（端末）は、項目の番号ごとに中身のハッシュと読んだ時の印を持つ

- 置き場ごとに `media/ledger-<置き場>.jsonl`（1 行 = `media_id`・`sha256`・`size`・`date_modified`・`generation_modified`・`source`・`trashed`）と、
  `media/cursor.json`（置き場ごとの世代の数・一覧の版・前回の全部の突き合わせの時刻）を持つ
- **ハッシュを計算し直すのは、新しい項目か、大きさ・`DATE_MODIFIED`・`GENERATION_MODIFIED` のどれかが台帳と違う項目だけ**。全部の突き合わせでも、
  変わっていない項目のファイルは開かない（29 GB を毎日読まない）
- **同じかどうかは中身のハッシュで決める**（C17）: 台帳に無い番号でも、同じハッシュの記録をすでに送っていれば新しい記録にしない（原文が違えば更新として送る。D4）
- 一覧の版が変わった（番号が振り直された）ら、台帳の番号を信じずに全部の項目のハッシュを計算し直し、ハッシュで台帳と結び直す（その 1 回だけ全部を読む）
- 台帳が無い（入れ直した・消えた）ときは全部が初めて見るものになり、全部を読んで送る。S-01 は外部識別子（内容ハッシュ）で畳むので記録は増えない
- **（仮）反転条件**: 世代の数が上がらない外れ方が 1 日 1 回の突き合わせでも追いつかない頻度で起きると分かったら、全部の突き合わせを 6 時間ごとにする（C14。P3 は確かさ 2）

### D3.（仮）論理ソースは保存先のフォルダ（`RELATIVE_PATH`）で決める

| 保存先 | 論理ソース |
|---|---|
| 動画の表の行（どこに保存されていても） | `c01-video` |
| `DCIM/Screenshots/`・`Pictures/Screenshots/` で始まる | `c01-screenshot` |
| 上の外で `DCIM/` で始まる | `c01-photo` |
| それ以外の画像（`Download/`・`Pictures/<アプリ名>/`・編集の書き出しなど） | `c01-image` |

- 1 つの項目の論理ソースは、最初に記録を作ったときのもので固定し、後で保存先が変わっても付け替えない（動かした写真は同じ記録の更新。D4）
- **（仮）反転条件**: 本人の端末のカメラが `DCIM/` の外に保存する、またはスクリーンショットが表の外のフォルダに入ると分かったら表に足す。
  すでに別のソースに入った記録は付け替えない（3 つとも承認は同じローカル AI だけで、成功条件 1 は生存信号で数えるので、入った先が違っても失うものは無い。読む側で合わせられる）

### D4. 記録の形（`payload`）と原文、外部識別子

`payload`（S-01 が解析した値として持つ。名前は書き出しの分類（D16）が読む `lat` / `lon` / `duration_ms` に合わせる）:

| 欄 | 何を |
|---|---|
| `kind` | `media`（写真・画像・動画）か `vanished`（消えた事実。D5） |
| `sha256` | ファイル全体のバイトの SHA-256（16 進の小文字） |
| `media_id` / `volume` | 端末の一覧の項目の番号と置き場の名前 |
| `previous_sha256` | 同じ項目の番号で中身が変わったとき、変わる前のハッシュ（Q7）。無ければ欄を持たない |
| `taken_at_exif` / `offset_exif` | EXIF の `DateTimeOriginal` と `OffsetTimeOriginal`（動画は入れ物の作成時刻）。文字列のまま |
| `date_taken_store` / `date_added` | 端末の一覧の `DATE_TAKEN` と `DATE_ADDED`（端末に保存された時刻） |
| `time_basis` | `taken`（撮影時刻を採った）か `stored`（保存された時刻を採った）。Q14 |
| `tz_basis` | `exif`（メタのずれ）か `device`（端末の地域を当てた）。C7 |
| `lat` / `lon` | 写真・動画自身のメタの位置だけ（C6）。無ければ欄を持たない |
| `make` / `model` / `width` / `height` / `mime` / `size_bytes` | あれば |
| `duration_ms` | 動画の長さ |
| `relative_path` / `display_name` | 保存先のフォルダと元のファイル名（D-02 の名前に使う。D10） |

- **出来事の時刻**（Q14）: 撮影時刻 = `taken_at_exif` を `offset_exif`（無ければ D4 の地域）で読んだもの**だけ**。端末の一覧の `DATE_TAKEN`（`date_taken_store`）は
  持つが採らない —— 端末が EXIF から作るか、無ければ保存の時刻で埋めるので、採ると本人が選んだ「保存された時刻 + 印」の枝が消える（review/spec.md R1）。
  撮影時刻が無い・`2000-01-02T00:00:00Z` より前・`date_added` より 24 時間以上後（ちょうど 24 時間を含む）なら `date_added` を採り `time_basis = stored`（R2）
- **地域**（C7）: `offset_exif` があればそれ、無ければ**読んだ時点の端末の地域**（`ZoneId.systemDefault()`）をその時刻に当てて `tz_basis = device`。
  過去の写真では撮った時の地域と違いうる（Risks）
- **原文**（C5）: `{"store": {<MediaStore の行の全部の列>}, "exif": {<タグ名>: <ExifInterface が返した文字列>}, "omitted": [<落としたタグ名>]}` を 1 つの JSON の文字列にする。
  動画は `exif` の代わりに `container`（`MediaMetadataRetriever` の全部のキー）。**縮小画像（`JPEGInterchangeFormat` の中身・`ThumbnailImage`）と、
  型が UNDEFINED / BYTE で 256 バイトを超えるタグ（`MakerNote` など）は値を入れず、名前を `omitted` に挙げる**（仮）。
  **文字のタグは長さで落とさない**（上限で切り詰めない。動画は原本が無いので、落としたメタは戻らない。review/spec.md R4）。大きさは D20 の門で見る
- **外部識別子**（C17）: `kind = media` は `sha256` そのもの（`external_id_kind = record`）。`kind = vanished` は `vanished:<sha256>:<volume>:<media_id>`
- **更新**: 同じハッシュの項目について、端末の一覧の行か原文が台帳に送ったものから変わったら、同じ外部識別子で原文を送り直す（FR-22 の経路で前の版が履歴に残る）。
  `source_updated_at` は載せない（届いた順に当たる。record-envelope の正典）
- **（仮）反転条件（`source_updated_at`）**: 未送信の再送で古い原文が新しい原文を書き戻すと分かったら、読んだ時刻を `source_updated_at` に載せる（ST08 D15 の形）。
  前の版は履歴に残るので、どちらでも失うものは無い
- **（仮）反転条件（`omitted`）**: 落としたバイナリのタグに本人が読みたい値があると分かったら入れる（写真の原本は D-02 に残るので、写真は後から読み直せる。動画の入れ物のメタは文字のキーなので落ちない）

### D5.（仮）消えた事実は同じ論理ソースの記録で、観測の記録として数える

- 全部の突き合わせ（D1 の 3）でだけ判定する。判定するのは、写真と動画へのアクセスが全部あり（「選んだ写真だけ」でない）、写真の位置の権限があるときだけ（Q8）
- 台帳にある番号が一覧に無く、**同じハッシュがどの置き場の一覧にも無く**、その項目の置き場がつながっている（`getExternalVolumeNames` にある）ときに消えたとする。
  ごみ箱の項目（`IS_TRASHED = 1`）は一覧にあるものとして数える（`QUERY_ARG_MATCH_TRASHED` で読む）
- 消えた事実の記録の出来事の時刻は**気づいた時刻**、位置は持たない。台帳から項目を外し、2 度目は作らない
- **（仮）反転条件**: 消えた事実の記録で「記録あり」になる日が、撮っていない日を撮った日に見せて紛らわしいと分かったら、格子の数えから外す
  （`collection-coverage` の「格子で数えない記録」に足す。記録は残るので数え直せる）

### D6.（仮）権限・取得可否の語彙・知らせ

- `AndroidManifest.xml` に `READ_MEDIA_VIDEO`・`READ_MEDIA_VISUAL_USER_SELECTED`・`READ_EXTERNAL_STORAGE`（`maxSdkVersion="32"`。minSdk 30 の端末用）を足す
- 初回の起動で、位置の許可の後に、写真と動画へのアクセス（33 以上は `READ_MEDIA_IMAGES` + `READ_MEDIA_VIDEO` + `READ_MEDIA_VISUAL_USER_SELECTED`、32 以下は
  `READ_EXTERNAL_STORAGE`）と `ACCESS_MEDIA_LOCATION` を求める。拒まれても収集は始める（ST06 の `ソースごとに独立して収集する`）
- メディアのソースの `blockers` の語彙（C-01 の `permission` / `sensor` / `network` と混ぜない別の語。サーバは語彙を検査しない）:

  | 語 | いつ |
  |---|---|
  | `permission` | 写真と動画へのアクセスが無い |
  | `media_location` | `ACCESS_MEDIA_LOCATION` が無い（Q15） |
  | `partial` | 「選んだ写真だけ」（C12） |
  | `stage_read` / `stage_hash` / `stage_enqueue` / `stage_ledger` | その区間の契機が 1 回以上あり、すべてがその段で失敗した（C19。D22） |

- **知らせ**（Q15。文言は仮）: 通知のチャンネル `media-capture`（重要度は既定）。題「写真と動画を取れていません」、本文「写真の位置へのアクセスを許可するまで、
  写真と動画を取らずに待っています。」（写真と動画へのアクセスが無いときは「写真と動画へのアクセスを許可するまで、…」）。押すとこのアプリの設定
  （`Settings.ACTION_APPLICATION_DETAILS_SETTINGS`）が開く。権限が戻ったら消す。「選んだ写真だけ」では出さない（生存信号だけ）
- **（仮）反転条件（文言）**: 本人が文言や出し方を変えたいと言ったとき（記録は変わらない）

### D7.（仮）生存信号の接続の有無は、任意の欄 `network` と列 `core.heartbeat.network`

- `/heartbeat` の要求に任意の真偽値 `network` を足す（送る契機の時点で接続があったか）。無い要求は今のまま受け、列は `NULL`（分からない）
- メディアの 4 つのソースの `capturable` は D6 の語だけで決め、`network` は別に載せる。位置・アプリ利用・集計・時計は今のまま（`network` を載せない）
- 移行で `core.heartbeat` に `network boolean NULL` を足す（書き換え禁止の門はそのまま）。書き出しは出す列に分類する（D16）
- **（仮）反転条件**: Q10 —— 本人が「圏外の日は写真も未達でよい」と言ったとき。`network` が行に残るので、達成を数え直せる

### D8.（仮）原本の送り待ちの台帳（端末）は、未送信の置き場と別に持ち、90 日・2 GB で捨てない

- `media/originals.jsonl`（1 行 = `sha256`・`volume`・`media_id`・`source`・`size`・`backlog`・`queued_at`・`state`）。`state` は `awaiting_record` か `ready`
- 画像の記録を未送信に積んだときに `awaiting_record` で 1 行足し、その記録が S-01 に受理（重複を含む）されたと送信の結果で分かったら `ready` にする
  （S-01 は記録の無い原本を受け取らない。D10）
- 1 行は数百バイトなので、過去ぶん 1 万件で数 MB。ST04 の 2 GB と 90 日の対象にしない（Q4。「生存信号と同じ扱い」）
- その記録が未送信の上限で破棄されたら（`Retention` が破棄の報告を作るとき）、その行を消して原本の欠け（`record_dropped`）を報告する（D11）
- その記録が S-01 に恒久的に断られて未送信から消えたら（正典の「恒久的に断られた記録は未送信から消える」の経路）、その行を消して原本の欠け（`record_rejected`）を報告する（review/spec.md R7）
- `backlog` は、収集がその項目を見つけた時刻より `date_added` が 24 時間以上前なら真（Q9。D9）。撮影の時刻では決めない（撮影が古く保存が新しい受け取った画像は新しいもの）
- **（仮）反転条件（24 時間）**: 入れ直し・権限の戻りの後に見つけた「保存から 1 日以上たった新しい写真」がモバイル通信で送られず困ると分かったら延ばす（記録の形は変わらない）

### D9.（仮）送り手は 1 つずつ、2 回読んで送る

- 未送信の記録を送った後に、`ready` の行を 1 つずつ送る。順は **`backlog = false` を `queued_at` の古い順、次に `backlog = true` を `date_added` の新しい順**
- **通信**（Q9）: `backlog = false` はどの通信でも、`backlog = true` は従量制でない通信（`NET_CAPABILITY_NOT_METERED`）のときだけ
- **送る前に問い合わせる**（review/spec.md R9）: `HEAD /media/originals/{sha256}?user_id=` で受け取り済みなら、読まずに行を消す（入れ直した後に約 29 GB を読み直して送り直さない）
- **2 回読む**: 1 回目で `setRequireOriginal` の URI からハッシュを計算し、記録のハッシュと合わなければ送らない（中身が変わった。原本の欠け `changed`）。
  合えば 2 回目で読みながら送る（`PUT` の固定長の流し送り）。2 回目の途中で変わったら S-01 が合わないと返し、次の回の 1 回目で `changed` になる。
  端末に写しを作らないので（Q4）、送るバイトと確かめたバイトを同じにする手段がこれしかない
- **応答**: 受け取った（`201` / `200`）→ 行を消す / `503 storage_unavailable`・届かない → 1 分から倍にして 1 時間で止める間隔で試し直す /
  `409 record_missing`（`ready` は受理の後なので、記録が後で生きていなくなった）→ 同じ間隔で試し直し、**最初の 409 から 7 日続いたら**行を消して原本の欠け `record_missing` を報告する（仮。R7）/
  `422 hash_mismatch` → 次の回に 1 回目からやり直す / `413` → 原本の欠け `too_large` / 読めない（項目が無い）→ 原本の欠け `vanished`（読めるが開けない → `unreadable`）
- **（仮）反転条件**: 初回の過去ぶんが Wi-Fi だけでは送り切れない（数週間かかる）と分かったとき（deep.md Q9）。2 回読みの電池や時間が目に見えて重いと分かったら、
  1 回目を省いて S-01 の確かめだけにする（送るバイトが変わった版でも S-01 が置かないので、失うものは無い）

### D10. 原本の受け口と D-02 の書き手（S-01）

- `PUT /media/originals/{sha256}?user_id=<uuid>`。本文は原本のバイトのまま。資格情報は `/ingest` と同じ
- この経路だけ本文の上限を **1 GiB**（仮）にし（`DefaultBodyLimit`。ほかの経路の 2 MB は変えない）、超えたら `413 too_large`。本文を流しながら `<置き場>/.incoming/<uuid>.part` に書き、SHA-256 を計算する
- `HEAD /media/originals/{sha256}?user_id=` は受け取りの行があれば `200`、無ければ `404`（本文を受けない）
- **S-01 の起動時に `.incoming/` の `.part` を全部消す**（書いている途中で S-01 が落ちたものが置き場の容量とバックアップを食い続けないように。R28）
- 書き終えたら: ハッシュが指したものと違う → `.part` を消して `422 hash_mismatch` / その利用者の `c01-photo` / `c01-screenshot` / `c01-image` の生きている記録に
  `payload.sha256` が一致するものが無い → `c01-video` にだけあれば `422 video_not_accepted`、どこにも無ければ `409 record_missing` /
  受け取りの行がすでにある → `.part` を消して `200` / それ以外 → `fsync` → 名前を変えて並びに置く → 受け取りの行を積む → `201`
- **並び**（Q12）: `<置き場>/<YYYY>/<MM>/<YYYYMMDD-HHMMSS>_<名前>`。時刻は記録の出来事の時刻を記録の地域で読んだもの、名前は `display_name` を D10a で整えたもの。
  同じ名前のファイルがあり中身が違えば `<stem>_<sha256 の頭 8 文字><ext>`。記録が複数あればいちばん古い受理のものを使う
- **D10a 名前の整え方**: `/` と `\` の最後の後ろだけを取り、`<>:"/\|?*` と制御文字を `_` に、末尾の `.` と空白を落とし、空・`.`・`..` なら `media`、
  Windows の予約名（`CON` など）には `_` を前に足し、120 文字で切る（拡張子は残す）。置いた場所が置き場の下にあることを、正規化した道筋で確かめてから名前を変える
- 受け取りの行（`core.media_original`）: `user_id`・`sha256`・`logical_source`・`size_bytes`・`received_at`。`(user_id, sha256)` で 1 つ。**ファイルの場所を持たない**（C2）。書き換え禁止
- D-02 に書けない（置き場が無い・ディスクが一杯・権限が無い）→ `503 storage_unavailable` と、種別だけを S-01 のログと量の読み出しの直近の失敗（D12）に出す。
  **設定された置き場が無ければ作らない**（外したドライブの空の差し込み口に書かない）。既定の置き場だけは S-01 の起動時に作る（spec の Scenario で固定）
- **（仮）反転条件（1 GiB）**: 本人の端末に 1 GiB を超える画像があると量の読み出しで分かったら上げる（超えたものは `too_large` の欠けとして残っていて、端末にあるうちなら送り直せる）

### D11. 原本の欠けの受け口

- `POST /media/missing`（`/drops` と同じ形: 複数件をまとめて受け、1 件ごとの結果を返す）。1 件 = `id`（収集側で採番）・`user_id`・`device_id`・`logical_source`・
  `sha256`・`reason`（`vanished` / `changed` / `unreadable` / `too_large` / `record_dropped` / `record_rejected` / `record_missing`）・`noticed_at`
- 表 `core.media_missing`。冪等キーは `id`。追記のみ（書き換え禁止の門）
- 端末は未送信の置き場に乗せて送る（`DropReport` と同じ扱い。1 件 数百バイト）。**生存信号・破棄の報告と同じく 90 日・2 GB の上限で捨てない**（R6）

### D12.（仮）量と原本の進みの読み出しは `GET /media/summary`

- ソースごとに: `records`（生きている `kind = media` の記録の件数）・`record_bytes`（その `size_bytes` の合計）・画像のソースは `originals_stored`（件数とバイト）・
  `originals_waiting`（記録はあるが受け取りの行も欠けも無い件数）・`missing`（理由ごとの件数）。全体で `last_storage_error`（種別と時刻。S-01 の実行中だけ持つ）
- 記録の値（位置・ファイル名・原文・ハッシュ）を載せない。資格情報は `/ingest` と同じ。`last_storage_error` は S-01 を起動し直すと消える（失敗そのものはログに残る）。`docs/openapi.json` を再生成する
- **（仮）反転条件**: ST31 / ST10 が別の切り口（日ごと・端末ごと）を求めたら足す（どれも記録と 2 つの表から数え直せる）

### D13.（仮）メディアのソースの収集開始日は、登録簿の印で生存信号だけから決める

- `core.source` に `started_on_basis text NOT NULL DEFAULT 'record'`（`record` / `heartbeat`）を足し、メディアの 4 つを `heartbeat` にする
- `touch_started_on` は `heartbeat` のソースについて `Arrival::Record` では何もしない（生存信号の登録日の門はそのまま）。収集開始日の引き直しも同じ規則に従う
- 移行は、4 つのソースの `collection_started_on` を「登録日以降でいちばん古い生存信号の日、無ければ `NULL`」に当て直す（記録は 1 件も変えない）
- **（仮）反転条件**: Q13 —— 本人が「過去の写真の日も窓に入れたい」と言ったとき。印を `record` に戻し、引き直せば記録から計算し直せる

### D14. 状態の判定の例外は、判定順の (1) の中だけに置く

- `heartbeat` のソースで、その日が収集開始日より前（収集開始日が `NULL` なら全日）で、その日に観測の記録が 1 件以上あれば ① を返し、無ければ ⑦ を返す
- 達成（NFR-13）と途絶（FR-80）は今のまま収集開始日から数えるので、変えない（⑦ を ① に変えるのは格子と状態の読み出しだけ）。
  変えていないことを Scenario `見始めた日より前の記録ありの日は達成の分母に入らない` で固定する

### D15. 登録簿の移行

  2. 4 つの `external_id_kind` を `record` にする —— **そのソースの記録が 0 件のときだけ**（ST08 D7 と同じ。記録のある行を後から変えると、識別子なしで入った行と畳めない）
  3. `started_on_basis`（D13）・`core.heartbeat.network`（D7）
  4. `core.media_original`・`core.media_missing`・`core.text_extraction`（D17）と、それぞれの書き換え禁止の門と、アプリの役割への権限（`SELECT` / `INSERT` だけ）

### D22.（仮）メディアの試行と成功の数え方

- **試行** = 読み手の契機（保存の知らせ・6 時間の見直し・1 日 1 回の突き合わせ）1 回。1 回の契機は 4 つのソースのそれぞれに 1 試行を数える（そのソースの項目が 0 件でも）。正典「ソースごとに独立して収集する」をこの形に MODIFIED した（review/spec.md R17）
- **成功** = その契機で、そのソースの読んだ項目のすべてが D6 の各段を通った（0 件なら成功）
- `SourceCadence` の 4 つは取得契機の間隔 6 時間・生存信号の区間 6 時間（不変条件 `生存信号の区間 ≥ 取得契機の間隔` を満たす）。保存の知らせの分だけ試行が満点の刻みより多くなるが、
  成功が試行を超えることは無い（整合の確認の「未確認」の 1 件目への答え）
- C19 の「失敗し続ける」= その区間の試行が 1 回以上あり、成功が 0 回で、失敗の段が同じ（違えば最後の段を載せる）
- **（仮）反転条件**: 取得率が知らせの多い日に 1 を超えて見える読み方が見つかったら、知らせを試行に数えず見直しだけを数える

  （外へ出す経路は書き出しも衛星も消した時間の撮影位置を出さないので、印の有無を後から変えても失うものは無い）

## Risks / Trade-offs

- **[送り切る前にまとめて消すと原本を失う]** → 本人が Q4 で選んだ。失ったものは原本の欠け（D11）にハッシュつきで残り、量の読み出し（D12）で見える
- **[初回の過去ぶんが大きい]** → 約 29 GB 以下（画像のぶん）。Wi-Fi だけで送るので数日かかりうる（Q9）。記録（メタ）は先に全部届く。D9 の反転条件
- **[初回のハッシュの計算]** → 全部のファイルを 1 回読む（端末の読み出しが律速。P14）。位置とは別のスレッドで、200 件ずつ（D1）。電池が目に見えて重いと分かったら、
  過去ぶんのハッシュを充電中だけに絞る（仮。記録の形は変えない）
- **[過去の写真の地域は読んだ時の端末の地域]** → `offset_exif` の無い過去の写真は、撮った時の地域と違いうる。`tz_basis = device` の印と元の値が残るので、
  並べ替え・表示は読む側で引き直せる。出来事の時刻と地域の列は書き換えられない（C7）
- **[世代の数の外れ方]** → 1 日 1 回の全部の突き合わせで拾う（D2 の反転条件）
- **[位置の権限を拒まれ続ける]** → その間の写真は取らない（Q15。本人が選んだ）。通知と生存信号の `media_location` で見える
- **[D-02 のディスクが一杯]** → 受け口が `503` を返し、端末に送り待ちが残る（捨てない）。ログと量の読み出しに出る。ST10 の週次を待たない（C19）
- **[2 回読みの間の上書き]** → S-01 が置かないので壊れた原本は残らない。次の回に `changed` の欠けになる（D9）
- **[名前の整え方の取りこぼし]** → 置き場の下にあることを正規化した道筋で確かめてから置く（D10a）。外れたら書かずに `422` にして欠けにしない（端末に残る）

## Migration Plan

- 移行 1 本（D15）。`external_id_kind` の変更は記録が 0 件のソースにだけ当たる
- 端末は入れ替えの後の最初の起動で権限を求め、全部の突き合わせから始める（台帳が無いので過去ぶんを全部読む。Q3）
- **merge の順序は書かない** —— gate が main に rebase するので、後から merge する側が追従する
