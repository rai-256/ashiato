## Why

写真は「そのとき何をしていたか」の最も濃い記録なのに、**端末やクラウドから消えた後は原本を取れない**（扉 #19）。
本人は「空き容量を増やす」でまとめて端末から消すことがあり（深掘り Q2）、端末にはいま写真と動画が合わせて約 29 GB ある（Q1）。
いまの収集アプリは端末の写真の一覧（MediaStore）を 1 度も読んでいない（`c01-photo` は登録簿にあるが、記録も生存信号も来ない）。

いま作れる理由: 先行の ST04（端末の未送信の保持・破棄の報告）が archive 済みで、写真の原本が未送信の 2 GB を食い潰さない形
（「壊してはいけないもの」）をその上に決められる。

## What Changes

深掘りは **2 回・17 問**（第 1 回 Q1〜Q16、第 2 回 Q17）。**17 問とも本人が選んだ**（推奨のまま 0 件）。推奨と違う側を選んだのは
**Q6（動画はメタだけ。代表の静止画も送らない）** と **Q16（滞在を消しても写真は消えない）**。全文は `deep.md`。

- **C-01 が端末の画像と動画を、収集がまだ取っていないものから全部取る**（Q3）。導入時に端末にある過去のものも、止めていた間のものも取る。
  保存の知らせを受けてすぐ取り、6 時間ごとにも見直し、1 日 1 回は一覧の全部と突き合わせる（Q11 / C14）
- **論理ソースを 4 つにする**: カメラの写真 `c01-photo`（既存）・スクリーンショット `c01-screenshot`・カメラ以外の画像 `c01-image`・動画 `c01-video`
  （Q5 / C1 / C18）。新しい 3 つを登録簿に足す。成功条件 1（NFR-13）の「写真」は `c01-photo` のまま
- **1 件の記録**は撮影時刻を出来事の時刻にし（無い・狂っていれば端末に保存された時刻 + 印。Q14）、位置は写真自身のメタだけ（C6）、
  内容ハッシュはファイル全体の SHA-256（C3）。**同じ写真かどうかは中身のハッシュで見分ける**（C17）。中身が変わったら新しい記録（Q7）。
  端末から消えたら消えた事実を 1 件残す（Q8）
- **写真の位置の権限（`ACCESS_MEDIA_LOCATION`）が無い間は、写真も動画も取らずに待ち、端末で知らせる**（Q15）
- **画像の原本は端末に写しを作らず、送るときに端末から読んで自宅 PC の D-02 に置く**（Q4）。未送信の置き場（ST04 の 90 日・2 GB）に入れない。
  新しく撮ったものはどの通信でも、初回の過去ぶんは Wi-Fi のときだけ送る（Q9）。**動画の原本は送らず、受け口も受け取らない**（FR-6 / Q6）
- **原本の受け口を JSON の取り込み口と別に作る**（C11）。届いたバイトのハッシュが記録と合ったときだけ受け取り、同じ原本は 1 つだけ置く。
  D-02 の置き場は設定で変えられ（C10）、撮影の年/月のフォルダに撮影日時と元の名前で並べる（Q12）。D-01 はファイルの場所を持たない（C2）
- **送る前に失った原本は「原本の欠け」として理由とハッシュで残す**（C8）。ST04 の破棄の報告（格子の⑤）には載せない
- **写真と画像の量と原本の進み**（記録の件数とバイト・置いた原本・待っている原本・欠け）を読み出す口を足す（整合の確認 C8。ST31 の試算の入力）
- **写真と動画の「取得できる状態か」に接続を含めず、接続の有無を別の欄に残す**（Q10 / FR-78 ★）。取得から送信待ちまでの全段で決める（C19）
- **メディアのソースの収集開始日は最初の生存信号の日にし、撮影日まで遡らせない。それより前でも記録のある日は格子に「記録あり」と出す**（Q13 / FR-79 ★）
- **滞在を消しても写真・動画・画像の記録に削除の印を付けず、D-02 の原本も消さない**（Q16 / Q17）。**ただし書き出しからは、消した時間の撮影位置つきの写真・動画・画像の行を今のまま除く**（NFR-16）——
  同じ写真が ashiato の中では消えず、外へは出ない、という差が残る（本人の答えの読み方。GO 資料で見せる）
- **文字抽出の結果を入れる表を、中身が空のまま作る**（FR-32 / C15）。エンジンとその世代の列を持つ
- 足したソースと表を**書き出しの分類に載せる**（C15。載せないと書き出しが分類の無い表で止まる）

**BREAKING は無い。** `/ingest` と `/heartbeat` の形は変えない（生存信号に任意の欄 `network` を 1 つ足すだけで、無い信号は今のまま受ける）。

## Capabilities

### New Capabilities

無し。

### Modified Capabilities

- **`device-collection`** —— 写真・画像・動画の取得・記録の形・見分け・消えた事実・権限・原本の送り方と受け口・D-02 の置き場・原本の欠け・量の読み出し・
  滞在を消したときの扱い・文字抽出の表の Requirement を足し（ADDED）、生存信号の取得可否の条項と、ソースごとの試行の数え方（保存の知らせも試行に数える）をメディアのソースについて `MODIFIED` する
- **`collection-coverage`** —— 生存信号の取得可否（接続の有無を別に受ける）・収集開始日（メディアのソースは最初の生存信号の日）・
  状態の判定順（見始めた日より前でも記録のある日は「記録あり」）の 3 本を `MODIFIED` する
- **`data-durability`** —— 足したソース・生存信号の欄・表を書き出しの分類に載せる Requirement を足す（ADDED）

**前倒しは無い。** `collection-coverage` と `data-durability` は record の段で INDEX の割当てに足した（`docs/stories/INDEX.md` の訂正 2026-10-17。整合の確認 C12）。
足すのは INDEX が許した範囲だけ（取得可否・収集開始日・格子の見え方 / 書き出しの分類）。
**`record-deletion` には触らない** —— 正典の「位置以外の記録には印を付けない」のままで Q16 が成り立つ（INDEX の同じ訂正）。
Q16 の Scenario は `device-collection` の写真の Requirement に置く。
