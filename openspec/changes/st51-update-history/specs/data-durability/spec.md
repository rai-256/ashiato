## MODIFIED Requirements

### Requirement: 書き出しは台帳・導出・内部の表と、消したことの痕跡を入れない

THE SYSTEM SHALL 削除の台帳・消去の台帳・書き出しの台帳・読み出しの記録・画面のログインの印・衛星の資格情報・日ごとの件数（稼働状況の導出）・取り込みと作り直しの内部の表を書き出しに入れない。
THE SYSTEM SHALL 写真・動画の原本（D-02）を書き出しに入れない（記録のメタは記録として入る）。
THE SYSTEM SHALL 写しの時点で除いた行の件数を、書き出したどのファイルにも、書き出しの状態の応答にも出さない（書き出しの状態が出すのは、前回の書き出しの後に消した記録の件数だけ）。
THE SYSTEM SHALL 記録の schema のどの表も、書き出しに入れるか入れないかが決まっている状態にし、決まっていない表があれば書き出しを始めずに失敗として終える。
THE SYSTEM SHALL 書き出しに入れる表のどの列も、出すか出さないかが決まっている状態にし、決まっていない列があれば書き出しを始めずに失敗として終える。出さない列は説明書の「入らないもの」に名前を挙げる。

導出元: NFR-16 / FR-50。深掘り C6 / C8 / C12 / C15 / Q3（第 2 回: 後に消した記録の件数は画面に出す）。日ごとの件数は削除済みも数えるので、記録の数との差から「その日に消した」ことが読める。
表や列を足す Story が分類を忘れると、黙って入る（台帳や回数が外へ出る）か黙って落ちる（記録が欠ける）ので、分類の無い表と列で止める。
★ ST29（深掘り C7）: 衛星の資格情報（値のハッシュ・最後に使われた時刻）を入らないものに足し、zip の中のファイルの一覧に衛星の登録簿を足した。
あわせて、一覧に場所（ST21）・気分の対象の種類と気分の通知（ST17）のファイルが書かれていなかったのを、実際の書き出しに合わせて書き足した（振る舞いは変えていない）。
★ ST51（深掘り Q5 の推奨・premises の C5）: zip の中のファイルの一覧に、更新の履歴（S-01 の版の変化）と収集アプリの版の変化（生存信号から導いた読み口）を足した。どちらも台帳ではなく、途絶の理由を後から区別する材料（扉 #33・#14）なので入れる。

#### Scenario: 台帳と導出の表は書き出しに入らない

- **WHEN** 滞在を消し（削除の台帳に行がある）、書き出しを 1 度済ませてから、もう一度書き出す
- **THEN** 2 度目の zip の中のファイルは、記録・前の版・ソースの登録簿・個人属性の種類と名前・場所・気分の対象の種類・気分の通知・滞在の基準・生存信号・停止と破棄の期間・破棄の報告（日ごと時間ごと）・衛星の登録簿・更新の履歴・収集アプリの版の変化のファイルと、説明書と目録だけで、それ以外のファイルは無い

#### Scenario: 除いた行の件数はどこにも出ない

- **WHEN** 滞在を消してから書き出し、書き出しの状態を読み出す
- **THEN** 説明書・目録・応答のどこにも、写しの時点で除いた行の件数が書かれておらず、応答で件数を持つ項目は後に消した記録の件数だけで、この状態では 0 である

#### Scenario: 分類の無い表があると書き出しは始まらない

- **WHEN** 記録の schema に、書き出しに入れるか入れないかが決まっていない表がある状態で書き出しを求める
- **THEN** 書き出しは失敗として終わり、書き終えた書き出しのファイルはできず、失敗の理由に分類の無い表の名前が出る

#### Scenario: 分類の無い列があると書き出しは始まらない

- **WHEN** 書き出しに入れる表に、出すか出さないかが決まっていない列がある状態で書き出しを求める
- **THEN** 書き出しは失敗として終わり、書き終えた書き出しのファイルはできず、失敗の理由にその表と列の名前が出る

#### Scenario: いまの記録の schema の表と列はすべて分類されている

- **WHEN** すべての移行を当てた DB で、記録の schema の表と、書き出しに入れる表の列を一覧にして、書き出しの分類と突き合わせる
- **THEN** 分類の無い表も列も 0 個である

## ADDED Requirements

### Requirement: 書き出しは、更新の履歴と収集アプリの版の変化と生存信号の版を、説明つきで持つ

THE SYSTEM SHALL 全記録の書き出しに、更新の履歴の全行を 1 行 1 件で持つファイル `update_history.jsonl` を入れ、`seq`・`at`・`component`・`via`・`from_version`・`to_version`・`outcome`・`applied_versions`・`failed_version`・`sqlstate` の全列を出す。
THE SYSTEM SHALL 全記録の書き出しに、収集アプリの版の変化の読み口の全行を 1 行 1 件で持つファイル `collector_version_changes.jsonl` を入れる。
THE SYSTEM SHALL 生存信号のファイル `heartbeats.jsonl` に列 `client_version` を出す。
THE SYSTEM SHALL 説明書に、3 つの説明を書く: 更新の履歴は「S-01 が自分の版の変化を書いた。前の版が空なら記録の始まり。落ちた回の行は、退避から D-01 を戻すと消えることがある」、
収集アプリの版の変化は「生存信号から導いた。端末・部品ごとに発信の時刻の順に並べて、版が変わった所。収集アプリの申告で、S-01 は確かめていない」、生存信号の `client_version` は「信号を積んだ時に動いていた収集アプリの申告。空なら申告なし」。
THE SYSTEM SHALL 更新の履歴の表を、書き出しの分類（記録の schema のどの表も入れるか入れないかが決まっている）に載せる。

導出元: FR-121。扉 #33・#14。深掘り（ST51）Q2（推奨）・Q5（推奨）・premises の C5・C8（design D3（仮）・D11）。
D-01 を書き出しから作り直しても、途絶の理由を区別する材料が残るように、書き出しに入れる。

#### Scenario: 書き出しに更新の履歴の全行と全列が入る

- **GIVEN** 更新の履歴に、移行の結果 `applied` の行と `failed` の行がある D-01
- **WHEN** 全記録を書き出す
- **THEN** zip の `update_history.jsonl` は 2 行で、どちらの行も `seq`・`at`・`component`・`via`・`from_version`・`to_version`・`outcome`・`applied_versions`・`failed_version`・`sqlstate` を持ち、値は D-01 の行と同じ

#### Scenario: 書き出しに収集アプリの版の変化が入る

- **GIVEN** 端末 `d1` の位置の生存信号が版 `0.1.0+<commit A>` から `0.1.0+<commit B>` へ変わった D-01
- **WHEN** 全記録を書き出す
- **THEN** zip の `collector_version_changes.jsonl` は 1 行で、前の版 `0.1.0+<commit A>`・今の版 `0.1.0+<commit B>`・端末 `d1` を持つ

#### Scenario: 書き出しの生存信号のファイルに版の列が入る

- **GIVEN** `client_version` に `0.1.0+<commit A>` を持つ生存信号が 1 件ある D-01
- **WHEN** 全記録を書き出す
- **THEN** zip の `heartbeats.jsonl` のその行の `client_version` は `0.1.0+<commit A>`

#### Scenario: 説明書が更新の履歴と版の変化と生存信号の版を説明する

- **WHEN** 全記録を書き出す
- **THEN** 説明書に `update_history.jsonl` と `collector_version_changes.jsonl` の節があり、`heartbeats.jsonl` の節に `client_version` の説明がある
