# CH21 — 確認バッチの前に Claude が配る形を入れて普通に使ってみる

> 第 1 回の深掘りの答えを待たずに、推奨の答え（`deep.md` の `（答え待ち・推奨: …）`）で先に書いた（2026-10-20 の流れ）。
> 本人の答えが推奨と違えば `spec --answers` が写し直す。Q7・Q8（外に出るもの）は A で、本人は答えを省略できない。
> `docs/changes/CH21.md` の「価値」「壊してはいけないもの」「完了の判定」も、この段で書いた。

## Why

今の試験（`install-check.sh`・`web/e2e`・録画）は、どれも spec の Scenario を 1 つずつ確かめる。e2e の相手は開発用の起動（`stack.sh`）で、インストールした形ではない。
「配る形を入れて普通に使うとどう見えるか」を見る席がどこにも無く、2026-11-19 には本人が最初の利用者になって違和感（更新の確認がエラーを出し続ける）を見つけた。
確認バッチの手順書が人間に渡る前に、Claude がまっさらな Windows で配る形を入れて使い、気になったことを根拠つきで手順書の冒頭に載せる。

## What Changes

- **確認バッチの準備（`tools/verify-prep.sh`）が、最後に「使ってみる席」（`tools/trial-use/`）を呼ぶ**。席がどう終わっても準備は止めず、結果か警告を manifest の 1 段落に書く（依頼で決定済み・Q9）
- **席は、この確認バッチの木から Windows の配る形を 2 つ組む** —— サーバの zip と PC の収集アプリの zip（Q1・Q2 の推奨）。組むのは手元の Windows（design D2（仮））
- **まっさらな Windows Sandbox を網を開けて起こし、Claude が筋書きなしで使う**（Q3・Q10 の推奨）。Claude に渡すのは、利用者の目的の一覧・配る zip・合成の書き出しだけで、
  仕様・Scenario・コード・前の回の結果は渡さない（Q4・Q5 の推奨）。時計は動かさない。外から操る仕組みは design D3（仮）で、最初の Task で通らなければ倒す先も書いてある
- **時間の上限は 45 分**（Q9 の推奨）。越えたらそこまでの候補で閉じる。自分が起こした Sandbox は必ず閉じ、他人の Sandbox が動いていれば起こさない・閉じない
- **違和感の候補は、利用者に見えたものだけ・根拠つき・手順書に出すのは 10 件まで**（Q6 の推奨）。根拠の欠けた候補は機械が数から外す。
  「1 回だけ」「既知: #<番号>」「Sandbox だから」の印を付ける
- **見たもの（画面の写し・ログ）と候補の全件は手元の置き場（`C:\dev\ashiato2-trial-use\<tag>\`）に置く。手順書には件数・題 1 行ずつ・置き場の場所だけを載せる**（Q7 の推奨。A）。0 件のときの見分けのため、巡った目的の札（固定の語）と所要・終わり方（機械の値）も添える（design D12（仮））。題は 1 行 60 文字までで、私的な値の形は伏せる
- **issue は作らない。** 各候補に、そのまま /iwakan に貼れる「違和感メモ」を添える（Q8 の推奨。A）
- **配る形の出所が前の回と同じなら走らず、前の回の結果を写す**（Q11 の推奨）
- **ハーネス（harness2）には手を入れない**（Q12 の推奨）。手順書の形・録画・/iwakan・ラベル「違和感」の意味はいまのまま
- 振る舞いを変えないもの: `verify-prep.sh` のいまの成果物（サーバ・画面・APK・`run.sh`）と manifest の既存の段落、録画の Sandbox の順番、Story ごとの「違和感」の問い

## Capabilities

### New Capabilities

- `trial-use`: 確認バッチの準備が、配る形をまっさらな Windows に入れて筋書きなしで使ってみる席を走らせること。何を組み・何を渡し・どこで止め・何を手元に残し・
  手順書に何を載せ、何を外に出さないか。製品の振る舞いではなく、人間が最初の利用者にならないための開発の道具の約束。
  既存の `verify-environment`（検証の準備の DB の作り直し）とは別にする: あちらは検証のたびの DB の約束で、こちらは確認バッチの準備の 1 段の約束。読む人と変える理由が違う（design D1（仮））
- schema の「tooling は `skip_specs`」は採らない（CH06 と同じ理由）: 落ちても準備が止まらない・手順書に載るもの・外に出さないものは、外から見える振る舞いで、
  Scenario を `check_scenarios.py` が印に縛り、正典に残る

### Modified Capabilities

（無し）

## Impact

- 道具: 新しいフォルダ `tools/trial-use/`（席の入口・本体・材料・報告・自己検査）、`tools/verify-prep.sh`（席を呼ぶ 1 行）、`tools/workbox.json`（`host_only` に席の 2 つの台本。作業箱では Sandbox が無い）
- CI: `.github/workflows/ci.yml` の `chain` job に席の `--self-test` を 1 行（偽の Sandbox・偽の Claude・偽の gh で走る。Windows も Claude も要らない）
- 文書: `docs/testing.md`（確認バッチの準備の節に 1 段落）、`docs/adr/` に ADR を 1 つ（確認バッチの前に「使ってみる席」を置く —— Story をまたぐ道具の規則）、`docs/changes/CH21.md`
- 手元の機械: `C:\dev\ashiato2-trial-use\`（報告の置き場）と `C:\dev\ashiato2-trial-build\`（組む写しと target。道具のキャッシュ）が増える。確認バッチ 1 回あたり、Sandbox の窓が最大 45 分と Claude の利用枠を使う（配る形の出所が変わったときだけ）
- 製品のコード・移行・画面・収集アプリ: 変えない。依存: 足さない
- harness2: 変えない（Q12）。録画（`record-run`）は準備の後に走るので、席が自分の Sandbox を閉じていれば順番は変わらない
- **走っている Story・change との重なり**: この木の `openspec/changes/` に走っている change は無い（CH21 だけ）。`tools/verify-prep.sh` を触る change が並走していれば、
  席を呼ぶ行は既存の段の後に 1 行足すだけにし、後から merge する側が rebase で追従する（merge の順は決めない）。判定は `spec_overlap.py check` が持つ
