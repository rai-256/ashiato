> 第 2 版の `review/` は消えたので、出所は第 3 版の `review/deep.md` の R と、この版の `review/spec.md` の R だけを指す。

## Context

- 席の台本 `scripts/tsukau.py run`（harness2）は、差し込み口 `tools/tsukau/tsukau.json` を読み、`env_hook up` → `ready` を待つ（`ready_timeout_s`）→ `claude -p "/tsukau seat <実行のフォルダ>"`（cwd は `--repo`）
  → 時間・token の上限で止める → `LOG_<名前>` を写す → `env_hook down` → `result.json`・`RESULT.md`・`public.json` を書く。rc は 0（done/time/tokens）・2（引数・設定の誤り。実行のフォルダを作らない）・3（crashed/env_failed/interrupted）。
  標準出力は 2 行: 1 行目「使ってみた結果: <実行のフォルダの絶対パス>/RESULT.md」、最後の行 `{"v","stop","count","titles","run","cleanup"}`。SIGTERM を受けると `interrupted` にして、片付けと記録を済ませてから終わる。
  候補は実行のフォルダの `candidates.jsonl`（題・種類・根拠・添付）にある（`.harness2/scripts/tsukau.py` の冒頭）
- 確認バッチ（harness2 `scripts/verify_batch.sh`）は、`<repo>-verify` の作業ツリーで `origin/main` から `verify/<tag>` を作り、PR ごとに「verify: #<PR> <head> を確認バッチ <tag> に入れる」merge を重ね、
  `tools/verify-prep.sh <tag>` を呼ぶ（落ちたら manifest なしで続ける）。その後に録画、手順書（`verify_checklist.py` が manifest を段落ごとに 1 つの note にする）、`docs/verify` の commit と push、PR 本文（manifest をそのまま載せる）
- 確認バッチの直しは 2 つある（premises.md）: 人間が手順書で「通らなかった」と答えた後の `fix`（固定した候補にだけ働く）と、統合の CI が赤のときの `ci_fix`（直しを原因の Story のブランチへ載せ、バッチを作り直す。`verify/<tag>` は使い捨て）。
  人間が答える前に AI の結果から直しへ入る道も、プロジェクトが手順書に答えられる問いを足す口も、harness2 の確認バッチの中にしか無い
- `tools/verify-prep.sh` は `set -euo pipefail`。main の checkout の `.env`（本物の合言葉）を作業ツリーへ写す。確認バッチの DB には確認の間に本人の携帯が送った記録が入りうる
- 録画の専用環境（`tools/record-env.sh`）は、専用の compose project・空いている port・乱数の合言葉で `tools/stack.sh up` を立て、PC の収集アプリは網を切った Sandbox に入れる。録画（harness2 `record-run`）は始める前に別の Sandbox が動いていれば撮らずに止まり、終わりに動いている Sandbox を全部止める
- `wsb` の CLI（premises.md、確かさ 5）: `wsb start -c` で窓を開かずに起こせる・`wsb exec` は終了コードだけを返す（出力は共有のフォルダで受ける）・利用者のセッション（`ExistingLogin`）で走らせる・画面の写しを撮るには `wsb connect`（窓を開く）が要る
- ashiato2 の repo は公開。手順書の問いと答え（`docs/verify/`）は main に入る。`dist/` は git が無視する。harness2 の repo は非公開
- エミュレータは `tools/emulator-start.sh`（`emu_check_kvm`・`emu_start`・`emu_wait_boot`・`emu_stop_own`）で起こし、自分の起こした PID だけを止められる。計測テスト（`tools/android-emulator.sh`）は AVD `ashiato-api35` を使い、同じ AVD が動いていれば断る。
  確認バッチの準備は、作った `app-debug.apk`（本人のサーバ向け。`~/.gradle/gradle.properties` の接続先）を、そのとき繋がっているエミュレータ全部に入れる（`tools/verify-prep-device.sh`。実機には入れない）
- 録画の専用環境は、録画用のサーバ向けの debug の APK（接続先は端末の中の `127.0.0.1:18787`、`adb reverse` で API の port へ渡す。合言葉は木の `collector-android/local.properties`）を組む（`tools/record-env.sh` の 166〜201 行）。
  debug の組み立ての更新の宛先は、`-PupdateCheckUrl` を渡さなければ空で、配布元に問い合わせない（`collector-android/app/build.gradle.kts` の 252 行）

## Goals / Non-Goals

**Goals**: 確認バッチを作るたびに、その回に新しく入った画面・PC・携帯の機能だけを AI が軽く使い（画面と PC は配る形、携帯はエミュレータに debug の APK）、見つけた違和感の候補を確認バッチの処置（選別 → 直す／本人に聞く／依頼にする）へ渡す。
ashiato2 は席を呼ぶまでと、処置が読む手元の目録・公開に出す題の伏せ方を持つ。処置そのものは harness2 の確認バッチへの依頼（D15）にし、それが入った後に本物の道で処置まで通して終える。

**Non-Goals**: 席の中身（触り方・候補の書き方。harness2）・手で呼んだ席の処置（Q5）・確認バッチに後から足す main の Story（`--story`）を範囲に入れること・本物の携帯（実機）と携帯の配る APK を使うこと（D30（仮））・携帯から外とつないで初めて出る不具合を見ること（D31）。
処置の台本（選別の席・直しの道・手順書の問い・違和感の issue）は ashiato2 に書かない（harness2 の依頼。D14）。

## Decisions

### D1（仮）. 差し込み口は `tools/tsukau/` に置き、置き場を明示する

- `tools/tsukau/tsukau.json`: `{"env_hook": "tools/tsukau/env-hook.sh", "targets": ["web", "pc", "android"], "out_root": "~/.local/state/ashiato2/tsukau", "ready_timeout_s": 900}`（`android` は仕様への違和感で足した）
- `out_root` を明示するのは、既定（`~/.local/state/harness2/tsukau/<repo の名前>`）だと作業ツリーの名前（`ashiato2`・`ashiato2-verify`・使い捨ての名前）で置き場が分かれ、手で呼んだ席と確認バッチの席が別の所に散るから
- 確認バッチの席は `--label verify-<tag>` で走らせ、実行のフォルダの `request.json` から回を引ける
- 反転条件: 本人が回の名前でない手がかり（日付・Story の ID）で手元の結果を探したいと言ったとき

### D2. 範囲と相手は、確認バッチの木の merge から機械で決める（深掘り Q6）

- 入力: 確認バッチの作業ツリーの `git log --merges --first-parent origin/main..HEAD` のうち、件名が「verify: #<PR> <head> を確認バッチ <tag> に入れる」のもの。ID は `<head>` の `feat/(st|ch)<NN>-` から（harness2 `scripts/sid.py` と同じ読み方）
- その merge が入れたファイル = `git diff --name-only <merge>^1 <merge>`。振り分けの表と試験の置き場の除き方は spec のとおり
- `tools/release/` を PC に入れるのは、配る zip の中身が変わり、PC の相手が入れる物そのものが変わるから。サーバの変更は PC の相手に入れる（配る zip のサーバは画面を中に持つ）
- `collector-android/` の下（`app/src/test/`・`app/src/androidTest/` を除く）を変えたものは携帯の相手に入れる（仕様への違和感で足した）。サーバだけの変更は携帯の相手に入れない（携帯の相手もその回のサーバに送るが、サーバの変更は PC の相手が見る。相手を増やすと準備が延びる）
- 範囲の文の「何のためか」は、価値の節の段落のうち引用（`>`）と注記（`（`）を飛ばした最初の段落（change の価値の節は雛形のままのことも、深掘りの注記で始まることもある）
- **同じ木からは同じ範囲**（AI に要約させない）。同じ範囲でないと、D10 で前の回に試したものと突き合わせられない
- 依頼の「その回に入った Story / change」を狭める: 確認バッチに後から足した、すでに main の Story は木の差に出ないので範囲に入らない（Q6 の context）

### D3（仮）. PC の相手は Sandbox を 1 つだけ起こし、自分の id だけを、中のログを写してから止める（review/deep.md R4）

- 起こす前に `wsb list` で動いている Sandbox があれば `UNAVAILABLE=別の Sandbox が動いている` を置く（待たない）。録画・本人・手で呼んだ席と取り合わない
- 起こした id を `<state>/sandbox-id` に残し、片付けはその id だけを `wsb stop --id` で止める（録画の「全部止める」を写さない）
- 片付けは止める前に、Sandbox の中のサービス・更新係・PC の収集アプリのログとイベントの抜き書きを共有のフォルダへ写させ、`$TSUKAU_EVIDENCE/pc-logs/` へ写す（Sandbox は閉じると中身ごと消え、選別の席が読む根拠が無くなる）
- 同じ確認バッチでは、席（verify-prep の中）が録画より先に終わる並び。閉じ損ねたら段落に「片付けに残りがある」が出て、同じバッチの PC の録画は撮れない（録画が自分で止まる）
- 反転条件: 別の Sandbox が動いていて PC の席が回らない回が続くとき（待つ形にする）・写したログが足りず、選別の席が根拠を辿れなかったとき（写すものを足す）

### D4. 席は窓を開いた Sandbox を `tools/tsukau/pc.sh` で触る（深掘り Q9）

- 順: `start` → サーバのインストール（`-r System`。合言葉はその場で `openssl rand` で作り、`--repo` と確認バッチの作業ツリーの `.env` は読まない。review/spec.md R10）→ サーバが応える → `wsb connect --id <id>`（窓を本人のデスクトップに開く）→ PC の収集アプリを `-r ExistingLogin` で起こす → `ready`
- 窓を開く前は `ExistingLogin` で走らず、`System` では利用者のデスクトップが無い（premises.md）。PC の収集アプリは前景の窓と入力を集めるので、利用者のセッションで起こさないと「入れて普通に使う」形にならない
- `tools/tsukau/pc.sh exec <PowerShell の文>`: `wsb exec --id <id> -r ExistingLogin` で走らせ、出力を共有のフォルダのファイルで受けて標準出力に出す。`tools/tsukau/pc.sh shot <置き場>`: 画面の写しを撮り `$TSUKAU_EVIDENCE` へ写す
- 画面の操作（押す・打つ）は専用の口を作らず、`exec` から PowerShell の UI Automation（`System.Windows.Automation`）と `SendKeys` で行う。案内にその書き方の例（窓を探す・ボタンを押す・文字を打つ）を載せる（review/spec.md R12）。反転条件: 席が UI Automation で操作できない画面が続くとき（`pc.sh click` などの口を足す）

### D5（仮）. PC の配る zip は、席を呼ぶ前に確認バッチの木から手元で組み、立てる時間に数えない（深掘り Q7・review/deep.md R11）

- `tools/tsukau/build-pc.sh <置き場>`: 木を `C:\dev\ashiato2-tsukau-build\src` へ写し（録画の写し先とは分ける）、Windows 側の Git Bash で `tools/release/package.sh windows` を走らせ、配る形のサーバの zip と PC の収集アプリの zip を置き場へ写す
- 組み立てを env_hook の `up` に入れない: 入れると `ready_timeout_s`（15 分）に数えられ、`target` が冷えた回は毎回「立てられなかった」になる。上限は 2,400 秒（まだ測っていない。Task 1 で測る）
- 反転条件: 測った組み立ての時間が、温まった `target` で 15 分を超えるか、組めないと分かったとき（CI の組み立てを待つ形を本人に聞く。Q7 の 2 つ目の案）

### D6. Sandbox は外にはつなぎ、私設網と手元の網を塞いで確かめてから入れる（深掘り Q8 の本人の答え）

- `.wsb` に `<Networking>Disable</Networking>` を書かない。起こした直後、何かを入れる前に、Sandbox の中のファイアウォールで外向きの既定を「塞ぐ」にし、
  「外の宛先（私設網の範囲（tailscale の CGNAT の範囲と IPv6 の範囲）・私用の範囲・リンクローカル・マルチキャストを除いた範囲）」と「既定のゲートウェイの 53 番（名前の問い合わせ）」だけを通す規則を足す。
  Windows のファイアウォールは塞ぐ規則が通す規則に勝つので、塞ぐ範囲を塞ぐ規則で書かず、既定を塞ぐにして通す範囲を書く。loopback はファイアウォールを通らないので、中のサーバと PC の収集アプリは通じる
- Sandbox の名前の問い合わせ先は既定のゲートウェイ（私用の範囲にある、この PC の NAT）なので、そこへの 53 番だけを通す。私設網の名前は引けても、その宛先には届かない
- 通す外の範囲は `env-hook.sh` が bash で数から組み（`--print-net-rules`）、PowerShell の台本に渡す。自己試験が見本の宛先を当てて、私設網・私用・リンクローカル・マルチキャスト・IPv6 の私用と私設網を含まないことを固定する（review/spec.md R23）
- **塞げたことを確かめてから渡す**（Q8 の選んだ案の「得」）: 対照つきで確かめる（D26（仮））。外は `api.github.com` を引いて HTTPS で届くかを見る
- **塞げなければ網を切る側に倒す**（Q8 の選んだ案の「確かめていないこと」）: 私設網か手元の網に届いたら、外を通す規則も外して外向きを全部塞ぎ、確かめ直す。それでも届けば、何も入れずに `UNAVAILABLE=`（回ごとに倒す。設計を戻すかは反転条件）。外にだけ届かなかった回は続け、案内に書く
- 守りの範囲: 確かめで当てるのはこの PC の宛先だけ。ほかの私設網の機器（本人の携帯など）への守りは、範囲の組み立て（自己試験で固定）と規則まで
- 字面: 私設網や手元の網の IPv4 の範囲を、台本・試験・文書に字面で書かない（`tools/check-private.sh` が commit で止める）。範囲は数から組むか名前で書く
- 外へ出るもの（Q8 の選んだ案の代償。本人が受け入れた）: PC を変えた回の確認バッチのたびに、更新係と PC の収集アプリの問い合わせ（この PC の網の IP と時刻）と、席が範囲の中で開いた外のサイトへの接続が残る。正典 distribution の「自動の試験が本物の配布元へ繋ぐのは名指しのものだけ」（CH22 が 2 つに書き直した Requirement）に 3 つ目として使ってみる席の PC の相手を MODIFIED で足す。requires に CH22 がある。CH22 は 2026-11-21 に archive され、その Requirement は正典に入った（CH21 の MODIFIED は正典の全文に (3) を足した形。2026-11-22 に突き合わせた）
- 守りの限界: Sandbox の中の管理者（インストーラ・席が走らせるコマンド）は規則を外せる。守りは「確かめてから渡す」と、案内の「ファイアウォールの規則に触らない」まで
- 反転条件: 本物の Sandbox（Task 8）で、塞いだ後に名前が引けない・外の HTTPS が通らない・インストールが通らない・私設網か手元の網に届くと分かったとき（A として人間に返す）。全部塞ぐ回が続くとき（塞ぎ方を直す）

### D7（仮）. 画面の相手は録画の専用環境と同じ立て方にし、本物の合言葉と確認バッチの DB を席に渡さない（review/deep.md R2）

- 実行ごとの compose project `ashiato-tsukau-<実行の時刻>`・空いている port・`openssl rand` の合言葉・`SEED=normal` の偽データで、`<state>/tree`（`--repo` の HEAD を detached で取り出した木。片付けで消す）の `tools/stack.sh up` を前景で立てる
- その木に乱数の合言葉と `COMPOSE_PROJECT_NAME` を持つ `.env` と port の上書きを置く（`tools/record-env.sh` の `up` と同じ形）。`--repo` には何も書かない
- サーバと画面は、確認バッチでは `verify-prep` が組んだものを絶対パスで受け、無ければ組まずに断る（組むと 15 分の上限を越えうる）。手で呼んだときは `<state>/tree` で組む
- 案内: 画面の URL・その回の画面の合言葉（案内は実行のフォルダにだけ写る）・本物のブラウザで開いて写しを撮るコマンド・サーバのログの場所・触らないもの
- `tools/record-env.sh` は `source` しない（録画の変数の契約に縛られる）。立て方を写す
- 反転条件: 画面の相手を立てる時間が 15 分の上限に近づく・偽データでは範囲の機能を触れない回が続くとき

### D8. 毎回の大きさは 10 分・20 万 token、立てる上限 15 分（深掘り Q10）

- `--minutes 10 --tokens 200000`。値は `verify-batch.sh` の頭の定数に置く。手で呼ぶときは呼ぶ側が決める
- 1 回の呼び出しは `timeout -k 360 1860`: 立てる上限 900 + 席 600 + 台本の片付け（`down_timeout_s` 300）+ 60 秒で SIGTERM、さらに 360 秒待って 2,220 秒で止める（片付けを数えないと、正しく終わる途中の回を打ち切って結果を捨てる。review/spec.md R9。SIGKILL を先に送ると env_hook が別のプロセスグループに残り、Sandbox と project が残る）。打ち切った後でも最後の行が読めて `done`・`time`・`tokens` なら、その結果を写す
- 確認バッチの準備は呼び出し全体を 9,360 秒（組み立て 2,400 + 3 つの相手の 2,220 ずつ + 300）で打ち切る。定数は `verify-batch.sh --print-limits` で出す（携帯の相手を足して 7,140 から延びた。携帯の相手は APK の組み立てとエミュレータの起動を立てる時間の 900 秒に含める。D30（仮））
- 直した後の確かめ直し（D27）は半分: 5 分・10 万 token
- 反転条件: 確認バッチの準備が 1 回 1 時間を超えることが続く・席が範囲を一通り触れずに `time` で終わることが続く（3 つの相手が全部回る回は、立てる時間を含めて 1 時間を超えうる）

### D9（仮）. 席は使い捨ての作業ツリーで走らせる（review/deep.md R2）

- `git worktree add --detach "$(mktemp -d …)" HEAD` → `python3 .harness2/scripts/init.py --worktree <その作業ツリー>`（`.claude/skills/tsukau` を繋ぐ。繋がないと席が起きない）→ `.env` は写さない
- `python3 <その作業ツリー>/scripts/tsukau.py run --repo <その作業ツリー> …` で呼ぶ（席の `claude -p` の cwd がその作業ツリーになる）

### D33（仮）. 外した後も `adb` か `emulator` が名前で見つかれば、どの相手の席も呼ばない（IMP-13 の答えの細部）

- `$ANDROID_HOME` の外（`apt` で入れた `/usr/bin/adb` など）に `adb` があると、置き場を外しても名前で見つかる。その置き場ごと外すと、ほかの命令（`git`・`docker` など）も消えて席が動かない。
  そこで、外した後も見つかれば、その回はどの相手の席も呼ばず、段落は既存の決まった文言「席を呼べなかった」、目録は `state: not_run` にする（理由「席の PATH から adb を外せない」は `dist/verify-<tag>/tsukau.log` にだけ書く。D11 の文言を足さない）。準備は止めない（rc=0）
- 失わない側: 本人の実機に届く席を起こさない。今の PC では `adb` は `$ANDROID_HOME/platform-tools` の 1 つだけ（premises.md）
- 費用: `$ANDROID_HOME` の外に `adb` を入れると、確認バッチで席が回らない
- 反転条件: 本人が `$ANDROID_HOME` の外に `adb` を入れて、席が回らない回が続くとき（その置き場から `adb` だけを隠す形を本人に聞く）

## Risks / Trade-offs

- **CH21 は harness2 の処置が入るまで終わらない**（Q13 の推奨）。CH21 の実装（下流のブランチ）は、最後の Task（処置まで本物で通す）が harness2 の処置が入るまで通らないので、それまで main に入らない。**その間、確認バッチで席は回らない**（review/spec.md R7。Q1・Q13 の代償の文もこれに直した）。早く席を回したいなら、Q13 の「席を呼んで結果を載せる実地 1 回まで」を選び、処置まで通す確かめを別の change に分ける
- **CH22 の上に積む**（Q8 の答え）: 正典 distribution の「名指しの接続」は CH22 が書き直した Requirement で、CH21 はそれを MODIFIED で足すので requires に CH22 がある。CH22 は 2026-11-21 に archive 済みで、CH21 の MODIFIED は今の正典の全文に (3) を足したもの。正典がまた変われば、archive の 3-way で突き合わせる
- **席は名前でなければ `adb` に届きうる**（IMP-13 の残り。D32）: 席の `PATH` から外しても、`$ANDROID_HOME` からの絶対パスや `adb` の待ち受け（ホストの 5037 番）に直に話しかければ、本人の実機に届く。手で呼ぶ `/tsukau` は、harness2 の鍵が入るまで `adb` が見える（D34（仮））
- **外に残るもの**（Q8 の選んだ案の代償）: PC を変えた回の確認バッチのたびに、この PC の網の IP と時刻が GitHub と、席が範囲の中で開いたサイトに残る。更新係の問い合わせは認証が無く、IP ごとに 1 時間 60 回の上限を、本人の PC と本人のサーバの更新係と分け合う（1 回の席で数回）
- **私設網と手元の網の塞ぎは Sandbox の中の規則**（D6）: 中の管理者は外せる。守りは「確かめてから渡す」と案内の規範まで
- **作り直しで前に試した機能は試し直さない**（Q11 の答えの代償）: 前に試した機能と新しく入った機能を一緒に使ったときの引っかかりは見ない。PR のコミットが進んだものは試し直す（D21）
- **本人の画面に窓が出る**（D4）: PC を変えた回ごとに、Sandbox の窓が本人のデスクトップに出る（1 日 1〜5 回まで）。本人の PC で収集アプリが動いていれば、その間の前景の記録に Sandbox の窓が入りうる。携帯のエミュレータは窓を出さない（D22（仮））
- **準備が延び、錠を握る**（D8）: その間、記録と fix の撮り直しが待たされる（最大 9,360 秒）。3 つの相手が全部回る回は 1 時間を超えうる
- **携帯の相手は debug の APK と網を切ったエミュレータ**（D30（仮）・D31）: 配る APK でだけ起きる違和感と、外とつないで初めて出る違和感は見えない。KVM が使えない日（Windows の更新で `/dev/kvm` が消えたことがある）は携帯の相手が回らず、段落は「相手を立てられなかった」になる

- **席の作業ツリーは HEAD を取り出す**: 確認バッチの木の `docs/verify` の commit より前に走るので、手順書を持たない木を見る
