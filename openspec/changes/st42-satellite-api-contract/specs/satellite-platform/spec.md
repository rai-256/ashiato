## ADDED Requirements

### Requirement: 衛星向けの API の契約を、内部の口の契約と分けて生成し、Apache-2.0 で公開する

THE SYSTEM SHALL 衛星が使う口の契約（衛星向けの契約）を、本体の収集アプリと画面だけが使う口の契約（`docs/openapi.json`）とは別の生成で作り、版ごとに `docs/satellite-api/v<大きい版>/openapi.json` に置く。
THE SYSTEM SHALL 衛星向けの契約に、衛星だけが使う口（この Story では自分が誰かを確かめる口）を載せ、内部の口の契約には載せない。
THE SYSTEM SHALL 衛星向けの契約の許諾の欄（`info.license.identifier`）を `Apache-2.0` にし、内部の口の契約の許諾の欄は今の式のまま変えない。
THE SYSTEM SHALL 衛星向けの契約に、資格情報の渡し方（`Authorization` の見出しに `Bearer ashsat_<識別子>_<乱数>` を付ける）を securitySchemes として持たせ、契約のすべての口にそれを付ける。
THE SYSTEM SHALL 衛星向けの契約のすべての口に、401（資格情報が無いか認められない）と 403（衛星の資格情報でない）の応答と、断りの本文の型（種別の欄 `error` を持つ JSON）を載せる。
THE SYSTEM SHALL 衛星向けの契約から、リポジトリの中でブラウザが整形して見せる Markdown のページ（`docs/satellite-api/README.md` と版ごとの `docs/satellite-api/v<大きい版>/README.md`）を機械で作る。
ページは、口・型・資格情報の渡し方・断りの種別・版の一覧・許諾（Apache-2.0）を示し、ページの中の相対リンクの先はどれもリポジトリにある。
THE SYSTEM SHALL `docs/satellite-api/LICENSE` に Apache License 2.0 の全文を置き、`README.md` と `CONTRIBUTING.md` のライセンスの節に、本体は AGPL-3.0 で、衛星向けの契約（`docs/satellite-api/`）は Apache-2.0 であることを分けて書く。
THE SYSTEM SHALL コミットされた衛星向けの契約とページが、コードから作り直したものと違えば CI を落とす。

導出元: FR-103 / 扉 #31。深掘りの AI の既定（Q1 の context。review/deep.md「聞かない既定」1〜3）。premises P1〜P5。
衛星の作り手は契約からクライアントを生成して衛星を作る。生成したクライアントに AGPL が及ばないことをはっきりさせるため、衛星向けの契約だけを Apache-2.0 にする（扉 #31。本体と内部の口の契約は AGPL のまま）。
内部の口は本体の都合で変えてよいが、衛星向けの契約は版を付けて守る（FR-89）。2 つを分けないと、内部の口の変更がすべて衛星への壊す変更に数えられる。
ページを Markdown にするのは、GitHub Pages を有効にしておらず（premises P2）、GitHub がリポジトリの中の Markdown をブラウザで整形して見せるため（premises P3）。
LICENSE は版をまたいで 1 枚にする（版ごとに写すと、同じ全文が版の数だけ並ぶ。design D2）。
記録の封筒の形（FR-103）は、衛星が書く口を作る ST39 が同じ版に追加として載せる（`docs/handoff/ST39.md`）。

#### Scenario: 衛星向けの契約は内部の口の契約と別に作られ、互いの口を持たない

- **WHEN** 2 つの契約をコードから作り直す
- **THEN** 衛星向けの契約は自分が誰かを確かめる口 `GET /satellite/v1/me` を持ち、内部の口の契約は衛星向けの道（`/satellite` そのものか `/satellite/` で始まる道）を 1 つも持たず、衛星向けの契約は内部の口（`/events` など）を 1 つも持たない

#### Scenario: 衛星向けの契約は Apache-2.0 を宣言し、内部の口の契約は今の式のまま

- **THEN** 衛星向けの契約の `info.license.identifier` は `Apache-2.0`、内部の口の契約の `info.license.identifier` は `AGPL-3.0-only WITH AdditionRef-ashiato-play-services` である

#### Scenario: 衛星向けの契約は資格情報の渡し方を持ち、すべての口に付ける

- **WHEN** 衛星向けの契約を作り直して読む
- **THEN** securitySchemes に HTTP の bearer の方式が 1 つあり、その説明に `ashsat_` の形が書かれ、契約のすべての口がその方式を求め、すべての口が 401 と 403 の応答と種別の欄 `error` を持つ断りの型を載せている

#### Scenario: コミットされた衛星向けの契約がコードとずれると検査が落ちる

#### Scenario: コミットされた衛星向けの契約のページがコードとずれると検査が落ちる

- **GIVEN** `docs/satellite-api/v1/README.md` の 1 行を消した使い捨ての木
- **WHEN** 衛星向けの契約の検査を当てる
- **THEN** 検査は 0 でない終了コードで終わり、`docs/satellite-api/v1/README.md` の名前が示される

#### Scenario: 衛星向けの契約のページは、口・資格情報の渡し方・断りの種別・版・許諾を示す

- **WHEN** 衛星向けの契約の検査を今の木に当てる
- **THEN** 終了コードは 0 で、`docs/satellite-api/v1/README.md` は `GET /satellite/v1/me`・`Authorization: Bearer ashsat_`・断りの種別 `unauthorized` `not_satellite` `unsupported_version` `not_found` `method_not_allowed` `internal`・版 `1.0`・`Apache-2.0` を含み、`docs/satellite-api/README.md` は版の一覧と各版のページへのリンクを含み、2 枚の相対リンクの先はどれも木にある

#### Scenario: 契約の置き場の LICENSE は Apache-2.0 の全文で、README と CONTRIBUTING は 2 つのライセンスを分けて書く

- **WHEN** 衛星向けの契約の検査を今の木に当てる
- **THEN** 終了コードは 0 で、`docs/satellite-api/LICENSE` は `tools/licenses/texts/Apache-2.0.txt` と同じ中身で、`README.md` と `CONTRIBUTING.md` のライセンスの節はどちらも `AGPL-3.0` と `Apache-2.0` と `docs/satellite-api/` を含む

#### Scenario: LICENSE が違うか、README か CONTRIBUTING の節が契約のライセンスを書いていないと検査が落ちる

- **GIVEN** `docs/satellite-api/LICENSE` の 1 行を書き換えた使い捨ての木と、`CONTRIBUTING.md` のライセンスの節から `Apache-2.0` を消した使い捨ての木
- **WHEN** 衛星向けの契約の検査をそれぞれに当てる
- **THEN** どちらも 0 でない終了コードで終わり、そのファイルの名前が示される

### Requirement: 衛星向けの口は道に大きい版を持ち、版の一覧を 1 か所に持つ

THE SYSTEM SHALL 衛星向けの口の道を `/satellite/v<大きい版>/` で始める。
THE SYSTEM SHALL 衛星向けの API の版を `<大きい版>.<小さい版>`（どちらも 0 以上の整数。例 `1.0`）で表し、製品の版（出所の版・組み立てに渡した版番号）から引かない。
THE SYSTEM SHALL サーバが受ける衛星向けの API の版の一覧を `docs/satellite-api/versions.json` の 1 つに持ち、サーバの口・版ごとの契約の `info.version`・ページは、ここから読む。
THE SYSTEM SHALL 版の一覧にある大きい版ごとに、`docs/satellite-api/v<大きい版>/openapi.json` があり、その `info.version` が一覧の版と同じで、その版の口がサーバの経路にあることを検査で確かめ、食い違えば CI を落とす。

導出元: FR-89 / FR-103。深掘り Q1（推奨: 道に版を入れる）・Q7（推奨: 小さい番号を上げる）。review/deep.md「聞かない既定」の版の数え方。
道に版を入れると、読み出しの記録に口の道が残るので、衛星がどの版で呼んだかも残る。版ごとの口をサーバの中で別々に並べられる。
衛星向けの API の版は、収集アプリの送信契約の版（`GET /contract`。record-envelope）とも、内部の口の契約の版（出所の版。distribution）とも別のもの。
版の一覧は版と外す日と知らせの画面の名前だけを持ち、出した印と外してよい日は持たない（検査が印から計算する。design D8）。

#### Scenario: 衛星向けの契約の版は、版の一覧の版で、渡した版番号に依らない

- **WHEN** 版番号 `0.4.0-beta.2` を渡して衛星向けの契約を作り直す
- **THEN** 契約の `info.version` は `docs/satellite-api/versions.json` の大きい版 1 の版（`1.0`）で、版番号を渡さずに作り直したものと差が無い

#### Scenario: 版の一覧と契約の版が食い違うと検査が落ちる

- **GIVEN** `docs/satellite-api/versions.json` の大きい版 1 の版を `1.1` に書き換え、契約は作り直していない使い捨ての木
- **WHEN** 衛星向けの契約の検査を当てる
- **THEN** 検査は 0 でない終了コードで終わり、版の一覧と契約の版が違うことが示される

#### Scenario: 版の一覧にある版の口は、サーバの経路にある

- **WHEN** 版の一覧にある大きい版ごとに、その版の衛星向けの契約のすべての口とメソッドを、有効な衛星の資格情報を付けてサーバに 1 回ずつ呼ぶ
- **THEN** どの求めも 404 でも 405 でもなく、契約に載った状態の番号のどれかで応える

#### Scenario: サーバの経路は、2 つの契約の口と生存確認と版の受け口を合わせたものにちょうど一致する

- **WHEN** サーバの経路の一覧を、内部の口の契約の口・衛星向けの契約の口・生存確認・版の受け口と突き合わせる
- **THEN** 経路の一覧にだけある道も、どれかの契約にだけある道も無い

### Requirement: 衛星は自分が誰かと、サーバが受ける版を確かめられる

WHEN 有効な衛星の資格情報を付けた求めが `GET /satellite/v1/me` に届く THE SYSTEM SHALL 200 で、本文 `{"satellite": {"id": <衛星の識別子>, "name": <衛星の名前>}, "api_versions": <版の一覧>}` を返す。
版の一覧は、サーバが受ける衛星向けの API の版ごとに `{"version": <版。1.0 の形>, "sunset": <外す日。YYYY-MM-DD か null>}` を持つ配列にする。
THE SYSTEM SHALL この口の応答の本文に、上の欄のほかの欄を持たせない（記録・件数・承認・資格情報の値・本体の中の番号・時刻を返さない）。
WHEN 資格情報が無いか認められない求め（取り消した・外した衛星の資格情報を含む）が衛星向けの道に届く THE SYSTEM SHALL 401 で、本文 `{"error": "unauthorized"}` を返す。
WHEN API の合言葉か画面のログインの求めが衛星向けの道に届く THE SYSTEM SHALL 403 で、本文 `{"error": "not_satellite"}` を返し、ハンドラの処理を行わない。

導出元: FR-89 / FR-103。深掘り Q4（推奨: 受ける版の一覧を返す）。ST29 の深掘り Q7（本人:「ST42 が置く」）と正典「衛星の資格情報では、まだどの口も通らない」の導出元の注記。
衛星の作り手は、資格情報を設定できたかと、相手のサーバがどの版を受けるかを、この口を 1 回呼んで確かめる。並べている間も、衛星はどの版へ移れるかを知れる。
承認（ST38）の前に通る口なので、衛星自身のことと版のほかは返さない（扉 #15）。
欄の名前・401 / 403 の形は版 1 として凍る（深掘り Q3 の推奨: main に入った日から）。

#### Scenario: 確かめる口は、衛星の識別子・名前と受ける版の一覧を返す

- **WHEN** 衛星「読書ログ」（識別子 `dev.example.booklog`）の有効な資格情報を付けて `GET /satellite/v1/me` を呼ぶ
- **THEN** 200 で、本文は `{"satellite": {"id": "dev.example.booklog", "name": "読書ログ"}, "api_versions": [{"version": "1.0", "sunset": null}]}` と同じで、ほかの欄を持たない

#### Scenario: 取り消した資格情報か外した衛星の資格情報で確かめる口を呼ぶと 401 になる

- **WHEN** 取り消した衛星の資格情報と、外した衛星の資格情報を付けて、それぞれ `GET /satellite/v1/me` を呼ぶ
- **THEN** どちらも 401 で、本文は `{"error": "unauthorized"}` で、衛星の識別子も名前も含まない

#### Scenario: 資格情報の無い求めは、衛星向けの口で種別つきの 401 になる

- **WHEN** 資格情報を付けずに `GET /satellite/v1/me` を呼ぶ
- **THEN** 401 で、本文は `{"error": "unauthorized"}` である

#### Scenario: 衛星の管理の口は衛星向けの道に数えない

- **WHEN** 正しい合言葉でログインした印を付けて衛星の一覧（`GET /satellites`）を求め、続けて有効な衛星の資格情報を付けて同じ口を求める
- **THEN** ログインの印の求めは 200 で衛星の一覧を返し、衛星の資格情報の求めは 403 で、本文は内部の口と同じ 1 つの文字列（`forbidden`）である

#### Scenario: API の合言葉と画面のログインでは、衛星向けの口は通らない

- **WHEN** API の合言葉を付けた求めと、正しい合言葉でログインした印を付けた求めで、それぞれ `GET /satellite/v1/me` を呼ぶ
- **THEN** どちらも 403 で、本文は `{"error": "not_satellite"}` で、衛星の情報を含まない

### Requirement: 同じ版の中で衛星を壊す変更を入れると CI が落ちる

THE SYSTEM SHALL 衛星向けの契約の検査で、作り直した版ごとの契約を、比べる相手（PR の行き先の commit にある同じ大きい版の契約の写し）と比べる。
THE SYSTEM SHALL 次のどれかに当たる差（壊す変更）が同じ大きい版の中にあれば、CI を落とし、当たった規則と場所を示す:
口（道とメソッドの組）を消す・口の応答の状態の番号を消す・応答の型から欄を消すか欄を必須でなくする・欄や引数の型か形式を変える・
送る側（求めの本文・引数）に必須の欄や引数を足すか任意のものを必須にする・送る側の選べる値を減らす・資格情報の方式か口の求める資格情報を変えるか外す・許諾の欄を変える。
THE SYSTEM SHALL 口・応答の欄・任意の送る欄・応答の状態の番号を足した差（足す変更）があるのに、小さい版が比べる相手より上がっていなければ、CI を落とす。
THE SYSTEM SHALL 衛星向けの契約に載らない内部の口の変更では、この検査を落とさない。
THE SYSTEM SHALL 比べる相手の commit を読めないときは、検査を通さずに落とす。比べる相手にその大きい版の写しが無いとき（その版を初めて足す PR）は、比べずに通す。
THE SYSTEM SHALL 衛星向けの契約の写し・ページ・版の一覧（`docs/satellite-api/` の下）と、`README.md`・`CONTRIBUTING.md` だけを変えた PR でも、この検査を走らせる。製品の番号を付けるかの判定（「製品に触れたか」）は変えない。

導出元: FR-89。深掘り Q2（推奨: 自前の台本で決めた規則を見る）・Q3（推奨: 版ごとの写し（main にあるもの）と比べる）・Q7（推奨: 小さい番号を上げる）。premises P7。
比べる相手を PR の行き先にある写しにするので、PR の中で写しを書き換えても、書き換えだけでは通らない。main に入った日から、その版の形が守られる。
応答の欄を足す・口を足すのは、既存の衛星を壊さない側に数える。断りの種別の欄 `error` は文字列で、知らない値は状態の番号で扱う（契約のページに書く）ので、種別を足すのも壊さない側。
規則に無い壊し方（参照の付け替えなど）は見逃しうる。見つけたら規則を足す（design D9 の反転条件）。
検査を走らせる判定を製品の番号の判定と分けるのは、ST61 が「製品に触れたか」で番号を付けるため（review/spec.md R18）。

- **WHEN** 衛星向けの契約の検査を当てる

#### Scenario: 同じ版の中で応答の欄を消すと検査が落ちる

- **WHEN** 衛星向けの契約の検査を当てる

### Requirement: 壊す変更は新しい大きい版として出し、前の版は 6 か月以上と本人への知らせの後でしか外さない

WHEN 衛星を壊す変更を出す THE SYSTEM SHALL それを新しい大きい版（`/satellite/v<次の版>/`・`docs/satellite-api/v<次の版>/`・版の一覧の新しい項目）として出し、前の版の口・契約・版の一覧の項目を残して並べて動かす。
THE SYSTEM SHALL 比べる相手にある大きい版を、版の一覧・契約の写し・作り直した契約（サーバの経路に載る口）のどれかから外す変更を、次の 2 つを両方満たすときだけ通し、満たさなければ CI を落とす:
(a) 外す版の次の大きい版の契約の写しを最初に含んだ配った印（`v*`）の「配った日」から 6 か月以上たっている。配った日は、その印を作った日（注釈つきの印の日）と、印の commit の日の遅い方とする。6 か月は暦の月で数え、同じ日が無い月は月の最終日にする。印がまだ無ければ満たさない。
(b) 版の一覧の外す版の項目の `notice` が、正典（`openspec/specs/`）にある Requirement の名前（本人に知らせる画面）を持つ。
THE SYSTEM SHALL 版の一覧の項目に外す日（`sunset`）を置く変更を、その日が (a) の 6 か月の終わり以後であるときだけ通し、そうでなければ CI を落とす。

導出元: FR-95。深掘り Q6（推奨: 新しい版を最初に配った日（印）から数える）・Q8（推奨: いま決める。外す前は見出しで予告し、知らせの画面ができるまで版は外せない）。premises P8・P10。review/spec.md R1・R2。
数え始めを配った日にするのは、衛星の作り手が新しい版を手にしてから、6 か月を下回らないようにするため。印を後から付けても数え始めが早い側にずれないよう、印を作った日と commit の日の遅い方にする（design D12（仮））。
いまは印が 0 個（premises P8）で、版も 1 つだけなので、外す場面は試しの材料（偽の版 2 と偽の印）で確かめる。
衛星の記録は途絶の通知（FR-35）に乗らない（FR-99）。前の版を黙って外すと、本人は格子の空白で初めて気づく。本人に知らせる画面（外す予定の版を最近使った衛星を出す）は、最初に前の版を外す作業の上流で作り、そのときに (b) の名前を書く。
それまで (b) を満たす項目は無いので、版を外す変更はいつも CI が止める。

### Requirement: サーバに無い版や外した版を呼ばれたら版の一覧つきで断り、外す日の決まった版は見出しで予告する

WHEN 有効な衛星の資格情報を付けた求めが、`/satellite`・`/satellite/` か、版の一覧に無い大きい版の道（`/satellite/<版の一覧に無いもの>` で始まる）に届く THE SYSTEM SHALL 404 で、本文 `{"error": "unsupported_version", "api_versions": <版の一覧>}` を返す（版の一覧は確かめる口と同じ形）。
WHEN 有効な衛星の資格情報を付けた求めが、版の一覧にある大きい版の道で、その版の契約に無い道に届く THE SYSTEM SHALL 404 で、本文 `{"error": "not_found"}` を返す。
WHEN 有効な衛星の資格情報を付けた求めが、契約にある道へ契約に無いメソッドで届く THE SYSTEM SHALL 405 で、本文 `{"error": "method_not_allowed"}` を返す。
THE SYSTEM SHALL 衛星向けの道では、資格情報の判定を版の判定より先に行う（資格情報が無いか認められない求めは、どの道でも 401 `{"error": "unauthorized"}`、衛星でない資格情報は 403 `{"error": "not_satellite"}`）。
WHERE 版の一覧の項目が外す日（`sunset`）を持つ THE SYSTEM SHALL その大きい版の道へのすべての応答（401・403・404・405 の断りを含む）に、見出し `Sunset`（その日の 00:00 UTC を HTTP の日付の形で）を付ける。外す日を持たない版の応答には付けない。

導出元: FR-95。深掘り Q8（推奨: いま決める。断り＋版の一覧、外す前は見出しで予告）。review/spec.md R7・R8。
外した版・無い版への応答は版 1 の衛星が受け取るので、版 1 の契約に書く（Q8 の points）。衛星の作り手は、外す日と移り先を応答から機械で知れる。
資格情報の断りにも `Sunset` を付けるのは、資格情報の設定を間違えた衛星にも外す日を届けるため。
`Sunset` の見出しの名前と形は RFC 8594 に合わせる（design D12（仮））。

- **THEN** 401 で、本文は `{"error": "unauthorized"}` で、版の一覧を含まない

### Requirement: 衛星向けの口への求めを、読み出しの記録に 1 求め 1 行残す

THE SYSTEM SHALL 衛星向けの道（`/satellite` そのものか、`/satellite/` で始まる道。ST29 の管理の口 `/satellites…` は含まない）に届いたすべての求めを、読み出しの記録に 1 求め 1 行残す。行の結果は、通したものは `ok`、資格情報が無いか認められないものは `unauthorized`、それ以外の断り（403・404・405）は `forbidden` とし、状態の列に実際に返す状態の番号を書く。
THE SYSTEM SHALL その行の口の名前に、届いた道の文字列ではなく、当たった経路の形（`/satellite/v1/me` や、版の受け口の形）を書く。
THE SYSTEM SHALL 衛星の資格情報の行には、今と同じく、どの衛星か・どの 1 本の資格情報かを本体の中の番号で持たせ、衛星の識別子の文字列・資格情報の値を持たせない。
WHEN 衛星向けの口への求めの行を書けない THE SYSTEM SHALL その求めに 500 で本文 `{"error": "internal"}` を返し、衛星の情報も版の一覧も返さない。

導出元: PERM-10 / FR-89。正典 data-sensitivity「誰がいつ読んだかを、追記のみの読み出しの記録に残す」の行の形（資格情報の種類・口の名前・結果）に合わせる。design D13（仮）。review/spec.md R9。
道に版を入れた（Q1）ので、口の名前から衛星がどの版で呼んだかが分かる。届いた道の文字列をそのまま書くと、衛星が道に入れた任意の文字列が記録に残る。
衛星向けの口は記録を返さないので、行はハンドラの応答を作った後に、返す状態で書く。書けなければ作った応答を捨てて 500 にする（行が欠けた応答を返さない）。

#### Scenario: 確かめる口を呼ぶと、衛星と 1 本の番号つきで ok の行が残る

- **WHEN** 衛星「読書ログ」の資格情報を付けて `GET /satellite/v1/me` を呼ぶ

### Requirement: 衛星の資格情報では、まだどの口も通らない

THE SYSTEM SHALL 衛星の資格情報を、呼び出し元を識別できる資格情報として受ける。
WHEN 衛星の資格情報を付けた求めが、資格情報の要らない口（生存確認・ログイン・ログアウト）と衛星向けの道（`/satellite` そのものか、`/satellite/` で始まる道。ST29 の管理の口 `/satellites…` は含まない。「衛星は自分が誰かと、サーバが受ける版を確かめられる」）以外の口に届く THE SYSTEM SHALL その求めを 403 で断り、ハンドラの処理を行わない。
THE SYSTEM SHALL 衛星向けの道のほかで衛星の求めを断る 403 の応答の本文を、どの口でも同じ 1 つの文字列にし、記録・件数・衛星や資格情報の情報を含めない。
THE SYSTEM SHALL 衛星の資格情報を付けた求めの応答で、ログインの印を出し直さない。
THE SYSTEM SHALL 資格情報の要らない口に、衛星の資格情報を付けた求めと付けない求めとで同じ応答を返す。
THE SYSTEM SHALL 衛星の資格情報を付けた求めを、同じ求めがログインの印を併せて持っていても、衛星の求めとして扱う。
THE SYSTEM SHALL 衛星の資格情報の求めをハンドラに届けるのは衛星向けの道だけにし、そのうち 2xx を返すのは衛星向けの契約に載った口だけにする（ほかは版の受け口が 404・405 で断る）。ST42 の時点で衛星向けの契約に載るのは、自分が誰かを確かめる口だけで、記録を読む口も書く口も無い。

導出元: PERM-8 / PERM-10 / 扉 #15。深掘り Q6 / Q7/ C8 / C12 / D18（仮）。申し送り `docs/handoff/ST29.md`（st17 C2・st33 C4）。
衛星が読めるのは承認（ST38）と衛星の読み出しの門（ST45）の後、書けるのは書き手の列（ST37）の後。それより前に通る口があると、承認していない種類が外へ出る（扉 #15）。
403 にするのは、衛星の作り手が「資格情報が間違っている（401）」と「承認がまだ（403）」を見分けられるため。
route ごとでなく router のすべての口で確かめるのは、走っている Story（ST09 の原本の送り口・ST13 の `GET /sources`）や後の Story が足した口も拾うため。
衛星向けの口（自分が誰かを確かめる口）は版の付いた契約（ST42）と一緒に置く（Q7）。設定できたかは最後に使われた時刻で分かる。

#### Scenario: 衛星の資格情報では、資格情報の要らない口のほかに 2xx を返す口が無い

- **WHEN** 内部の口の契約に載る router のすべての口とメソッドを、有効な衛星の資格情報を付けて 1 回ずつ呼ぶ
- **THEN** 生存確認・ログイン・ログアウトを除くすべての求めが 403 で断られ、どの 403 の応答の本文も同じ 1 つの文字列で記録を含まず

#### Scenario: 資格情報の要らない口は衛星の資格情報の有無で応答が変わらない

- **WHEN** 生存確認・ログイン（違う合言葉）・ログアウトを、衛星の資格情報を付けた場合と付けない場合でそれぞれ呼ぶ
- **THEN** 口ごとに、2 つの応答の状態の番号と本文は同じである

#### Scenario: 衛星の資格情報で送った記録は取り込まれない

- **THEN** どの求めも 403 で断られ、記録・生存信号・破棄の報告の件数は増えない

#### Scenario: 衛星の資格情報ではログインの状態も読めない

- **THEN** 求めは 403 で断られる

- **THEN** 求めは 403 で断られ、応答に記録は含まれず、ログインの印を出し直す `Set-Cookie` も含まれない
