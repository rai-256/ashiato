## R1 — 「既に分かっている食い違い」が部品と場合の組だけで名指しされ、実際の値を見ない。同じ組の別の赤も既知の節に入って埋もれる
- 対象: impact.findings[IMP-01].options / impact.situations[normal].can（「既知の赤とそれ以外の赤を分けて読める」）
- 種類: 新しい帰結
- 指摘: tasks.md:28 は名指しを「部品と場合の組」（`collector` の `status-503`、`updater`/`collector-dev` の `nightly-object`、`shape` の「1 件の道の答えの形」など）で書いている。期待と実際の値で名指す旨は無い。spec の Scenario（`503` の行が前の節、`draft` の行が後の節）も、組が違うものしか試していない。このため `collector` の `status-503` で実際が「配布元に届かない」以外（記録なし・時間切れなど）に変わった赤も、`shape` の 1 件の道で項目が消えるような本物の形の変化も、既知の節に入る。「それ以外の赤が空」を見る 8.1 と、IMP-01 の「新しい赤を見分ける」という緩和が、その入った赤を見落とす。この検査の目的（形の変化・食い違いに気づく）と逆に働く。分析は IMP-01 の帰結を「毎晩赤で慣れる」ことだけに置き、この点を扱っていない。
- 直し方の案: 既知の名指しを（部品・場合・期待・実際）の 4 つ組にして、実際が違えば「それ以外の赤」に出す Scenario を足し、IMP-01 の帰結にこの隠れ方を書く。
- 処置: fixed: IMP-05（medium・derived）を足し、名指しを 4 つ組にする直し方を選択肢に置いた。仕様は reading の段で変えない（人間が「仕様を直す」と答えれば spec の段が直す）

## R2 — 本人が見たエラーに近い開発版の道の 404 が「緑」になる点が、影響として挙がっていない
- 対象: impact.overview / impact.problem / impact.findings（欠落）
- 種類: 新しい帰結
- 指摘: spec「開発版の道の 404 は「配布元が見つからない」なら緑」（Q7 の推奨）で、部品が 404 を記録し続ける状態は毎晩の判定では緑になり、注意の 1 行が出るだけになる。依頼（docs/changes/CH20.md「エラーを記録し続けず、決めた振る舞いになること」）と premises P4 の食い違いは、spec の導出元と design にだけある。go.json の findings には無い。overview は「次に同じ種類の食い違いが起きたら赤」と読める書き方で、本人が見た種類のエラーがこの検査では赤にならないことを言っていない。Q7 は答え待ちなので、答えが依頼寄りなら期待が変わる。その分岐は IMP にも unknowns にも無い。
- 直し方の案: Q7 の答えで緑・赤が変わることを IMP（または overview の限定）として足し、「本人が見たエラー」は赤にならない旨を書く。
- 処置: fixed: IMP-06（medium）を足し、Q7 の答えで変わる分岐を unknowns と選択肢に置いた。overview に「開発版の道の 404 を記録し続けることは赤にならない」と限定を足した

## R3 — 部品が「届かない」と記録しても、検査の側が 200 を取れた晩は製品側の不具合と区別されず、3 晩までは注意で済む
- 対象: impact.situations[mixed].cannot / impact.findings[IMP-02]
- 種類: 新しい帰結
- 指摘: spec は、部品が本物の段で「問い合わせの上限」「時間切れ」「配布元に届かない」を記録したらその段は比べないとしている（「届かなかった段」）。E3（update_check.rs:484）の `_ => Unreachable` は、証明書の検証失敗・転送先の検査落ち・5xx・ほかの状態コードもまとめている（update_check.rs:447-475 も `Unreachable` を返す）。検査の側が同じ晩に同じ道で 200 を取れていても、部品の Unreachable は「ネットワーク」として注意になり、3 晩続いて初めて赤になる。製品の通信の不具合（例: OS の根の証明書、プロキシ）は本人が見た「エラーが出続ける」種類に最も近く、この検査が最も拾うべき対象である。IMP-02 は上限の頻度だけを扱い、この検査の側が届いたのに部品が届かない場合の扱いに触れていない。situations[mixed] の cannot も下書きと上限だけを挙げている。
- 直し方の案: 検査の側が 200 を取った晩は、Unreachable・Timeout を注意でなく比べる対象にするか、少なくとも IMP に「製品側の通信不具合が 3 晩まで注意に隠れる」と書く。
- 処置: fixed: IMP-07（medium・derived）を足し、situations[mixed].cannot に検査の側が 200 で部品だけが届かない晩を足した。依存 D6 から繋いだ

## R4 — IMP-02 の重大度と閉じ方: 根拠が推測のまま、受け入れの理由が「見て決める」だけ
- 対象: impact.findings[IMP-02]
- 種類: 閉じ方
- 指摘: basis は `guess`、unknowns に runner の IP の残りがあり、verify は merge の後の 1〜2 週間の観察である。手当ては「3 晩続けば赤」だが、上限に当たる晩が多いと、本物の段は判定されないまま緑が続く（赤は 3 晩連続のときだけ）。acceptance は IMP-01〜04 を「受け入れる」と書くだけで、断続的に当たる場合（2 晩届かず 1 晩届く）は永遠に赤にならず本物の段が見られない、という穴が解消されない。medium は妥当だが、「いま進めて安全」と言える手当てではなく、観察の予定を書いただけである。
- 直し方の案: 届かなかった晩の割合（たとえば 7 晩のうち 4 晩）でも赤または別の知らせにするか、IMP-02 の interim に「断続だと緑のまま」と明記する。
- 処置: fixed: IMP-02 の text・undefined・unknowns に断続すると赤にならない穴を書き、割合で赤にする直し方を選択肢に足した。重大度は medium のまま（指摘も妥当とした）

## R5 — 配る形のインストールが対話なしに通るかが未確認のまま、更新係の段全体が merge の後の確認に載っている（重大度）
- 対象: impact.dependencies[D3] / impact.findings[IMP-03]
- 種類: 重大度
- 指摘: 更新係の「配る形」の段（依頼の中心。CH20.md「何を」）は、install-check.sh を呼ばず collect が自前で入れる（IMP-03 の text）。通らなければ `updater-release real` の記録なし赤が毎晩出て、「それ以外の赤」に入る。E7（install-check.sh:683）は install-check.sh の呼び方を示すだけで、collect の手順が同じ入力で通ることの根拠ではない（D3 は `unknown`）。IMP-03 を `low` にし verify を「下流で手動の起動を 1 回」としているが、tasks 8.1 は merge の後の確認バッチである。merge の前に runner で 1 回通す手順は tasks にあるかが読み取れない。更新係の段が成り立たないままでは検査の中心が働かないので、low は軽い。
- 直し方の案: 手動の起動での 1 回の通りを archive の前の条件にするか、IMP-03 を medium にして interim（その間は updater の段が赤であること）を書く。
- 処置: fixed: IMP-03 を medium に上げ、手動の起動で 1 回通ることを archive の前の条件にする直し方を選択肢に置いた

## R6 — 「予定の workflow が止まると赤も出ない」が residual だけで、無音の停止への手当てが無い
- 対象: impact.scope.residual[3]
- 種類: 閉じ方
- 指摘: 検査の失敗の知らせは GitHub の既定のメール（design D9（仮））に頼り、止まったことは何も知らせない。residual に「知識。確かめていない」とあるのみで、前の実行を読む `history` が持つ実行の一覧（`gh run list --event schedule`）で「直近の予定の実行が 2 日以上無い」を見る口は spec に無い。認証が切れる・通知先が変わるなど、無音で止まる他の道も同じ扱いになる。「次に同じ種類の食い違いが起きたら機械が気づく」（CH20.md）が、検査自身の停止では成り立たない。
- 直し方の案: 直近の予定の実行が古いときに警告する（他の workflow の実行時に見るなど）か、残る条件として IMP に昇格して interim を書く。
- 処置: fixed: residual だけだった停止を IMP-08（low・guess）に上げ、直近の予定の実行が古いときの警告を選択肢に置いた
