## MODIFIED Requirements

### Requirement: 更新を確かめる問い合わせは、版の一覧を取る決まった形だけを配布元へ送る

THE SYSTEM SHALL 3 つの部品の更新の問い合わせを、方法 `GET`・本文なしにし、道を次の 2 つに限る: 開発版でない部品は `/repos/rai-256/ashiato/releases?per_page=20`、開発版の部品は `/repos/rai-256/ashiato/releases/tags/nightly`。
THE SYSTEM SHALL 問い合わせの見出しを、`Host`・`User-Agent`・`Accept`・`Accept-Encoding`・`Connection` の 5 つの名前の内側に限り、`User-Agent` の値を `ashiato-update-check` に、`Accept` の値を `application/vnd.github+json` に固定する。
THE SYSTEM SHALL 問い合わせのどこ（道・見出し・本文）にも、自分の版番号・端末の機種・OS の版・端末や利用者の識別子・資格情報・記録を入れない。
THE SYSTEM SHALL 転送（3xx）は同じ `api.github.com` の中のものだけを追い、ほかの宛先への転送は「確かめられない」として扱う。
THE SYSTEM SHALL 暗号化した接続の証明書を OS の持つ根で確かめ、更新係と PC の収集アプリに根の一覧の部品を同梱しない。
THE SYSTEM SHALL 宛先を組み立てのときの定数にし、配る組み立て（サーバの更新係・PC の収集アプリの配る zip、携帯の配る APK）には宛先を実行時に変える口を持たせない。
THE SYSTEM SHALL 宛先を差し替える口を試験の組み立てにだけ持たせ、試験の組み立ては差し替えの宛先が無ければ確かめない（PR ごとの CI の試験は本物の配布元に問い合わせない。PR ごとの CI で配る組み立てを動かすときは、外への接続を塞いで走らせる）。
THE SYSTEM SHALL 自動の試験と検査のうち本物の配布元に問い合わせるものを、毎晩の検査（「毎晩、本物の配布元との組み合わせを確かめる」）だけにし、その 1 回の実行で部品が本物の配布元に問い合わせる回数を 3 回までにする。

導出元: FR-116（機械の検査で固定する。要件の Q7）。聞かない既定 C2・C8。premises P1〜P3・P10。
CH20 で改めた（2026-11-19。CH20 深掘り Q10）: 本物に問い合わせないのを PR ごとの CI に限り、毎晩の検査だけを許す。PR ごとの CI の外向きの遮断（ST57 design D18）は変えない。
GitHub の API は `User-Agent` の無い問い合わせを断る（P3）ので、見出しを 1 つは送る。`Connection` は Android の通信の部品が自分で足すことがある（design D13（仮）。聞かない既定 C2 の 4 つに足した）。
自分の版は送らず、取った一覧を手元で選ぶ。配布元から見分けられるのは開発版かどうか（道の違い）だけで、開発版の印 `nightly` は公開されている。

#### Scenario: 更新係の問い合わせは版の一覧の取得だけである

- **GIVEN** 宛先を手元の受け手に差し替えた試験の組み立ての更新係（版 `0.4.0`）
- **WHEN** 更新係が 1 回確かめ、受け手が受けた問い合わせを全部読む
- **THEN** 問い合わせは 1 件で、方法は `GET`、道は `/repos/rai-256/ashiato/releases?per_page=20`、本文は 0 バイト、見出しの名前は許した 5 つの内側、`User-Agent` は `ashiato-update-check`、`Accept` は `application/vnd.github+json` で、どの見出しの値にも `0.4.0` が無い

#### Scenario: PC の収集アプリの問い合わせは版の一覧の取得だけである

- **GIVEN** 宛先を手元の受け手に差し替えた試験の組み立ての PC の収集アプリ（版 `0.4.0`・端末の識別子 `pc-0123456789ab`）
- **WHEN** PC の収集アプリが 1 回確かめ、受け手が受けた問い合わせを全部読む
- **THEN** 問い合わせは 1 件で、方法・道・本文・見出しの名前と値は更新係と同じ決まりのとおりで、どの見出しの値にも `0.4.0` と `pc-0123456789ab` と資格情報が無い

#### Scenario: 携帯の問い合わせは版の一覧の取得だけである

- **GIVEN** 宛先を端末の中の受け手に差し替えた試験の組み立ての携帯の収集アプリ（本物の Android の上）
- **WHEN** 携帯の収集アプリが 1 回確かめ、受け手が受けた問い合わせを全部読む
- **THEN** 問い合わせは 1 件で、方法・道・本文・見出しの名前と値は更新係と同じ決まりのとおりで、どの見出しの値にも端末の機種名（`Build.MODEL`）・OS の版（`Build.VERSION.RELEASE`）・アプリの版・資格情報が無い

#### Scenario: 更新係と PC の収集アプリは根の一覧を同梱しない

- **WHEN** 更新係と PC の収集アプリを組み立てる部品の一覧を、同梱の根の一覧の部品（一覧は検査の側が持つ）と突き合わせる
- **THEN** 一致する部品は 0 件である

#### Scenario: 開発版の部品は印 nightly の 1 件だけを取る

- **GIVEN** 宛先を手元の受け手に差し替えた、版 `0.4.0-dev.20261102` の更新係
- **WHEN** 更新係が 1 回確かめる
- **THEN** 受け手が受けた道は `/repos/rai-256/ashiato/releases/tags/nightly` だけである

#### Scenario: 別の宛先への転送は追わない

- **GIVEN** 手元の受け手が `301` で `api.github.com` でない宛先へ転送を返す
- **WHEN** 更新係が確かめる
- **THEN** 更新係は転送先へ問い合わせず、その回を「確かめられない」（理由: 読めない答え）として記録する

#### Scenario: 配る組み立ては宛先を変える口を持たない

- **WHEN** 配る形でサーバの Windows の配布物と PC の収集アプリの配布物を組み、`ashiato-updater.exe` と `ashiato-collector-windows.exe` の中の文字列を読む
- **THEN** 宛先を差し替える口の名前（`ASHIATO_UPDATER_TEST_`・`ASHIATO_COLLECTOR_TEST_UPDATE_URL`）が無く、宛先 `https://api.github.com/repos/rai-256/ashiato/releases` がある

#### Scenario: 携帯の配る APK の宛先は配布元である

- **WHEN** 配る形で携帯の APK を組み、組み立ての定数の更新の宛先を読む
- **THEN** 宛先は `https://api.github.com/repos/rai-256/ashiato/releases` で、配る組み立てに宛先の差し替え（`-P`）を渡すと組み立ては 0 でない終了コードで落ちる

#### Scenario: 試験の組み立ては差し替えの宛先が無ければ確かめない

- **GIVEN** 宛先を差し替えていない試験の組み立ての PC の収集アプリ
- **WHEN** 確かめる時を迎える
- **THEN** 外への問い合わせは 0 件で、確かめた記録に「宛先なし」が 1 行ある

#### Scenario: PR ごとの CI は本物の配布元に問い合わせない

- **WHEN** 配線の検査が `.github/workflows/ci.yml` を読む
- **THEN** `install-windows` の job は最初のインストールより前に更新係の外向きを塞ぐ step（`update-check-install.sh --block-outbound`）を持ち、どの job も毎晩の検査の本物に当てる口（`release-source-check.sh` の `collect` と `fetch`）と PC の収集アプリの本物に当てる試験（`ch20_real_source`。`--ignored`・`--include-ignored`）を走らせない

## ADDED Requirements

### Requirement: 毎晩、本物の配布元との組み合わせを確かめる

THE SYSTEM SHALL 毎晩 1 回（予定の起動）、サーバの更新係と PC の収集アプリが本物の配布元（`api.github.com` のリポジトリ `rai-256/ashiato` のリリース）と話したときの振る舞いを確かめる検査を、配る物の組み立てと公開（`nightly.yml`）とは別の workflow で走らせる（組み立ての有無に依らず走り、公開を止めない）。手動の起動も受ける。
THE SYSTEM SHALL その検査で、配る形のサーバ（インストーラと更新係）を Windows に入れて更新係のサービスに確かめさせ、PC の収集アプリは試験の組み立てで本物の配布元に 1 回確かめさせ、開発版の道は試験の組み立ての更新係に開発版の版を与えて 1 回確かめさせる（部品の問い合わせは合わせて 3 回）。
IF 配る形の更新係のサービスが、インストールの後 180 秒のうちに確かめた記録を 1 行も書かない THEN THE SYSTEM SHALL 赤にし、理由を「更新係のサービスが確かめなかった」と出す。
THE SYSTEM SHALL 検査の側が本物の答えを取る問い合わせを 1 回の実行で 4 回（`rai-256/ashiato` の一覧と印 `nightly`、比べに使う別の公開の repo の一覧 1 件とその印の 1 件）に限り、取り直さない。
THE SYSTEM SHALL 部品の問い合わせには資格情報を渡さず、検査の側の問い合わせ（本物の答えの取得と、前の実行の結果の読み出し）にだけ workflow の資格情報を使う。
THE SYSTEM SHALL 検査の workflow に、読む権限（`contents: read`・`actions: read`）だけを持たせる。
THE SYSTEM SHALL その晩に取った本物の答えと、部品が書いた確かめた記録と、判定の要約を、結果に依らず実行の成果物として 90 日残す。
IF 部品を走らせる段（組み立て・インストール・部品の実行）が途中で落ちた THEN THE SYSTEM SHALL 判定と成果物の保存を続け、記録の無い段ごとに赤の行を出す。
WHEN 検査が赤で終わる THE SYSTEM SHALL 赤の理由を 1 行ずつ（部品・場合・期待・実際）実行の要約に出し、要約の先頭で「既に分かっている食い違い」（名指しした食い違いに当たる赤）と「それ以外の赤」を分ける。

導出元: CH20（依頼「何を」「どこまで」）。CH20 深掘り Q2（推奨: サーバの更新係と PC の収集アプリ）・Q3（推奨: サーバは配る形、PC の収集アプリは試験の組み立て）・Q10（推奨: 毎晩の検査だけは数回まで）。
携帯の収集アプリは見ない（Q2。選び方のコードを共有しておらず、偽の配布元の試験のまま）。赤の知らせは、GitHub が予定の workflow の失敗を知らせる既定の仕組みに任せる（design D9（仮））。
本物の答えを 90 日より長くは残さない（design D13（仮））。形が変わった夜はその夜の判定が名前つきの赤で出し、その実行の成果物が 90 日残る。

- **THEN** workflow は `schedule` と `workflow_dispatch` を持つ

- **THEN** `nightly.yml` には毎晩の検査の job も、それへの `needs` も無い

- **WHEN** 台本の判定（`release-source-check.sh judge`）がそれを読む

- **THEN** 判定は赤で、`updater-release real` の行の実際は「更新係のサービスが確かめなかった」である

#### Scenario: 要約は既に分かっている食い違いとそれ以外の赤を分けて出す

- **GIVEN** 名指しした食い違い（PC の収集アプリの `503`）に当たる赤と、名指ししていない赤（答えの形の `draft` の型）を持つ置き場
- **WHEN** 台本の判定がそれを読む
- **THEN** 要約の先頭に「既に分かっている食い違い」の節と「それ以外の赤」の節があり、`503` の行は前の節に、`draft` の行は後の節にだけある

### Requirement: 2 つの部品が、本物の状態と流し直した状態で正典どおりに記録したかを判定する

THE SYSTEM SHALL 毎晩の検査で、部品が記録した確かめた結果（成否・理由・見つけた最新の版）を、正典（「新しい版かどうかは、入っている版のチャンネルで決める」「確かめた結果は「見つけた最新の版」で持ち、確かめた記録を追記で残す」）がその答えに決めている結果と突き合わせ、1 つでも違えば赤にする。期待は正典から決め、部品のいまの振る舞いからは決めない。
THE SYSTEM SHALL 本物の状態の期待を、その晩に検査の側が同じ道から取った答えで決める: 一覧の道が `200` で数えるリリースが無ければ「確かめた・見つけた最新の版なし」、数えるリリースがあれば正典の選び方を当てた版、開発版の道が `404` なら「配布元が見つからない」、`200` でも読めない形なら「読めない答え」。検査の側が届かなかった（`403`・`429`・`5xx`・ほかの部品の知らない状態コード・時間切れ・接続できない）道は、本物の状態を判定しない。
THE SYSTEM SHALL 部品が受けた答えを検査は見られないので、部品が本物の段で「問い合わせの上限」「時間切れ」「配布元に届かない」を記録したら、その段は期待と比べずに届かなかった段として扱う（下の「配布元に届かない夜は注意を出し、3 晩続けば赤にする」）。
THE SYSTEM SHALL 本物の配布元の今の状態に加えて、その晩に取った本物の答えを手元の受け手から流し直し、次の場合を作って試験の組み立ての部品に通す。各場合の期待は次のとおり:
最新が自分と同じ版（`v<自分の版>` だけ）→ 確かめた・見つけた最新の版は自分の版。
新しい版がある（`v<自分の版>` と `v<PATCH+1>`）→ 確かめた・見つけた最新の版は PATCH+1。
印 `nightly` のリリース 1 件（オブジェクト。開発版の版の更新係と PC の収集アプリにだけ通す）→ 確かめた・見つけた最新の版あり。
リリースが 20 件の一覧（`v<自分の版>` から古い方へ）→ 確かめた・見つけた最新の版は自分の版。
`503` → 読めない答え。
`api.github.com` でない宛先への `301` → 読めない答え。
WHILE `rai-256/ashiato` に数えるリリースが無い THE SYSTEM SHALL 流し直す各リリースを、別の公開の repo の最新のリリース 1 件を土台にし、その配布物を自分の部品の配布物 4 つ（土台の最初の配布物の写しの名前と取り先の版の部分を書き換えたもの）に置き換えて作る。
WHEN 開発版の道が `404` を返し、部品が「配布元が見つからない」と記録した THE SYSTEM SHALL 正典どおりとして緑にし、要約に「依頼と正典の食い違い（開発版の道の 404 を記録し続ける）」を出す。
WHEN 流し直しの場合の行を出す THE SYSTEM SHALL その場合に流し直した本文のバイト数を行に添える。

導出元: CH20（依頼「本物の配布元の今の状態…のどれでも…決めた振る舞いになることを判定する」）。CH20 深掘り Q4（推奨: その晩の答えを流し直して版の名前を書き換える）・Q6（推奨: 別の公開の repo の最新のリリース）・Q7（推奨: 正典どおりなら緑）・Q9（推奨: 製品は直さず、検査は 3 つの食い違いを捕まえる形にする）。
`503` と `301` は本物に依らない作った答えだが、Q9 の推奨（3 つの食い違いを捕まえる）で入れる（design D6（仮））。
2026-11-19 の時点で、次の 3 つは部品が正典と食い違い、初日から赤になる（直しは別の change）: 印 `nightly` のリリース 1 件を読めない（更新係と PC の収集アプリ）・20 件の一覧が 64 KiB を超えて読めない（更新係と PC の収集アプリ）・`503` と別の宛先への `301` を「配布元に届かない」と記録する（PC の収集アプリ）。

#### Scenario: 空の一覧で「確かめた・新しい版なし」を記録すれば緑

- **GIVEN** 記録した本物の答え（正式版の道が `200`・本文 `[]`）と、配る形の更新係と PC の収集アプリがそれに「確かめた・見つけた最新の版なし」を記録した確かめた記録
- **WHEN** 台本の判定がそれを読む
- **THEN** 判定は緑（rc=0）で、本物の状態の行に 2 つの部品が「正典どおり」と出る

#### Scenario: 流し直した同じ版を正典どおりに記録すれば緑

- **GIVEN** 版 `0.1.0` の部品に流し直した一覧（`v0.1.0` だけ）と、部品が「見つけた最新の版 0.1.0」を記録した確かめた記録
- **WHEN** 台本の判定がそれを読む
- **THEN** 判定は緑で、その場合が更新なしとして正典どおりと出る

#### Scenario: 流し直した新しい版を正典どおりに記録すれば緑

- **GIVEN** 版 `0.1.0` の部品に流し直した一覧（`v0.1.0` と `v0.1.1`）と、部品が「見つけた最新の版 0.1.1」を記録した確かめた記録
- **WHEN** 台本の判定がそれを読む
- **THEN** 判定は緑で、その場合が更新あり 0.1.1 として正典どおりと出る

#### Scenario: 開発版の道の 404 は「配布元が見つからない」なら緑で、食い違いを要約に出す

- **GIVEN** 記録した本物の答え（開発版の道が `404`）と、開発版の版の更新係がそれに「配布元が見つからない」を記録した確かめた記録
- **WHEN** 台本の判定がそれを読む
- **THEN** 判定はその場合を緑とし、要約に「依頼と正典の食い違い（開発版の道の 404 を記録し続ける）」が 1 行ある

#### Scenario: 部品の記録が正典と違えば赤で、部品・場合・期待・実際を出す

- **GIVEN** 流し直した `503` に、更新係が「読めない答え」を、PC の収集アプリが「配布元に届かない」を記録した確かめた記録
- **WHEN** 台本の判定がそれを読む
- **THEN** 判定は赤（rc=1）で、PC の収集アプリ・`503`・期待「読めない答え」・実際「配布元に届かない」の行があり、更新係の行は無い

#### Scenario: 別の宛先への 301 を「読めない答え」と記録しなければ赤

- **GIVEN** 流し直した `api.github.com` でない宛先への `301` に、PC の収集アプリが「配布元に届かない」を記録した確かめた記録
- **WHEN** 台本の判定がそれを読む
- **THEN** 判定は赤で、場合 `redirect-offhost`・期待「読めない答え」・実際「配布元に届かない」の行がある

#### Scenario: 印 nightly のリリース 1 件を読めなければ赤

- **GIVEN** 流し直した印 `nightly` のリリース 1 件（オブジェクト）の本文と、開発版の版の更新係がそれに「読めない答え」を記録した確かめた記録
- **WHEN** 台本の判定がそれを読む
- **THEN** 判定は赤で、期待は「確かめた（見つけた最新の版あり）」、実際は「読めない答え」と出る

#### Scenario: 20 件の一覧を読めなければ赤

- **GIVEN** 流し直した 20 件の一覧の本文と、部品がそれに「読めない答え」を記録した確かめた記録
- **WHEN** 台本の判定がそれを読む
- **THEN** 判定は赤で、場合の行に流し直した本文のバイト数が出る

#### Scenario: 部品が本物の段で届かなかったと記録すれば、その段は期待と比べない

- **GIVEN** 検査の側の正式版の道が `200`・`[]` で、PC の収集アプリが本物の段で「問い合わせの上限」を記録した確かめた記録
- **WHEN** 台本の判定がそれを読む
- **THEN** `collector real` の赤の行は無く、注意「本物の配布元に届かなかった（collector real）」が出る

#### Scenario: 流し直しは版の名前と配布物だけを差し替え、ほかの項目を土台のまま残す

- **GIVEN** 記録した別の公開の repo のリリース 1 件
- **WHEN** 台本が「新しい版がある」の場合の答えを組む
- **THEN** 組んだリリースの `tag_name` は `v<PATCH+1>`、`assets` は 4 つで各 `name` は自分の部品の配布物の名前、各 `browser_download_url` は土台の最初の配布物の取り先の版と名前の部分だけを書き換えたもので、各配布物の `digest` は土台の最初の配布物と同じ、リリースの `draft` ほか `assets` と `tag_name` 以外の項目は土台と同じ値である

#### Scenario: 20 件の一覧の本文は部品の本文の上限を超える

- **GIVEN** 記録した別の公開の repo のリリース 1 件
- **WHEN** 台本が「リリースが 20 件の一覧」の場合の答えを組む
- **THEN** 組んだ本文は 20 件の配列で、バイト数は 65536 を超える

### Requirement: 配布元の答えの形を、偽の配布元の形の基準と比べる

THE SYSTEM SHALL 毎晩の検査で、本物の答えのうち部品が読むもの（状態コード・転送の行き先・本文の大きさ・道ごとの答えの形（一覧の配列か、1 件のオブジェクトか）・各リリースの `tag_name`・`draft`・`assets[].name`・`browser_download_url`・`digest`）を、repo に置いた基準（偽の配布元と共有の材料が返している形）と比べる。
IF 部品が読む項目が無い・型が違う・道ごとの答えの形が違う THEN THE SYSTEM SHALL 赤にし、どの道のどの項目が、基準と本物でどう違うかを出す。
IF 状態コードが部品の知っている値（`200`・`301`・`302`・`307`・`308`・`403`・`404`・`429`）でない THEN THE SYSTEM SHALL その道の答えの形を比べずに注意を出し、届かなかった晩として数える（`5xx` は配布元の障害として扱う）。
IF `rai-256/ashiato` の一覧の本文が、部品の本文の上限（65536 バイト）を超える THEN THE SYSTEM SHALL 赤にし、本文のバイト数を出す。
THE SYSTEM SHALL 部品が読まない項目の増減と、どの項目の値の変化でも赤にしない。
WHILE `rai-256/ashiato` にリリースが無い THE SYSTEM SHALL 各リリースの項目と 1 件の答えの形を、別の公開の repo のリリースで見て、要約に見た repo の名前を出す。
IF 比べに使う repo の答えが `200` なのに読めない（JSON でない・リリースが無い）THEN THE SYSTEM SHALL 赤にし、「比べに使う repo の答えを読めない」と出す。

導出元: CH20（依頼「配布元の応答の形が変わったことも拾えるようにする」）。CH20 深掘り Q5（推奨: 製品が読む項目だけを比べる）・Q6。

#### Scenario: 読む項目が揃い型が同じなら、読まない項目が増えても緑

- **GIVEN** 基準と、読む項目を全部同じ型で持ち、読まない項目 `reactions` が増えた記録した本物の答え
- **WHEN** 台本の判定がそれを読む
- **THEN** 答えの形の判定は緑である

#### Scenario: 読む項目の値が変わっても緑

- **GIVEN** 基準と、`tag_name` と `digest` の値だけが前の材料と違う記録した本物の答え
- **WHEN** 台本の判定がそれを読む
- **THEN** 答えの形の判定は緑である

#### Scenario: 読む項目が消えれば赤

- **GIVEN** 基準と、配布物の `digest` が無い記録した本物の答え
- **WHEN** 台本の判定がそれを読む
- **THEN** 赤で、`assets[].digest` が無い、と道と項目の名前つきで出る

#### Scenario: 読む項目の型が変われば赤

- **GIVEN** 基準と、`draft` が文字列の記録した本物の答え
- **WHEN** 台本の判定がそれを読む
- **THEN** 赤で、`draft` の型が基準と違う、と道と項目の名前つきで出る

#### Scenario: 道ごとの答えの形が基準と違えば赤

- **GIVEN** 印の道の答えを配列とする基準と、1 件の道の答えがオブジェクトの記録した本物の答え
- **WHEN** 台本の判定がそれを読む
- **THEN** 赤で、「偽の配布元が本物とずれた: 1 件の道の答えは本物がオブジェクト、基準が配列」と出る

#### Scenario: 一覧の本文が上限を超えれば赤

- **GIVEN** `rai-256/ashiato` の一覧の本文が 70000 バイトの記録した本物の答え
- **WHEN** 台本の判定がそれを読む
- **THEN** 赤で、本文のバイト数 70000 と上限 65536 が出る

#### Scenario: 部品の知らない状態コードは形を比べずに注意を出す

- **GIVEN** `rai-256/ashiato` の一覧の道が `502` の記録した本物の答え
- **WHEN** 台本の判定がそれを読む
- **THEN** その道の答えの形の赤の行は無く、注意に `502` と「届かなかった」が出る

#### Scenario: 自分の repo にリリースが無い間は、別の repo で項目を見たと要約に出す

- **GIVEN** `rai-256/ashiato` の一覧が `[]` で、別の公開の repo のリリースを持つ記録した本物の答え
- **WHEN** 台本の判定がそれを読む
- **THEN** 要約に、各リリースの項目を見た repo の名前が出る

#### Scenario: 比べに使う repo の答えを読めなければ赤

- **WHEN** 台本の判定がそれを読む
- **THEN** 赤で、「比べに使う repo の答えを読めない」と出る

### Requirement: 配布元に届かない夜は注意を出し、3 晩続けば赤にする

THE SYSTEM SHALL 「晩」を予定の起動の実行で数える（手動の起動の実行は数えず、数える前の実行にも入れない）。
WHEN その晩に、検査の側の問い合わせか部品の本物の段が本物の配布元へ届かなかった（`403`・`429`・`5xx`・時間切れ・接続できない）THE SYSTEM SHALL 届かなかった問い合わせに依る判定（本物の状態・答えの形・その答えから組む流し直し）を飛ばし、飛ばした判定の名前を注意に出し、赤にしない。
IF 予定の起動の直前の 2 回の実行も本物の配布元へ届かなかった THEN THE SYSTEM SHALL 赤にし、届かなかった晩の数を出す。
IF 前の実行の結果を読めない THEN THE SYSTEM SHALL その晩だけで数え、注意に「前の実行を読めない」と出す。
THE SYSTEM SHALL 本物に依らない流し直しの場合（`503`・別の宛先への `301`）を、届かない夜も判定する。

導出元: CH20 深掘り Q8（推奨: その夜は注意、3 晩続けて届かなければ赤）。
部品が受けた答えは検査から見えないので、部品が届かなかった理由（上限か時間切れか）が本物と合っているかは確かめない。

#### Scenario: 届かない夜は注意だけで、飛ばした判定の名前を出す

- **GIVEN** 検査の側の `rai-256/ashiato` の一覧の問い合わせが `403` だった記録した晩と、前の 2 回は届いた予定の起動の実行の結果
- **WHEN** 台本の判定がそれを読む
- **THEN** 判定は緑（rc=0）で、注意「本物の配布元に届かなかった（1 晩目）」と、飛ばした判定（本物の状態・答えの形）の名前が出る

#### Scenario: 届かない夜も、本物に依らない流し直しは判定する

- **GIVEN** 検査の側の問い合わせが全部届かなかった記録した晩と、PC の収集アプリが流し直した `503` に「配布元に届かない」を記録した確かめた記録
- **WHEN** 台本の判定がそれを読む
- **THEN** 判定は赤で、`collector status-503` の行がある

#### Scenario: 3 晩続けて届かなければ赤

- **GIVEN** 本物の配布元に届かなかった記録した晩と、直前の 2 回の予定の起動の実行も届かなかった結果
- **WHEN** 台本の判定がそれを読む
- **THEN** 判定は赤で、「本物の配布元に 3 晩続けて届かない」と出る

#### Scenario: 手動の起動の実行は晩に数えない

- **GIVEN** 本物の配布元に届かなかった記録した晩と、直前の 2 回が手動の起動で届かなかった結果、その前の予定の起動の実行は届いた結果
- **WHEN** 台本の判定がそれを読む
- **THEN** 判定は緑で、注意は「1 晩目」である

#### Scenario: 前の実行を読めなければ、今夜だけで数える

- **GIVEN** 本物の配布元に届かなかった記録した晩と、読めない前の実行の結果
- **WHEN** 台本の判定がそれを読む
- **THEN** 判定は緑で、注意に「前の実行を読めない」が出る
