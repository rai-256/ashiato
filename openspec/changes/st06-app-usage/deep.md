## 先に確かめた事実 —— FR-2 の未決（`UsageStatsManager` の保持期間）

FR-2 には `[NEEDS CLARIFICATION: UsageStatsManager のイベント保持期間が未確認。
一次情報は本文を返さず逐語が取れなかった]` が付いたままだった。**AOSP の実装から逐語で取れた**ので、
この未決は深掘りの問いにせず、事実として問いの前提に置いた（機械が判定できることは機械に決めさせる）。

| 何 | 保持 | 出所 |
|---|---|---|
| 生のイベント（`queryEvents`） | **10 日** | `UsageStatsDatabase.prune()`: `mCal.addDays(-10); pruneFilesOlderThan(mIntervalDirs[INTERVAL_DAILY], …)` |
| 週ごとの集計 | 4 週 | 同 `mCal.addWeeks(-4)` |
| 月ごとの集計 | 6 か月 | 同 `mCal.addMonths(-6)` |
| 年ごとの集計 | **2 年** | 同 `mCal.addYears(-2)` |

`queryEvents` が日ごとの箱だけを読むことも裏が取れた（`UserUsageStatsService.queryEvents` は
`queryStats(INTERVAL_DAILY, …)` を呼ぶ）。範囲は `[begin, end)`（javadoc: "The **inclusive** beginning" /
"The **exclusive** end"）。どちらも 2026-09-18 取得。

→ **要件へ戻すもの**: FR-2 の `[NEEDS CLARIFICATION]` を、この事実で置き換える（★ 訂正）。
取得間隔の値そのものは Q6 の答えで決まる。

## 聞かずに決めた既定（C）—— 扉を開けたままにする側に倒したもの

「片方の選択肢が扉を開けたままにし、費用が小さい」ものは問いにせず、ここに残して design の D 番号にする。

| # | 決めたこと | 扉をどちらへ開けておくか |
|---|---|---|
| C1 | **1 イベント = 1 記録**（1 回の取得を 1 件にまとめない） | まとめると、重ねた窓で配列の中身が変わって冪等キーが動き、再送のたびに行が増える。削除（ST22）・感度（ST24）・時間ごとの件数の粒度も失われる |
| C2 | **アプリの表示名を取得時に解決して `payload` に載せる**（`raw` には入れない） | アプリを消した後でも「何だったか」が残る。`raw` に入れると、アプリの更新や端末の言語変更で冪等キーが変わり同じイベントが行として増える（R2） |
| C3 | 初回と再開の遡りは、**OS が持っている分だけ**（イベントは 10 日、集計は Q5 の答えによる） | 取れるものは全部取る。上限は OS 側が決めるので、こちらで短く切らない |
| C4 | 取得の窓は**重ねて進める**（前回の終わりより少し手前から取り直す） | 境界の取りこぼしを作らない。重複はサーバの冪等が畳む |
| C5 | **`null` と「0 件」を区別し、`null` のときは窓を進めない**（R3） | 解錠していない端末では `queryEvents` が `null` を返す。0 件と同じに扱って窓を進めると、その期間は 10 日で消える |
| C6 | 端末の時計が飛んだときは、**窓を単調な経過時間で押さえ、飛びが直るまで取り直さない**（R4） | OS 側は時計が変わると過去の統計ファイルを丸ごと改名してずらす。ずれた時刻で取り直すと `event_time` が変わって畳まれず、行が増える。`event_time` は凍結されていて後から直せない |
| C7 | 生存信号の **試行 = 契機の数**（区間の長さ ÷ 取得間隔）・**成功 = 取得できた回数**（0 件でも成功） | 位置と同じ数え方。取得率が「眠っていた / 生きていた」を分ける |
| C8 | 生存信号の間隔は**登録簿の想定間隔**（`c01-app-usage` は 6 時間）のまま | ずらすと受け手の途絶判定の窓とずれる |
| C9 | `blockers` は **`permission` と `network`**（アプリ利用に `sensor` は無い） | 契約の語彙をそのまま使う |
| C10 | 感度は**収集側で付けない**（サーバの既定に委ねる） | 契約の「収集側が厳しい側を付けない」に従う |
| C11 | 未送信の置き場は**位置と同じ**（保持の上限は全ソースを通して古い順） | 正典がそう定めている。ソースごとに分けると上限の意味が変わる |
| C12 | 遡って取ったイベントの `tz_id` / `tz_offset_min` は、**取得時点の端末の地域**を付ける（R12） | `tz_id` / `tz_offset_min` は凍結の対象外（DB が明示）なので、後から引き直せる。design の D 番号に（仮）と反転条件を書く |

## 確かめたが問わなかったこと（人間が決めることが無い。tasks / design で塞ぐ）

- **収集側が単一ソース前提で書かれている箇所が 4 つある**（R10）。ログの `source=c01-location` の焼き込み、
  生存信号の満点の刻みが `FIX_INTERVAL_MS` 固定（塞がないと**アプリ利用の取得率が毎回 3 % と読める**）、
  数えの置き場のファイル名が 1 本、常駐通知の文言。tasks で 4 か所とも塞ぐ
- **`Retention` が破棄の報告の範囲の終わりに「置き場全体の最も古い記録」を使っている**（R11）。
  正典は「**同じソースで**残った最も古い記録」。位置 1 本のいまは偶然一致しているが、
  2 本目を同じ置き場に載せた瞬間に、片方の破棄の範囲がもう片方の記録の時刻で閉じる。tasks で塞ぐ
- **要件は直したが正典を直し忘れた前例**（R6）。ST07 が NFR-13 に足した但し書き
  （PC の 2 ソースだけは生存信号が届いた日を分母とする）が `collection-coverage` の spec に入っていない。
  Q2 の答えが NFR-13 を動かすなら同じ型を踏むので、**ST14 への申し送り**に残す（`docs/handoff/ST14.md`）
