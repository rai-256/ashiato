# ST59 design — 合言葉を画面から変えられる

## Context

なぜ要るかは proposal.md の Why。ここでは今の持ち方と制約だけを書く。

- **秘密の持ち方**: サーバは起動の時に 1 回だけ、環境から共有の値（`API_TOKEN`）・画面の合言葉の照らす値（`WEB_PASSWORD_VERIFIER`）・ログインの印の鍵（`WEB_SESSION_KEY`）を読み、`App` が値で持つ
  （`crates/server/src/lib.rs` の `App.token`・`App.login`。`web_session::WebLogin` が照らす値・印の材料 `tag`・失敗の数え `limiter` を持つ）。差し替える道は無い。
- **設定のファイル**: サービスの口（`service --settings <場所>`。Windows だけ）は `settings\server.json` を読んで環境へ入れ、場所を `ASHIATO_SETTINGS_PATH` に置き、`ASHIATO_SERVICE_MODE` で照らす形の検査を通す（`service.rs`・`lib.rs` の `run_inner`）。
  サーバが `server.json` を書く口は無い。書くのはインストーラ（`crates/installer/src/main.rs` の `write_settings`。`server.json.writing` に書いて名前を付け替える）だけ。
  開発の形（`.env` で起こす）は元の合言葉 `WEB_PASSWORD` を持ち、照らす値を渡すと `verifier_in_development` で起動を断る。
- **ログインの印**: `core.web_session` の行は `secret_tag` を持ち、今の `tag` と一致する行だけが有効（`session_valid`）。照らす値が変われば `tag` が変わり、それまでの印は全部通らなくなる（`secret_tag_for_verifier`。premises 3 行目）。
- **合言葉の照合**: ログインの口と「収集アプリの設定」の口（ST56）は `check_given_password` を共有する。1 つずつの印（`LOGIN_CHECK`）を持って照合し、失敗を `limiter` に数える（CH15 で 2 つの口を 1 つの道にした）。
- **読み出しの記録**: `core.access_log.outcome` は CHECK で `ok`・`unauthorized`・`forbidden`・`login_ok`・`login_failed`・`login_throttled`・`logout` に限られる。`/session` と `/collector-setup` は middleware を素通しし、ハンドラが結果どおりに 1 行書く。
- **e2e**: 全部の spec が `tools/stack.sh` の開発の形のサーバ 1 つを共有し、`.env` の `WEB_PASSWORD` でログインする（`web/e2e/global-setup.ts`）。そこで合言葉を変えるとほかの spec が落ちる。

## Goals / Non-Goals

**Goals**
- 設定のファイルを指して起こしたサーバで、画面から 2 つの値を変え、起動し直さずに効かせ、起動し直しても残す
- 変えている最中のログインの照合と、変えた後のログインの印が食い違わない（古い合言葉で通った人に新しい印を渡さない）
- インストーラの `password`・走らせ直し・`repair` が、サーバが書き直した `server.json` を今どおり扱える

**Non-Goals**
- ログインの印の鍵（`WEB_SESSION_KEY`）を画面から変える（FR-133 は 2 つの値だけ。合言葉を変えればログインは締め出せる）
- 開発の形（`.env`）での書き戻し（Q3）。Linux の配る形（ST60）
- 衛星の資格情報の取り消し（ST38）

## Decisions

### D1. 照らす値・印の材料・共有の値を、版の付いた 1 つの組にまとめて差し替える（C2）

`App` は 3 つ（照らす値・印の材料 `tag`・共有の値）を、差し替えられる共有の置き場（`Arc` の中の 1 つの組。読み手は組を丸ごと 1 つ取る）で持つ。
期限（`max_age_days`）・失敗の遅れ・失敗の数え（`limiter`）は組の外に置き、差し替えで数え直さない。

- 1 つの求めは、組を**最初に 1 回だけ**取り、照合・印の発行・印の照会・共有の値の照合をその組で行う（`decide` の共有の値の照合・`session_valid` の `tag`・ログインの口の印の行の `secret_tag`）。
  ログインの口は、照合した組の `tag` で印の行を書く。照合の後に差し替わっても、その印は古い `tag` を持つので、差し替えの後は通らない
- 変える 2 つの口は、`LOGIN_CHECK`（1 つずつの印）を、今の合言葉の照合から、（合言葉のときは）変えた画面の新しい印の行の書き込み・読み出しの記録の行・設定のファイルへの書き戻し・組の差し替えまで持ち続ける。
  そのあいだ、ほかの口の照合は始まらない
- 合言葉の口の順は: 照合 → 新しい照らす値と新しい `tag` を作る → 新しい `tag` で印の行を書く（まだ通らない。差し替えた時に通り始める）→ 読み出しの記録に `ok` の行（D9）→ 書き戻し（D2）→ 差し替え → `Set-Cookie` で印を返す（Q1 の推奨）。
  印の行か記録の行を書けなければ、何も変えずに 500。書き戻しで落ちたら、差し替えず、打ち消しの行を足して 500（書いた印の行は、使われない `tag` を持つので通らない）。review/spec.md R2・R5
- 寿命の出し直し（`refresh_cookie`）は、応答を返す時点の組の `tag` に合う印にだけ付ける（判定は印の行の `secret_tag` を求めの初めに取っておき、返す時点の組と比べる）。
  差し替えの前に始まった求めの応答が、変えた画面の新しい印を古い印で上書きしないため（review/spec.md R3）
- 照合に使う組と応答を書く組がずれないことを、照合の途中で差し替えを割り込ませる試験で固定する（`st59_swap_`）

反転条件: Q1 が「変えた画面も含めて全部切る」になったら、新しい印を渡さず、変えた画面にも `Set-Cookie`（寿命 0）を返す。

### D2. 書き戻しは、今のファイルを読み直して 1 つの鍵だけを置き換え、一時のファイルをディスクへ流してから名前を付け替える（C3）

`service.rs` に書き戻しの関数を置く。手順は (1) `ASHIATO_SETTINGS_PATH` の `server.json` を読み直す（`load_settings` と同じ読み方。環境から組み立て直さない —— サービスは `server.json` に無い 3 つの置き場を環境に補っているので、環境から書くと鍵が増える。review/deep.md R3）、
(2) `WEB_PASSWORD_VERIFIER` か `API_TOKEN` の 1 つだけを置き換える、(3) 同じフォルダの `server.json.writing`（インストーラと同じ名前）に書き、`sync_all` でディスクへ流す、(4) `server.json` へ名前を付け替える。
どこかで失敗したら組を差し替えずに 500（`not_saved`）。読み直しで今のファイルが読めない・JSON でないときも書かずに 500。

- 書きかけで落ちても、`server.json` は前の中身か新しい中身のどちらか（premises 2 行目）。残った `server.json.writing` は、次の書き戻し（サーバかインストーラ）が上書きする。
  サーバの起動・インストーラの `read_settings`・`repair_allowed` はどれも `server.json` だけを見るので、残っても止まらない（review/deep.md R3 の残り）
- ファイルを書くのはサーバのプロセスで、Windows ではサービスのアカウント（`NT SERVICE\ashiato-server`）。`settings` はそのアカウントに書きを継ぐ（premises 1 行目）。
  書いた一時のファイルは `settings` の権限を継ぐので、ACL は今の `server.json` と同じになる
- インストーラの `password` はサーバのサービスを止めてから書くので、サーバとインストーラが同時に書くことは無い

### D3. 値の置き場は `server.json` の 1 つに限る（C4）

変えた値を DB や別のファイルに持たない。インストーラの `password` の決め直しは `server.json` の照らす値を書き換えて起こし直すので、置き場が 1 つなら今どおり効く。

### D4. 新しい合言葉はインストーラの決め直しと同じ 5 つで検査し、新しい共有の値は照らす値とログインの印の鍵に当たらないことを確かめる（C5）

- 新しい合言葉: 16 文字以上（文字の数）・`change-me` で始めない・今の共有の値と違う・ログインの印の鍵と違う・もう一度の入力と一致する（`crates/installer/src/password.rs` の `validate` と同じ順と同じ規則）。
  ログインの印の鍵はサーバが環境から持っている（`WEB_SESSION_KEY`）。照らす値の形では元の合言葉を持たないので、「今の合言葉と同じ」は比べない（変えても塩が変わり、ログインは締め出せる）
- 新しい照らす値は Argon2id の既定の値で作る（インストーラの `password::verifier` と同じ。起動の検査 `check_web_password_verifier` を通る）。書く前に、起動の 2 つの検査（`check_web_password_verifier`・`check_web_session_key_verifier`）に新しい組を通し、落ちる値は書かない
- 新しい共有の値: D6 で作った値を、照らす値が受ける（`verify_password_verifier`）・ログインの印の鍵と同じ、なら作り直す（3 回で当たらなければ 500。実際には起きない）
- 検査の順（spec に写した）: ログインの印（401）→ 呼び出し元の種類（403）→ 本文が JSON か（415）→ 開発の形か（409）→ 失敗の数え（429）→ 今の合言葉の照合（403）→ 新しい合言葉の検査（400）→ D1 / D9 の順で書く。今の合言葉が合わない求めには、新しい合言葉の検査の結果を返さない

### D5. 画面で変えた後もインストーラの `password` が使えることを、Windows の CI で確かめる（premises 5 行目）

インストーラの一時の書き（`TemporaryWrite`）は、中のファイルの持ち主がインストーラだった前提で書かれ、`takeown /A /R` で持ち主を戻す。サーバのアカウントが付け替えで作った `server.json` に届くかは、まだ実物で見ていない（確かさ 2）。
`tools/release/install-check.sh` に、インストールした形で画面の口から 2 つの値を変え、サービスを起こし直し、インストーラの `password` で決め直す通しを足す（Task 7）。
外れたときに失うもの: 画面で変えた後に合言葉を忘れると、`password` の口が使えない。残る出口は `repair`（設定のファイルが無いことが条件。`distribution` の「DB はあるのに秘密が無くて止まったら…」）のために管理者として `server.json` を退けることだけで、そのとき共有の値と DB の合言葉も作り直しになる。
だからこの前提は CI で確かさ 4 に上げてから merge する（Task 7.1 の終わりは CI の `install-windows` の緑）。`crates/installer/src/commands.rs` の一時の書きのコメント（「settings はインストーラだけが書く」）は ST59 の後は外れるので、Task 7.1 で直す（review/spec.md R10）。

反転条件: 通しで `password` が `server.json` を書けない・読めないなら、インストーラの一時の書きを、持ち主に依らず書ける形（`takeown` の後に書きの ACE を足す）に直す。直せなければ A として人間に返す（忘れたときの戻り道が無くなるので P にしない）。

### D6. 新しい共有の値はサーバが OS の暗号の乱数で作り、変えた直後に設定の文字列を出す（C6）

32 バイトを `OsRng` で取り、base64url（埋めなし）にする（インストーラの `secrets::secret` と同じ形。43 文字）。本人は値を入れない。
口は答えに新しい値を返し（`{"token": "…"}`。`/collector-setup` と同じ形）、画面は ST56 の `buildSetupString` で、画面を開いているアドレスの `/api` を送り先にした設定の文字列を組む（ST56 D7）。
案内は「全部の収集アプリ（携帯と PC）にこの文字列を貼り直してください。携帯に入れる文字列は、携帯から開いた画面で『収集アプリの設定』から出してください」。

### D7. 前の共有の値は、差し替えた瞬間から断る（C7。FR-128 ★ 2026-11-02）

`decide` は差し替えた後の組の共有の値とだけ比べる。前の値は資格情報の一致しない求めとして、今どおり 401（取り込みの口）で断り、読み出しの記録に `unauthorized` の行を残す。
収集アプリはそれを受けて記録を溜め、1 時間続くと知らせる（ST56 D12。この Story では変えない）。端末ごとの値・猶予は持たない。

### D8（仮）. 「設定のファイルを指して起こしたサーバ」は、照らす形（`ASHIATO_SERVICE_MODE`）で `ASHIATO_SETTINGS_PATH` があるサーバ。Linux の試験は台本で起こす

- 変える 2 つの口は、`ASHIATO_SERVICE_MODE` で起き、`ASHIATO_SETTINGS_PATH` を持つサーバでだけ書き戻す。それ以外（開発の形）は、ログインの印を見た後に 409（`not_changeable`）で断る（Q3 の推奨）
- Windows の配る形は今の `service --settings` の口がそのまま当たる。Linux（e2e と試験）には新しい口を足さず、台本 `tools/settings-server.sh <設定のファイル>` を置く:
  設定のファイルの鍵を環境へ入れ、`WEB_PASSWORD` を環境から外し（照らす形は元の合言葉が環境にあると `raw_password_present` で起動を断る。e2e の process は `.env` の `WEB_PASSWORD` を持つ。review/spec.md R11）、`ASHIATO_SERVICE_MODE=1`・`ASHIATO_SETTINGS_PATH` を付けて `target/release/ashiato-server`（`tools/stack.sh` が画面を組み込んで組んだもの）を起こす。
  待ち受けは `tools/ports.sh` の `ASHIATO_HTTP_PORT + 1`（縦串の 2 つ目のサーバと同じ番号。縦串と e2e は同時に走らない）、DB は stack と同じ DB に実行時の役割で繋ぐ。
  設定のファイルは試験ごとに `$TMPDIR` に作り、照らす値は試験用の固定の合言葉から作った PHC 文字列（台本が持つ。`tools/check-secrets.sh` が拾うなら許可の表に足す）
- e2e（`web/e2e/st59-change-secrets.spec.ts`）は、この台本で起こしたサーバの組み込みの画面を開く。開発の形の断り（409）だけは、共有の stack のサーバで見る（何も変わらないので、ほかの spec を壊さない）

反転条件: ST60 が Linux の配る形に設定のファイルから起こす口を作ったら、台本をその口に替える。`ASHIATO_HTTP_PORT + 1` が e2e と同時に走る台本と取り合うと分かったら、台帳（`ports.sh`）に名前を足して割り当てる。

### D9（仮）. 読み出しの記録は、口ごとに 1 求め 1 行。結果の語は今あるものを使い、移行を足さない（C1）

- 口の名前は `/web-password` と `/collector-token`。middleware を素通しし（`/session`・`/collector-setup` と同じ）、ハンドラが結果どおりに 1 行書く
- 結果の語（`outcome`）は今の CHECK の中から選ぶ: 変えた → `ok`（状態 204 / 200）、ログインの印が無い → `unauthorized`（401）、失敗の数えで断った → `login_throttled`（429）、
  それ以外の断り（今の合言葉の違い 403・API の合言葉と衛星 403・検査 400・開発の形 409・書けない 500・本文が JSON でない 415）→ `forbidden` と実際の状態。どの断りかは状態の列で分かる
- 断る行は応答の前に書き、書けなければ 500（ST56 と同じ）。**変えた行（`ok`）は、`LOGIN_CHECK` を持ったまま、設定のファイルへ書き戻す前に書く。書けなければ何も変えずに 500**（正典の「書けなければ返さない」と ST56 の形に合わせる。変えたのに行が無い、を作らない）。
  行を書いた後に書き戻しで落ちたら、差し替えず、結果 `forbidden`・状態 500 の打ち消しの行を足して 500 を返す（その求めは 2 行になる。行が多い側に倒し、欠けない。review/spec.md R2）
- 語と状態の対応は spec の「誰がいつ読んだかを…」の本文に写した

反転条件: 断りの種類を語で分けたくなったら、CHECK に語を足す移行を作る（`migrations/ORDER` の末尾）。打ち消しの行が読み手を誤らせると分かったら、`ok` と打ち消しを 1 行にまとめる語を移行で足す。

### D10（仮）. 口と本文の形

- `POST /web-password`: 本文 `{"password": "<今>", "new_password": "<新>", "confirmation": "<もう一度>"}`。成功は 204 と新しい印の `Set-Cookie`
- `POST /collector-token`: 本文 `{"password": "<今>"}`。成功は 200 と `{"token": "<新しい値>"}`
- 断り: 401 `unauthorized`（本文は今のログインの口と同じ文字列）・403 `{"error": "wrong_password"}`（今の合言葉の違い）・403 `forbidden`（API の合言葉・衛星）・400 `{"error": "<理由>"}`・409 `{"error": "not_changeable"}`・415・429・500 `{"error": "not_saved"}`
- 本文が JSON と名乗らない求めは 415（ログインの口と同じ。よそのサイトの単純な送信を受けない）。2 つの口は API の合言葉の許可の一覧に入れない
- `utoipa` の注釈を付け、`docs/openapi.json` を作り直す

反転条件: 画面の実装で本文の形が足りないと分かったら変える（外の利用者はいない）。

### D11（仮）. 画面の節と文言

- `SettingsView.tsx` の「収集アプリの設定」（ST56）のすぐ下に、「画面の合言葉を変える」「収集アプリの値を変える」の 2 つの節を、それぞれ別の部品（`WebPasswordChangePanel.tsx`・`CollectorTokenChangePanel.tsx`）で置く。
  2 つの節の上に「携帯を落としたときは両方を変える（画面の合言葉 → 収集アプリの値の順）」の 1 行を置く。部品の形は `CollectorSetupPanel.tsx` と同じ（`sectionStyle`・`inputStyle`・`primaryStyle`・`FOCUS_ATTR`）
- 入力欄は `type="password"`・`autoComplete`（今は `current-password`、新しいものは `new-password`）。押したら入力欄を空にする
- 文言（`messages.ts`）: 変えた「合言葉を変えました。ほかの端末のログインは切れました」/ 今の合言葉の違い「合言葉が違います」/ 検査「16 文字以上にしてください」「change-me で始めないでください」「収集アプリの値と同じにしないでください」「ログインの印の鍵と同じにしないでください」「2 つの新しい合言葉が一致しません」/
  開発の形「この形のサーバでは画面から変えられません。.env を書き換えて起動し直してください」/ 書けない「保存できませんでした。合言葉は変わっていません」（値の節は「値は変わっていません」）/ 429「失敗が続いたので、しばらく待ってから試してください」/ それ以外「変えられませんでした」
- 新しい値の設定の文字列は、ST56 と同じく別の画面へ移る・読み込み直すと消す（部品の状態に持つだけで、保存しない）

反転条件: 確認バッチで並びや文言に違和感が返ったら直す（Q2 の答えが「まとめの操作」なら節の数を変える）。

### D12. 合言葉を変えた後の画面の印の受け渡し

変えた応答の `Set-Cookie` は、ログインの口と同じ形（`HttpOnly; Secure; SameSite=Strict; Path=/; Max-Age=…`）。最も外側の層（`refresh_cookie`）は、応答がもう `Set-Cookie` を持つので寿命の出し直しを付けない（ST28 final review R2 と同じ規則）。
変える前の印の行は消さない（`secret_tag` が合わないので通らない。行は追記のみの扱いのまま）。

## Risks / Trade-offs

- [書き戻しに失敗した求めは、読み出しの記録に `ok` と打ち消しの 2 行が残る（D9）] → 打ち消しの行が同じ口・続く時刻で並ぶ。行が欠けるより読み手に優しい
- [インストーラの `password` が、サーバの書いた `server.json` に届かない（premises 5 行目。D5）] → Windows の CI の通しで確かめ、届かなければこの Story でインストーラの一時の書きを直す

- [収集アプリの値を変えると、全部の収集アプリが貼り直すまで送れない] → FR-128 ★ 2026-11-02 の帰結として本人が受け入れている。記録は溜まり、1 時間で知らせが出る（携帯は 90 日の上限）
- [衛星の資格情報は変わらない] → 今は衛星の求めがどれも断られるので害が無い。ST38 へ申し送り済み
