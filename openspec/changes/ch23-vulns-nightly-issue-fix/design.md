# CH23 の設計

軽い路（`reason: bug`）。決めることは、知らせの段が落ちた夜にどう知らせるかと、その範囲。どれも台本と workflow の書き直しで戻る（`loss` なし）。
本人の決定（受け皿の依頼 #333 の「議論で決めたこと」）: 空の文字を空の一覧とみなす・偽の `gh` を本物に合わせる・赤が届かなかった理由を調べて届く形にする・
見つかった当たりの処置はしない・ラベルが無い状態でも動くことを試験で確かめる。

## Context

- 調べたこと（`premises.md`）: 9 晩の赤は、予定した workflow の失敗の知らせとして cron を最後に変えた人（本人）に送られていた見込み。届いたか・埋もれたか・知らせの設定は確かめていない
- 勧告が残る夜は `vulns`・`pg-minor` の job が毎晩赤（11-19 の run も、issue が立った後で赤）。「赤」は「知らせが壊れた」とも「勧告がある」とも読め、知らせとして区別できない
- 本人はこのリポジトリを watch していない（`premises.md`。2026-11-20 に実物で確かめた）。#334〜#337 は立ったが、本人に知らせは届いていない見込み。issue を立てるだけでは届かない

## Decisions

### D1（仮）. 空の文字を空の一覧とみなすのは、実測した `label list` だけ

`gh_json` に「空なら空の一覧」の扱いを渡せるようにし、`label list` で使う（振る舞いは specs の「gh がラベルの一覧に空の文字で答えたら、ラベルが無いと読む」）。
`issue list` は当てはまるものが無くても `[]` を返すと実測したので、扱いを変えない（`premises.md`）。
偽の `gh` は実測した返し方だけに合わせる: `label list` は無いとき空の文字、`issue list` は `[]` のまま。`label create` の出力は読まないので変えない。
反転条件: `gh` の版が上がって別の問い合わせも空の文字を返すと分かったら（毎晩の知らせの issue が立つ）、その問い合わせにも同じ扱いを足す。

### D2（仮）. 知らせの段が落ちた夜は、ラベル無しの決まった題の issue 1 件で知らせる

`issues` の job の `file-issues` の段に `id: file` を付け、次に `if: failure() && steps.file.outcome == 'failure'` の段で
`tools/check-vulns.sh report-unfiled "$GITHUB_SERVER_URL/$GITHUB_REPOSITORY/actions/runs/$GITHUB_RUN_ID"` を走らせる（`GH_TOKEN: ${{ github.token }}`）。
`report-unfiled` は、開いた issue を `--state open --limit 1000 --json number,title` で読んで同じ題を探す（件数の上限の確かめはしない。開いた issue が 1000 件を越えると知らせの issue を見落として立て直しうるが、重複が増えるだけで知らせは届く側に倒れる）。
落ちた run ごとに追記する（同じ日の重複を省かない。手動の起動で 2 回落ちたら 2 回知らせる）。本文・ラベル・使い方の振る舞いは specs の Requirement が持つ。落ちた原因の文は本文に書かない（`gh` の stderr を公開の issue に写さない。原因は run のログにある）。
ラベルを使わないのは、今回落ちたのがラベルの問い合わせだったから（同じ所で落ちる経路は知らせにならない）。
`issues` の job の外（別の job・別の workflow）には置かない（正典の「`issues: write` を持つ job は 1 つだけ」を変えない）。
反転条件: 確認バッチで、Actions が立てた issue の知らせが本人に届いていない（#334〜#337 を知らなかった）と分かったら、issue では足りないので
別の経路（ハーネスの操作盤など。この change のパスの外）を通常の路の change で決める。`gh` そのもの・権限が壊れた夜はこの段も落ちる（赤だけが残る）。

### D3（仮）. 検査できなかった夜（rc=2）は、正典のとおり issue を立てない

正典の Requirement「勧告を問い合わせられなければ、通さずに「検査できなかった」で落ちる」は「rc=2 のとき、毎晩の検査は issue を立てない（Actions の赤だけで知らせる）」と言う。
これを変えるのは `MODIFIED`（振る舞いを変える）で、軽い路の外。`report-unfiled` は `file-issues` の段が落ちたときだけ走り、材料の無い夜は `file-issues` を走らせない（今の workflow のまま）ので、rc=2 の夜には走らない。
残るもの: osv.dev や版の一覧に何晩も届かないと、その間は赤だけで、本人に届かないことがある。PR 本文と `docs/changes/CH23.md` に残るものとして書く。
反転条件: 本人が rc=2 の夜も issue で知りたいなら、正典を変える change（通常の路）で扱う。

### D4（仮）. job の赤・緑の付き方は変えない

勧告が残る夜に `vulns`・`pg-minor` が赤になるのは今のまま（赤を緑にするのは、正典の「rc=1 で終わる」の workflow での見え方を変える）。知らせは issue で届ける。
反転条件: 赤が多すぎて本当に壊れた夜を見分けられないと本人が言ったら、別の change で job の色の意味を決める。

### D5（仮）. 毎晩の検査が立てる issue には、リポジトリの持ち主を担当者として付ける

`file-issues` と `report-unfiled` が新しく立てる issue に、`--assignee "$GITHUB_REPOSITORY_OWNER"`（Actions の既定の環境変数。手元では渡さなければ付けない）を付ける。
担当者は watch に依らず知らせを受ける（参加している人になる）と見込む。watch していない本人に届く、この change のパスの中で取れる経路はこれだけ。
本人にリポジトリ全体を watch してもらう案は、ハーネスの PR・issue の知らせ全部が届くようになり、毎晩の知らせが埋もれる（9 晩の赤と同じ型）。
既に開いている issue（#334〜#337）に追記するときは担当者を足さない（追記は開いた issue の今の担当者・購読者に届く。#334〜#337 は本人が手で担当にすれば届く）。
担当者つきの `issue create` が落ちたときは、担当者を外して 1 回だけ立て直す（担当者 1 つで、その夜の issue が全部立たない落ち方を足さない。知らせの段も同じ `--assignee` を付けるので、そこで拾うことはできない）。立て直しも落ちたら、今のとおり rc=2。
反転条件: 確認バッチで担当者にしても知らせが届かないと分かったら、担当者を外し、別の経路（ハーネスの操作盤など。この change のパスの外）を通常の路の change で決める。

## Risks

- `report-unfiled` も `gh` を使う。`gh` そのもの・`GH_TOKEN` の権限・GitHub の障害で落ちる夜は、知らせの issue も立たない（D2 の残り）
- 担当者にした issue の知らせが本人に届くかは確かめていない（`premises.md` の確かさ 1）。確認バッチで聞く
- 持ち主が組織になる・担当者にできなくなると、担当者無しで立て直すので、知らせは watch している人にしか届かない（今は本人を担当者にできる。`premises.md`）
