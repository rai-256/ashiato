## Why

**Google 系の過去の行動（マップのタイムライン・YouTube・検索・Chrome）は、本人が書き出したファイルの形でしか手に入らず、しかもそのファイルは腐る。**
Takeout の書庫は約 7 日で失効してダウンロードは 5 回まで（EXT-B）、マップのタイムラインはクラウドから端末へ移り（EXT-M）、端末を替えれば消える。
いまの S-01 にはそのファイルを読む口が無く、FR-14 / FR-16 / FR-17 / FR-55 は 1 行も満たされていない。
本人の現状は「Google マップ履歴のみを月 2 回程度」（要件 §1.2）で、**置くだけで入る経路が無い間は、その手作業の結果がどこにも積まれない。**

いま作る理由は 2 つ。

1. **成功条件 2（AI に聞いて満足のいく答え）は過去の厚みで決まる。** C-01 / C-02 は今日から先しか集めない。1 年待たずに問いに答えられる材料は、手元の書庫だけ
2. **ST13（アカウント系の定期取得）が requires: ST12。** 取り込み器（C-03）の置き場・台帳・最終日の表示をここで作り、ST13 はそこに定期取得を足す

## What Changes

深掘りは **1 巡・8 問**（A 6 / B 2）。本人がすべて選択肢から明示的に選んだ（未回答 0・推奨のまま 0）。**推奨と違う側は Q1**（読む中身を 6 つすべてにした）。
独立レビュー（`deep-review`）は **11 件** —— 聞かずに決めるつもりだった鍵の作り方を問いに上げ（Q6）、問いを 2 件新設（Q7 / Q8）、Q1 を A に上げ、
扉を開けたままにする既定を 5 件足した。聞かずに決めた既定 C1〜C18 に本人の異論は無かった。

- **取り込み器（C-03）を S-01 の中に置く。** 専用のフォルダと、ブラウザのダウンロードのフォルダの `takeout-*.zip` を数分おきに見て、置かれた書庫を読む
- **読む中身は 6 つ**: 端末から書き出したマップのタイムライン（`Timeline.json`）/ 移行前の Takeout のロケーション履歴（`Records.json` / Semantic Location History）/
  YouTube の視聴履歴 / YouTube の検索履歴 / マイアクティビティ / Chrome の履歴。**製品 × 記録の種類ごとに別の論理ソース**として登録簿に入れる
- **端末からの記録と同じ格納の関門を通す**（原文はそのまま・削除済みは戻らない・利用者ごと）。**重複は同じソースの中で内容の鍵だけで判定する**（ST03 の既定のまま。FR-17 ★）
- **読んだ製品のファイルは写しを残す**（既定。設定で残さない側にできる）。**本人のファイルは消さない**（専用のフォルダの書庫は「取り込み済み」へ移す。ダウンロードのフォルダは触らない）（FR-14 ★）
- **置いた書庫ごとに追記のみの台帳**を残す（書庫の素性・読んだ時刻・解析器の版・ソースごとの入った / 既にあった / 削除済みで入れなかった / 読めなかった件数）。
  読んだ書庫は中身のハッシュと解析器の版で覚え、版が上がったときだけ読み直す
- **取り込み器は書庫のソースごとに 1 日 1 回の生存信号を送る**（置き場を読めるか。FR-78）
- **ソースごとの取り込み済み最終日**（入った記録のうちいちばん新しい出来事の日。運んだ書庫の作られた時刻も持つ）を保持する（FR-16 ★）
- **稼働状況の画面に書庫のソースの格子を出す。** Must の 5 本の後ろ・退役したソースの前に、見出しの横に「`YYYY-MM-DD` まで（N 日前）」、
  格子の群の頭に「直近に置いた書庫」1 件の結果、まだ無いソースは「まだ無い」（FR-55 ★）

**BREAKING は無い。** `/ingest` と `/heartbeat` の契約の形は変えない。稼働状況の応答に書庫のソースと最終日と直近の書庫が増える。

## Capabilities

### New Capabilities

- **`external-ingestion`** —— 取り込み待ち置き場の走査、書庫の読み取り（6 つの中身）、論理ソースの割り当て、写しと本人のファイルの扱い、書庫の台帳、
  取り込み器の生存信号、取り込み済み最終日の保持と表示（稼働状況の画面の書庫のソースの格子・直近に置いた書庫）

### Modified Capabilities

なし。**`record-envelope` と `collection-coverage` の要件は変えない**（design D13）。
書庫の記録は `record-envelope` の格納の関門をそのまま通り、生存信号と稼働状況の判定は `collection-coverage` の要件のまま使う。
画面に書庫のソースの格子を足す振る舞いは `external-ingestion` の要件として書き、`collection-coverage` の「Must の 5 ソースがひとスクロール以内」「退役したソースは後ろ」を壊さないことを Scenario に置く。

## Impact

- **移行を 1 本足す**（名前は作成時刻）: 書庫の台帳（追記のみ）・ソースごとの取り込み済み最終日・書庫のソースの登録簿の行（外部識別子の粒度は「無し」、想定間隔 60 日）
- `crates/server`: 取り込み器（置き場の走査・書庫の読み取り・6 つの解析器・写し・台帳・生存信号）を起動時の背景の仕事として足す。
  **`/ingest` の 1 件の格納（`ingest_one`）を、HTTP を経ずに呼べる形に切り出す**（判定は変えない）。
  稼働状況の応答に書庫のソースの格子・最終日・直近の書庫を足す（`coverage_get`）。OpenAPI に載せる
- `web`: 稼働状況（`App.tsx` / `CoverageGrid.tsx`）に書庫のソースの格子・見出しの最終日・直近に置いた書庫の箱
- `collector-android` / `collector-windows`: **変わらない**（Q8。運ぶ仕組みを作らない）
- `docs/`: 運ぶ手順と置き場の設定の手順書
- 要件: FR-14 / FR-16 / FR-17 / FR-55 / NFR-12 に ★、§5 に EXT-M。Story: ST12 の価値・壊してはいけないもの・完了の判定を足した（`deep.md` の「要件へ戻すもの」）
- 後続へ: **ST23**（書庫の写しも消去の対象にするか）/ **ST24**（検索語を持つソースの既定の感度）/ **ST14**（書庫のソースの途絶の数え方）/
  **ST25 / ST27**（2 経路で入る同じ出来事の読み方）/ **ST13**（Data Portability API は restricted で採らない）
