## 聞かないで決めるもの（C —— 扉を開けたままにする既定）

design の D 番号に残す。**異論があれば、答えを貼り戻すときに番号で書いてください。**

- **C1. 書庫から入るものは、既存と別の論理ソースとして、製品 × 記録の種類ごとに登録する**
  （例 `c03-youtube-watch` / `c03-timeline-visit` / `c03-timeline-activity` / `c03-timeline-path` / `c03-legacy-location`）。
  **R10** で「製品ごとに 1 本」から直した —— Timeline.json は訪問・移動・経路の点が混ざり、FR-23 は性質の違う記録が混ざるソースを分けると決めている。
  論理ソースは冪等の鍵の入力で凍結される（`gates.sql:59`）ので、**混ぜた行は後から分けられないが、分けた行は読むときに合わせられる**（細かい粒度で持つ）。
  マップのタイムラインを携帯端末の位置（`c01-location`）に混ぜると、収集開始日（FR-79）が何年も遡って NFR-13 の窓が閉じ、
  滞在の導出（ST16）が Google の推定を自前の観測と区別できなくなる
- **C2. 地域（FR-20）は取得元が示したとおりに持ち、推定しない。**
  Timeline.json は時刻にずれ（`+09:00`）を持つのでそれを使う。YouTube / マイアクティビティの JSON は UTC（`Z`）しか持たないので
  ずれ 0・識別子 `UTC` として持ち、「取得元が地域を持たなかった」を解析済みの内容に印として残す。
  **R11** で理由を直した —— 地域の列は凍結されていない（`gates.sql:66-70`）ので後から直せるが、**推定した値と取得元の値を見分ける印が無いと、どれを直すべきか分からなくなる**。
  凍結されるのは出来事の時刻の側で、**UTC の瞬間の読み方を誤ると直せない**（ずれの無い時刻を地方時として読まない）
- **C3.（Q6 へ移した）** 時刻と対象から鍵を作る案は、独立レビュー **R1** の指摘で問いに上げた。本人は内容の鍵だけを選んだ
