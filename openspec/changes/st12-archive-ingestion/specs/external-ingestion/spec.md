## Purpose

本人が外部サービスから書き出したファイル（Takeout の書庫・端末から書き出したマップのタイムライン）を、置き場に置くだけで記録にする。
書き出したファイルは失効し端末から消えるので、**置いた時点で読み、読めなかったことも含めて残す**。取り込み済みの最終日を保持して画面に出す。

## ADDED Requirements

### Requirement: 取り込み待ち置き場に置かれた書庫を読む

WHEN 取り込み待ち置き場に書庫が置かれる THE SYSTEM SHALL その書庫を読み、中身から記録を生成する。
THE SYSTEM SHALL 取り込み待ち置き場を、**専用のフォルダ**と、**ブラウザのダウンロードのフォルダのうち名前が `takeout-` で始まり `.zip` で終わるファイル**の 2 つとする。
THE SYSTEM SHALL 専用のフォルダでは、`.zip` の書庫と `.json` のファイル（端末から書き出したタイムライン・移行前のロケーション履歴）を読む。
THE SYSTEM SHALL ダウンロードのフォルダでは、`takeout-*.zip` 以外のファイルを読まず、台帳にも残さない。
THE SYSTEM SHALL 置き場を一定の間隔で見に行き、**読んでいる書庫が無いとき、置かれてから 10 分以内**に読み始める。
WHILE 別の書庫を読んでいる THE SYSTEM SHALL 置かれた書庫を見つけた順に並べ、読み終えたら続けて読む。
THE SYSTEM SHALL 大きさが変わり続けているファイルと、ブラウザの書き込み途中のファイル（`.crdownload` / `.part` / `.tmp`）を読まない。
THE SYSTEM SHALL Takeout の分割書庫（`-001.zip` / `-002.zip` …）を、揃うのを待たずに 1 本ずつ読む。
THE SYSTEM SHALL 専用のフォルダに置かれた、読めない形のファイル（`.tgz` など）を、**読めなかった書庫として台帳に残す**（黙って無視しない）。

導出元: FR-14, NFR-12。深掘り Q3 / C6 / C7 / C8。
**書庫は約 7 日で失効する**（EXT-B）ので、置いたのに入っていないことが画面から分からないと、気づいたときには取り直せない。
ダウンロードのフォルダを見るのは、Takeout を**ダウンロードするだけで入る**ようにするため（本人の決定）。

#### Scenario: 専用のフォルダに置いた書庫が読まれる

- **WHEN** 形の確認の印を置いた後に、専用のフォルダに YouTube の視聴履歴を含む Takeout の書庫を置き、10 分待つ
- **THEN** その書庫の視聴履歴が記録として格納されている

#### Scenario: ダウンロードのフォルダの Takeout の書庫が読まれる

- **WHEN** 形の確認の印を置いた後に、ダウンロードのフォルダに `takeout-20260913T041200Z-001.zip` を置き、10 分待つ
- **THEN** その書庫の中身が記録として格納されている

#### Scenario: ダウンロードのフォルダの他のファイルは読まれない

- **WHEN** ダウンロードのフォルダに `photos.zip` と `Timeline.json` を置き、10 分待つ
- **THEN** どちらからも記録は格納されず、台帳にも行が増えない

#### Scenario: 端末から書き出したタイムラインを専用のフォルダに置くと読まれる

- **WHEN** 専用のフォルダに端末から書き出した `Timeline.json` を置き、10 分待つ
- **THEN** その訪問・移動・経路の点が記録として格納されている

#### Scenario: 書き込み途中のファイルは読まれない

- **WHEN** ダウンロードのフォルダに `takeout-20260913T041200Z-001.zip.crdownload` がある
- **THEN** そのファイルは読まれない

#### Scenario: 名前が書き込み途中でなくなったファイルは読まれる

- **WHEN** 形の確認の印を置いた後に、`takeout-20260913T041200Z-001.zip.crdownload` の名前が `takeout-20260913T041200Z-001.zip` に変わり、大きさが変わらなくなる
- **THEN** そのファイルの中身が格納される

#### Scenario: 既定の間隔でも置かれてから 10 分以内に読み始める

- **WHEN** 走査の間隔を既定のままにし、読んでいる書庫が無いときに、走査の直後に書庫を置く
- **THEN** 置いてから 10 分以内にその書庫を読み始める

#### Scenario: 読んでいる間に置いた書庫は読み終えた後に読まれる

- **WHEN** 大きな書庫を読んでいる間に、別の書庫を置く
- **THEN** 大きな書庫を読み終えた後、次の書庫が読まれる

#### Scenario: 大きさが変わり続けているファイルは読まれない

- **WHEN** 専用のフォルダのファイルに書き込みが続いていて、見に行くたびに大きさが変わる
- **THEN** 大きさが変わらなくなるまで読まれない

#### Scenario: 分割書庫は 1 本ずつ読まれる

- **WHEN** 形の確認の印を置いた後に、`-001.zip` だけを置き、`-002.zip` を置かない
- **THEN** `-001.zip` の中身は格納されている

#### Scenario: 読めない形の書庫は台帳に残る

- **WHEN** 専用のフォルダに `takeout-20260913T041200Z-001.tgz` を置く
- **THEN** 台帳にその書庫が「読めなかった」として残り、理由の種別が示される

### Requirement: 読む中身は 6 つで、製品と記録の種類ごとに別の論理ソースに入る

THE SYSTEM SHALL 書庫の中の次の 6 つを読む ——
端末から書き出したマップのタイムライン（`Timeline.json`）/ 移行前の Takeout のロケーション履歴（`Records.json` と Semantic Location History）/
YouTube の視聴履歴 / YouTube の検索履歴 / マイアクティビティ（製品ごとのファイル）/ Chrome の履歴。
THE SYSTEM SHALL 記録を、**製品と記録の種類ごとに別の論理ソース**に入れる（タイムラインなら訪問・移動・経路の点を別にする）。
THE SYSTEM SHALL 書庫の記録を、携帯端末の位置・PC のブラウザ履歴など、**書庫以外から集める論理ソースに入れない**。
THE SYSTEM SHALL 書庫の記録を「収集した」に分類する（Google が推定した訪問と移動を含む）。
THE SYSTEM SHALL 書庫の論理ソースを、成功条件 1（NFR-13）の 5 ソースに含めない。
THE SYSTEM SHALL 書庫の中の、この 6 つに当たらないファイルを読まず、**台帳にファイルの数だけを残す**。
THE SYSTEM SHALL マイアクティビティと YouTube の履歴を JSON の形で読む。
THE SYSTEM SHALL HTML の形のファイルを、**同じ製品の JSON が同じ書庫に無いとき**は読めなかったものとして、**あるとき**は読まなかったファイルとして台帳に残す。

導出元: FR-14, FR-24, FR-25, FR-22, NFR-13。深掘り Q1 / C1 / C11 / R10。
**論理ソースは冪等の鍵の入力で、収集した行では書き換えられない** —— 混ぜた行は後から分けられないが、分けた行は読むときに合わせられる。
携帯端末の位置に混ぜると、収集開始日（FR-79）が何年も遡って成功条件 1 の窓が閉じ、滞在の導出が Google の推定を自前の観測と区別できない。

#### Scenario: タイムラインの訪問と経路の点は別の論理ソースに入る

- **WHEN** 訪問 1 件と経路の点 3 件を含む `Timeline.json` を置く
- **THEN** 訪問と経路の点は、異なる 2 つの論理ソースに格納されている

#### Scenario: 書庫の位置は携帯端末の位置に入らない

- **WHEN** 移行前のロケーション履歴を含む書庫を置く
- **THEN** 携帯端末の位置の論理ソースの記録の件数は変わらない

#### Scenario: 書庫の位置は携帯端末の位置の収集開始日を動かさない

- **WHEN** 携帯端末の位置の収集開始日より 5 年古い点を含む移行前のロケーション履歴を置く
- **THEN** 携帯端末の位置の収集開始日は変わらない

#### Scenario: 6 つの中身がそれぞれ読まれる

- **WHEN** 形の確認の印を置いた後に、YouTube の視聴履歴・YouTube の検索履歴・マイアクティビティ（検索）・Chrome の履歴を含む Takeout の書庫と、`Timeline.json` と、`Records.json` を置く
- **THEN** 6 つの中身のそれぞれから、少なくとも 1 件の記録が格納されている

#### Scenario: 書庫の記録は収集したに分類される

- **WHEN** Google が推定した訪問を含む `Timeline.json` を置く
- **THEN** その訪問の記録の由来の分類は「収集した」である

#### Scenario: 書庫の論理ソースは成功条件 1 の達成に数えられない

- **WHEN** 書庫の記録が格納された後に、成功条件 1 の達成を読み出す
- **THEN** 達成の対象は Must の 5 ソースのままである

#### Scenario: 対象でないファイルからは記録が作られない

- **WHEN** 形の確認の印を置いた後に、Google フォトの写真 2 枚と YouTube の視聴履歴を含む書庫を置く
- **THEN** 写真からは記録が作られない

#### Scenario: 対象でないファイルは数だけ台帳に残る

- **WHEN** Google フォトの写真 2 枚と YouTube の視聴履歴を含む書庫を置く
- **THEN** 台帳のその書庫の行に、読まなかったファイルが 2 件と残る

#### Scenario: HTML のマイアクティビティは読めなかったものとして残る

- **WHEN** マイアクティビティを HTML の形だけで含む書庫を置く
- **THEN** そのファイルからは記録が作られず、台帳に読めなかったものとして残る

#### Scenario: JSON と同居する HTML は読まなかったに数える

- **WHEN** 形の確認の印を置いた後に、同じ製品の JSON と HTML の両方を含む書庫を置く
- **THEN** JSON から記録が作られ、台帳の読めなかった件数は 0、読まなかったファイルに HTML が数えられる

### Requirement: Takeout の書庫の中身は、形の確認の印を置くまで格納しない

THE SYSTEM SHALL Takeout の書庫の中身（YouTube の視聴履歴・検索履歴・マイアクティビティ・Chrome の履歴）を、**利用者が形の確認の印を置くまで記録として格納しない**。
THE SYSTEM SHALL 確認を待っている書庫を台帳に「形の確認待ち」として残し、その書庫の読んだ製品のファイルの**写しを、写しの設定に関わらず作る**。
THE SYSTEM SHALL 形の確認のために、書庫の中のファイルの種類・最上位の鍵・項目の欄の名前・件数・製品の名前の種類だけを出す手段を用意し、**記録の値（題名・URL・検索語・座標）を出さない**。
WHEN 利用者が形の確認の印を置く THE SYSTEM SHALL 確認を待っていた書庫を写しから読み直して格納する。
THE SYSTEM SHALL 形を、**振り分けを決めるもの**（ファイルをどの中身と見分けたか・マイアクティビティの製品の名前）だけで比べ、項目の欄の名前・書庫の中のパスの名前の違いでは確認待ちにしない。
WHEN 後から置かれた書庫のファイルに、**印を置いた形に無い製品の名前**がある THE SYSTEM SHALL そのファイルだけをまた確認待ちにし、同じ書庫の他のファイルは格納する（★ 第 3 回 Q12 で本人に確かめている。design D16）。
THE SYSTEM SHALL 確認待ちの書庫について、1 回の読みに台帳の行を 1 つだけ足し、置き場に残り続けても走査のたびに行を足さない。
WHEN 印を置く THE SYSTEM SHALL 確認待ちだった書庫を、同じ中身・同じ解析器の版でも読み直し、台帳に読み直した行を 1 つ足す。
THE SYSTEM SHALL 端末から書き出したタイムラインと移行前のロケーション履歴を、確認を待たずに格納する。

導出元: FR-14, FR-22, FR-23。深掘り 第 2 回 Q10（本人の決定）/ spec R12 / deep-r2 R5 / R6。
**書庫の中身を振り分ける論理ソースは、格納した時点で書き換えられない。** 振り分けの規則が本物の書庫で外れていたと分かっても、既に入った行は直せない。
写しを設定に関わらず作るのは、写しを残さない設定のとき確認待ちの書庫が読み直せなくなるのを防ぐため。

#### Scenario: 印を置く前の Takeout の書庫は格納されない

- **WHEN** 形の確認の印を置く前に、YouTube の視聴履歴・YouTube の検索履歴・マイアクティビティ・Chrome の履歴を含む Takeout の書庫を置く
- **THEN** タイムラインと移行前のロケーション履歴のほかの、書庫の論理ソースに記録が 1 件も格納されない

#### Scenario: 確認待ちの書庫は走査を重ねても台帳の行が増えない

- **WHEN** 形の確認の印を置く前にダウンロードのフォルダに Takeout の書庫を置き、走査が 3 回来る
- **THEN** 台帳のその書庫の行は 1 つである

#### Scenario: 印を置く前の書庫は確認待ちとして台帳に残る

- **WHEN** 形の確認の印を置く前に Takeout の書庫を置く
- **THEN** 台帳にその書庫が「形の確認待ち」として残る

#### Scenario: 確認待ちの書庫は写しを残さない設定でも写される

- **WHEN** 写しを残さない設定で、形の確認の印を置く前に Takeout の書庫を置く
- **THEN** その書庫の読んだ製品のファイルの写しがある

#### Scenario: 形の確認の出力に記録の値が出ない

- **WHEN** 検索語「京都 旅館」を含む書庫の形を出す
- **THEN** 出力に「京都 旅館」の文字列が無い

#### Scenario: 形の確認の出力に見分けた中身と製品の名前と件数が出る

- **WHEN** マイアクティビティ（製品「検索」）を含む書庫の形を出す
- **THEN** 出力に、マイアクティビティと見分けたこと・製品の名前「検索」・件数が出る

#### Scenario: 印を置くと確認待ちの書庫が格納される

- **WHEN** 確認待ちの書庫がある状態で形の確認の印を置く
- **THEN** その書庫の中身が記録として格納される

#### Scenario: 印を置いた後の読み直しは台帳に 1 行足す

- **WHEN** 確認待ちの書庫がある状態で形の確認の印を置き、読み直しが終わる
- **THEN** 台帳にその書庫の読み直した行が 1 つ増える

#### Scenario: 知らない製品のマイアクティビティはまた確認待ちになる

- **WHEN** 印を置いた後に、印を置いた形に無い製品の名前を含むマイアクティビティと、YouTube の視聴履歴を含む書庫を置く
- **THEN** そのマイアクティビティのファイルは確認待ちになる

#### Scenario: 知らない製品があっても同じ書庫の他のファイルは格納される

- **WHEN** 印を置いた後に、印を置いた形に無い製品の名前を含むマイアクティビティと、YouTube の視聴履歴を含む書庫を置く
- **THEN** 視聴履歴は格納される

#### Scenario: 欄の名前が増えただけでは確認待ちにならない

- **WHEN** 印を置いた後に、印を置いたときより項目の欄が 1 つ多い YouTube の視聴履歴を含む書庫を置く
- **THEN** その視聴履歴は格納される

#### Scenario: タイムラインは確認を待たない

- **WHEN** 形の確認の印を置く前に `Timeline.json` を置く
- **THEN** その訪問が記録として格納される

### Requirement: 書庫の記録は原文を切り出したまま持ち、取得元の示した地域で時刻を持つ

THE SYSTEM SHALL 記録 1 件の原文を、**ファイルのバイト列からその項目の範囲をそのまま切り出したもの**とする（解析して直列化し直さない）。
THE SYSTEM SHALL 出来事の時刻の地域を、取得元が示したとおりに持つ —— 時刻が UTC からのずれを持てばそのずれを、持たなければずれ 0 と `UTC` を。
THE SYSTEM SHALL 取得元が地域を持たなかった記録に、**そのことを示す印**を解析済みの内容に持たせる。
THE SYSTEM SHALL 地域を位置や本人の居住地から推定して記録に書かない。
THE SYSTEM SHALL 書庫の記録に、**それを最初に運んだ書庫のハッシュ**を解析済みの内容に持たせる。

導出元: FR-18, FR-20, FR-24。扉 #6 / #7。深掘り C2 / C15 / C16 / R3 / R11。
直列化し直すと、元のバイト列は書庫を消した時点で戻らない。切り出したバイト列は後からいつでも直列化し直せる。
推定した地域と取得元の地域を見分ける印が無いと、後から直すときに**どれを直すべきか分からない**。

#### Scenario: 原文は書庫のバイト列の一部と一致する

- **WHEN** 形の確認の印を置いた後に、字下げと改行を含む YouTube の視聴履歴のファイルを置く
- **THEN** 各記録の原文は、そのファイルのバイト列の連続した一部とバイト単位で一致する

#### Scenario: ずれを持つ時刻はそのずれで残る

- **WHEN** 開始の時刻が `+09:00` のずれを持つ訪問を含む `Timeline.json` を置く
- **THEN** その記録の UTC からのずれは 540 分である

#### Scenario: UTC しか持たない時刻は UTC で残る

- **WHEN** 形の確認の印を置いた後に、時刻が `Z` で終わる YouTube の視聴履歴を置く
- **THEN** その記録の UTC からのずれは 0、タイムゾーン識別子は `UTC` である

#### Scenario: UTC しか持たない時刻には取得元が地域を持たなかった印が付く

- **WHEN** 形の確認の印を置いた後に、時刻が `Z` で終わる YouTube の視聴履歴を置く
- **THEN** 解析済みの内容に、取得元が地域を持たなかった印がある

#### Scenario: 地域は位置から推定されない

- **WHEN** 形の確認の印を置いた後に、同じ時刻にニューヨークにいたことを示すタイムラインが既に格納されている状態で、時刻が `Z` で終わる YouTube の視聴履歴を置く
- **THEN** その視聴の記録のタイムゾーン識別子は `UTC` である

#### Scenario: 記録から運んだ書庫が分かる

- **WHEN** 形の確認の印を置いた後に、書庫を置いて記録が格納される
- **THEN** 各記録の解析済みの内容に持たせた書庫のハッシュが、台帳のその書庫の行のハッシュと一致する

### Requirement: 書庫の記録は端末からの記録と同じ関門を通り、同じソースの中の内容の鍵で重複を判定する

THE SYSTEM SHALL 書庫の記録を、端末からの記録と**同じ格納の判定**（登録簿・値の妥当性・重複・削除済み・書き換えの禁止）を通して格納する。
THE SYSTEM SHALL 書庫の論理ソースを、外部サービス上の識別子を**持たない**ソースとして登録簿に宣言する。
THE SYSTEM SHALL 書庫の記録の重複を、**同じ利用者・同じ論理ソースの中で内容の鍵によって**判定する。
THE SYSTEM SHALL 次の書庫で同じ出来事が異なる内容で出てきたとき、**既存の記録を書き換えず、別の記録として格納する**。
THE SYSTEM SHALL 論理ソースをまたいで記録を突き合わせて、格納を取りやめない。
THE SYSTEM SHALL 削除済みの記録と同じ内容を、古い書庫からも新しい書庫からも格納しない。

導出元: FR-17, FR-22, FR-23, FR-50, FR-30。深掘り Q6 / C10。
**時刻と対象から鍵を作る形は本人が採らなかった** —— 鍵は格納した時点で凍結されるので作り方を後から変えられず、
書庫の作られた時刻で古い到着を止めると古い書庫の内容の違う版が捨てられる。内容の鍵だけなら何も捨てず、増えた行は読む側で畳める。

#### Scenario: 同じ書庫をもう一度置いても行が増えない

- **WHEN** 形の確認の印を置いた後に、書庫を置いて格納された後、同じ書庫をもう一度置く
- **THEN** 記録の件数は変わらない

#### Scenario: 同じ出来事を含む別の書庫を置いても行が増えない

- **WHEN** 形の確認の印を置いた後に、2026-07 に作られた書庫を置いた後、同じ視聴を同じ内容で含む 2026-09 に作られた書庫を置く
- **THEN** その視聴の記録は 1 件のままである

#### Scenario: 題名が変わった同じ視聴は別の記録として残る

- **WHEN** 形の確認の印を置いた後に、ある視聴を含む書庫を置いた後、同じ時刻・同じ動画で題名だけが異なる視聴を含む書庫を置く
- **THEN** その視聴の記録は 2 件になり、どちらの原文も残っている

#### Scenario: 古い書庫を後から置いても新しい記録は書き換わらない

- **WHEN** 形の確認の印を置いた後に、2026-09 に作られた書庫を置いた後、同じ視聴を異なる内容で含む 2024-07 に作られた書庫を置く
- **THEN** 2026-09 の書庫から入った記録の内容は変わらない

#### Scenario: 消した記録は書庫を置き直しても戻らない

- **WHEN** 形の確認の印を置いた後に、書庫から入った記録を削除した後、同じ書庫をもう一度置く
- **THEN** その記録は削除済みのままで、同じ内容の生きた記録は増えない

#### Scenario: 消した記録は別の書庫からも戻らない

- **WHEN** 形の確認の印を置いた後に、書庫から入った記録を削除した後、その記録と同じ内容を含む、中身の違う別の書庫を置く
- **THEN** 同じ内容の生きた記録は増えない

#### Scenario: 書庫の位置と端末の位置が同じでも取りやめない

- **WHEN** 携帯端末の位置の記録と同じ時刻・同じ座標の点を含む `Records.json` を置く
- **THEN** その点は書庫の論理ソースに格納される

### Requirement: 1 件が読めなくても書庫の残りを読む

WHEN 書庫の中の 1 件の項目が読めない THE SYSTEM SHALL その項目を飛ばして残りを読み続ける。
THE SYSTEM SHALL 読めなかった項目の件数と場所（書庫の中のファイル名と、ファイルの中の位置）を台帳に残す。
THE SYSTEM SHALL 1 件の格納がサーバの失敗で落ちたとき、その書庫を**読み終えたものとして覚えない**（次の走査で読み直す）。
WHEN 同じ書庫の読み取りがサーバの失敗で続けて 3 回中断する THE SYSTEM SHALL 台帳に「格納に失敗した」書庫として 1 行残し、
以後は 1 時間に 1 回だけ読み直す（読み終えたら通常の行を残す）。

導出元: FR-14。深掘り C4。
書庫全体を落とすと、1 件の壊れた項目のために残りの全部が入らない。読み終えたと覚えると、失敗した分が永久に入らない。

#### Scenario: 壊れた 1 件があっても残りは格納される

- **WHEN** 形の確認の印を置いた後に、視聴履歴 10 件のうち 1 件の時刻が壊れている書庫を置く
- **THEN** 残りの 9 件が格納されている

#### Scenario: 壊れた 1 件の場所が台帳に残る

- **WHEN** 形の確認の印を置いた後に、視聴履歴 10 件のうち 1 件の時刻が壊れている書庫を置く
- **THEN** 台帳のその書庫の行に、読めなかった項目が 1 件と、そのファイル名とファイルの中の位置が残る

#### Scenario: 格納に続けて失敗した書庫は台帳と画面に出る

- **WHEN** 同じ書庫の読み取りが D-01 の失敗で 3 回続けて中断する
- **THEN** 台帳にその書庫が「格納に失敗した」として 1 行残り、稼働状況の「直近に置いた書庫」にそのことが文字で出る

#### Scenario: 格納が落ちた書庫は次の走査で読み直される

- **WHEN** 書庫を読んでいる途中で D-01 への接続が切れ、その後つながる
- **THEN** 次の走査でその書庫が読み直され、全件が格納されている

### Requirement: 本人のファイルは消さず、読んだ製品のファイルの写しを残す

THE SYSTEM SHALL 置き場にある本人のファイルを、**読んだ後も消さない**。
THE SYSTEM SHALL 専用のフォルダの書庫を、読み終えたら専用のフォルダの中の「取り込み済み」へ移す。
THE SYSTEM SHALL 「取り込み済み」に同じ名前のファイルがあるとき、上書きせずに名前の後ろに番号を付けて移す。
THE SYSTEM SHALL ダウンロードのフォルダのファイルを、読んだ後も**動かさない**。
THE SYSTEM SHALL 書庫のうち、**読んだ製品のファイルの写し**をシステムの置き場に残す。
THE SYSTEM SHALL 写しを残すかを設定で変えられるようにし、**既定を「残す」**とする。
WHEN 設定が「残さない」である THE SYSTEM SHALL 写しを作らない。既に作った写しは消さない。
WHEN 設定が「残さない」である THE SYSTEM SHALL それでも、**形の確認を待っている書庫の写しは作り、印を置いて読み直し終えたら、その写しを消す**（本人が選んだ「写しを作らない」に戻す）。
THE SYSTEM SHALL 同じ中身のファイルの写しを 2 つ作らない。

導出元: FR-14。深掘り Q2（本人の補足: 残すか消すかを設定できるようにする、既定は残す）/ Q3 / C14 / R9 / **第 2 回 Q11（補足の「消す」は写しを作らないこと。既存は残す）**。
**写しがあれば、解析器を直して読み直せる**。本人のファイルは約 7 日で取り直せなくなるので、システムが消すと戻らない。

#### Scenario: 専用のフォルダの書庫は取り込み済みへ移る

- **WHEN** 専用のフォルダに書庫を置き、読み終わる
- **THEN** その書庫は専用のフォルダの「取り込み済み」にあり、中身のハッシュは置いたときと一致する

#### Scenario: 取り込み済みに同じ名前があっても上書きしない

- **THEN** 「取り込み済み」に 2 つのファイルがあり、元からあったファイルの中身は変わらない

#### Scenario: ダウンロードのフォルダの書庫は動かない

- **WHEN** ダウンロードのフォルダの `takeout-*.zip` が読み終わる
- **THEN** そのファイルは同じ場所に同じ中身で残っている

#### Scenario: 読んだ製品のファイルの写しが残る

- **THEN** システムの置き場に視聴履歴のファイルの写しがあり、中身が書庫の中のファイルと一致する

#### Scenario: 読まなかった製品のファイルは写されない

- **WHEN** YouTube の視聴履歴と Google フォトの写真を含む書庫を、写しを残す設定で置く
- **THEN** 写真の写しは無い

#### Scenario: 残さない設定では写しを作らない

- **WHEN** 形の確認の印を置いた後に、写しを残さない設定で書庫を置く
- **THEN** システムの置き場に写しが増えない

#### Scenario: 残さない設定でも記録は格納される

- **WHEN** 形の確認の印を置いた後に、写しを残さない設定で書庫を置く
- **THEN** 書庫の中身は記録として格納されている

#### Scenario: 確認待ちのために作った写しは読み直した後に消える

- **WHEN** 写しを残さない設定で、形の確認の印を置く前に Takeout の書庫を置き、印を置いて読み直しが終わる
- **THEN** その書庫のために作った写しは無い

- **THEN** そのファイルの写しは 1 つである

### Requirement: 読んだ書庫は中身と解析器の版で覚え、版が上がったときだけ読み直す

THE SYSTEM SHALL 読み終えた書庫を、**中身のハッシュと解析器の版**で覚える。
THE SYSTEM SHALL 覚えている書庫と同じ中身・同じ解析器の版のファイルを、置き場を見に行くたびに読み直さない。
WHEN 本人が覚えている書庫と同じ中身のファイルを置き直す THE SYSTEM SHALL 名前が同じか違うかを問わず、中身を読まず、台帳に「既に読んだ書庫」として 1 行残す。
THE SYSTEM SHALL 置き場に残り続けるファイル（ダウンロードのフォルダのファイル）について、走査のたびに台帳の行を足さない。
WHEN 解析器の版が上がる THE SYSTEM SHALL 覚えている書庫を、置き場か写しから読み直す。

導出元: FR-14, FR-17。深掘り C5 / R9。
ダウンロードのフォルダのファイルは動かさないので、覚えないと**数十 GB の書庫を数分おきに読み直し続ける**。

#### Scenario: 読んだ書庫は次の走査で読み直されない

- **THEN** その書庫は読み直されない

- **WHEN** 専用のフォルダの書庫が読み終わって取り込み済みへ移った後、同じ名前・同じ中身のファイルを専用のフォルダに置く
- **THEN** 台帳に「既に読んだ書庫」の行が 1 つ増え、そのファイルも取り込み済みへ移る

- **THEN** 台帳のその書庫の行は 1 つのままである

- **THEN** その書庫が読み直され、台帳に新しい版での行が増える

### Requirement: 置いた書庫ごとに追記のみの台帳が残る

THE SYSTEM SHALL 読んだ書庫（読めなかった書庫・既に読んだ書庫を含む）ごとに、台帳へ 1 行を足す。
THE SYSTEM SHALL 台帳の 1 行に、書庫の中身のハッシュ・名前・大きさ・作られた時刻・置き場の種類（専用 / ダウンロード）・読み始めた時刻・読み終えた時刻・解析器の版と、
**論理ソースごとの入った / 既にあった / 削除済みで入れなかった / 読めなかった件数**と、読まなかったファイルの数を持たせる。
THE SYSTEM SHALL 書庫の作られた時刻を、取得元が示せばその値（Takeout の書庫の名前の時刻）で、示さなければ**置き場で最初に見つけた時刻**で持ち、どちらかを区別できるようにする。
THE SYSTEM SHALL 台帳の行を書き換えさせず、削除させない。
THE SYSTEM SHALL 台帳に、記録の本文（題名・URL・検索語・座標）を持たせない。
THE SYSTEM SHALL 台帳の行に利用者識別子を持たせる。
THE SYSTEM SHALL 台帳の論理ソースごとの行に、**その書庫が運んだ記録のうちいちばん新しい出来事の時刻**を持たせる（入った・既にあった・削除済みで入れなかった項目を含む）。

導出元: FR-14, FR-24, FR-29。扉 #14。深掘り C16 / R4。
**書庫を消した後に「どの行がどの書庫から来たか」「読めなかった項目があったか」は作れない。** 台帳は追記のみ（書き換えると読めなかった事実が消せる）。

#### Scenario: 読んだ書庫の件数が台帳に残る

- **WHEN** 形の確認の印を置いた後に、視聴履歴 10 件（うち 3 件は既に格納済み）を含む書庫を置く
- **THEN** 台帳のその書庫の行の視聴履歴の論理ソースに、入った 7 件・既にあった 3 件が残る

#### Scenario: 削除済みで入れなかった件数が台帳に残る

- **WHEN** 形の確認の印を置いた後に、削除済みの記録と同じ内容を 1 件含む書庫を置く
- **THEN** 台帳のその書庫の行に、削除済みで入れなかった 1 件が残る

#### Scenario: 台帳の行は書き換えられない

- **WHEN** 台帳の行の件数を書き換える、または行を削除する操作を D-01 に対して行う
- **THEN** その操作は拒否され、行は元のまま残る

#### Scenario: 名前の時刻を持たない書庫は見つけた時刻を持つ

- **WHEN** `Timeline.json` を置く
- **THEN** 台帳のその行の作られた時刻は置き場で見つけた時刻で、取得元が示した値ではないことが分かる

#### Scenario: 台帳の行は利用者ごとに分かれる

- **WHEN** 2 人の利用者識別子で同じ書庫を読ませる
- **THEN** 台帳に利用者識別子の違う 2 つの行が残る

- **THEN** 台帳のどの列にも「京都 旅館」の文字列が無い

### Requirement: 取り込み器は自分の論理ソースに 1 日 1 回の生存信号を送る

WHILE 取り込み器が置き場を見ている THE SYSTEM SHALL **取り込み器そのものの論理ソース**（書庫の論理ソースとは別の 1 本）に、
`Asia/Tokyo` の日ごとに、その日の最初の走査で生存信号を 1 件残す。
THE SYSTEM SHALL 同じ日に 2 件目を残さない（取り込み器を起動し直しても）。
THE SYSTEM SHALL その生存信号の「取得できる状態か」を、**2 つの置き場がどちらも読める状態か**で決め、読めない置き場の種類を満たされていないものとして残す。
THE SYSTEM SHALL その生存信号の取得の試行回数と成功回数を、前回の生存信号からの**置き場の走査の回数と、2 つの置き場をどちらも読めた走査の回数**とする。
THE SYSTEM SHALL その回数を、**取り込み器を起動し直しても失わずに**積む。
THE SYSTEM SHALL その生存信号を、端末からの生存信号と同じ受け入れの判定と保護（冪等・書き換えの禁止）で残す。
THE SYSTEM SHALL **書庫の論理ソースには生存信号を残さない**（書庫のソースの稼働状況は記録だけから決まる）。
WHEN 直近の取り込み器の生存信号が取得できない状態を示す THE SYSTEM SHALL 稼働状況の「直近に置いた書庫」に、読めない置き場を文字で出す。
WHEN 取り込み器の最後の生存信号が 3 日より前か、一度も無い THE SYSTEM SHALL 稼働状況の「直近に置いた書庫」に、取り込み器の最後の確認が何日前か（一度も無ければそのこと）を文字で出す。

導出元: FR-78, FR-35, FR-80。深掘り C17 → C19（独立レビュー spec R8 / R9）。
FR-78 の「収集側が稼働していること」の担い手は、書庫のソースでは取り込み器。**置き場が読めなくなって書庫が入らなかった期間は、そのとき残さないと後から区別できない。**
**書庫の各ソースに信号を送ると、本人が書き出しを 1 年忘れても書庫のソースが「途絶」にならず、FR-35 の通知も鳴らない** —— 60 日の想定間隔（第 1 回 Q7）が効かなくなる。

#### Scenario: 取り込み器が動いている日に生存信号が 1 件残る

- **WHEN** 取り込み器が 1 日動き、書庫は置かれない
- **THEN** 取り込み器の論理ソースに、その日の取得できる状態の生存信号が 1 件残る

#### Scenario: 起動し直しても同じ日の生存信号は 1 件

- **WHEN** 同じ日に取り込み器を 2 回起動し直す
- **THEN** 取り込み器の論理ソースのその日の生存信号は 1 件である

#### Scenario: 生存信号は走査の回数と読めた走査の回数を持つ

- **WHEN** 前回の生存信号の後に走査が 5 回あり、そのうち 2 回は専用のフォルダが読めなかった
- **THEN** 次の生存信号の試行回数は 5、成功回数は 3 である

#### Scenario: 起動し直しても走査の回数は失われない

- **WHEN** 前回の生存信号の後に走査が 4 回あり、取り込み器を起動し直して、次の日の最初の走査が来る
- **THEN** 次の生存信号の試行回数は、起動し直す前の 4 回を含めた 5 である

#### Scenario: 置き場が読めない日は取れない状態で残る

- **WHEN** 専用のフォルダが存在しない状態で取り込み器が 1 日動く
- **THEN** 取り込み器の論理ソースに、取得できない状態で専用のフォルダが満たされていないと示す生存信号が残る

#### Scenario: 書庫のソースには生存信号が残らない

- **WHEN** 取り込み器が 3 日動く
- **THEN** 書庫の論理ソースの生存信号は 0 件である

#### Scenario: 書き出しを忘れると書庫のソースは途絶になる

- **WHEN** 視聴履歴の最後の記録の日から 61 日たった日の状態を読み出す
- **THEN** その日の視聴履歴の論理ソースの状態は「途絶」である

#### Scenario: 取り込み器が止まっていることが画面に出る

- **WHEN** 取り込み器の最後の生存信号が 4 日前の状態で稼働状況の画面を開く
- **THEN** 「直近に置いた書庫」に、取り込み器の最後の確認が 4 日前であることが文字で出る

#### Scenario: 置き場が読めないことが画面に出る

- **WHEN** 直近の取り込み器の生存信号が専用のフォルダを読めないと示す状態で稼働状況の画面を開く
- **THEN** 「直近に置いた書庫」に、専用のフォルダが読めないことが文字で出る

### Requirement: ソースごとに取り込み済みの最終日が残る

THE SYSTEM SHALL 書庫の論理ソースごとに、**入った記録のうちいちばん新しい出来事の日**を取り込み済みの最終日として保持する。
THE SYSTEM SHALL 併せて、**その最終日の出来事を運んだ書庫のうち、いちばん新しく作られた書庫の作られた時刻**を保持する。
WHEN 最終日より古い出来事しか含まない書庫が読まれる THE SYSTEM SHALL 最終日を動かさない。
THE SYSTEM SHALL 最終日に、**後から削除された記録の出来事も含める**（取り込んだ事実は削除で消えない）。
THE SYSTEM SHALL 出来事の日を `Asia/Tokyo` の日で数える。
THE SYSTEM SHALL 1 件も入っていない論理ソースの最終日を「無い」とする。

導出元: FR-16。深掘り Q4 / C12。
「書庫が作られた日」を最終日にすると、期間を絞って書き出した書庫では「その日まで全部入っている」が言い過ぎになる（本人の決定）。
両方を持つので、表示の規則は後から変えられる。日の区切りは稼働状況（NFR-13）と揃える。

#### Scenario: 最終日はいちばん新しい出来事の日

- **WHEN** 形の確認の印を置いた後に、2026-09-13 に作られ、最後の視聴が 2026-09-10 の書庫を置く
- **THEN** 視聴履歴の論理ソースの最終日は 2026-09-10 である

- **THEN** 視聴履歴の論理ソースの最終日と一緒に保持された書庫の作られた時刻は 2026-09-13 の時刻である

#### Scenario: 最終日の記録を消しても最終日は戻らない

- **WHEN** 最終日が 2026-09-10 の後に、2026-09-10 の視聴の記録を削除する
- **THEN** 最終日は 2026-09-10 のままである

#### Scenario: 古い書庫を後から置いても最終日は戻らない

- **THEN** 最終日は 2026-09-10 のままである

#### Scenario: 日本時間で日をまたぐ出来事は日本時間の日になる

- **THEN** 最終日は 2026-09-11 である

### Requirement: 稼働状況の画面に書庫のソースの格子と最終日と直近に置いた書庫が出る

WHEN 利用者が稼働状況の画面を開く THE SYSTEM SHALL 書庫の論理ソースごとに、Must の 5 ソースと同じ形の格子を出す。
THE SYSTEM SHALL 書庫のソースの格子を、**Must の 5 ソースより後ろ、退役したソースより前**に置く。
THE SYSTEM SHALL 各格子の見出しの横に、取り込み済みの最終日と、今日（`Asia/Tokyo` の日）からの日数を「`YYYY-MM-DD` まで（N 日前）」の形で出す。
THE SYSTEM SHALL 1 件も入っていない書庫のソースに「まだ無い」と出す。
THE SYSTEM SHALL **Must の 5 ソースの格子の前（成功条件 1 の達成の下）**に「直近に置いた書庫」の箱を置き、**直近に置いた書庫 1 件**の名前・置き場で見つけた時刻・入った件数・既にあった件数・読めなかった件数を出す。
WHILE 書庫を読んでいる THE SYSTEM SHALL 箱に、読んでいることと、読んでいるファイルの名前・そこまでに読んだ件数・読み始めた時刻を文字で出す（読み終えるまで待たせない）。
WHILE 形の確認を待っている書庫がある THE SYSTEM SHALL 箱に、形の確認を待っていることを文字で出す。
THE SYSTEM SHALL 箱の高さを **160 CSS px 以下**に収める（出しきれない文字は省き、省いたことを示す）。
THE SYSTEM SHALL 箱の文字を省くとき、**直近に置いた書庫を読めなかったこと・格納に失敗していることは省かない**。
THE SYSTEM SHALL 書庫のソースの格子を、開いた直後から直近 4 週の行を出した状態で置く（押さなくても見える。退役したソースは除く）。
WHEN 直近に置いた書庫が読めなかった書庫・格納に失敗した書庫である THE SYSTEM SHALL そのことを**文字で**出す（色だけで示さない）。
WHEN 直近に置いた書庫が既に読んだ書庫である THE SYSTEM SHALL 「既に読んだ書庫」であることと、前に読んだ時刻を文字で出す。
THE SYSTEM SHALL まだ 1 つも書庫が置かれていないとき、そのことを文字で出す。
THE SYSTEM SHALL 書庫のソースの格子を足しても、**Must の 5 ソースの格子の高さの予算**（`collection-coverage` の「稼働状況は 1 年を週に畳んだ格子で見える」。箱の高さを除いて数える）を超えないようにする。
THE SYSTEM SHALL 書庫のソースの格子の日の状態を、Must の 5 ソースと同じ判定と同じ 3 段で出す。
THE SYSTEM SHALL 書庫のソースの格子と箱を、幅 360 CSS px で横スクロールなしに収め、操作できる対象を 24 × 24 CSS px 以上にする。

導出元: FR-55, FR-54, NFR-3, NFR-19, NFR-23。深掘り Q5（proto で選んだ）/ Q4 / **第 2 回 Q9（直した proto で選んだ）/ Q10**。
**箱を Must の前に置くのは第 2 回の本人の決定**（第 1 回は格子の群の頭と読み取っていたが、その proto は読めた書庫の箱を描いていなかった）。開いてすぐ、置いた書庫が入ったか・読めなかったか・読んでいる途中かが見える。
本人は「箱の高さぶん予算を超える」と読んで選んだので、予算は箱の高さを除いて数え、箱が際限なく伸びないよう高さに上限を置く。
**読めなかった書庫が画面に無いと、置いたのに入っていないことに気づけない**（書庫は約 7 日で失効する）。
格子に載せるのは、本人が「ソースの扱いを揃える」を選んだため。書庫のソースだけ別の判定にはしない（ST02 の判定順は本人の決定）。
60 日を過ぎたことを知らせるのは ST14 で、この画面は見えるだけ（格子では、記録の間が 60 日を超えた日が「途絶」として見える）。

### Requirement: 書庫のソースは想定間隔 60 日で登録簿に入る
