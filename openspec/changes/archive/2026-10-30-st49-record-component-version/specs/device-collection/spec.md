## ADDED Requirements

### Requirement: 携帯の収集アプリは、記録を未送信に積む時点で自分の版を焼き込み、溜めた行の欄を落とさない

THE SYSTEM SHALL C-01 が記録・破棄の報告・原本の欠けを未送信に積むとき、その時点の C-01 の組み立ての印を部品の版の欄に書き込む。生存信号には書き込まない。
THE SYSTEM SHALL 未送信を送るとき、積んだときの部品の版をそのまま送る（送る時点の版で書き換えない）。
THE SYSTEM SHALL 溜めた行を読み戻したとき、部品の版の欄が無ければ、今の版を入れずに欄の無いまま送る。
THE SYSTEM SHALL 溜めた行が今の C-01 の知らない欄を持っていても、その欄を捨てずに送る。
THE SYSTEM SHALL ST01 / ST02 の形の未送信を今の置き場へ移すとき、部品の版を書き込まない。
THE SYSTEM SHALL C-01 の組み立ての印を、組み立てのたびに作り直す（「組み立ての印は、版番号・commit・その部品のソースの未 commit の変更・組み立ての種類を持ち、組み立てのたびに作り直す」の形。release の組み立てだけが `.debug` を持たない）。

導出元: FR-122。扉 #32。FR-122 ★ 2026-10-25 訂正（送った時の版ではなく作った時の版）。深掘り（ST49）Q1（推奨）。design D3（仮）・D13。
未送信は更新の後に送られるので、送る時点の版を付けると取り違えた版が作った記録に直した版が付く。

#### Scenario: 携帯の収集アプリを更新した後に送った未送信は、積んだときの版で届く

- **WHEN** 組み立ての印 `0.1.0+<commit A>.debug` の C-01 が位置の記録を未送信に積み、送る前に印 `0.1.0+<commit D>.debug` の C-01 に入れ替わってから送る
- **THEN** 送った要求の部品の版は `0.1.0+<commit A>.debug`

#### Scenario: 版の欄を持たない未送信の行は、版の欄の無いまま送られる

- **WHEN** 版の欄を足す前の形で積まれた未送信の行を、版の欄を知る C-01 が読み戻して送る
- **THEN** 送った要求に部品の版の欄は無く（か空で）、読めない行の置き場へは回らない

#### Scenario: 携帯の未送信の行が知らない欄を持っていても、送るときに落ちない

- **WHEN** 今の C-01 の知らない欄 `future_field` を持つ未送信の行を読み戻して送る
- **THEN** 送った要求に `future_field` が同じ値で載っている

#### Scenario: 古い形の未送信を移すとき、版は書き込まれない

- **WHEN** ST01 / ST02 の形の未送信を今の置き場へ移して送る
- **THEN** 送った要求に部品の版の欄は無い

#### Scenario: 携帯の生存信号には版が書き込まれない

- **WHEN** C-01 が生存信号を未送信に積む
- **THEN** 積んだ行に部品の版の欄は無い

#### Scenario: 携帯の収集アプリの組み立ての印は、組み立てのたびに作り直される

- **WHEN** C-01 を組み立てた後に commit を 1 つ足し、構成キャッシュとビルドキャッシュを効かせたまま、もう一度組み立てる
- **THEN** 2 回目の組み立ての印の commit は、足した commit の 40 桁

#### Scenario: 携帯の収集アプリの release の印は .debug を持たず、debug の印は持つ

- **WHEN** 同じ綺麗な木から、C-01 の debug と release の組み立ての印を作る
- **THEN** debug の印は `.debug` で終わり、release の印は `<版番号>+<40 桁>` で終わる

#### Scenario: 携帯の収集アプリの印は、add していないソースの変更の後に .dirty になる

- **WHEN** 綺麗な木で C-01 を組み立てた後に、携帯の収集アプリのソースを 1 つ書き換えて add せずにもう一度組み立てる
- **THEN** 2 回目の組み立ての印は `.dirty` を持つ

### Requirement: 破棄の報告と原本の欠けは、作った収集アプリの版と、書いた S-01 の版を持つ

THE SYSTEM SHALL 破棄の報告と原本の欠けの 1 件ごとに、作った C-01 の版（部品の版の欄。API の合言葉の要求のときだけ使う）と、それを D-01 に書いた S-01 の版を持たせる。
THE SYSTEM SHALL 部品の版を、破棄の報告の重複の判定（論理ソースと原文）と原本の欠けの重複の判定にも原文にも入れない。
THE SYSTEM SHALL C-01 の破棄の報告の下書きに、下書きを始めたときの C-01 の版を持たせ、下書きに足そうとしたときの版が下書きの版と違えば、その下書きを閉じて次の報告を始める。
THE SYSTEM SHALL 部品の版の欄を持たない破棄の報告と原本の欠けも、今と同じに受け付ける（版は「不明」）。

導出元: FR-122, FR-123。深掘り（ST49）Q3（推奨）。design D14・D15。
破棄の報告と原本の欠けは追記のみで、後から列を埋められない。1 本の報告に 2 つの版の破棄が混ざると、どちらの版が捨てたかを分けられない。

#### Scenario: 破棄の報告は、作った収集アプリの版と書いた S-01 の版を持つ

- **WHEN** API の合言葉で、部品の版に `0.1.0+<commit A>.debug` を書いた破棄の報告を送る
- **THEN** 格納された報告の収集アプリの版は `0.1.0+<commit A>.debug`、S-01 の版はその S-01 の組み立ての印

#### Scenario: 原本の欠けは、作った収集アプリの版と書いた S-01 の版を持つ

- **WHEN** API の合言葉で、部品の版に `0.1.0+<commit A>.debug` を書いた原本の欠けを送る
- **THEN** 格納された原本の欠けの収集アプリの版は `0.1.0+<commit A>.debug`、S-01 の版はその S-01 の組み立ての印

#### Scenario: 部品の版だけが違う同じ破棄の報告は、1 件のまま

- **WHEN** 同じ論理ソースと原文の破棄の報告を、部品の版 `0.1.0+<commit A>` と `0.1.0+<commit D>` で 1 回ずつ送る
- **THEN** 報告は 1 件だけで、2 回目は重複、報告の収集アプリの版は `0.1.0+<commit A>` のまま

#### Scenario: 収集アプリの版が変わったら、破棄の報告の下書きは閉じて次の報告になる

- **WHEN** 印 `0.1.0+<commit A>` の C-01 が同じ論理ソース・同じ理由で記録を 1 件捨てて下書きを始め、印 `0.1.0+<commit D>` の C-01 に入れ替わってからもう 1 件捨てる
- **THEN** 報告は 2 本になり、1 本目の部品の版は `0.1.0+<commit A>`・件数 1、2 本目は `0.1.0+<commit D>`・件数 1

#### Scenario: 版を持たない保存済みの下書きは閉じられ、その報告は版の欄の無いまま送られる

- **WHEN** 版の欄を足す前に保存された破棄の報告の下書きがある状態で、版の欄を知る C-01 が同じ論理ソース・同じ理由で記録を 1 件捨てる
- **THEN** 保存済みの下書きは閉じられて部品の版の欄の無い報告として送られ、捨てた 1 件は今の版を持つ次の報告に入る

#### Scenario: 部品の版の欄を持たない破棄の報告と原本の欠けも受け付けられる

- **WHEN** 部品の版の欄を持たない（いまの形の）破棄の報告と原本の欠けを送る
- **THEN** どちらも受け付けられ、収集アプリの版は「不明」、S-01 の版はその S-01 の組み立ての印
