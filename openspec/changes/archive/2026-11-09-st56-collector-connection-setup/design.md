# ST56 design — 収集アプリを入れた後に、送り先と資格情報を設定できる

## Context

動機は `proposal.md` の Why。いまの状態（`premises.md`・`review/deep.md` の手順 5）:

- 携帯: `Config.kt` は送り先・資格情報・利用者・画面のアドレスを `BuildConfig`（`-P`）からだけ読む。配る APK ではどれも空（ST52 の検査 `tools/release/build.sh:151`）。
  `LocationService.startFlushing` は設定が揃わないと送る仕組みを立てずに戻り、後から立て直す道が無い（`:926-931`）。送り先と資格情報は仕組みを立てた時の値で固まる（`:241`・`:254`・`:258`）。
  記録の利用者は積んだ時点で行に凍り（`FixCollector.kt`・`IngestRequest.kt:54`）、配る APK では空の文字列なので、サーバは `malformed` で断り、携帯は恒久の拒否として捨てる（`review/deep.md` R1）。
  バックアップの規則は `health_permission.xml` だけを外している（`res/xml/health_*`）
- PC の収集アプリ: `Config::from_env` が 5 つの環境変数を読み、1 つでも欠けると `main.rs:14` で起動ごと終わる（`config.rs:5-6` の「取得は続ける」は成り立っていない）。置き場と端末識別子は既定を持たない（`config.rs:104-127`）。
  `--install-autostart` は 5 つの変数を合言葉ごと `ashiato-collector.cmd` に平文で書く（`autostart.rs:27-39`）
- サーバ: 収集アプリの資格情報（`API_TOKEN`）を自分で持ち、ST44 の許可の一覧の口だけに通す。画面の合言葉の照合は `web_session.rs`。画面は API を相対の `/api` で呼ぶ（`web/src/*.ts`）
- 401 で断られた記録は、携帯も PC も未送信から取り除かない（`Sender.kt:345-349`・`sender.rs:254`）

## Goals / Non-Goals

**Goals**: 配る APK と PC の収集アプリを入れた後に、本人が画面から設定の文字列を出して貼るだけで送り始めること。設定の前に積んだ記録を捨てないこと。設定の誤り・資格情報の変更・送り先の取り違えで、記録を捨てずに設定し直しを促すこと。今の開発と試験の組み立てを壊さないこと。

**Non-Goals**:
- 資格情報を変える口（FR-133。ST59）。ST56 は変えた後に収集アプリが知らせる側だけを作る
- 利用者を資格情報から決める仕組み（FR-92）。ST56 は利用者を既定の利用者に固定するだけ（下の Risks）
- 端末ごとの資格情報・発行と取り消しの画面（ST44 Q2 で作らないと決まっている）
- QR の読み取り（Q1 の選択肢 2。選ばなかった）
- PC の収集アプリの窓の画面（GUI）（Q2 の選択肢 3。選ばなかった）

## Decisions

### D1. 記録の利用者は、設定の前も後も既定の利用者（nil の UUID）に固定する。設定した後、送る仕組みを立て直す

> 聞かない既定（`review/deep.md` C1）。R1・R2

- 携帯: `Config.userId` は `BuildConfig.USER_ID` が空なら `00000000-0000-0000-0000-000000000000` を返す。記録・生存信号・健康データの権限の記録・原本の受け口の利用者・途絶の問い合わせの `user_id` は全部ここから読む
- PC: `--config-from-env` が無いときの利用者は nil の UUID
- 設定の文字列に利用者を入れない（FR-92 と逆向きの値を外から入れる口を作らない。nil 以外を貼ると画面に出ず、後で揃えるには全行の利用者を書き直す —— R2）
- 送る仕組みの立て直しは D11（仮）

### D2. PC の収集アプリは設定が無いままでも起動し、取って積む。送るのは設定の後

> 聞かない既定（`review/deep.md` C2）。R4

`main.rs` は設定が読めなくても終わらない。`Runtime` は「送り先なし」で始まり、前景の窓・入力・ブラウザの履歴を取って未送信に積む。送る契機は送り先が無ければ何もしない（`GET /contract` も引かない）。
二重起動の止め・除外の登録・未送信は D16 の既定の置き場で動く（設定が無くても置き場は決まる）。

### D3. 携帯の設定は Google のバックアップと端末の移し替えから外す。`-P` の値は保存した設定が無いときの初期値

> 聞かない既定（`review/deep.md` C3）。premises.md 1 行目

- 設定は専用の SharedPreferences（`collector_setup.xml`）に置き、`health_full_backup_content.xml`（Android 11 以前）と `health_data_extraction_rules.xml` の `cloud-backup`・`device-transfer`（Android 12 以降）の両方で `<exclude domain="sharedpref" path="collector_setup.xml"/>` を書く
- 外したことは新しい `tools/check-android-backup-rules.sh` が manifest から規則のファイルを辿って見る（`--self-test` が規則の行を消した写しで落ちることを見る）。premises.md 1 行目の確かさは、この検査とエミュレータでの `bmgr` の確かめ（人間の確認待ちに置かない。Task 5 の計測テスト）で上げる
- 未送信（`filesDir`）は今どおり写る。戻した端末は未送信だけを持ち、承認した送り先を持たない —— D13 が「承認した送り先が無くても未送信があれば押すまで送らない」で守る
- `-P` の値: `Config` は保存した設定を先に読み、無ければ `BuildConfig` の値。`-P` の送り先は承認した送り先として扱う（D13）。今の開発・計測テスト・縦串はこのまま動く

### D4. 通知が開く画面のアドレスは、送り先から `/api` を外して作る

> 聞かない既定（`review/deep.md` C4）。R8

`Config.webUrl` は保存した設定があれば送り先の末尾の `/api`（と末尾の `/`）を外した値、無ければ `BuildConfig.WEB_URL`。配る形のサーバは画面と API を同じ口で出す（ST52 D13。premises.md 3 行目）。

### D5. 携帯に貼った送り先は `https://` で loopback 以外に限る。`-P` の値には当てない

> 聞かない既定（`review/deep.md` C5）。R7

PC の画面（`http://127.0.0.1:18700`）から作った文字列を携帯に貼る誤りを、貼った時点で止める。携帯の平文の許可は今も `localhost`・`127.0.0.1` だけ（`build.gradle.kts:162-197`）で、`http://` の別の host は Android が断る。
PC は今の規則（`http://` は loopback だけ）のまま。

### D6. 利用者に見せる語は「送り先」に揃える

> 聞かない既定（`review/deep.md` C6）。R10。docs/handoff/ST56.md の 3 つ目

FR-106 の文（「送り先が開発版／正式版のサーバです」）に揃え、画面・携帯・PC の文と通知はどれも「送り先」と書く。要件の本文の「接続先」は変えない。

### D7. 設定の文字列の送り先は、画面を開いているアドレスから作る

> 聞かない既定（`review/deep.md` C7）。premises.md 3 行目

画面は `window.location.origin + "/api"` を送り先にする。本人が Tailscale のアドレスで開けば携帯から届く送り先になり、`127.0.0.1` で開けば PC だけが使える送り先になる（D5 が携帯で止める）。
画面の節には「携帯に入れるなら、携帯から開いているアドレス（Tailscale）でこの画面を開いてください」と添える。

### D8. 画面の設定に「収集アプリの設定」を置き、合言葉を入れ直すと設定の文字列を出す

> 深掘り Q1（答え待ち・推奨: 画面の設定に「収集アプリの設定」を置き、画面の合言葉を入れ直すと 1 行の設定の文字列を出す。収集アプリはそれを貼る）

- サーバ: `POST /collector-setup`（本文 `{"password": "…"}`。応答 `{"token": "…"}`）。ログインの印が要り（無ければ 401）、本文の合言葉を `web_session.rs` のログインと同じ照合・同じ失敗の遅れと回数の制限で見る。合言葉が違えば **403** `{"error": "wrong_password"}`。API の合言葉の許可の一覧には入れない（ST44 の既定で 403）
- 違う合言葉を 401 にしないのは、画面の `watchUnauthorized`（`web/src/session.tsx:28-31`）が `/api/` の 401 を全部ログイン切れとして読み、画面全体をログインに戻すため（review/spec.md R2）。見張りの例外を足すより、口の側で「ログインは有効・合言葉が違う」を 403 で表すほうが、見張りの規則（401 = ログイン切れ）を変えない
- 画面: `SettingsView.tsx` に新しい部品 `CollectorSetupPanel.tsx`。合言葉の入力欄と「表示」→ 応答の資格情報と D7 の送り先から D18（仮）の形で文字列を組み、読み取り専用の欄とコピーのボタンを出す。文字列は React の状態にだけ持ち、保存しない（開き直すと消える）
- ST55 の「秘密は人が見ない」（ST55 proposal）は、ST56 の後は「画面にログインして合言葉を入れ直した本人には、収集アプリの資格情報を見せる」になる。ST55 には tasks があるので、`docs/handoff/ST55.md` に申し送る（差し戻さない）
- 合言葉の入れ直しの守りは ST59（合言葉を画面から変える）が同じ形で使う。`docs/handoff/ST59.md` に書く

### D9. 携帯は入れて初めて開くと設定の画面を先に出し、「後で」で飛ばせる

> 深掘り Q3（答え待ち・推奨: 最初に設定の画面を出す。「後で」で飛ばせ、権限の要求と収集はどちらでも始まる。未設定の間は通知で促し、押すと設定の画面が開く）

- 新しい `SetupActivity`。`MainActivity.onCreate` は、送り先が無く（保存した設定も `-P` も空）「後で」をまだ押していないときだけ、権限の要求より前に `SetupActivity` を開く。「後で」を押した印は SharedPreferences に置く（D3 と同じく外す）
- メインの画面に「送り先の設定」の行を置き、いつでも `SetupActivity` を開ける
- 未設定の通知は D20（仮）の通知のチャンネルに出す

### D10. 設定を保存した時点で `GET /contract` を 1 回引いて結果を見せ、答えに依らず保存する

> 深掘り Q4（答え待ち・推奨: 確かめて結果を見せる。繋がらないときも保存して後で送る）

- 携帯は `ContractGate` の、PC は `sender.rs::read_contract_answer` の今の 4 つの分け方を使う: 版を読めた 200（ST54 の `Ashiato-Channel` の見出しが自分と同じ）→「繋がりました」/ 同じく見出しが違う →「送り先が開発版（正式版）のサーバです」（FR-106 の文）/ 401 →「資格情報か送り先が違います」/ それ以外（届かない・時間切れ・5xx・404・読めない本文）→「保存しました。繋がったら送ります」
- 404 と読めない本文を「保存しました」に寄せるのは、古いサーバ・公衆の Wi-Fi の入口の判断を ST50 の知らせ（FR-125・FR-126）に任せるため
- この問い合わせは D13 の保留の対象外（記録を送らず、相手に残るのは読み出しの記録の 1 行だけ。ST44 の許可の一覧の口）
- ST54 が入るまで `Ashiato-Channel` は無く、正式版とみなす（ST54 D7 と同じ）。ST54 は requires

### D11（仮）. 設定を保存したら、収集のサービスに知らせて送る仕組みを立て直す

- 携帯: `Config` は保存した値を毎回読む（`HttpTransport` などを作るときに値を固めない —— 送り先と資格情報を関数で渡す）。`SetupActivity` が保存したら `LocationService` に `ACTION_SETUP_CHANGED` の Intent を送り、`startFlushing` を（立っていなければ）立てる。立っていれば次の契機から新しい値で送る
- PC: 送る契機ごとに置き場の設定のファイルの更新時刻を見て、変わっていれば読み直す（`setup` は別のプロセスで走るので、走っている収集アプリへの通り道はファイルだけ）
- 反転条件: 設定を保存してから送り始めるまでに、携帯で 1 分・PC で 5 分（送る契機の間隔）より長くかかると確認バッチで分かったら、PC は名前付きのイベントで知らせる形にする

### D12. 401 が 1 時間続いたら知らせ、24 時間ごとに出し直す。一度も届かない送り先は 24 時間で知らせる

> 深掘り Q5（答え待ち・推奨: 断られる状態が 1 時間続いたら知らせ、続く間は 24 時間ごとに出し直す。文は「サーバに断られています。資格情報か送り先が違います。設定し直してください」。押すと設定の画面が開く）

- 数え始め（最初の 401 の時刻）・最後に知らせた時刻・最後に届いた時刻を、携帯は SharedPreferences（D3 と同じく外す）、PC は置き場の `setup-state.json` に置き、再起動をまたいで持つ（FR-126 の数え方と同じ向き）
- 「断られる」は送信（記録・生存信号・破棄の報告・原本）と問い合わせ（`/contract`・`/outages`・`/feelings/reminder`）のどれかが 401 を返したこと。401 でない答えが 1 回届けば数え直す。届かない・5xx は数えを止めない
- 「届いた」は、状態符号のある答えが返ったこと（401 も 5xx も含む）。「届かない」は接続できない・時間切れだけが続くこと。設定してから 24 時間届かなければ知らせ、以後は 24 時間ごと。401 だけを返す送り先は「断られている」の知らせだけになる（review/spec.md R5）。2 つの知らせは通知の id・札を分ける
- 出し直しの決め方は ST50 の `contract_notice::decide`・`ContractNotifier` と同じ形にし、札（PC）・通知の id（携帯）を分ける（D20（仮））
- 断られた記録は捨てない（今どおり）。携帯の保持の上限（FR-8）は今どおり当たり、83 日目の知らせ（FR-9 (3)）も今どおり出る

### D13. 未送信があるまま送り先を変えたら、本人が押すまで全部の経路を止める

> 深掘り Q7（答え待ち・推奨: 変えた時点（前の送り先が分からないまま未送信がある時も）で未送信の件数と期間を見せ、「この送り先へ送る」を押すまで何も送らない）

- 承認した送り先（`approved_url`）を、携帯は設定と同じ SharedPreferences（D3 で外す）、PC は置き場の `settings.json` に持つ
- 保存の時の確かめ（`GET /contract` 1 回。D10）は、押す前に新しい送り先へ届き、相手の読み出しの記録に 1 行残る。記録の中身は送らない。この例外は spec の本文と Q7 の context に書いた（review/spec.md R4）
- 保存のとき: 新しい送り先が承認した送り先と同じ（D19（仮）の比べ方）なら何もしない。違う（承認した送り先が無いを含む）とき、未送信（携帯: 記録・生存信号・破棄の報告の置き場と、原本の送り待ち。PC: 記録・生存信号・破棄の報告）が 1 つも無ければ承認する。あれば保留にする
- 保留の間に止めるもの: 記録・生存信号・破棄の報告・原本の送り（`PUT`・`HEAD`・`POST /media/missing`）・途絶の問い合わせ（`GET /outages`）・気分の通知の問い合わせ（`GET /feelings/reminder`）。止めないもの: 設定の確かめの `GET /contract`（D10）・PC の時計合わせ `GET /healthz`（Date を読むだけ。ST54 D13 と同じ扱い）
- 一つの門（携帯は `DestinationGate`、PC は `destination_gate`）を全部の送り手が送る前に見る。送り手ごとに条件を書かない
- `-P` の送り先と `--config-from-env` の送り先は承認したものとして扱う（今の開発・試験・縦串を止めない）
- 前の送り先が受けた記録の原本の送り待ちは、新しい送り先では `409 record_missing` が 7 日続いて欠けになる（今の `RECORD_MISSING_GIVE_UP`。Q7 の選択肢 1 の detail に書いた帰結）
- PC の答え方は D21（仮）

### D14（仮）. PC は、窓があれば設定の文字列をその窓で待ち、窓が無ければ通知で `setup` へ誘う

- 起動したとき設定が無く、標準入力が端末なら、窓に「画面の設定の『収集アプリの設定』で出した文字列を貼ってください」と出し、収集とは別の糸で 1 行を待つ（収集は待たない）
- 自動起動は最小化した窓（`start "" /min`）で動くので、本人は窓に気づきにくい。未設定の通知を出し、押すと `ashiato-collector-windows.exe setup` が新しい窓で開く
- `setup` は別のプロセスとして走り、設定を置き場に書いて終わる。走っている収集アプリは D11（仮）で読み直す
- 反転条件: 確認バッチで、本人が通知から `setup` に辿れない・窓を閉じてしまうと分かったら、小さな設定の窓（Q2 の選択肢 3）に替える

### D15. PC の資格情報は DPAPI（利用者の範囲）で包んで置き場の `credential.bin` に置き、自動起動の台本には実行ファイルの場所だけを書く

> 深掘り Q2（答え待ち・推奨: 設定が無いまま起動したら、黒い窓で設定の文字列を貼らせる。資格情報は Windows の暗号（DPAPI。その利用者だけが戻せる）で包んで置き場のファイルに置き、自動起動の台本には実行ファイルの場所だけを書く）

- 新しい `secret.rs`: `CryptProtectData` / `CryptUnprotectData`（`windows` crate の `Win32_Security_Cryptography`。crate は既にあり、機能を 1 つ足す）。Windows 以外の組み立てでは同じ口を試験用の可逆な包みにする（Linux の `cargo test` で上の層を試せるように。配る形は Windows だけ）
- 置き場の `settings.json`（送り先・承認した送り先・端末の識別子。秘密でない）と `credential.bin`（資格情報の DPAPI の包み）に分ける
- `autostart::startup_script` は送り先・資格情報・利用者の行を書かない。書くのは `start "" /min "<exe>"` と、既定でない置き場・端末の識別子の `set` 行だけ（D23（仮））。`setup` で保存したとき、`ashiato-collector.cmd` に `ASHIATO_BASE_URL`・`ASHIATO_API_TOKEN`・`ASHIATO_USER_ID` の行があれば、それを消して書き直す
- 同じ Windows の利用者として動くほかのプログラムは戻せる（premises.md 2 行目）。今の平文の台本より狭く、未送信（題名と URL）と同じ読み手の範囲

### D16. 配る PC の収集アプリの置き場は `%LOCALAPPDATA%\ashiato\collector`、端末の識別子は最初の起動で作って覚える

> 深掘り Q8（答え待ち・推奨: 置き場は利用者のプロファイルの下の固定の場所（`%LOCALAPPDATA%\ashiato\collector`）。識別子は最初の起動で作ってそこに覚える。開発版は ST54 の規則をこの既定に当てる）

- 識別子は `pc-` + 小文字の 16 進 12 文字（OS の乱数）。`settings.json` の `device_id` に書き、以後は読むだけ
- 前の形の台本で動いていた置き場と識別子は D23（仮）で引き継ぐ（既定の置き場に移さない）
- ST54 D2 の規則（置き場の下の `dev`・識別子の `-dev`・除外は渡された置き場から）は「渡された置き場」を「`--config-from-env` なら `ASHIATO_STATE_DIR`、無ければ既定の置き場」と読む。ST54 の正典は「渡された置き場」と書いているので、ST56 の Requirement が既定の側を足す
- 開発版の `setup` は開発版の置き場（`…\collector\dev`）に設定を書く（開発版と正式版は別の送り先を持つ。ST54 の Non-Goals）
- `%LOCALAPPDATA%` が読めないときは起動を止め、理由をログに書く（置き場を `.` に倒さない —— R27 と同じ理由）。振る舞いは spec の desktop-collection に書いた
- 開発版の端末の識別子は、正式版の置き場に覚えた識別子に `-dev` を付けた値（`dev` の下に別に覚えない）。正式版を一度も起動していないときは、開発版が正式版の置き場に識別子を作って覚える（ST54 の「渡された値に `-dev`」をそのまま当てる）

### D17（仮）. 環境変数は開発と試験の印を付けて起動したときだけ読む

- 印は引数 `--config-from-env` か環境変数 `ASHIATO_CONFIG_FROM_ENV=1`（前の形の台本はどちらも持たないので、古い台本の変数で設定を上書きしない）。録画の起動は harness2 の台本が持ち、引数を足せないので環境の印を使う（`tools/record-env.sh` が `WINDOWS_ENV_ASHIATO_CONFIG_FROM_ENV=1` を渡す）
- 印があれば今の `Config::from_lookup`（5 つの変数。1 つでも欠ければ起動を止める）。無ければ D15・D16 の置き場から読む
- PC の収集アプリを環境変数で起こす道具（`tests/runtime_windows.rs` の起動・`examples/`）に印を足す
- `--install-autostart` を印と一緒に使ったときも、台本には印も送り先・資格情報・利用者も書かない（spec の「書くのは実行ファイルの場所と、既定でない置き場と端末の識別子だけ」。review/spec.md R6）。開発の PC で環境変数のまま自動起動したいなら、利用者の環境変数に `ASHIATO_CONFIG_FROM_ENV=1` と 5 つの変数を置く（開発の手順書に書く）
- 反転条件: 環境の印が、前の形の台本や利用者の環境に残って設定を上書きしたと確認バッチで分かったら、印を引数だけにして録画の台本（harness2）に引数を足す

### D18（仮）. 設定の文字列は `ashiato-collector:1:` に base64url（埋めの `=` なし）の JSON を続けた 1 行

- JSON は `{"url": "<送り先>", "token": "<資格情報>"}`。ほかの欄は無視する（後から足せる）。`1` は形の版で、知らない版は「読めません」
- 画面（TypeScript）が組み、携帯（Kotlin）と PC（Rust）が読む。3 つの言語の試験が同じ材料のファイル `docs/contracts/collector-setup-vectors.json`（正しい文字列・読めない文字列と、その読んだ結果）を読む
- 前後の空白と改行は読むときに外す（貼るときに混ざる）
- 反転条件: 本人が手で打つ・目で見比べる場面が確認バッチで出たら、短い形（送り先と資格情報を別の欄で）を足す

### D19（仮）. 同じ送り先かは、送り先のアドレスを揃えて比べる

- scheme と host を小文字にし、既定の port（`https` の 443・`http` の 80）を外し、path の末尾の `/` を外して文字列で比べる。資格情報は比べない（Q7 の context）
- 同じサーバを `127.0.0.1` と Tailscale のアドレスで開いた文字列は別の送り先になる（携帯は D5 で loopback を断るので、起きるのは PC だけ。PC で別のアドレスを貼ったら 1 回押す）
- 反転条件: サーバが自分の印（ID）を `GET /contract` で返すようになったら、それで比べる

### D20（仮）. 新しい知らせの口と出し直し

- 携帯: 通知のチャンネル `setup`（「送り先の設定」）を足し、通知の id を 4 つ分ける（未設定・断られ続け・届かない・送り先の保留）。押すと `SetupActivity`
- PC: 通知の差出人は今のまま、札を `setup`（未設定）・`auth`（断られ続け）・`unreachable`（届かない）・`destination`（保留）に分ける（ST50 の `contract`・ST14 の `outage`・ST54 の `channel` と別）。押すと `setup` の窓
- 未設定と保留の通知は、状態が続く間 24 時間ごとに出し直す（D12 と同じ決め方）
- 反転条件: 確認バッチで通知が多すぎると分かったら、未設定の出し直しを止める

### D21（仮）. PC の保留は `setup` の窓で y/N を聞き、答えなければ保留のまま

- `setup` は保存の後、保留に当たれば「未送信 <n> 件（<最も古い時刻> 〜 <新しい時刻>）があります。この送り先へ送りますか [y/N]」と聞く。`y` で承認、それ以外・窓を閉じたら保留を続ける
- 保留を解くには `setup` を走らせ直す（設定の文字列を貼らずに Enter で今の設定のまま聞き直す）
- 反転条件: D14（仮）の反転と同じ（窓の画面に替えたら、そこに押すボタンを置く）

### D22（仮）. 設定の文字列を出した求めは、読み出しの記録に `collector-setup` の口として残す

- 読み出しの記録の行は今の形（時刻・経路・資格情報の種類・口の名前・結果）。値は持たない
- ログインの失敗の数え（回数の制限）を、ログインの口と共有する（どちらで失敗しても同じ窓で数える）
- 失敗の数えの共有と 429 は spec の data-sensitivity に書いた（review/spec.md R7・R11）
- 反転条件: ST59 が合言葉の入れ直しを別の数えにすると決めたら、それに揃える

### D23（仮）. 前の形の台本の置き場と端末の識別子は、印が無くても引き継ぐ

- 置き場は「環境の `ASHIATO_STATE_DIR` → 自動起動の台本の `ASHIATO_STATE_DIR` の行（`autostart::read_vars`）→ 既定の置き場」、端末の識別子は「環境の `ASHIATO_DEVICE_ID` → 台本の行 → 置き場の `settings.json` → 作る」の順で決める。秘密でない 2 つだけで、送り先・資格情報・利用者は印が無ければ環境から読まない（D17（仮））
- なぜ: 印が無いと環境を読まない形だけにすると、今の開発の PC（前の形の台本で `ASHIATO_STATE_DIR` を渡している）は、新しい実行ファイルに替えた最初のログオンから既定の置き場で動き、前の置き場の除外の登録を読まずに、除外したサイトの閲覧履歴を送りうる（R27・ST54 design の実例と同じ型。`exported`）。台本の行を読むのは、別の窓で走らせる `setup` が、環境変数を持たずに同じ置き場を見つけるため
- `setup` は前の形の台本を書き換えるとき、置き場と識別子の行を残す（台本の置き場が既定と同じなら消してよい）
- ST54 の「自動起動の項目に、渡された置き場と端末識別子を書く」はこの形でも成り立つ（渡された＝環境か台本の値）
- 反転条件: 本人の PC が前の形の台本で動いていないと確かめられ（確認バッチ）、配る形の利用者だけになったら、台本の行を読む段を外してよい

### D24（仮）. 最初の設定でも、設定の前に積んだ分があれば Q7 の保留に従う

- Q3 の推奨（「後で」で飛ばしても記録は積まれ、設定した後に送られる）と Q7 の推奨（承認した送り先が無く未送信があれば押すまで送らない）は、入れたばかりの携帯で重なる。Q7 に従い、最初の設定でも 1 回「この送り先へ送る」を押してから送る（review/spec.md R3）。Story の完了の判定「設定すると送信が始まる」は、押すことを含めて読む（確認バッチ 13.1 の手順）
- 入れてから積んだ分と、バックアップから戻した分は見分けられない（Q7 の context）ので、最初の設定だけを外すと、戻した端末の未送信が黙って新しい送り先へ出る
- 反転条件: 本人が Q7 で押さずに送る側（選択肢 2）を選んだら、この D は消える。入れてから積んだ分だけを見分ける印（入れた時刻より後に積んだ行だけ）が作れると分かったら、最初の設定でその分だけは押さずに送る

### D25（仮）. 続けて送っている最中に送り先が変わったら、次の要求から止める（携帯）

- 携帯は送り先と資格情報を要求ごとに読む（D11）。保存は送り先・資格情報・保留を 1 つの編集で書く（R1）ので、門を見るのを契機の頭の 1 回にすると、続けて送る周回（90 日分なら 648 回）と写真の原本の 1 件ごとの送信が、押す前に新しい送り先へ届く（review/code.md R31。`exported`）
- 門は 3 か所で見る: `Drainer` の周回と送り手（記録・生存信号・破棄の報告・欠け）の 1 本ごと、`OriginalUploader` の 1 件ごと、送る要求の資格情報を読んだ直後（送り先 → 資格情報 → 門の順。保留なら要求を出さずに「届かない」で終える）
- Q7（押すまで 1 つも送らない）の向きに従う。失わない側（送らない）の費用は、続けて送る途中で止まった分を「この送り先へ送る」の後の契機で送ることだけ
- 反転条件: 送る契機の頭で送り先と資格情報を取り、その契機の間は固定する形（D11 の読み直しを契機単位にする）に替えたら、要求ごとの門は外してよい

## Risks / Trade-offs

- [FR-92 は満たさない] 利用者は nil の UUID に固定するだけで、資格情報から決める仕組みは無い（収集アプリの資格情報は利用者を持たない。`lib.rs:709-716`）。いずれ渡す相手が自分のサーバを持つ形（サーバごとに 1 人）なら困らないが、1 つのサーバを複数人で使う形になったら FR-92 の Story が要る → proposal と GO 資料に書く。設定の文字列に利用者を入れないので、そのときに全行の書き直しは起きない
- [資格情報を画面で見せる] 画面にログインして合言葉を入れ直した人は、収集アプリの資格情報を持ち出せる。その人はもともと全部の記録を読めるので、増えるのは「偽の記録を送れる」こと → 合言葉の入れ直し（D8）と読み出しの記録（D22（仮））で、拾った携帯からの持ち出しと、持ち出したことの痕跡を残す
- [Q7 の手間] 入れたばかりの携帯でも、設定の前に積んだ生存信号があるので、最初の設定で 1 回押す手間がある。押さずに 90 日で捨てる（83 日目の知らせは出る）
- [Q8 の置き場] `%LOCALAPPDATA%` は移動プロファイルでも端末に残る（ローミングしない）。Windows の利用者を作り直すと置き場ごと失い、未送信と除外の登録を失う（今の環境変数の置き場でも同じ）
- [DPAPI] 同じ利用者として動くほかのプログラムは戻せる。Windows の合言葉を管理者がリセットすると戻せなくなる → 戻せない包みは設定が無いのと同じに扱う（spec の desktop-collection。記録は捨てない）
- [ST54 の上に積む] ST54 の `Ashiato-Channel` と `dev` の規則が変われば D10 と D16 が直る。ST54 は requires で、下流の入口は ST54 の gate 済みの SHA を取り込む
- [前提の確かさ] premises.md の 5 行はどれも確かさ 2。loss のある決定（Q7・Q8）は外の形式に依らない。1 行目（自動バックアップ）は Task 5 のエミュレータの `bmgr` で、5 行目（401 で取り除かない）は既存の試験と Task 7・Task 10 の試験で 4 に上げる

## Migration Plan

- 今の開発の携帯（`-P` で焼き込んだ APK）: 保存した設定が無いので今どおり動く。設定の画面から貼れば保存した設定が先になる
- 今の開発の PC（`ashiato-collector.cmd` に変数を書いた形）: 新しい実行ファイルは `--config-from-env` が無いと送り先・資格情報・利用者を環境から読まない。台本は変数を `set` してから引数なしで `start` するので、新しい実行ファイルは設定の無い起動（D2）になり、**前の置き場と端末の識別子のまま**（D23（仮））取って積み、未設定の通知を出す。
  本人は `setup` で貼る（台本の秘密の行が消える）か、台本に `--config-from-env` を足す。`docs/collector-setup.md` に両方の手順を書く
- 戻し: 前の版の実行ファイルに戻せば、今の台本の変数で今どおり動く（新しい置き場のファイルは読まれないだけ）
