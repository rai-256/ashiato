## 聞かずに決めた既定（C）—— 扉を開けたままにする側に倒したもの

「片方の選択肢が扉を開けたままにし、費用が小さい」ものは問いにせず、ここに残して design の D 番号にする。

| # | 決めたこと | 扉をどちらへ開けておくか |
|---|---|---|
| C1 | **1 イベント = 1 記録**（1 回の取得を 1 件にまとめない） | まとめると、重ねた窓で配列の中身が変わって冪等キーが動き、再送のたびに行が増える。削除（ST22）・感度（ST24）・時間ごとの件数の粒度も失われる |
| C2 | **アプリの表示名を取得時に解決して `payload` に載せる**（`raw` には入れない） | アプリを消した後でも「何だったか」が残る。`raw` に入れると、アプリの更新や端末の言語変更で冪等キーが変わり同じイベントが行として増える（R2） |
| C3 | 初回と再開の遡りは、**OS が持っている分だけ**（イベントは 10 日、集計は Q5 の答えによる） | 取れるものは全部取る。上限は OS 側が決めるので、こちらで短く切らない |
| C4 | 取得の窓は**重ねて進める**（前回の終わりより少し手前から取り直す） | 境界の取りこぼしを作らない。重複はサーバの冪等が畳む |
| C5 | **`null` と「0 件」を区別し、`null` のときは窓を進めない**（R3） | 解錠していない端末では `queryEvents` が `null` を返す。0 件と同じに扱って窓を進めると、その期間は 10 日で消える |

### Q9 [時計が恒久的にずれたままの端末で、アプリ利用の取得を止め続けるか] -> c（止まりが取得元の保持（10 日）を超えたら、諦めて見込みの下限から再開する）

- **段**: A（`loss: uncaptured` —— 止まっている間のイベントは取得元の保持（10 日）を過ぎたら二度と手に入らない）
- **kind**: `conflict`（既定 C6 の帰結が、想定していたより重い側に出た）

**何が起きるか**: 端末の壁時計が単調な経過と 1 時間（design D8（仮）の幅）を超えて食い違ったまま
戻らないと、アプリ利用の取得は**止まったまま**になる。既定 C6「飛びが直るまで取り直さない」と
spec の「その食い違いが解消するまで窓を進めず」を逐語で実装した結果で、実装は正しい。
本人が時刻を直せば直る。止まっている間は契機ごとに `kind=usage_clock_skew` が出て、
窓の始まりはやがて見込みの保持の下限より古くなるので D4 の gap の記録にも現れる（黙っては消えない）。

**選択肢**

| | どうする | 失われるもの | 開いたままになる扉 |
|---|---|---|---|
| a | **いまのまま**（直るまで止める） | ずれている間のイベント（10 日で消える） | `event_time` は凍結されているので、**間違った時刻の行を正典に入れない**。後から時刻を直せば残っている分は取れる |
| b | 飛んだ幅だけ窓の終わりをずらして追従する | 無し（取得は続く） | **凍結された `event_time` の行が増える** —— 取得元は時計の変化で統計をずらすので、同じイベントが別の時刻で二重に入り、後から直せない |
| c | 止まりが取得元の保持（10 日）を超えたら、諦めて見込みの下限から再開する | 10 日より前のぶん（どのみち取得元から消えている） | 取得は必ず再開する。**ただし spec の「解消するまで窓を進めず」を書き換える必要がある** |

**推奨**: c。失うのは「どのみち取得元から消えているもの」だけで、b のように正典を汚さない。
ただし spec の Requirement 本文を直すので、**本人の答えが要る**（CLAUDE.md:「反転条件のうち spec を破る手は本人に返す」）。

**なぜ下流で決めなかったか**: a / b / c のどれを選んでも**取り返せないもの**が決まる
（a と c はイベント、b は正典の行）。計算し直して戻せる判断ではない。

**下流がいましていること**: a（spec のとおり）。誤検知のほう（30 日より長い電源断を
「時計が飛んだ」と読む `AgeClock` の頭打ち由来の偽陽性）は spec を破らずに直せるので、**Task 3 の中で直した**。

### 本人の答え（2026-09-24。貼り戻された文字列の逐語）

```
=== ST06 の深掘り の回答 ===

```

**c を選んだ**（上の表の 3 行目。「止まりが取得元の保持（10 日）を超えたら、諦めて見込みの下限から再開する」）。
補足は付いていない。推奨と同じ側で、**未回答は無い**。

**決まったこと**: 時計の食い違いが解消しないまま止まりが取得元の保持（10 日）を超えたら、

D4 の gap の記録として残る（FR-85 のとおり。黙っては消えない）。b は選ばれなかったので、
**飛んだ時刻のまま取り直して `event_time` の行を増やすことはしない**（C6 の芯は残る）。

**効く先**（この record では書き換えない。deep.md に決定として残すだけ）:

| 何を | いまの逐語 | c にするとどうなるか |
