### Q4. W32Time が止まっている間、PC の測定記録に「最後に同期した時刻・同期元」が残らない（premise。review/code.md R22）

- **なぜ人間の判断か**: 前提の誤り（`premise`）かつ `uncaptured`。Q3 の ③（Windows の時刻同期の状態も並べる）は「`w32tm` で読める」を前提にしていた
  （design D8 の Task 1.3 の確かめ）。ところが W32Time は既定で手動（トリガー）起動で、手元の既定の状態は**停止中**
  （`sc.exe query w32time` → `STOPPED`、`sc.exe qc w32time` → `DEMAND_START`）。止まっている間の記録は `clock_unavailable` に
  `windows-time-sync` / `service_stopped` だけを持ち、**最後に同期した時刻と同期元は 1 つも残らない**。残さなかった期間の値は後から作れない
- **分かっていること**: 同じ情報は OS のイベントログに残っている。`wevtutil.exe qe System "/q:*[System[Provider[@Name='Microsoft-Windows-Time-Service']]]" /c:5 /rd:true /f:text`
  が rc=0 で、Event 35（`2026-09-30T01:18:08Z`「タイム ソース time.windows.com,0x9 … の同期をとっています」）と Event 37 が読めた。
  design D8 は読めないときの候補にこのイベントログを挙げていたが、2026-09-30 の訂正（commit 51cebee、本人の指示）は `service_stopped` で残す形にし、イベントログは確かめていない
- **分かっていないこと**: 管理者権限なしで System のイベントログの Time-Service の記録が読めるか（読めたのは WSL から起動した高い完全性のプロセス）
- **推奨**: 止まっている間はイベントログ（Time-Service の 35 / 37）から最後の同期の時刻と同期元を読んで並べる。先に一般の利用者の権限で読めるかを確かめ、読めなければ止まっていることだけを残す（いま）に戻る
- どちらでも **W32Time は起動しない・起動の種類も変えない**（2026-09-30 の本人の指示のまま）
- **本人の答え**: 止まっている間はイベントログから最後の同期の時刻と同期元を読んで並べる（明示的に選択。補足なし）
- **効く先**: design D8（口を 1 つ足す）/ tasks（PC の Task 8・9 の追加分）/ spec（desktop-collection の「Windows の時刻同期の状態」の Scenario に、止まっているときの形を足すか）
