## Why

**D-01 の記録を、このシステムを使わずに読む手段が無い。** 読み出し口は `GET /events` だけで、6 列を全件 1 回で返す
（感度・端末・2 つ目の時刻・`payload`・前の版・稼働の元データが無く、1 年分をメモリに載せる）。
データ所有・可搬性はこのシステムの第一の優先順位（NFR-16）なのに、いま持ち出せるのは DB のダンプだけで、
**それは本人が消した場面もそのまま含む**。

いま作る理由は 2 つ。

1. **ST22 が「消したことにする」を作った今、書き出しが無いまま DB を持ち出すと消した場面が外へ出る。**
   ST22 の Q1（`loss: exported`）は「書き出しができたときに消した場面の緯度経度が外へ出て戻らない」を理由に決めた。
   その担保の残り半分は ST33 が持つ（`docs/handoff/ST33.md` の R2）
2. **S-7 設定の最初の節になる。** 後続（ST13 / ST15 / ST24 / ST29）が同じ画面に節を足す型をここで作る

## What Changes

深掘りは **1 巡・5 問**（A 3 / B 2）。本人がすべて選択肢から明示的に選んだ（未回答 0・推奨のまま 0・**推奨と違う側 1**（Q4））。
独立レビュー（`deep-review`）は **12 件** —— 問いを 1 つ足し（Q5。印だけでは ST22 の Q1 に届かない）、問いの前提と文面を 5 件直し、
聞かないで決める既定を 5 件足した・直した。聞かずに決めた既定 C1〜C18 に本人の異論は無かった。

- **設定画面（S-7）に「全記録の書き出し」の節を置く**（Q3）。押す前にソースごとの件数と期間を出し、押したらその場で進み具合を出す
  （画面を離れても書き出しは続く）。前回の書き出し（時刻・行数・大きさ）を常に出す。書き出した後に記録を消しても知らせない
- **書き出したファイルは自宅 PC の決まったフォルダにだけ置く**（Q1）。画面から端末へは渡さない。
  置き場の既定は `%LOCALAPPDATA%\ashiato\export`（C16。同期されうるドキュメント・デスクトップを既定にしない）
- **毎回、日時つきの別のフォルダに書く**（Q4。推奨を覆した）。古い書き出しを消すのは本人の手で、システムは消さない
- **形式は JSON Lines（1 行 1 件）＋ 説明書**（Q2。仮）。表ごとに 1 ファイル、全列、原文は受け取った文字列のまま（C4）、
  時刻は UTC の ISO 8601 にずれとタイムゾーン識別子を列のまま添える（C14）。畳まずに出し、畳む規則を説明書に書く（C3）
- **本人が消した場面を出さない**（C1 / Q5）: 削除の印の付いた記録を出さず、**さらに本人が消した滞在の時間に入る緯度経度を持つ行を、
  ソースを問わず（書庫の位置・写真の位置を含む）、前の版を含めて出さない**。書き出しの前に、遅れて届いた位置に印を付ける判定
  （ST22 の作り直しと同じもの）を 1 回走らせる（C18）。画面の件数も同じ範囲で数える（書き出す行数と食い違わせない）
- **入れるもの**: 記録・前の版（親が生きているもの）・読むための辞書（登録簿・個人属性の種類と名前・滞在の基準）・
  稼働の元データ（生存信号から取得の回数と原文を除いたもの・停止と破棄の期間・破棄の報告）（C2 / C7 / C15）
- **入れないもの**: 削除と消去の台帳・日ごとの件数（`core.coverage`）・取り込みと作り直しの内部表・書き出しの台帳・D-02 の原本（C6 / C12）。
  説明書に削除済みの件数を書かない（C8）
- **全期間・全ソースを 1 つの時点の写しで読む**（C9 / C10）。書き出す列は `core.event` の列の一覧と機械で突き合わせ、欠けていたら落とす（C4）
- **書き出した事実を 1 回 1 行、追記のみの台帳に残す**（C17。開始・写しの時点・終了・表ごとの件数・置き場。中身は残さない）

**BREAKING は無い。** `GET /events` は変えない（C13。ST01 の読み出し経路）。書き出しは別の口にする。
口の資格情報は `GET /events` と同じ扱い（C11）。

## Capabilities

### New Capabilities

- **`data-durability`** —— 全記録の書き出し（範囲・除くもの・形式と説明書・置き場・写しの時点・書き出しの台帳）と、
  S-7 設定の書き出しの節。**ST33 が最初に作る。** ST10 / ST30 / ST31 / ST32 が後から同じ capability に足す

### Modified Capabilities

なし。`record-deletion`（ST22）は**読むだけで要件を変えない**（「本人が消した滞在」と遅着に印を付ける判定を呼ぶ）。
`record-envelope` / `collection-coverage` / `browsing-views` も変えない。

**capability の前倒し**: なし。INDEX の割当（`data-durability` → ST33）のとおり。

## 止めた理由と、解ける時点

**proposal で止める。** `requires` の **ST22 が下流を走っていて archive 前**（record で requires に足したので、
`board.py` の `admit()` はいま `proposal` を返す）。

1. 書き出しが除く範囲（Q5）と遅着の判定（C18）は、ST22 の `record-deletion` の「本人が消した滞在」と
   「消した時間帯に後から届いた位置に印を付ける」の上に立つ。ST22 の実装がその spec に穴を開けたら、ST33 の specs も書き直しになる
2. `record-deletion` の正典は ST22 の archive まで `openspec/specs/` に無く、Scenario から引けない

ST22 が archive されたら、specs → design → tasks を書く。

## Impact
