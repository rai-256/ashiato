## この Story に宛てられたもの（深掘りより先に読んだ）

- `docs/handoff/ST33.md` の **st22-record-deletion R2** —— 書き出しは削除済みを除いた読み出し（`core.event_live` / `core.event_version_live`）を読む。
  出す側に回すなら本人に問う（`loss: exported`）。**印の付いた記録は出さない側に置いたので問いにしない**（C1）。削除と消去の台帳を入れるかは ST33 が決める（C6）
- **ただし印だけでは申し送りの目的（ST22 の Q1 の担保）に届かない**（レビュー **R1 / R2**）。印の無い行（書庫の位置・生きている滞在の前の版・写真の位置）が同じ場面の緯度経度を持つ → **Q5**

## 前提として確かめたこと（schema の手順 1〜5）

### 手順 1: satisfies の要件どうしの衝突

- satisfies は **NFR-16** の 1 本だけ。ただし NFR-16 と **NFR-15**（「拠点外に出るのは暗号化されたバックアップのみ」）が、
  書き出したファイルの行き先で衝突する。画面（V-01）は携帯から Tailscale 越しに開くので、画面から受け取れる形にすると携帯に全記録の平文が入る → **Q1**
- NFR-15 を持つのは ST28（`data-sensitivity`。いま上流を並走している）。ST33 は NFR-15 を満たす側の選択肢を推奨にし、訂正が要る選択肢には訂正を書いた

### 手順 2: doors

- `doors: []`。satisfies の要件は扉リストのどの項の関与要件にも現れない
- ただし **扉 #15**（緩く始めて締めると、締める前に外へ出た分が戻らない）と同じ性質が Q1 にある。書き出しは「外へ出す」経路そのもの

### 手順 3: この Story で新たに立つ一方通行

- **外に出すもの**: 書き出したファイル。一度出たら回収できない → 何を出すか（C1〜C7）と、どこへ出るか（Q1）
- **書き出した後に消した記録**: ファイルはその時点の写しなので、後から滞在を消してもファイルの中に残る → Q3 の軸 3 と Q4
- 捨てるもの・変換するもの: **原文を変換しない**（C4。`raw` は `text` のまま逐語。`jsonb` にすると崩れる理由は `migrations/202609092315_raw_text.sql`）

### 手順 4: 日常に影響する選択

- 書き出しは本人が押したときだけ走る（定期実行は作らない —— バックアップは ST30）。毎日目に入るものは無い
- 容量: 運用 1 年目で 1 回 約 1.0 GB（推定。1 日 約 3,240 行 × 約 0.9 KB。位置 約 960 件 = 60 秒間隔 × 取得率 67 %（ST01 の実測）、ウィンドウ 約 2,000 件（FR-12 の通常 1,500〜3,000）、
  生存信号 約 13 件（6 時間ごと）。NFR-5 の上限（年 6 GB）なら 3 年で 17 GB 前後）→ Q4。**当初の proto は生存信号を 100 倍多く、ウィンドウを 1/7 に数えていた**（レビュー **R7**）
- 画面: S-7 設定はまだ 1 枚も無く、ST33 が最初の節 → Q3

### 手順 5: 既存のコード

- **読み出し口は `GET /events` だけ**（`crates/server/src/lib.rs` の `events`）。`core.event_live` を読み、6 列（`id` / `logical_source` / `event_time` / `tz_id` / `origin` / `raw`）を
  **全件 1 回で**（`fetch_all`）返す。書き出しには使えない —— 列が足りず（感度・端末・2 つ目の時刻・`payload` など）、前の版も稼働の元データも無く、
  1 年分をメモリに載せる。**ST01 の読み出し経路で「壊してはいけないもの」なので変えない**（C13）。書き出しは別の口にする
- **削除済みを除く読み出しは既にある**: `core.event_live`（`deleted_at IS NULL`）と `core.event_version_live`（親が生きている前の版だけ。感度も親から）。
  ST22 の連鎖（`user:cascade`）と後から届いた印（`user:late`）も `deleted_at` に載るので、**印の付いた行は**ビューを読めば除かれる（ST22 design D4）。
  **印の無い行は除かれない**（レビュー **R1 / R2**）: 印を付けるのは基準のソース（`c01-location`）だけで（ST22 design D3）、書庫の位置（ST12）・写真の位置（ST09）は別のソース。
  `core.event_version_live` が除くのは**親が消えた**版だけで、生きている滞在の前の版が消した時間を含むことがある（ST22 のテストの DB で 4 件）。
  作り直しが失敗している間の遅着は印がまだ無い（ST22 design D6 の「残る穴」）→ **Q5** と C18
- **畳む読み出しもある**: `core.event_folded`（FR-22 の「1 件として読む形」。適用は書き出しを含む各 Story）。書き出しは畳まずに出す（C3）
- `core.coverage.event_count` は**削除済みも数える**（ST02 の design D34 / ST22 の Q3）。書き出しに入れると、日ごとの件数と記録の数の差から「その日に消した」ことが読める → 入れない（C6）
