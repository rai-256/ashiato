## ADDED Requirements

### Requirement: PR の CI は、インストールと更新の試験の後に、配る形を外につながる状態で初めから入れて 5 分置く

WHEN Windows のインストールの試験の job が、インストールと更新の試験の段を全部終えた THE SYSTEM SHALL 置く段（インストールと更新の試験の手順より後の段）で、次の順に進める: 前の段が入れたもの（サーバ・DB・更新係のサービスの登録、プログラムの置き場、状態の置き場、更新係の置き場、PC の収集アプリの置き場）を全部消す → 更新係の外向きの塞ぎを外す → 配る形のサーバの zip（Windows の配布物の job が組んだ配る形のもの）を入れる → 配る形の PC の収集アプリを設定せずに起こす → 入れ終わってから 5 分置く。
THE SYSTEM SHALL 「置く段の始まり」を、塞ぎの規則を消す直前の時刻とし、「置く間」を、配る zip を入れ終わってサーバの healthz が 200 になった時刻からの 5 分とする（確かめた記録は置く段の始まりより後を、起こし直し・止まり・誤りの行は置く間を数える。更新係は入れた直後に確かめるので、置く間より前に記録を書く）。
THE SYSTEM SHALL 置く段より前の段を、job の最初のインストールより前に置いた更新係の外向きの塞ぎを外さずに走らせる。
IF 前の段が入れたものを消せない、または塞ぎを外した後も塞ぎの規則が残る THEN THE SYSTEM SHALL 配る zip を入れずに置く段を落とす。
THE SYSTEM SHALL 置く段と、Windows のインストールの試験の job に、時間の上限を持たせる。
THE SYSTEM SHALL 置く段が出すもの（起こし直しの回数・見つけた誤りの行・確かめた記録の行・落ちたときの観測）を、インストールの試験の台本と同じ観測の部品で秘密の値を伏せてから出す（公開の CI のログに出る）。
THE SYSTEM SHALL 置く段の判定（下の 4 つの Requirement）が 1 つでも外れたら、Windows のインストールの試験の job を落とす。

導出元: CH22（受け皿の依頼 #332。本人の決定: CI の Windows のインストールの試験で、配る形のサーバを入れた後に外向きの塞ぎを外して数分置き、サービスの再起動の繰り返し・panic・誤りの記録の連続・クラッシュを機械が判定する。PR の CI の後段で 5 分ほど。最初のインストールより前に塞ぐ ST57 D18 は残す。製品のコードは変えない。長く置く毎晩の試験と、本物の答えの形の比べはやらない）。
深掘り第 1 回 Q5（消してから塞ぎを外し、それから入れる。更新係は入れた直後に 1 回確かめ、次は 24 時間後なので、入れた後に外すと 5 分の間に配布元へ聞かない。premises P1・P9）・Q1（PC の収集アプリも置く）・Q7（見つけた不具合で段を緩めない）。design D1〜D3・D5・D8・D9・D12（外れを許す一覧を持たない・送り先を設定しない・答えの形を見本と比べないは、台本の作りの決まりとして D12・D7 に置く）。
0.1.0 は入れて放っておくだけで更新係が 10 秒ごとに落ちたが、CI は外向きを塞ぎ、偽の受け手だけで試していたので素通りした（#329）。

- **THEN** 検査は終了コード 0 で終わる

#### Scenario: 配る形のサーバを外につながる状態で 5 分置くと、落ちず・止まらず・誤りが続かず、本物の配布元に確かめる

- **GIVEN** CI の Windows の runner で、ほかのインストールと更新の試験を終えた後
- **WHEN** 置く段が、前の段の入れたものを消し、塞ぎを外し、配る形のサーバの zip を入れて 5 分置く
- **THEN** 置く間の 3 つのサービスの起こし直しは 0 回で、置き終わりに 3 つのサービスが実行中で healthz が 200 で、同じ誤りの行が続かず、更新係の確かめた記録に置く段の始まりより後の確かめた行が 1 行以上ある

### Requirement: 置く間にサービスが起こし直された・止まったままなら、置く段を落とす

WHILE 置く間（入れ終わって healthz が 200 になってから 5 分）THE SYSTEM SHALL `ashiato-db`・`ashiato-server`・`ashiato-updater` の状態とプロセスの番号を見続ける。
IF 置く間に 3 つのサービスのどれかが 1 回でも、実行中でなくなる・プロセスの番号が変わる・サービスの異常な終わりの記録（Windows のシステムの記録）を持つ THEN THE SYSTEM SHALL 置く段を落とし、どのサービスが何回起こし直された・止まったかを出す。
IF 置き終わりに 3 つのサービスのどれかが実行中でない、またはサーバの healthz が 200 でない THEN THE SYSTEM SHALL 置く段を落とす。
THE SYSTEM SHALL 置く間より前のサービスの終わりの記録（前の段がわざとサービスを終わらせる試験の記録と、入れる最中の記録）を数えない。
THE SYSTEM SHALL システムの記録を読めたか（読めたなら置く間の件数）を、落ちない回にも 1 行出す。
IF システムの記録を読めない THEN THE SYSTEM SHALL 置く段を落とさず、CI の警告を出し、状態とプロセスの番号の読みだけで判定する。

導出元: CH22。深掘り第 1 回 Q2（1 回でも起こし直されたら落とし、置き終わりの状態も見る）。review/deep.md R2（サーバの起動の拒否は終了コード 0 で止まり、起こし直されない。起こし直しを数えるだけでは止まったままを見逃す）・R7。premises P2・P11。design D4・D5。
更新係の panic はログに出ず、プロセスの終わりとしてだけ見える。

#### Scenario: 置く間に 1 回でも起こし直されたら、サービスの名前と回数を出して落ちる

- **WHEN** 置く段の判定を走らせる

- **WHEN** 置く段の判定を走らせる
- **THEN** 判定は 0 でない終了コードで終わり、標準エラーに `ashiato-server` が実行中でないことがある

#### Scenario: 置き終わりに healthz が 200 でなければ落ちる

- **WHEN** 置く段の判定を走らせる
- **THEN** 判定は 0 でない終了コードで終わり、標準エラーに healthz の番号 503 がある

#### Scenario: 置く間より前のサービスの終わりの記録は数えない

- **GIVEN** 置く間より前の時刻だけに `ashiato-server` の異常な終わりの記録を持つ偽のシステムの記録と、置く間ずっと実行中で番号の変わらない 3 つのサービスと、200 の healthz
- **WHEN** 置く段の判定を走らせる
- **THEN** この判定は通り、起こし直しの回数は 3 つとも 0 と出て、システムの記録を読めたことと置く間の件数 0 の行がある

#### Scenario: システムの記録を読めなければ、警告を出し、状態とプロセスの番号で判定する

- **GIVEN** 終了コード 1 で何も返さない偽のシステムの記録の命令と、置く間ずっと実行中で番号の変わらない 3 つのサービスと、200 の healthz
- **WHEN** 置く段の判定を走らせる
- **THEN** この判定は通り、標準出力に CI の警告の行（`::warning::`）とシステムの記録を読めなかった行がある
- **AND** 同じ命令のまま `ashiato-db` の番号を 1 回変えた入力では、判定は 0 でない終了コードで終わる

### Requirement: 置く間に同じ誤りの行が続いたら、置く段を落とす

THE SYSTEM SHALL 置く間に書かれた誤りの行を、置き場ごとに次のとおり数える: 更新係の誤りのログ（`logs/updater.log`）は全部の行、サーバの日付のログは誤りの段の行と panic の行、DB のログは `ERROR`・`FATAL`・`PANIC` の行、PC の収集アプリのログは誤りの段の行（どれも警告の段の行は数えない）。
THE SYSTEM SHALL 行の頭の日時と DB のログのプロセスの番号を除いた中身が同じ行を、同じ誤りとして数える。
IF 置く間に 1 つのログに同じ誤りが 3 回以上ある THEN THE SYSTEM SHALL 置く段を落とす。
IF 置く間にサーバのログに panic の行が 1 行でもある THEN THE SYSTEM SHALL 置く段を落とす（分けた作業の panic はプロセスを止めず、起こし直しとしては見えない）。
THE SYSTEM SHALL 落とすかどうかに依らず、置く間に見つけた誤りの行を全部、置き場の名前を付けて出す。

導出元: CH22。深掘り第 1 回 Q3（同じ誤りが続いたら落とし、1〜2 回の誤りは出力に出すだけ）。review/deep.md R8（更新係は誤りしか書かない・panic の hook はサーバだけ・DB のログは LOG と ERROR が混ざる）。premises P8。design D6（仮）。review/spec.md R8（サーバは分けた作業で動き、その中の panic は誤りの段の 1 行だけを書いてプロセスを残す。`crates/server/src/lib.rs:4583-4586`）。

### Requirement: 置く間に更新係と PC の収集アプリが本物の配布元に確かめた記録が無ければ、置く段を落とす

THE SYSTEM SHALL 置く間に、更新係の確かめた記録と PC の収集アプリの確かめた記録（PC の収集アプリは台本の起こし直しより後）に、時刻が置く段の始まりより後の「確かめた」（成功）の行がそれぞれ 1 行以上あることを確かめる。
IF その行が無く、置く段の始まりより後の行の理由が全部「問い合わせの上限」である THEN THE SYSTEM SHALL 置く段を落とさず、CI の警告を出す。
IF その行が無く、ほかの理由（配布元に届かない・時間切れ・配布元が見つからない・読めない答え・宛先なし）の行がある、または置く段の始まりより後の行が 1 行も無い THEN THE SYSTEM SHALL 置く段を落とす。
THE SYSTEM SHALL 置く段の始まりより後の確かめた記録の行を全部出す。

導出元: CH22。深掘り第 1 回 Q4（段の始まりより後の「確かめた」が 1 回は無ければ落とす。上限だけ警告）。review/deep.md R1（記録が 1 行も無いまま緑になる道: 24 時間の間隔・塞ぎの外し漏れ・前の段が残した切った印）・R4（理由の語は ashiato の誤りか外の揺れかで分かれていない）。premises P1・P5・P6・P12。design D5・D13。
配布元が落ちている日（5xx・時間切れ）も赤になり、走らせ直しで済ませる。

- **WHEN** 置く段の判定を走らせる
- **THEN** 判定は 0 でない終了コードで終わる

### Requirement: 置く段は、PC の収集アプリを設定せずに起こし、途中で 1 回起こし直して、終わらずに動き続けることを確かめる

THE SYSTEM SHALL 置く段で、配る形の PC の収集アプリの zip を、送り先を設定せず、前の置き場を消してから起こし、入れ終わってから決まった時間（置く段の台本の定数）の後に 1 回止めて起こし直す（本人が翌日 PC を起こした場面にあたる。2 回目の起動で、案内の済んだ PC の収集アプリは起きてすぐに配布元へ確かめる）。
IF 置く間に、台本が止めた 1 回のほかに PC の収集アプリのプロセスが終わる、または置き終わりにプロセスが無い THEN THE SYSTEM SHALL 置く段を落とす。

導出元: CH22。深掘り第 1 回 Q1（設定せずに置き、途中で 1 回起こし直して確かめさせる）。依頼の「PC の収集アプリも配る形で置くかは深掘りで決める」。review/deep.md R3（1 回目の起動は案内を出すだけで確かめない・定期の確かめは起動の 1 時間後から・通知の差出人を登録できなければ確かめる係を付けない）。premises P3・P7・P10。design D7。
確かめた記録と誤りの行は、上の 2 つの Requirement が同じ規則で見る。

#### Scenario: 台本が止めたほかに PC の収集アプリが終われば落ちる

- **GIVEN** 台本の起こし直しより後にプロセスが消える偽の PC の収集アプリ
- **WHEN** 置く段の判定を走らせる
- **THEN** 判定は 0 でない終了コードで終わり、標準エラーに PC の収集アプリが終わったことがある

#### Scenario: 起こし直しより前の確かめた行だけなら、PC の収集アプリの確かめは無いとみなす

- **GIVEN** 台本の起こし直しより前の時刻にだけ「確かめた」の行を持つ PC の収集アプリの確かめた記録と、置く段の始まりより後に「確かめた」の行を持つ更新係の確かめた記録
- **WHEN** 置く段の判定を走らせる
- **THEN** 判定は 0 でない終了コードで終わり、標準エラーに PC の収集アプリの確かめた行が無いことがある

#### Scenario: 配る形の PC の収集アプリは、設定せずに起こし直すと本物の配布元に確かめ、動き続ける

- **GIVEN** CI の Windows の runner で、置く段が配る形のサーバを入れた後
- **WHEN** 置く段が配る形の PC の収集アプリを設定せずに起こし、決まった時間の後に 1 回起こし直して、置き終わりまで置く
- **THEN** PC の収集アプリの確かめた記録に起こし直しより後の確かめた行が 1 行以上あり、置き終わりにプロセスが動いていて、同じ誤りの行が続かない

## MODIFIED Requirements

### Requirement: 更新を確かめる問い合わせは、版の一覧を取る決まった形だけを配布元へ送る

THE SYSTEM SHALL 3 つの部品の更新の問い合わせを、方法 `GET`・本文なしにし、道を次の 2 つに限る: 開発版でない部品は `/repos/rai-256/ashiato/releases?per_page=20`、開発版の部品は `/repos/rai-256/ashiato/releases/tags/nightly`。
THE SYSTEM SHALL 問い合わせの見出しを、`Host`・`User-Agent`・`Accept`・`Accept-Encoding`・`Connection` の 5 つの名前の内側に限り、`User-Agent` の値を `ashiato-update-check` に、`Accept` の値を `application/vnd.github+json` に固定する。
THE SYSTEM SHALL 問い合わせのどこ（道・見出し・本文）にも、自分の版番号・端末の機種・OS の版・端末や利用者の識別子・資格情報・記録を入れない。
THE SYSTEM SHALL 転送（3xx）は同じ `api.github.com` の中のものだけを追い、ほかの宛先への転送は「確かめられない」として扱う。
THE SYSTEM SHALL 暗号化した接続の証明書を OS の持つ根で確かめ、更新係と PC の収集アプリに根の一覧の部品を同梱しない。
THE SYSTEM SHALL 宛先を組み立てのときの定数にし、配る組み立て（サーバの更新係・PC の収集アプリの配る zip、携帯の配る APK）には宛先を実行時に変える口を持たせない。
THE SYSTEM SHALL 宛先を差し替える口を試験の組み立てにだけ持たせ、試験の組み立ては差し替えの宛先が無ければ確かめない。
THE SYSTEM SHALL 自動の試験が本物の配布元（`api.github.com`）へ繋ぐのを、次の 2 つに限る: (1) CI の PC の収集アプリの実行時の job が走らせる握手の試験 `tls_online_*`（試験の組み立ての HTTPS の係が OS の根で証明書を確かめて握手を終える。更新係のものは版の一覧の道へ、PC の収集アプリのものは根 `/` へ、それぞれ 1 回）、(2) CI の Windows のインストールの試験の job の最後の置く段（配る形のサーバと PC の収集アプリを、更新係の外向きを塞がずに入れて置く。Requirement「PR の CI は、インストールと更新の試験の後に、配る形を外につながる状態で初めから入れて 5 分置く」）。ほかの自動の試験は本物の配布元に問い合わせず、配る組み立てを動かす CI は、置く段より前の全部の段を、更新係の外への接続を塞いで走らせる（塞ぐのは更新係の外向きだけで、ST57 D18 の今の塞ぎと同じ。配る組み立ての中で配布元に問い合わせるのは更新係だけで、PC の収集アプリの配る組み立ては置く段より前の段で動かさない）。

導出元: FR-116（機械の検査で固定する。要件の Q7）。聞かない既定 C2・C8。premises P1〜P3・P10。
CH22 で、自動の試験が本物の配布元へ繋ぐのを名指しの 2 つに限る形に改めた（受け皿の依頼 #332 の本人の決定「正典の『自動の試験は本物の配布元に問い合わせない』を、置く段と握手の試験 `tls_online_*` に合わせて改める」。design D10）。2 つとも共有の runner の IP から 1 回の run で数回だけ聞く（認証の無い問い合わせの上限は IP ごとに 1 時間 60 回。CH22 premises P6）。
GitHub の API は `User-Agent` の無い問い合わせを断る（P3）ので、見出しを 1 つは送る。`Connection` は Android の通信の部品が自分で足すことがある（design D13（仮）。聞かない既定 C2 の 4 つに足した）。
自分の版は送らず、取った一覧を手元で選ぶ。配布元から見分けられるのは開発版かどうか（道の違い）だけで、開発版の印 `nightly` は公開されている。

#### Scenario: 更新係の問い合わせは版の一覧の取得だけである

- **GIVEN** 宛先を手元の受け手に差し替えた試験の組み立ての更新係（版 `0.4.0`）
- **WHEN** 更新係が 1 回確かめ、受け手が受けた問い合わせを全部読む
- **THEN** 問い合わせは 1 件で、方法は `GET`、道は `/repos/rai-256/ashiato/releases?per_page=20`、本文は 0 バイト、見出しの名前は許した 5 つの内側、`User-Agent` は `ashiato-update-check`、`Accept` は `application/vnd.github+json` で、どの見出しの値にも `0.4.0` が無い

#### Scenario: PC の収集アプリの問い合わせは版の一覧の取得だけである

- **GIVEN** 宛先を手元の受け手に差し替えた試験の組み立ての PC の収集アプリ（版 `0.4.0`・端末の識別子 `pc-0123456789ab`）
- **WHEN** PC の収集アプリが 1 回確かめ、受け手が受けた問い合わせを全部読む
- **THEN** 問い合わせは 1 件で、方法・道・本文・見出しの名前と値は更新係と同じ決まりのとおりで、どの見出しの値にも `0.4.0` と `pc-0123456789ab` と資格情報が無い

#### Scenario: 携帯の問い合わせは版の一覧の取得だけである

- **GIVEN** 宛先を端末の中の受け手に差し替えた試験の組み立ての携帯の収集アプリ（本物の Android の上）
- **WHEN** 携帯の収集アプリが 1 回確かめ、受け手が受けた問い合わせを全部読む
- **THEN** 問い合わせは 1 件で、方法・道・本文・見出しの名前と値は更新係と同じ決まりのとおりで、どの見出しの値にも端末の機種名（`Build.MODEL`）・OS の版（`Build.VERSION.RELEASE`）・アプリの版・資格情報が無い

#### Scenario: 更新係と PC の収集アプリは根の一覧を同梱しない

- **WHEN** 更新係と PC の収集アプリを組み立てる部品の一覧を、同梱の根の一覧の部品（一覧は検査の側が持つ）と突き合わせる
- **THEN** 一致する部品は 0 件である

#### Scenario: 開発版の部品は印 nightly の 1 件だけを取る

- **GIVEN** 宛先を手元の受け手に差し替えた、版 `0.4.0-dev.20261102` の更新係
- **WHEN** 更新係が 1 回確かめる
- **THEN** 受け手が受けた道は `/repos/rai-256/ashiato/releases/tags/nightly` だけである

#### Scenario: 別の宛先への転送は追わない

- **GIVEN** 手元の受け手が `301` で `api.github.com` でない宛先へ転送を返す
- **WHEN** 更新係が確かめる
- **THEN** 更新係は転送先へ問い合わせず、その回を「確かめられない」（理由: 読めない答え）として記録する

#### Scenario: 配る組み立ては宛先を変える口を持たない

- **WHEN** 配る形でサーバの Windows の配布物と PC の収集アプリの配布物を組み、`ashiato-updater.exe` と `ashiato-collector-windows.exe` の中の文字列を読む
- **THEN** 宛先を差し替える口の名前（`ASHIATO_UPDATER_TEST_`・`ASHIATO_COLLECTOR_TEST_UPDATE_URL`）が無く、宛先 `https://api.github.com/repos/rai-256/ashiato/releases` がある

#### Scenario: 携帯の配る APK の宛先は配布元である

- **WHEN** 配る形で携帯の APK を組み、組み立ての定数の更新の宛先を読む
- **THEN** 宛先は `https://api.github.com/repos/rai-256/ashiato/releases` で、配る組み立てに宛先の差し替え（`-P`）を渡すと組み立ては 0 でない終了コードで落ちる

#### Scenario: 試験の組み立ては差し替えの宛先が無ければ確かめない

- **GIVEN** 宛先を差し替えていない試験の組み立ての PC の収集アプリ
- **WHEN** 確かめる時を迎える
- **THEN** 外への問い合わせは 0 件で、確かめた記録に「宛先なし」が 1 行ある

#### Scenario: 網に出る試験を走らせる手順は、握手の試験の 1 つだけである

- **GIVEN** この repo の CI の定義（`.github/workflows/` の全部の定義）
- **WHEN** 手順の命令（注記の行を除く）を読む
- **THEN** 網に出る試験（`--ignored`・`--include-ignored`）を走らせる手順は、PC の収集アプリの実行時の job の `tls_` に絞った 1 つだけである
- **AND** `tls_` に絞らない `--ignored` の手順を足した写しでは、検査が 0 でない終了コードで落ちる

#### Scenario: 更新係の外向きの塞ぎを外す手順は、置く段の 1 つだけである

- **GIVEN** この repo の CI の定義（`.github/workflows/` の全部の定義）
- **WHEN** 手順の命令（注記の行を除く）を読む
- **THEN** 更新係の外向きの塞ぎを外す手順（置く段の台本を走らせる・塞ぎの規則を消す）は、Windows のインストールの試験の job の置く段の 1 つだけである
- **AND** 別の手順に塞ぎの規則を消す命令を足した写しでは、検査が 0 でない終了コードで落ちる
