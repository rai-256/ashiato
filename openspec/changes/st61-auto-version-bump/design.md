## Context

今は版を `Cargo.toml` の出所の版（0.1.1）から手で上げる決まりで、上げないまま同じ 0.1.x で中身の違う組み立てができていた（2026-11-19）。
FR-134 は「main に merge されたら、main に commit を積まずに、番号を 1 つ進めた組み立てを作る」を求める。番号は 1 列に並び、チャンネルの意味を持たない（FR-104）。左の数字だけ本人が決める（NFR-25）。

いまの仕組みで効くもの（premises）:

- main への push の CI は次の push に取り消される（`ci.yml` の `concurrency`。P12）。確認バッチの merge の run は、直後の archive の merge にほぼ取り消されていた
- 同じ group で待てる run は 1 つだけ（P13）
- 30 日の merge 115 回のうち、製品に触れたのは 27 回。確認バッチの merge は 21 回（P2・P3）
- CI の成果物は 90 日で消える（P1）。配布元にリリースも印もまだ無い（P9）
- 版の検査は 4 か所にある: `tools/release/version.sh`・`crates/build-stamp/src/lib.rs`・`collector-android/app/build.gradle.kts`・`web/build-stamp.ts`。どれも「渡した版の MAJOR.MINOR.PATCH = 出所の版」を見る
- 携帯の versionCode の式は真ん中・右を 99 までしか持てない（P8）

第 1 回の深掘りは答え待ちで、この design は推奨の答えで書いた（deep.md Q1〜Q4）。

## Goals / Non-Goals

**Goals:**

- main の、CI が通り製品が変わった commit に機械が番号を付け、番号ごとに 1 つの組み立てを残す
- 同じ番号で中身の違う組み立てを作らない（番号を持たない組み立ては 0.0.x を名乗る）
- 携帯の組み立てが 1 年分の番号でも落ちない
- 札の形（ST62・ST63）ができるまで、今の正式版・開発版の組み立てを緑のまま保つ

**Non-Goals:**

- 札（正式版・ベータ版・開発版）を番号へ動かす操作・公開・正式な鍵の署名（ST62）
- 開発版の札と更新の確認の追う相手（ST63）
- 札の無い組み立てを入れない守り・本人の PC と携帯の移行（ST64）
- 番号の組み立ての消し方（ST62。docs/handoff/ST62.md）

## Decisions

### D1（仮）. 番号を付けた組み立ては全部、配布元の下書きのリリースに残す（premises の C1）

番号ごとに下書き 1 つ（印 `build-<番号>`）に、4 つの配布物と署名していない携帯の APK（D2）を置く。消さない。

- 失わない側: 消さないので、どの番号にも後から組み直さずに札を付けられる（FR-135）
- 費用: 月に約 1.7 GB（P2 の 27 回 × P4 の 62 MB）。公開のリポジトリで置き場の代金は無い（review/deep.md R3）
- 下書きは認証なしの一覧に出ない（P5。公式文書で確かさ 2。Task 9 で使い捨ての下書きと認証なしの `curl` で 4 に上げる）。出ても、更新の確認は `draft: true` を数えない（正典の Scenario「一覧に `draft: true` の `v0.5.0` がある」）
- 反転条件: 置き場の容量の上限に当たる（P11。確かめていない）・下書きが認証なしの一覧に出る（P5 が外れる）→ 置き場を変える（失うものは無い）

### D2（仮）. 番号ごとに残す携帯の APK は、署名していないものも一緒に残す（premises の C6）

debug の鍵で署名した APK（本人が試しに入れる用）と、署名していない APK（`ASHIATO_APK_UNSIGNED=1` で組んだもの）の 2 つを置く。署名していない APK の名前は `ashiato-collector-<番号>-unsigned.apk`。

- 失わない側: 正式な鍵を札のときに足すか main で付けるか（FR-135 の未決。ST62）のどちらに決めても、組み直さずに済む。debug の鍵で署名済みの APK を署名し直す道は試していない（P16）
- 費用: 番号ごとに APK が 1 つ増える（数十 MB 以下）
- 反転条件: ST62 が main の組み立てで正式な鍵を付けると決めたら、残すのは署名済みだけでよい

### D3（仮）. 携帯の versionCode は `左×10,000,000 + 真ん中×10,000 + 右`（deep.md Q2）

後ろの `-beta.<N>`・`-dev.<日付>` は値に入れない。真ん中 999・右 9,999・左 209 を上限にし、超えれば組み立てを落とす（上限の `209.999.9999` は 2,099,999,999 で、Android の上限 2,100,000,000 の内側。P7）。

- 最初の番号 0.2.0 は 20,000 で、前の式の 0.1.1 の 10,199 より大きい（D13）
- 同じ番号の `-beta.N` と正式は同じ値になる。札の形では同じ番号は同じ組み立てなので、同じ値でよい。移る間に同じ番号のベータ版と正式版を両方出すと、Android は同じ値の上書きとして入れる
- 開発版は別のアプリ（識別子 `.dev`）なので、正式版と値を比べない
- 対応表 `tools/release/version-table.tsv` を新しい式で書き直し、`version.sh` と gradle の `verifyVersionCodeTable` が同じ表で確かめる（今の型のまま）
- 反転条件: Q2 の答えが「今の式のまま」→ 式を戻し、D5 の規則を「右が 99 を超えるときだけ真ん中を上げる」にする（Q2 と Q3 は結び付いている。今の式で確認バッチごとに真ん中を上げると約 5 か月で 99 を超える）。「通し番号」→ 台帳（印 `build-*`）の数から値を決める

### D4（仮）. 番号は、main の push の CI が成功し、前の番号から製品が変わった commit に付ける（deep.md Q1）

番号付け（D10）は CI の run が終わったときに起き、次の全部を満たす commit に番号を付ける:

1. run は main への push で、この repo の枝から走り、成功で終わった
2. その commit は、番号の印 `build-*` の付いた最後の commit（以下「前の番号の commit」）の子孫で、main の first-parent の上にある
3. 前の番号の commit からその commit までの差分が `tools/release/changes.sh code` で真（`docs/`・`openspec/`・`*.md` 以外に触れる）
4. その commit にまだ番号が無い

判定はまず 4. を見る: 番号の印が既にある commit は、最新の番号でなくても（欠番の commit を、後の番号が付いてから走らせ直しても）その番号を返し、下書きに欠けた配布物だけを足す（D7。review/spec.md R4）。
番号の印がまだ 1 つも無いときは、3. の差分を、その commit の first-parent の親からの差分にする（最初の番号は、製品に触れる merge の commit に付く。review/spec.md R5）。

番号の組み立てが落ちたら、番号付けの run を走らせ直して同じ番号の続きを置く（D7）。走らせ直さないまま次の番号が付けば、落ちた番号は欠番になる（中身は次の番号の組み立てに入っている）。

- 取り消された・落ちた run の中身は、次に番号が付く子孫の commit の番号に入る（R1）
- 道具・CI・試験だけの merge にも番号が付く（R2。見分けを細かくしない —— 判定は PR の CI と同じ 1 つ）
- 反転条件: Q1 の答えが「コードに触れる merge 1 つずつ」→ 番号付けを CI から外して merge ごとに走らせ、待ちの仕組み（P13 の 1 つしか待てない制限を越える列）を足す。「全部の merge 1 つずつ」→ 上に加えて 3. を外す
- 要件へ戻すもの（D4 は仮。Q1 の答えで record の段が戻す。review/spec.md R11）: FR-134 の今の本文「merge のたびに」と、その未決「文書だけの merge でも番号を進めるか」（Q1）・「真ん中の数字をいつ上げるか」（Q3）・「式を変えるか」（Q2）を ★ で閉じる。Story ST61 の題「merge するたびに」と完了の判定 1 つ目（「main に merge すると…1 つ進んだ番号の組み立てができる」）も、答えに合わせて `stories.json` から直す（推奨のままなら「製品が変わった後の、CI が通った main の commit に」）

### D5. 真ん中の数字は、前の番号から間に確認バッチの merge があれば上げる（deep.md Q3）

前の番号の commit（D4）を除き、番号を付ける commit を含む main の first-parent の commit のうち、1 つでも確認バッチの merge（D15）があれば `<左>.<真ん中+1>.0`、無ければ `<左>.<真ん中>.<右+1>`。

- 年に 250 ほど真ん中が進む（0.250.x）。D3 の式の真ん中の上限 999 に約 4 年で届く。届く前に左を上げるか式を見直す（D14 が止めて知らせる）
- 反転条件: Q3 の答えが「月が変わったら」→ 前の番号と番号を付ける commit の日時（日本時間）の月が違えば上げる。「右が 99 を超えるときだけ」→ 右が 99 のときだけ上げる

### D6（仮）. 番号を持たない組み立ては 0.0.x を名乗る（deep.md Q4）

| 組み立て | 版番号 |
|---|---|
| PR・手元・main の push の CI | 出所の版 `0.0.1`（`Cargo.toml`） |
| CI の更新の試験 | `0.0.2`（前）・`0.0.3`（新）・`0.0.4`（互換の前）・`0.0.5`（互換の新）・`0.0.2-dev.20261115`・`0.0.3-dev.20261116` |
| 番号 | `0.2.0` から（D13） |

- `0.0.0` は使わない（インストーラが「版を読めない古いサーバ」の互換値に使う。P15）
- 更新の試験は今と同じく、組むたびにその runner の木の `Cargo.toml` の出所の版だけを替えて組む（ST58 D24 の形）。`update-apply-install.sh` の版の値と、それを書く正典の 8 つの Requirement の Scenario を直す（specs の MODIFIED）
- PR の組み立てどうしは同じ `0.0.1` を名乗る。組み立ての印の commit で見分ける
- 携帯の PR の APK の versionCode は 1（`0.0.1`）になり、本人の携帯の 0.1.x（10,099・10,199）と番号の組み立て（20,000〜）の上に上書きで入らない。試すには消して入れ直す（手元の未送信を先に送り切る）か、番号の組み立ての APK を使う（review/spec.md R13。Q4 の問いには書いていなかったので、GO 資料で示す）
- CI の配る形の組み立ての job（PR と main の push）は番号の形の版番号を渡さない。`check-guards.sh workflows` が見る（review/spec.md R9）
- 反転条件: Q4 の答えが「元にした main の番号を名乗る」→ 番号を持たない組み立てに `<番号>` を渡す。同じ番号で中身の違う組み立てができることを受け入れる答えなので、FR-134 の本文と食い違う（record で要件を直す）

### D7. 番号の記録は印 `build-<番号>`。先に印を作って番号を取り、番号は使い捨て（premises の C2・C5）

番号付けは、番号を決めたら**組む前に**、その commit を指す軽い印 `build-<番号>` を配布元へ push する（同じ名前の印があれば push は断られる）。その後で組み、下書き（D1）を同じ印の名前で作って配布物を置き、説明文に `ashiato-build: <番号> <commit の 40 桁>` を書く。

- 印を記録にするので、次の番号は `git` の印の一覧（`build-*` の最大）から決まり、番号付けの判定は使い捨ての git の木だけで試せる（配布元の API を偽にしなくてよい）
- 組み立てが落ちた番号は使い捨てる（印は残し、次の commit に回さない）。落ちた番号の組み立ての途中の成果物（job の間で渡す CI の成果物）にも同じ番号が入るので、回すと同じ番号で中身の違う物ができる
- 同じ commit の run を走らせ直したら、印の番号のまま、下書きに欠けた配布物だけを組んで足す（揃っていれば何もしない）。下書きの説明文の `ashiato-build:` の commit が渡した commit と違えば、何も置かずに止まる（印を消して別の commit に作り直した場合に、前の commit の配布物を「揃っている」と読まない。review/spec.md R3）
- 印を作る（`number.sh tag`）のと置く（`number.sh place`）のは別の手順で、印を作る job の後（`needs`）に組み立てと置く job がある（review/spec.md R2）。置く前に配布物の検査を通し、落ちれば何も書かない
- 番号の印は配った印（`v[0-9]*`）にも開発版の印にも数えない（今の検査は `v[0-9]*` に限っている）
- 確かめの下書き（`draft.sh`）は `v<版番号>` を名乗るので、記録に混ざらない
- premises の C2 は「下書きの名前と、その commit」を記録にするとしていた。印にしたのは、下書きの一覧を読むには配布元へ書ける権限が要り（P5。下書きは push できる人にしか見えない）、判定を git だけで閉じられるから。下書きは置き場として残る
- 反転条件: 配布元の規則が `build-*` の印の push を断る・印の数が配布元の扱える数を超える → 記録を下書きの説明文に移す

### D8. main への push の CI は、前に成功した main の run の commit からの差分で出し分ける

`ci.yml` の `changes` の job は、main への push のとき、直前の push（`github.event.before`）でなく、この workflow の main への push の run のうち最後に成功で終わったものの commit を基準にする（Actions の API を `actions: read` で読む）。見つからない・木に無ければ全部走らせる（今の「比較できないときは全部走らせる」）。

- 取り消された merge のコードを、文書だけの merge の run が試してから番号が付く（Q1 の推奨の「CI が通り」を成り立たせる）
- PR の出し分けは変えない
- 反転条件: API の読み出しが落ちて全部走らせる回が多い → 基準を番号の印 `build-*` の最後の commit にする

### D9. 左の数字はファイル `tools/release/MAJOR`。`Cargo.toml` の版は `0.0.1`（premises の C4）

- `tools/release/MAJOR` は数字 1 つ（今は `0`）。本人が PR で変える（NFR-25。0.x → 1.0）。変えた PR が main に入って最初の番号が `<左>.0.0`（D5 の前に効く）
- 左を下げたら番号付けは止まる（番号は 1 列に並び、下がらない）
- 根の `Cargo.toml` の `[workspace.package] version` は `0.0.1` にし、番号を持たない組み立ての版にする（D6）。版の検査は「出所の版は `0.0.<N>`（N≥1）」を見る（旧い「MAJOR が 0」の検査を置き換える）
- API の契約の `info.version` は出所の版のまま（`0.0.1`）。番号にすると main に commit を積むことになる（FR-134）。契約の版の比べは封筒の写し（`docs/contract/envelope.json`）が持ち、`info.version` を読む口は `tools/check-openapi.sh` だけ
- 版の検査の 4 か所（bash・Rust・gradle・TypeScript）を同じ規則にする。受ける・断る版番号の表 `tools/release/version-check-table.tsv`（`<版番号>\t<出所の版>\t<左>\tok|ng`。`0.4.0-beta.2` ok・`1.4.0` ng・`0.0.2`（出所 `0.0.1`）ng・`0.0.0` ng など）を 4 か所の試験が読み、そろいを固定する（versionCode の表と同じ型。review/spec.md R17）。規則: 渡した版が無ければ出所の版。渡した版の 3 つの数字が出所の版と同じなら「番号を持たない版」、左がファイルの値で `<左>.<真ん中>` が `0.0` でなければ「番号」。後ろの形（`-beta.<1〜98>`・`-dev.<YYYYMMDD>`）は今のまま
- gradle と TypeScript と Rust は `tools/release/MAJOR` を読む（`Cargo.toml` を読むのと同じ方法で）
- 反転条件: 左の数字を変える PR を本人以外が出す運用になった → `MAJOR` の変更に本人の承認の規則を足す

### D10. 番号付けは CI と別の workflow で、取り消さず 1 本ずつ流し、run の commit から組み直す（premises の C5）

新しい workflow `.github/workflows/number.yml`:

- 起きる: `workflow_run`（workflow `ci` の `completed`、枝 `main`）。job の条件で、run が `push`・成功・`head_repository` がこの repo のときだけ進む
- `concurrency: { group: number, cancel-in-progress: false }` を workflow でなく**判定の job** に置く。job の `if`（push・成功・この repo）を満たした run だけが順番待ちに入るので、取り消された・落ちた CI の run や fork の枝の run が、待っている番号付けを取り消さない（同じ組で待てるのは 1 つだけ —— P13。review/spec.md R1）。待ちが条件を満たす新しいものに入れ替わっても、新しい方の commit が古い方の中身を含む（D4 の 2.）。組み立てと置く job は番号ごとに別なので、組に入れない
- 判定の job: run の `head_sha` を `fetch-depth: 0` で取り出し、`tools/release/version.sh number <commit>` で「付けない／番号」を出す。付けるなら印 `build-<番号>` を push する（この job だけが `contents: write`）
- 組み立ての job: 判定の番号を `ASHIATO_BUILD_VERSION` に渡し、run の `head_sha` から Linux（サーバ・携帯の APK 2 つ）と Windows（サーバ・PC の収集アプリ）を組む。CI のキャッシュの前の組み立てを使わない（D12）
- 置く job: 配布物の検査（`check-artifacts.sh --allow-debug-key --expect-version <番号>`）を通し、下書きに置く（`contents: write`）。公開しない・印 `v*` を作らない
- 前提 P18（飛ぶ job は順番待ちの席を取らない。確かさ 1）が外れても、2 つの判定が同時に走るだけで、同じ番号の印の 2 つ目の push は断られる（P19）。起きるのは片方の番号付けが落ちて番号が次の成功まで遅れることで、同じ番号が 2 つの commit に付くことは無い。外れたと分かったら（tasks 12.5）、判定を `workflow_run` の外の 1 本の流れ（予定の実行で最新の成功の run を拾う）に移す
- 組み直しの費用: 番号ごとに Linux と Windows の組み立てが 1 回ずつ走る（月に約 27 回）。CI の run の成果物を使えば組み直さずに済むが、CI の組み立ては番号の決まる前に走るので、番号を焼き込めない（同じ番号を 2 つの run が焼く道ができる）
- 反転条件: 組み直しの時間が問題になる → CI の main の run の組み立てを外し、番号付けの組み立てだけにする

### D11. 移る間（ST62・ST63 まで）の印 `v*` と開発版（premises の C7）

- 印 `v<番号>`（と `-beta.<N>`）は、印の commit に番号の印 `build-<番号>` があり、印の版番号の 3 つの数字がその番号と同じときだけ公開する（`version.sh plan`）。番号の無い commit・番号の違う印は止める
- 修正の枝 `release/*` の例外を外す（REMOVED。番号は main にだけ付く）
- 開発版の作り直しは、main の HEAD でなく、main の first-parent の上で最も大きい番号の commit を `<番号>-dev.<日本時間の YYYYMMDD>` で組む。印 `nightly` もその commit へ動かす。番号がまだ無ければ組まない
- 旧い「出所の版の正式版を出した後は組まない」は外す（同じ番号は同じ commit なので、開発版が正式版より古い版番号を名乗ることはない）
- 反転条件: ST62・ST63 が札の形を入れたら、この節の振る舞いは札の側へ移る（この Story では消さない）

### D12. Windows の組み立ての使い回しに、番号の組み立てを混ぜない（premises の C8 を変えた）

番号付けの組み立ては CI のキャッシュを引かず、保存もしない（number.yml は既定の枝の上で走るので、そこで保存したキャッシュは PR から引ける。保存しないことが要）。premises の C8 は「使い回しの鍵に版番号を含める」としていたが、番号の組み立てがキャッシュに入らないので鍵を変えなくてよい形にした（review/spec.md R10）。PR の組み立ては今のまま（版は `0.0.1` か試験の `0.0.x` で、`ci.yml` の blob と `Cargo.toml` が鍵に入っている）。

- 番号を環境変数で渡す組み立てはキャッシュに入らないので、使い回しの鍵に版番号を足さなくても取り違えない（R6 の懸念は「main の番号付きの組み立てを、同じ鍵の PR が引ける」）
- 反転条件: 番号付けの組み立てでキャッシュを使うことにした → 鍵に `ASHIATO_BUILD_VERSION` を足す

### D13. 最初の番号は 0.2.0（premises の C3）

今の形で使った 0.1.0・0.1.1 より大きい（FR-134 ★・FR-117・FR-137）。0.1.2 から始めると D3 の式で 10,002 になり、前の式の 0.1.x（10,099・10,199）より小さい。

### D14. 番号が versionCode の上限を超えるなら、番号を付けずに止まる

真ん中 999・右 9,999・左 209 を超える番号は付けない（D3 の組み立てが落ちるので、付けても組めない）。止まった理由を出す（番号付けの run が落ち、本人が左を上げるか式を見直す）。

### D15. 確認バッチの merge は、first-parent の merge の題で見分ける

main の first-parent の commit のうち、親を 2 つ持ち、題が `Merge pull request #<数字> from <owner>/verify/` で始まるものを確認バッチの merge とみなす（確認バッチの枝は `verify/<日付>`。P3）。

- 反転条件: 確認バッチの枝の名前か merge の仕方（squash など）が変わる → 見分けを PR の情報（API）に移す

## Risks / Trade-offs

- **番号の印 `build-*` は消せる・動かせる** → 配った印 `v*` の規則（消せず動かせない）は `build-*` に掛かっていない。印を動かすと、番号と中身の対応が崩れる。ST62 の札の規則と一緒に `build-*` も守る（docs/handoff/ST62.md）。この Story の間は、番号付けが「印が別の commit を指せば止まる」で気づく
- **番号の組み立ては CI で試した組み立てと別の組み立て** → 同じ commit から同じ手順で組み直すので中身は同じはずだが、道具の版（runner の image）が違えば微妙に違いうる。配布物の検査（印・`.dirty`・資格情報・名前）は番号の組み立てにも掛ける
- **組み立てが落ちた番号は欠番になる** → 番号は「どの組み立てか」だけを表すので、欠番で困る読み手はいない（FR-104）。欠番は印だけあって下書きが無いことで分かる
- **番号を付けた後の commit の CI が落ちても、付けた番号は残る** → 番号は付けた commit の run が成功したことだけを表す
- **ベータ版の印と正式版の印が同じ versionCode** → 移る間だけの話。札の形（ST62）では同じ番号は同じ組み立て
- **確認バッチの見分けを題に頼る** → 題の形が変わると真ん中が上がらなくなる（右が進むだけで、番号は 1 列に並ぶ。D15 の反転条件）

- **版の検査は、番号の形の版番号を誰からでも受け取る** → 旧い規則では出所の版と違う版番号は組み立てが落ちたが、新しい規則では左が合えば `0.1.0` なども通る（組み立ては番号の印を見ない。浅い木もある）。手元で `ASHIATO_BUILD_VERSION=0.2.5` を渡せば、番号 0.2.5 を名乗る別の中身を組める。CI の配る形の組み立ての job が番号を渡さないことは検査で固定する（D6）。入れる側の守り（札の無い組み立てを正式版の上に入れない）は ST64（docs/handoff/ST64.md。review/spec.md R9）

## Migration Plan

1. 版の検査の 4 か所・`Cargo.toml` の版 `0.0.1`・`tools/release/MAJOR`・versionCode の式・CI の更新の試験の版を同じ PR で変える（PR の CI が新しい規則で緑になる）
2. 番号付けの workflow を足す。main に入った後、最初に製品に触れる commit の成功で `0.2.0` が付く
3. 本人の PC と携帯の 0.1.x は、この Story では触らない（ST64）

戻し方: 番号付けの workflow を外せば、番号は付かなくなる（付けた印と下書きは残る）。版の検査を戻すと `Cargo.toml` の版を 0.1.x に戻す必要がある。
