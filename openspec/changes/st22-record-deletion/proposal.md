## Why

**見たくない記録を消す手段が、API にも画面にも 1 つも無い。** FR-50 は「削除済みの印と時刻を付け、同じ内容を戻さない」と決め、
ST03 は取り込みの側（削除済みの内容を戻さない判定）を、ST16 は派生の側（本人が消した時間帯に滞在を戻さない）を先に作ったが、
**印を付ける操作そのものが無い**。いま「記録されたくない場面」を残さない方法は、収集ごと止めることしか無い（Story の価値）。

いま作る理由は 2 つ。

1. **受け皿だけが先にできていて、操作が無いまま空回りしている。** ST16 は `deleted_by` の読み方・作り直しの錠・消した時間の出し方を
   ST22 へ申し送った（`docs/handoff/ST22.md` の 5 件）。そのうち「位置を消したら滞在を作り直す」は、操作ができるまで検証できない
2. **ST23（本文の物理削除）が requires: ST22。** 物理削除の前段は「消したことにする」で、ここが無いと ST23 の上流が始まらない

## What Changes

深掘りは **1 巡・4 問**（A 2 / B 2）。本人がすべて選択肢から明示的に選んだ（未回答 0・推奨のまま 0・推奨と違う側 0）。
独立レビュー（`deep-review`）は **13 件** —— Q1 を B から A（loss: exported）に上げ、問いと proto の前提を 6 件直し、
聞かないで決める既定を 3 件直した・足した（削除の台帳 / 口を狭める / 利用者の取り方）。聞かずに決めた既定 C1〜C10 に本人の異論は無かった。

- **1 日の滞在の一覧から滞在を消せる。** 行をタップすると詳細がその場で開き（ui-direction）、その時間の記録の件数
  （位置 N 件・同じ時間の PC のウィンドウ / ブラウザ履歴の件数）と、末尾に 44 px の「この滞在を消す」が出る。押すとその場で確認する
- **滞在を消すと、その時間の位置の記録も削除済みになる**（Q1）。位置を消した日の滞在は作り直す（申し送り R37）
- **消した時間帯に後から届いた位置は、削除済みの印を付けて入れる**（Q2。捨てない）
- **消した時間は、1 日の一覧で「記録なし」ではなく「消した 始まり – 終わり」の行として出し、その行から戻せる**（Q4）。
  戻すと、滞在とその時間の位置（後から印を付けて入れた分を含む）が戻り、その日の滞在を作り直す
- **消す・戻すは追記のみの削除の台帳に 1 操作 1 行で残す**（C2）。`deleted_at` / `deleted_by` は今の状態として併せて書き、
  `deleted_by` に `rebuild:` で始まる値は書かない（申し送り R14）
- **稼働状況は消した記録も数える**（Q3。いまの実装のまま、本人の決定として明文化する）

**BREAKING は無い。** 取り込みの口（`/ingest`）の応答と、1 日の並びの読み出し（`GET /stays`）の既存の項目は変えない。
消す口・戻す口を足し、1 日の並びに「消した」の種類を足す。

## Capabilities

### New Capabilities

- **`record-deletion`** —— 本人が記録を消したことにする・戻す操作、消したときに一緒に消えるもの、消した時間帯に後から届いた記録の扱い、
  削除の台帳、稼働状況との関係。**ST23（物理削除）が同じ capability に足す。**

### Modified Capabilities

- **`browsing-views`** —— 1 日の一覧の「位置の記録が無い時間は記録なしの行として出る」と「削除済みの滞在は一覧に出ない」に、
  消した時間の「消した」行・行の中の詳細・消す操作を足す。**ST16 が archive されるまで `openspec/specs/browsing-views` が無いので、
  specs はそこで止める**（下の「止めた理由」）

`derived-records` と `record-envelope` と `collection-coverage` は**変えない**。滞在を消す操作・位置を消したときの作り直し・
後から届いた位置に印を付ける経路は `record-deletion` に ADDED で置く（ST16 の「作り直しは本人が消した時間帯に滞在を戻さない」と
ST03 の「削除済みの内容は取り込みのどの経路からも戻らない」は、そのまま成り立つ）。

**capability の前倒し**: ST22 を `browsing-views` にも割り当て、`requires` に ST16 を足した（`docs/stories/INDEX.md` の訂正 2026-09-15）。
完了の判定「削除すると**画面から消え**」の画面は ST16 の一覧で、Q4 の答えが ST16 の要件を書き換えるため。

## 止めた理由（proposal で止める）

**ST16 は merge 済みだが archive 待ち。** Q4 の答えは ST16 の `browsing-views` の要件への MODIFIED で、
その capability は ST16 の archive まで `openspec/specs/` に無い。書いても、ST16 の archive で正典の文面が確定するまで古くなりうる。
ST16 の archive 後に specs → design → tasks → PR と issue へ進む。

## Impact

- **サーバ**（`crates/server`）: 消す口と戻す口（利用者は消す行の `user_id` から取る。C10）、削除の台帳の表と移行
  （`migrations/YYYYMMDDHHMM_<slug>.sql`）、取り込みで消した時間帯に入る位置に印を付ける経路、
  1 日の並び（`stay_store.rs` の `day_view`）に「消した」の種類、位置を消した / 戻した日の作り直し（作り直しと同じ錠。R44）
- **画面**（`web/src/DayView.tsx` / `stays.ts`）: 行の中に開く詳細、件数、消す操作と確認、「消した」行と戻す操作
- **並走している Story との重なり**
  - **ST16**（archive 待ち）: `browsing-views` を書き換える。ST16 の design D8（仮）の「空白」を Q4 の形に置き換える
  - **ST25**（衝突待ち）: ST16 の archive 後も、ST22 が `browsing-views` を触る間は同時に走らせない（盤面に反映済み）
  - **ST04**（下流）: `collection-coverage` は触らない（Q3 は数えたまま）。取り込みの口のコード（`lib.rs`）は両方が触りうるので、後から merge する側が追従する
  - **ST05**（上流）: `record-envelope` は触らない
  - **ST12**（上流）: 書庫から別のソースで入る同じ場面は ST22 の削除に当たらない（R6）。外部識別子のソースで起きる失われ方 2 件（R3 / R4）と合わせて `docs/handoff/ST12.md`
  - **ST33**（着手可）: 書き出しが削除済みを出さないことは ST33 が決める。ST22 は「滞在を消すと位置も削除済み」にしたので、削除済みを除けば場面は外に出ない
- **ST23**: 物理削除は、この Story の台帳と「消した」状態を前提にする
