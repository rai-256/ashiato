## D1. 日境界は `Asia/Tokyo` を SQL 側で当てる

`crates/server/src/lib.rs:219` の `($2 AT TIME ZONE 'UTC')::date` を
`($2 AT TIME ZONE 'Asia/Tokyo')::date` に替える。**アプリ側で日を計算しない。**

理由: 日を引く場所が 2 つ（取り込み時の INSERT と、集計のクエリ）あり、
どちらも SQL で書く。片方だけアプリ側にすると、夏時間の無い `Asia/Tokyo` でも
うるう秒やライブラリ差でずれる余地が残る。PostgreSQL の `AT TIME ZONE` は
`pg_timezone_names` を単一の権威にする。

`Asia/Tokyo` を定数として 1 か所（`const DAY_TZ: &str`）に置き、SQL へは束縛で渡さず
リテラルで埋める（`AT TIME ZONE` は列名の位置なのでプレースホルダを取れない）。

## D2. `core.coverage` を作り直す（BREAKING）

現在の `(logical_source, day, state)` を主キーとする表は、`state` が
`('alive','stopped','dropped')` の 3 値で**日に焼き込まれて**おり、8 状態も時刻範囲も乗らない。

作り直し後の `core.coverage` は「**その日に何件入ったか**」の事実だけを持つ:

```sql
CREATE TABLE core.coverage (
  user_id        uuid NOT NULL,
  logical_source text NOT NULL REFERENCES core.source(logical_source),
  day            date NOT NULL,          -- Asia/Tokyo で区切った日（D1）
  event_count    integer NOT NULL DEFAULT 0,
  PRIMARY KEY (user_id, logical_source, day)
);
```

**`state` 列を落とす。** 8 状態は導出する（D6）。理由は D6 に書く。

既存データは**縦串のダミーのみ**なので移行先を作らない。前進のみの migration
（`0005_coverage_rebuild.sql`）で、戻し手順は `.down.sql` に置く。

## D3. 生存信号は `core.heartbeat` に別表で持つ

`core.event` に入れない。`origin` が `('collected','authored','derived')` の 3 値で、
生存信号はどれでもない —— 生存信号は**出来事ではなく、出来事が無かったことの証拠**にあたる。
`origin` に 4 つ目を足すと、記録を読むすべての経路（`core.event_live`・検索・AI 越しの参照）が
生存信号を記録として拾う。

```sql
CREATE TABLE core.heartbeat (
  id             uuid PRIMARY KEY,       -- 収集側で生成（FR-21 と同じ向き）
  user_id        uuid NOT NULL,          -- FR-29
  logical_source text NOT NULL REFERENCES core.source(logical_source),
  device_id      text,
  emitted_at     timestamptz NOT NULL,   -- 収集側が信号を作った時刻
  received_at    timestamptz NOT NULL DEFAULT now(),  -- 受信時刻（Q14: 日に丸めない）
  capturable     boolean NOT NULL,       -- 取得できる状態か（Q5）
  blockers       text[] NOT NULL DEFAULT '{}',  -- 満たされていないもの（permission / sensor / network）
  attempts       integer NOT NULL,       -- 前回の信号からの取得の試行回数（第 5 回 Q17）
  successes      integer NOT NULL,       -- そのうち成功した回数（同上）
  content_hash   text NOT NULL,          -- 冪等キー（Q13）
  raw            text NOT NULL           -- 原文の素通し。0003 と同じく text（jsonb は原文を保たない）
);
CREATE UNIQUE INDEX heartbeat_dedup ON core.heartbeat (logical_source, content_hash);
```

`raw` を `text` にするのは 0003 と同じ理由 —— `jsonb` はキー順を変え、重複キーを落とし、
数値の表記を展開する。ST01 が実測でこれを踏んでいる。

`attempts` / `successes` は**想定間隔より細かい空きを残すための 2 列**（第 5 回 Q17）。
位置は 60 秒間隔なので 6 時間の区間は 360 回が満点になり、**取得率がそのまま出る**。
実測（ST01 の R46）の 1 日 24 回・192 分の空きは、この比でしか見えない。

**年間の行数**: 5 ソース × 6 時間間隔 × 365 日 ≒ 7,300 行。NFR-5 の年 3〜6 GB に対して無視できる。

## D4. 保護は 0004 と同じ形のトリガで掛ける

`core.reject_collected_rewrite()` と同型の
`core.reject_heartbeat_rewrite()` を `BEFORE UPDATE ON core.heartbeat` に置き、
**全列の更新を拒む**（生存信号には論理削除の例外が無いので、0002 のような通し道を作らない）。

アプリ層のチェックでは足りない理由は 0002 のコメントと同じ —— 同じ PC で動く
第三者製プラグイン（PERM-8）や `psql` を直に叩く運用が素通りする。
0004 が「分類を動かしてから書き換える」3 手の迂回を実測で見つけているので、
**迂回路になる列を最初から作らない**（`origin` に相当する分類列を持たせない）。

## D5. 収集開始日は `core.source` の列で持つ

```sql
ALTER TABLE core.source ADD COLUMN user_id uuid;                     -- FR-29
ALTER TABLE core.source ADD COLUMN collection_started_on date;       -- FR-79
```

**`core.source` の主キーは `logical_source` のまま変えない。** `core.event.logical_source` が
FK で参照しており、主キーを `(user_id, logical_source)` にすると FK と既存の全行が壊れる。
FR-29 は「**列**を持たせる」であって主キーにせよとは言っていない。
複数利用者を実際に受けるときに、その Story が主キーを動かす。

**★ 2026-09-11: 本人が決めた**（第 5 回 Q22。当初は AI が独断で
「どちらも無ければ migration を当てた日」と決めていた。`review/spec.md` の R12）。

**収集開始日 = そのソースの最初の記録が作られた日**（生存信号なら発信された日。
★ 2026-09-11 の第 6 回 Q24 で「届いた日」から訂正）。
1 件も無いうちは `NULL` のままにし、**まだ開始していない**ものとして扱う（⑦「導入前」で、
FR-80 の「途絶」にならない）。**登録簿に登録した日ではない** —— ウィンドウとブラウザ履歴は
C-02 がまだ存在せず、登録だけ先にあると作っていないのに計測が始まる。

**★ 2026-09-11: 本人が決めた**（第 6 回 Q24）——
**最初の記録が「作られた」日**（`min(event_time)` を `Asia/Tokyo` で切った日。
生存信号なら `emitted_at`）。**受信時刻（`ingest_time` / `received_at`）ではない** ——
圏外で 3 日ぶん溜めて送ると、**記録のある日が⑦「導入前」になり NFR-13 の分母からも落ちる**。

実装は**受け口の側で埋める** —— 記録または生存信号を受けたとき、
そのソースの `collection_started_on` が `NULL` か、受けたものの
`event_time` / `emitted_at` の日より後なら、その日で更新する
（**`least()` を取る**ので、古い記録が届くたびに前へ動く）。

**★ 2026-09-11: 遡ることを本人が決めた**（第 7 回 Q26）。
design はこの振る舞いを書いていたが、**それでよいと誰も決めていなかった**
（`review/spec-r3.md` の R2）。遡ると NFR-13 の窓の起点も動き、
**過去に表示した達成率が変わることがある**。
「判定式は計測開始後に変えられない」との非対称はこう整理される ——
**変えないのは式**（割合・主語の仕分け・窓の長さ）で、**動くのは入力**。
式が同じなら、同じ入力からは必ず同じ答えが出る。
migration でのバックフィルは既存の `core.event` から `min(event_time)` を引く。

## D6. 途絶は行に焼かず、引くたびに導出する

FR-80 は「その期間を『途絶』として稼働記録に残す」と書いているが、
**途絶の行を書くバッチは作らない。** 導出でこれを満たす。

理由:

1. **バッチが止まると途絶が記録されない。** 途絶は「何かが止まったこと」の検知なので、
   検知する側が同じ理由（サーバの停止・OS の停止）で止まりうる。
   止まっている間の途絶を、止まっている当人が書けるはずがない
2. **Q14 の向きと同じ。** 生存信号の受信時刻を日に丸めないと決めたのは、
   日境界の決定を行に焼き込まないため。途絶も同じで、想定間隔（`expected_gap_sec`）が
   後から変われば、過去の途絶の判定も変わるべき
3. **材料がすべて残っている。** 記録・生存信号・停止/破棄の範囲・収集開始日・想定間隔は
   いずれも行として残るので、途絶はいつでも同じ答えに引き直せる

`specs` の Scenario「途絶は収集側の報告なしに立つ」は導出でも満たす ——
観測される振る舞いは「稼働状況を引くと途絶が出る」であり、行の有無ではない。

## D7. 8 状態の決定順序

同じ日に複数の条件が成り立つので、**上から評価して最初に当たったものを返す**:

| 順 | 条件 | 状態 |
|---|---|---|
| 1 | `day < collection_started_on` | ⑦ 導入前 |
| 2 | その日を丸ごと覆う `kind='dropped'` の範囲がある | ⑤ 破棄された期間 |
| 3 | その日を丸ごと覆う `kind='stopped'` の範囲がある | ④ 意図的な停止 |
| 4 | `coverage.event_count > 0` | ① 記録あり |
| 5 | `capturable = true` の生存信号がその日にある | ② 動いていた・記録なし |
| 6 | 生存信号がその日にある（すべて `capturable = false`） | ③ 動いていたが取れない状態だった |
| 7 | 上のどれでもない **かつ、直前の記録・生存信号からの経過が想定間隔を超えている** | ⑥ 途絶 |
| 8 | 上のどれでもない（想定間隔を超えていない） | ② 動いていた・記録なし |

**★ 2026-09-11: 本人が決めた**（第 5 回 Q19）。**順序はこの表のとおりで確定**し、
`specs` の Requirement 本文に列挙した（正典に残る。`review/spec.md` の R6）。

当初ここには「破棄を停止より先に見るのは、破棄がデータの喪失を意味するため」と
**AI が理由を後付けしていた**。本人が選んだ理由は別で、
**「なぜこの日はデータが少ないのかに画面が先に答える」**側 ——
1 日を丸ごと止めた日に記録が一部残っていても、その日は④「意図的な停止」として見える。
**結論は同じだが根拠が入れ替わった**ので、specs の根拠ブロックには本人の理由を書いた。

**7 行目に想定間隔の条件を入れたのは技術判断**（R4）。FR-80 の逐語が
「**そのソースに登録された想定間隔を超えて**」と書いており、条件を落とすと
ブラウザ履歴（24 時間）や Takeout 系（60 日）の**正常な空白日がすべて⑥途絶になる**。

**丸ごと覆わない停止・破棄は状態を決めない。** 半日だけ止めた日は記録があれば①になる。
これは Q3 の決定（分母から除くのは 1 日を丸ごと覆う停止だけ）と同じ粒度に揃えている。

## D8. 停止と破棄は 1 つの範囲表に入れる

```sql
CREATE TABLE core.coverage_span (
  id             uuid PRIMARY KEY,
  user_id        uuid NOT NULL,
  logical_source text NOT NULL REFERENCES core.source(logical_source),
  kind           text NOT NULL CHECK (kind IN ('stopped','dropped')),
  started_at     timestamptz NOT NULL,
  ended_at       timestamptz,           -- NULL = まだ続いている
  event_count    integer,               -- dropped のときの破棄件数（FR-9）
  note           text
);
```

停止（FR-34）と破棄（FR-9）を別表にしない。どちらも「**ある期間、そのソースの記録が
無いことに理由がある**」という同型の事実で、D7 の評価も同じ形で書ける。
`kind` を分けておけば ST15（停止の入力）も ST04（破棄）も同じ表に足すだけで済む。

`ended_at` が `NULL` を取れるようにするのは、停止が「いま続いている」状態を持つため
（ST15 が終了日を入れるまで開いたまま）。

## D9. API は受け口 1 本と読み出し 2 本

既存は `/ingest`（POST）と `/events`（GET）。同じ階層に足す:

| パス | 何を |
|---|---|
| `POST /heartbeat` | 生存信号の受け口。`/ingest` と同じく**複数件をまとめて受け、1 件ごとの結果を返す** |
| `GET /coverage?from=&to=` | ソース × 日 の 8 状態。D7 の順序で導出して返す |
| `GET /coverage/achievement` | 5 ソースの達成日数と分母、5 本すべてが分母の 95 % 以上かの合否。**期間は取らない**（窓は仕様で決まっている。第 6 回 Q23） |

認証は既存と同じ（record-envelope「すべての API 要求は資格情報を要求する」）。
`POST /heartbeat` を `/ingest` と統合しない —— `/ingest` は `core.event` の
エンベロープ（`event_time` / `tz_id` / `schema_version` / `crs` …）を必須にしており、
生存信号はそのどれも持たない。混ぜると片方のために必須の欄が緩む。

`docs/collector-contract.md` と `docs/openapi.json` に反映する。

## D10. 格子の明度は 3 段。8 状態は週を選んだときの文字が担う

`ui-direction.md` は**色を意味の担い手にしない**と決めている（宿題 1）。
**★ 2026-09-11: 本人が決めた**（第 5 回 Q21）。格子が担う区別は **3 段**:

| 格子の段 | 中身 | 明度の位置 |
|---|---|---|
| 「それ以外」 | ③ 取れない状態 / ④ 停止 / ⑤ 破棄 / ⑥ 途絶 / ⑦ 導入前 | 最も暗い（地に近い） |
| 「動いていた・記録なし」 | ② | 中 |
| 「記録あり」 | ① | 最も明るい |

**隣り合う 2 段は相対輝度比 3:1 以上**（WCAG SC 1.4.11）。3 段なら 3:1 × 3:1 = 9:1 で、
sRGB の上限 21:1 に収まる。**8 状態の区別は週を選んだときの文字**が担う（Q20 / Q21）。

**なぜ 7 段にできなかったか**（`review/spec.md` の R9）: WCAG SC 1.4.11 は
隣接する色に **3:1** を求めるが、7 段を隣接 3:1 で並べると **3⁶ = 729:1** が要る。
**sRGB の理論最大は 21:1** で、21:1 を 6 等分しても隣接 **1.661:1** にしかならない。
6 段でも 243:1 で足りない。**計算で不成立が確定した**
（第 1 回 Q6 で「明度の段差」と決めたときは 6 状態だった）。

`ui-direction.md` の宿題 1 の「色を意味の担い手にする箇所には**形かラベルを併せる**」の
**「ラベル」がこれにあたる** —— 第 4 回 Q15 がソースの区別を格子に添えた文字で閉じたのと同じ形で、
状態の区別は週を選んだときの文字が閉じる。

**NFR-18（4.5:1）はセルには掛からない** —— セルは本文でも文字画像でもない。
掛かるのは各格子に添えたソース名と、週を選んだときに出る状態名の文字。

具体のトークン値は下流が `ui-direction.md` の確定値（地の明るさ 12% / 3 段）から引く。
**格子の 3 段は面の段数（3 段）とは別軸** —— 面はカード・リストの階層で、
格子の段は格子の中だけに出る。数が同じなのは偶然。

## D11. 達成日数は SQL 1 本で数える

ソースの主語（端末 / 利用）は `core.source` に列で持たせない。**5 ソースの固定の割り当て**を
サーバ側の定数に置く:

```rust
const DEVICE_SUBJECT: [&str; 2] = ["location", "app_usage"];
const USAGE_SUBJECT:  [&str; 3] = ["photo", "window", "browser_history"];
```

理由: NFR-13 が名指しで 5 ソースを挙げており、**判定式は 1 年の計測が始まったら変えられない**。
DB の列にすると、行を 1 つ更新するだけで判定式が動く。定数なら変更が diff に出て、
CI とレビューを通る。ソースが 6 つ目になっても NFR-13 の 5 ソースは動かない。

**★ 2026-09-11: 本人が決めた**（第 6 回 Q23）——
**窓はソースごとに「そのソースの収集開始日から 365 日」**。
365 日が経っていないソースは「収集開始日から今日まで」を分母にして同じ式で途中経過を出す。

**`GET /coverage/achievement` から `?from=&to=` を落とす。** 窓が仕様で決まったので、
呼び出し側に委ねる余地が無い（委ねると窓の取り方で合否が動く）。
画面は期間を指定せずに引く。

**★ 合否は 5 本すべての窓が閉じた日に確定する**（第 7 回 Q27）。
それまでは**暫定**として返し、確定までの残り日数を併せて返す。
**収集が始まっていないソースがあるあいだは確定日を定めない** ——
ウィンドウとブラウザ履歴は C-02 がまだ無いので、確定日は当面動き続ける。
これが無いと、**収集開始 10 日目のソースが 10 日とも達成していれば 100 % で
「達成」に見える**（`review/spec-r3.md` の R3）。

## D12. web は S-1 を最初の画面として作る

`web/src` は現在 `App.tsx` と `main.tsx` の骨組みだけで、実質 ST02 が最初の画面になる。
`ui-direction.md` の確定値（色相 132° / 彩度 30% / 明るさ 12 / 3 段）をトークンとして
1 か所に置き、S-1 はそこから引く。**S-1 のためだけの色を足さない** ——
足すと ST25（S-2 主表現）が別のトークン系を持つことになる。

格子は 53 週 × 7 日 × 5 ソース。**ソースごとに 1 つの格子を縦に積む**（Q15）。
**縦長**（1 行 = 1 週）なので横に並ぶのは 7 日ぶんで、360 px 幅なら 1 セル 51 px 前後になる
（★ 2026-09-11 の第 6 回 Q25。当初は横長を前提に「53 列 → セル 6 px」と書いていた）。
セルは表示専用なので NFR-19 に触れない（Q16）。

**★ 2026-09-11: 本人が決めた**（第 5 回 Q20 / Q21）。

### D13. Must の 5 ソースの論理ソース名は `c01-` / `c02-` 前置き

D11 は `["location", "app_usage"]` のように**裸の名前**で書いていたが、
ST01 が実際に登録した名前は `c01-location`（`collector-android/.../LocationFix.kt:10`）で、
**定数と登録簿がずれると達成日が永久に 0 のまま緑になる**（引く先の行が無いだけなので誰も落ちない）。

既存の 1 本に合わせて、収集側の前置きを持つ名前で確定する:

| ソース | 論理ソース名 | 主語 | 想定間隔 |
|---|---|---|---|
| 位置（FR-1 / C-01） | `c01-location` | 端末 | 6 時間 |
| アプリ利用（FR-2 / C-01） | `c01-app-usage` | 端末 | 6 時間 |
| 写真（FR-3 / C-01） | `c01-photo` | 利用 | 6 時間 |
| ウィンドウ（FR-12 / C-02） | `c02-window` | 利用 | 6 時間 |
| ブラウザ履歴（FR-13 / C-02） | `c02-browser-history` | 利用 | 24 時間 |

**登録簿への 5 行は `migrations/0005` が置く。`tools/seed.sh` ではない** ——
tasks 1.6 は seed.sh を検証手段に挙げていたが、CI の `cargo test --workspace` は seed.sh を
走らせないので、**seed.sh に置くと CI では想定間隔が 1 つも入っていない DB でテストが通る**。
想定間隔は FR-35 が定める**システムの定義**であって開発用の偽データではない。
既にある行は動かさない（FR-35 の値は「初期値」なので、本人が変えた値を migration が戻さない）。
ずれの再発は `expected_gap_seeded` が定数と登録簿を突き合わせて止める。

### D14. DB を要するテストは本物の PostgreSQL を叩き、**飛ばさない**

稼働記録の振る舞いは日境界（`AT TIME ZONE`）・一意索引・書き換え禁止のトリガと、
**どれも DB の側にある**。模擬すると 0004 が実測で見つけた「3 手の迂回」の型の穴がそのまま残る。

- 接続先は `DATABASE_URL`（既定は `docker compose` の `127.0.0.1:55432`）。
  **接続できなければテストは落ちる。** 飛ばすと、DB が無い環境で全部が緑になり、
  稼働記録の検査が 1 本も走っていないことに気付けない
- **CI の `rust` ジョブに postgres の service を足した。** 足さないと `cargo test --workspace` が
  接続できずに落ちる（＝上の規律がそのまま CI に効く）
- テストどうしの隔離は**論理ソース名と利用者識別子をテストごとに一意にする**ことで取る。
  schema を掘り直さない —— 本物と同じ表を叩くことに意味がある

### D15. 達成日数は「**終わった日**」だけを数える

`specs` の固定値がこの数え方を指している —— 「収集開始日から 200 日なら分母 200 日」
（第 6 回 Q23）と「1 本が 300 日目なら残り 65 日」（第 7 回 Q27）は、
**今日を分母に入れない**と両立しない。窓は `[開始日, 開始日 + 364]` の 365 日、
確定日は `開始日 + 365`、分母は `[開始日, min(今日 - 1 日, 窓の最終日)]` の日数。

「窓はソースごとに別の日に始まる」の Scenario（位置 04-01 / 履歴 07-01 で 06-30 に引くと
分母 90 日と 0 日）もこの数え方でちょうど合う。**今日を入れると 91 日になって合わない。**

原理としても正しい —— まだ終わっていない日は「達成しなかった」とも言えない。

### D16. 0005 は旧 `core.coverage` の行を移さず、`core.event` から数え直す

旧 `core.coverage` は**日を UTC で切っていた**（既存の欠陥 1）ので、行をそのまま移すと
日がずれたまま残る。`core.event` は全件残っているので、`Asia/Tokyo` で数え直すほうが正しい。
重複は `event_dedup_hash` が INSERT の時点で弾いているので、`count(*)` が
そのまま「新しく入った記録の数」（ST01 design D13）にあたる。

**作り直しは「古い形のときだけ」行う。** `run()` は起動のたびに全版を当てるので、
無条件に `DROP TABLE` すると**起動のたびに稼働記録が全部消える**
（画面には「ずっと途絶」と出るだけで、誰も落ちない）。
`tools/check-immutable.sh` が当て直しで行が消えないことを検査する。

### D17. 途絶は**日の粒度**で測り、想定間隔以内に前**か**後の活動があれば②

`specs` は「(7) 直前の記録・生存信号からの経過が想定間隔を超えていれば途絶」と
「(8) …その日をまたぐ前後の記録または生存信号が想定間隔以内にあるときに限る」を並べている。
**「前後」を「前または後」と読む。** 「前と後の両方」と読むと、
想定間隔 60 日のソースで最後の記録の翌日（経過 1 日）が途絶になり、
FR-80 の逐語（「想定間隔を**超えて**…届かない」）と矛盾する。

測る単位は**日**（状態が日単位なので、日より細かく測っても出力は変わらない）。
想定間隔 6 時間なら 1 日の空白でも「超えて」いるので⑥、
24 時間なら隣り合う日に活動があれば②、60 日なら 60 日ぶんの空白まで②になる。

### D18. 読み出し口の `user_id` は省略できる

`GET /coverage` と `GET /coverage/achievement` は `user_id` を任意の絞り込みとして取り、
**省略すると絞らない**。単一利用者なので既定の識別子を発明する必要が無く、
かつ FR-29 の「列を day one から持つ」は満たしたまま。
複数利用者を実際に受ける Story が、ここを資格情報から引くように変える。

### D19. `GET /coverage` は NFR-13 の 5 ソースを、**定数の順**で返す

登録簿には検査用・偽データ用の行も入る（`tools/seed.sh` / `tools/smoke.sh` / テスト）ので、
登録簿を全部返すと画面に無関係な格子が並ぶ。画面が並べるのは NFR-13 の 5 本で、
**その縦の並びも定数の順**（位置 → アプリ利用 → 写真 → ウィンドウ → ブラウザ履歴）に固定する。

### D20. 収集側が生存信号を出すのは、**自分が実際に収集しているソースだけ**

tasks 7.1 は「間隔は登録簿の想定間隔（位置・写真とも 6 時間）に合わせる」と書いているが、
これは**間隔の値**の話で、C-01 が写真の信号も出すという意味には取らない。
**FR-3（写真）の収集は C-01 にまだ無い。**

写真の生存信号を出すと、**収集していないものを「動いていた・取得できる状態だった」と
報告する**ことになる。NFR-13 は利用が主語の 3 ソースを生存信号で数えるので、
これは**達成日数を偽装する**のと同じで、成功条件 1 が測るものが「壊れていなかった日数」
ではなくなる。生存信号は証拠なので、無い収集の証拠を立てない。

結果、いまは `c01-location` の 1 本だけが出る。写真・ウィンドウ・ブラウザ履歴は
**収集を作る Story が、同じ `HeartbeatEmitter` に論理ソース名を渡して足す**
（`logicalSource` を引数にしてあるのはそのため）。
それまで 3 本は⑦「導入前」のままで、⑥「途絶」にはならない（第 5 回 Q22）。

### D21. 生存信号の `attempts` は**経過時間から引く**

Play Services は「取れなかった」を報告しない —— 失敗の契機が起きるのではなく、
**callback ごと呼ばれない**（Doze の maintenance window の外）。数えられるのは成功だけ。

区間の長さを取得間隔（FR-1 の 60 秒）で割った数を満点とし、それを `attempts` にする。
6 時間なら 360 回で、design D3 が挙げている数と一致する
（「位置は 60 秒間隔なので 6 時間の区間は 360 回が満点になり、取得率がそのまま出る」）。
**新しい契機を起こさないので電池は増えない。**

端末の時計が戻ったときは `attempts` を `successes` より小さくしない ——
「成功が試行を超える」信号は受け口が断り（2 巡目 R7）、**未送信に居座り続ける**。

### D22. 未送信の仕組みは**総称化して共有し、ファイルは分ける**

specs は「生存信号を、記録と同じ未送信の仕組みに乗せて再送する」と定めている。
`Outbox` / `OutboxStore` / `Sender` を型引数つきにして、記録と生存信号が同じ実装を通る
—— 別に書くと、`FileOutboxStore` が実測で積み上げた復旧（書きかけの回収・
壊れた行の退避・追記）を生存信号だけが持たないことになる。

**ファイルは分ける**（`outbox.jsonl` / `heartbeat.jsonl`）。同じ JSONL に混ぜると、
読み戻しで片方が「壊れた行」に見えて `salvage` に回る。

`HttpTransport` は送り先の道を引数に取る（`/ingest` / `/heartbeat`）。
**受け口を統合しない**のは design D9 のとおり —— `/ingest` は記録のエンベロープを
必須にしており、混ぜると片方のために必須の欄が緩む。

### D23. 画面の検査は jsdom で「指定」と「勘定」を固定し、実寸は人間に残す

NFR-19（24 × 24 CSS px）も「開いた直後に 5 ソースの直近 1 か月が収まる」も、
**jsdom はレイアウトを計算しない**ので実寸を測れない。測れない道具で測ったふりをすると、
緑のまま NFR-19 を割る（`ui-direction` の UIR-13 と同じ型）。

だから検査が見るのは次の 3 つで、**実寸の目視は `docs/stories/ST02.md` の完了の判定に残す**:

1. **操作対象すべてに 24 px 以上の指定が実際に付いているか**（DOM を走査して全部見る）
2. **セルが操作対象になっていないか**（`role`・要素・`cursor` を見る。ここが崩れると 24 px を割る）
3. **勘定そのもの**（5 ソース × 5 週 × 24 px ≦ 700 px）。週数か最小高さが増えたら先に落ちる

対比（NFR-18 / NFR-23）は計算で閉じるので、**描くのと同じ値から相対輝度を計算し直す**。
トークンに書いた「3:1 以上」という文を信じない —— `ui-direction` の独立レビューは、
**測る色と実際に描く色がずれていて全状態の 23.4 % が 4.5:1 未満**だった事例を実測している。

**「開いた直後の週数」の検査は定数と突き合わせない。** `INITIAL_WEEKS` を 53 にしても
`shown <= INITIAL_WEEKS` は通ってしまい、**当の回帰（最初から 1 年ぶん出す）を見逃す**（実測）。
生の数（6 週以下）で止める。

### D24. `MIT-0` を許諾の許可一覧に足した

`vitest` が引く jsdom の依存（`@csstools/color-helpers` ほか）が `MIT-0`。
**MIT から表示義務すら外したもの**で、MIT を許している以上これを断る理由が無く、
AGPL-3.0 での配布と両立する。

### D25. 生存信号の欄名は **grep ではなく実際の直列化**で守る

`tools/check-openapi.sh` は Kotlin のファイルを grep して欄名の一致を見ていたが、
**同じ語が docstring や別の行にも出るので空振りする** —— 実測で、
`capturable` を `capturableX` に改名しても検査は緑のままだった。

`HeartbeatContractTest` が **実際に直列化した JSON の鍵**を契約の一覧と突き合わせ、
`check-openapi.sh` はその一覧と `docs/openapi.json` を突き合わせる。
**両方を同時に書き換えないと通らない。**

> 記録側（`IngestRequest` / `IngestResult`）の grep は ST01 のもので、**同じ弱さを持つ**。
> ST02 の担当外なので触っていないが、同じ形に寄せる価値がある。

### D26. 受け口の書き込みは 1 トランザクションにまとめる

`ingest_one` は `core.event` の INSERT・`core.coverage` の UPSERT・
`collection_started_on` の更新を**別々の文**で投げていた。加算だけが落ちると、
そのあと収集側が再送しても記録は `duplicate` で弾かれ、加算は 0 のまま ——
**その日の稼働記録は二度と戻らない**（独立検証が実測で作って確かめた。R2）。

引き金は異常な事象に限らない —— 一過性のロック競合・接続断・statement timeout でも起きる。
`ingest_is_atomic_across_event_and_coverage` が、加算を必ず落とす制約を一時的に掛けて
**記録の側も一緒に巻き戻ること**を固定する。生存信号の受け口も同じ形にした。

### D27. 検査は「定数と定数」を突き合わせない

独立検証が、**実装を逆向きに書き換えても緑のまま**の箇所を 6 つ実測で見つけた ——
`MIN_TARGET_PX` を 8 に、`YEAR_WEEKS` を 20 に、主語の割り当てを入れ替え、
セルの色を 1 色に、`bool_or` を `bool_and` に、分母から破棄も除く。
どれも**期待値が実装と同じ定数を参照している**か、**そもそも検査が無い**かだった。

規律をここに残す:

1. **要件の数はリテラルで持つ**（NFR-19 の 24 px、1 年の 53 週、想定間隔の 21600 秒）。
   トークンの都合で動いてよい値ではない
2. **本人の決定は逐語で固定する**（主語の割り当ては (名前, 主語) の組を丸ごと）。
   個数や集合の大きさでは守れない
3. **描いた結果を読む**（`BAND` の相対輝度ではなく、DOM に実際に入った `background`）。
   `ui-direction` の UIR-13（測る色と描く色がずれていて 23.4 % が 4.5:1 未満）と同じ型
4. **偽物が本番の経路を捨てていないか見る**（`FakeScheduler` は task を捨てており、
   周期の emit を空にしても緑だった）

### D28. 端末の状態を読む口は、落ちずに「取れない」側へ倒す

`androidCapability` は `ACCESS_NETWORK_STATE` の宣言漏れで `SecurityException` を投げ、
起動時の生存信号がそれを貫通して**クラッシュループ**になっていた（R31。実機でしか出ない）。

宣言を足したうえで、3 つの読み口を `runCatching { … }.getOrDefault(false)` で包んだ。
**倒す向きは「取れない」側** —— 読めていないのに「取れている」と報告するのは、
壊れているのに「動いていた」と残すのと同じで、深掘り Q5 が塞いだ当の型。
理由は `Capability.of` が必ず埋めるので「理由の無い取れない」にはならない。

### D29. 数えと未送信は、失われる向きに倒さない

- **数えは端末の保存領域に置く**（R16）。インスタンスの中だけだと `START_STICKY` の
  立て直しで区間の起点ごと新品になり、**死んでいた区間が観測から落ちる**
- **積めてから戻す**（R24）。`takeAfter` が `outbox.add` の成否を見てから数えを戻す
- **読めなかったら書き直しを断る**（R17）。`load()` が失敗した状態で `save()` が走ると
  ファイルを丸ごと上書きして、読めなかった分が痕跡なく消える。
  **退避はしない** —— 一過性の失敗で正常なファイルを脇へ退けるほうが損。
  送った分が残って次の起動で再送になるが、取り込み口は冪等（FR-22）
- **恒久的に断られた項目を先頭に居座らせない**（R18）。捨てはしない（ST04 の担当）

### D30. ライセンス検査は `npm ci` の後に置く

`tools/check-licenses.sh` の Node の節は CI の `rust` job で走っていたが、
そのジョブに `npm ci` が無く `web/node_modules` が存在しないので、
**「0 件を確認 / 不許可 0 件」で緑**になっていた（R8）。
ローカルの緑と CI の緑が別物だった —— ST02 が `MIT-0` を許可一覧に足した根拠（D24）
そのものを CI は一度も見ていない。

**対象が無いことと、不許可が無いことを混ぜない。** 節の冒頭で
`web/node_modules` が無ければ NG で落とす。検査自体は `web` job へ移した。
