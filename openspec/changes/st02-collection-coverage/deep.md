## 問うた項目

### Q1. 記録が 0 件の日の意味 —— 生存信号を入れるか

- **なぜ人間の判断か**: **要件の衝突かつ不可逆**。FR-33 は「WHEN いずれかのソースが**記録を生成する**」
  ときにしか稼働記録を書かない。つまり記録が 0 件の日は行が無いだけで原因が残らず、
  **扉 #14 が稼働記録に求めた「動きが無かったのか / 収集が壊れていたのか」の区別が成立しない**。
  しかも遡って埋められない —— day one から入れなければ、その期間は永久に判別できない
- **当初の案**: なし（既存実装（`crates/server/src/lib.rs` の `core.coverage` への INSERT）は取り込み時にしか書いておらず、
  区別できていない状態が「現状」だった）
- **本人の答え**: **収集側が定期的に「生きている」信号を送る**
- **効く先**:
  - `specs/collection-coverage/` に「記録が 0 件でも稼働が残る」振る舞いを立てる（**新設**）
  - `design.md`: 生存信号の受け口と、稼働記録への反映経路
  - `tasks.md`: 収集側（C-01 / C-02）の送信と、サーバ側の受け口
  - **FR-33 だけでは足りないことが確定した。** 要件の側に戻す必要がある（下の「要件へ戻すもの」）

### Q2. 「その日」の区切り

- **なぜ人間の判断か**: **不可逆**。NFR-13 が「365 日中 350 日以上」を数える単位そのもので、
  1 年の計測の途中で変えると過去の実測値と比較できず、成功条件 1 の判定が成立しない。
  ST01 が「ST02 の担当」として明示的に申し送っている（`st01-location-ingest/design.md` の「→ **ST02 …の担当**。そこで決める」）
- **当初の案**: UTC 固定（既存実装 `crates/server/src/lib.rs` の `($2 AT TIME ZONE 'UTC')::date`）
- **本人の答え**: **固定のタイムゾーン（Asia/Tokyo）で全部区切る**
- **効く先**: **当初案を覆した。**
  - `design.md`: 日境界を `Asia/Tokyo` に固定する。理由は「1 年が必ず 365 日になる」
    —— 記録ごとの `tz_id` で切ると、東西の移動で 1 年が 364 日や 366 日になり NFR-13 の分母がぶれる
  - `tasks.md`: 既存の `AT TIME ZONE 'UTC'` を差し替え、**境界のテストを固定する**
    （日本時間の 00:00 直前・直後の記録が別の日に入ること）
  - ST01 の Open Questions はこれで閉じる

### Q3. 停止と破棄の粒度

- **なぜ人間の判断か**: **不可逆**。粗く記録した過去は後から細かくできない。
  現在の表 `core.coverage`（`migrations/0001_envelope.sql` の `create table core.coverage`）は (ソース, 日, 状態) が主キーで、
  期間は `note` の自由文しか持てず、FR-34「停止したソースと**期間**」/ FR-9「破棄した**期間**と件数」
  を満たしていない
- **当初の案**: なし（現状は自由文）
- **本人の答え**: **時刻の範囲で持ち、判定は「1 日を丸ごと覆う停止だけ分母から除く」**
- **効く先**:
  - `specs/collection-coverage/`: 停止・破棄が時刻の範囲として残る振る舞い
  - `design.md`: `core.coverage` の作り直し（日単位の集計 + 時刻範囲の実体）
  - `tasks.md`: migration。**NFR-13 の分母から除くのは「1 日を丸ごと覆う停止」だけ**であることをテストで固定
  - ST15（開始日と終了日で止める）は、この形の上に**日単位の入力**として乗る

### Q4. NFR-13 の「達成日」の数え方

- **なぜ人間の判断か**: **要件どうしの衝突**。NFR-13 の逐語は「日単位で**記録が 1 件以上ある日**を数え」
  だが、Must ソースに含まれる**写真は「毎日届くはずのもの」ではない**（FR-3 = 新しい写真が保存された
  ときに 1 件）。逐語のままだと撮らなかった日が未達に積み上がり、**収集が正常でも 350/365 に届かない**。
  判定式は計測の途中で変えられない
- **当初の案**: なし。**旧プロジェクトが同じ問題を実測で踏んでいる**（`reference/requirements.md:765`、
  2026-09-01 の追記）——「Takeout 経路と週次取得のアカウント系は**対象外**（含めると**正常動作時から
  未達で固定される**ため）」。ただし旧プロジェクトは生存信号を持っていなかったので、
  同じ結論になるとは限らないものとして問うた
- **本人の答え**: **ソースごとに判定を分ける** —— 毎日届くはずの 4 つ（位置・アプリ利用・ウィンドウ・
  ブラウザ履歴）は「記録が 1 件以上ある日」、**写真は「生存信号があった日」**
- **効く先**:
  - `specs/collection-coverage/`: 達成日の判定がソースごとに違う振る舞い
  - `design.md`: ソース登録簿に「判定の型」を持たせる（毎日届く型 / イベント駆動型）
  - **NFR-13 の逐語を変える必要がある。** 要件の側に戻す（下の「要件へ戻すもの」）
  - **前提の確認済み**: 写真は FR-3 で端末が常時収集しており（Takeout 経路ではない）、
    日次の生存信号を出せる。この確認をせずに選んでいたら実装できない選択肢だった

### Q5. 生存信号が何を保証するか

- **なぜ人間の判断か**: **不可逆**。Android は長期間使っていないアプリの権限を自動で剥がす。
  位置の権限が剥がれると**収集プロセスは生きたまま位置が 0 件**になり、「動いている」だけを
  送っていると壊れているのに「動いていた」と記録が残る。載せなかった期間は後から特定できない
- **当初の案**: なし
- **本人の答え**: **取得できる状態か（権限・センサ・接続）も載せる**
- **効く先**:
  - `specs/collection-coverage/`: 「動いていたが取れない状態だった」が固有の状態として残る
  - `design.md`: 生存信号が運ぶ項目
  - `tasks.md`: 収集側で権限・センサの状態を読む
  - **一次情報が裏付けている**: EXT-D（`docs/requirements.md` の §5 EXT-D）—— 「写真の EXIF 位置が読めるかは、
    撮影時期ではなく**実行時点の権限状態**で決まる」。`ACCESS_MEDIA_LOCATION` は実行時に落ちうる
  - ST14（FR-35 の通知）は、記録が途切れきる前に鳴らせるようになる

### 回答（2026-09-10 受領。**10 問すべて本人が選択肢から明示的に選んだ**）

#### Q7. 生存信号で数える達成日に取得可否を要るか

- **本人の答え**: **取得できる状態の生存信号があった日だけ達成**
- **効く先**: NFR-13 の判定式。状態③「動いていたが取れない状態だった」の日は**未達**になり、
  毎日届く側（③の日は記録 0 件なので自動的に未達）と扱いが揃う。
  成功条件 1 は「収集の仕組みが動いていた日数」ではなく「**壊れていなかった日数**」を測ることになった
- **要件へ戻す**: NFR-13

#### Q8. ウィンドウとブラウザ履歴の判定型

- **本人の答え**: **5 ソースを「端末が主語 / 利用が主語」で仕分ける**
