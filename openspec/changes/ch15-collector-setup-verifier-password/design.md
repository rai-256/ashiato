# CH15 設計

## Context

ログインの口（`session_post`）は、ST55 で照らすための値の形を足したとき、照合を次の形にした（ST55 review R23・R78）:
断る数の判定から失敗の数え上げまでを `LOGIN_CHECK`（1 つずつ通す印）の中で行い、`WebLogin::accepts` を `spawn_blocking` の側で呼び、
一致しなければ同じ側で `limiter.record_failure()` する。資格情報を返す口（`collector_setup_post`、ST56）はこの形を持たず、
`throttled()` を見た後、async の側で `token_matches(&given, &app.login.password)` を呼んでいる。照らす形では `password` が空で、常に一致しない。

## Goals / Non-Goals

- Goals: 配った形（照らすための値）でも、正しい画面の合言葉で資格情報が返る。2 つの口の照合と失敗の数えが同じ道を通る
- Non-Goals: 口の応答の形・状態の番号・読み出しの記録の行・失敗の遅れの長さ・回数の上限を変えない。画面と e2e には触れない

## Decisions

### D1. 資格情報を返す口の照合を、ログインの口と同じ道に通す

`web_session.rs` に、2 つの口が共に使う照合の関数を 1 つ置く（名前と形は実装に任せる。例: 結果が「断る数を超えた / 一致 / 不一致」の 3 つの値を返す async の関数）。
中身は今の `session_post` の照合そのもの: `LOGIN_CHECK` の印を取る → `limiter.throttled()` なら「断る数を超えた」→ 合言葉が空なら不一致（失敗に数える。照らす形でも Argon2id を回さない）→ そうでなければ `spawn_blocking` の側で `login.accepts(&given)`、不一致ならその側で `record_failure()`、印を放す → blocking の側が落ちたら失敗に数えて不一致。
`session_post` と `collector_setup_post` はこの関数の結果で、それぞれ今と同じ記録の行（`login_throttled` / `forbidden` / `ok` など）と応答を出す。

- **順は今と同じ**: 断る数の判定が先、空の判定が後。数えを超えた窓では空の合言葉も 429（失敗に数えない）。数えの下では空の合言葉は失敗に数えて、資格情報の口は 403（`wrong_password`）、ログインの口は 401（どちらも今と同じ）。空の判定は共通の関数の中に置く（照らす形の `accepts` は空を自分では断らない）
- **なぜ `accepts` に差し替えるだけにしないか**: 照らす形では `accepts` が Argon2id で CPU を使う。async の worker の上で照らすと他の求めを塞ぎ、印の外で照らすと並んだ求めが失敗の数えより先に照合を通り、回数の制限をすり抜ける（ST55 review R23 と同じ穴）。正典は「ログインの口と同じ失敗の遅れと回数の制限を当て、失敗の数えを共有する」と言っているので、同じ道に通すのが正典どおり
- **なぜ `collector_setup_post` に同じ形を書き写さず、`session_post` も関数へ移すか**: 2 つの口の照合を 1 つの道にする（Goals）。写すと、次に片方だけ直して同じ食い違いが起きる。ログインの口のコードに触れるので、その振る舞いは 1.2 の試験で固定する
- 合言葉そのものの形（開発・試験の形）の振る舞いは変わらない（`accepts` は同じ `token_matches` で比べる）
- **最後の段の処置で足したこと**（review/code.md R1・R4・R5・R9）:
  - 2 つの口の「照合 → 記録の行 → 答え」は `tokio::spawn` した task で走らせ、handler はそれを待つだけにする。求めが取り消されても（接続が切れても）照合の後の行は残る。取り消された照合も失敗に数えるので、行が無いと「1 件ごとに 1 行」が崩れる（R1）
  - 断る数の判定は、印を取る前にも 1 回行う。断られている間は印を待たず、本文も読まずに 429 を返す（R4・R5）。印を取った後にも数え直すので、並んだ照合が上限をすり抜けることはない（R23 の順は変えない）
  - 印は static で誰も閉じないので、取れなかったときの 503 の道は置かない（R9）

## Risks / Trade-offs

- `session_post` の照合を関数へ移すので、ログインの口の振る舞いを壊しうる → 既存の試験（`web_session_` と `st55_` と `st56_`）を全部通すことを Task 1.2 の検証にする
- 照らす形の口の試験は router を通した試験で、画面（e2e）は合言葉そのものの形のサーバで走る。配った形の画面で文字列が出ることは、確認バッチ（tasks の「人間の確認待ち」）で見る
