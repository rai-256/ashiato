### 実測（手順 5）

- **門は派生を守っていない。** `migrations/202609120944_gates.sql:82` の
  `require_version_or_ledger()` は `OLD.origin <> 'collected'` で即 `RETURN NULL` し、
  `reject_collected_delete()` も `collected` しか見ない。つまり **`origin='derived'` の行は
  UPDATE も DELETE も素通し**。ST03 の深掘り Q7 が「派生の作り直しは ST16 の担当」として
  意図的に開けたもので（`crates/server/src/dedup_tests.rs` の `derived_rebuild_is_not_folded`
  がそれを固定している）、**作り直しの土台はもう空いている**
- **`TRUNCATE` だけは派生でも塞がっている**（`event_no_truncate`）。全件消して入れ直す形は取れない
- **一意索引は派生にも掛かる（レビュー R1 が実測）。** `event_dedup_hash` は
  `(user_id, logical_source, content_hash) WHERE external_id IS NULL` で **`origin` の述語が無い**。
  同じ内容の滞在を 2 回入れると `duplicate key value violates unique constraint "event_dedup_hash"`、
  取り込み経路の `ON CONFLICT … DO NOTHING` の形だと `INSERT 0 0` で**黙って消える**。
  既存テスト `derived_rebuild_is_not_folded` は**内容が違う** 2 件しか通していないので、
  この経路を 1 度も踏んでいない。
  **FR-22 の「派生（FR-31）は対象外」と ST03 の spec は、索引の側で守られていない**
- **`core.event.event_time` は 1 点しか持てない。** 滞在は期間なので、C7 のとおり
  開始を `event_time` に置き、開始と終了は `payload` に両方持つ
- **`raw` は `NOT NULL`**（`202609092315_raw_text` で `text` 化済み）。派生に原文は無いので、
  何を入れるかを design で決める（C2 / C3 の内容を入れるのが素直）
- **`core.source.external_id_kind` の既定は `'record'`。** 滞在用の論理ソースを
  `'none'` で登録しないと、その記録は全件 400 で断られる（C9）。
  **ただし Q1 で「安定な鍵を持つ」を選ぶなら `'record'` のままにする**
- **取り込みの契約に感度の欄が無い**（`IngestRequest` に `sensitivity` が無い）。
  何もしなければ DB の既定 `sensitivity = 1`（＝外部 AI に出してよい）に必ず乗る（R5 の前提 (b)）
