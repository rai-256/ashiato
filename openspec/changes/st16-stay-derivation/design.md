# ST16 設計 — 位置から滞在を作り、派生を作り直せる

## Context

D-01 にあるのは端末の位置（`c01-location`。60 秒ごと、`payload` に `lat` / `lon` / `acc_m`）だけで、
滞在は 1 行も無い。`core.event` の `origin` は day one から `'derived'` を持ち、
ST03 の門（`migrations/202609120944_gates.sql:82`）は派生の行の UPDATE / DELETE を素通しにしてある。
一方で一意索引 `event_dedup_hash` には `origin` の述語が無く、**派生にも掛かる**（deep-review R1 の実測）。
動機は `proposal.md` の Why。

深掘りで本人が決めた 9 件は `deep.md`。**ここで決めるのは、その決定を実装に落とすときの技術判断だけ**で、
観測可能な振る舞いは `specs/derived-records/spec.md` と `specs/browsing-views/spec.md` に置いてある。

## Goals / Non-Goals

**Goals**
- `derived-records` を作り、ST17（主観）と ST20（人物）が紐づけ先として滞在を使える土台にする
- 作り直しても、識別子（Q1）と本人が消した判断（Q2）が失われない
- `browsing-views` を前倒しで作り、1 日の滞在の一覧を出す（Q5）

**Non-Goals**
- **紐づけそのもの**（主観・人物を滞在に付ける操作と、吸収されたときに紐づけが吸収先へ移るかどうか）。ST17 / ST20。
  ST16 は「吸収された」事実を残すところまで
- **滞在を消す操作。** ST22。ST16 は「本人が消した時間帯」を読むだけ
- **場所の名前**（ST21）/ **ソースをまたいだ時刻順の表示**（FR-56。ST25）/ **主観と人物の本文の置き場**（ST17 / ST20。
  行の形は `docs/ui-direction.md` ★ 2026-09-13 補足に書いた）
- **一意索引 `event_dedup_hash` を派生から外すこと。** `record-envelope`（ST03 が archive 待ち）の移行に触れる。
  滞在は D3 で `external_id` を持つので当たらない
- **感度の操作。** ST24。滞在は DB の既定に乗るだけ（D9）

## Decisions

### D1. 滞在は `core.event` の 1 行。ソースは `s01-stay`

**`origin='derived'`、`logical_source='s01-stay'` の行として入れる。**
エンベロープ（FR-19〜FR-29）が自動で掛かり、読み出し（`core.event_live`）・削除の印（FR-50）・
感度（PERM-2）を既存のまま使える。§5「扉ではないもの」がテーブルの置き場を移行できると明記している（deep.md C1）。

| 列 | 入れるもの |
|---|---|
| `id` | 滞在の識別子（D3。作り直しで引き継ぐ） |
| `external_id` | `id` と同じ値の文字列（D3） |
| `user_id` | 入力にした位置の記録の `user_id`（利用者ごとに作る） |
| `event_time` | 滞在の始まり（deep.md C7） |
| `tz_offset_min` / `tz_id` | 始まりの位置の記録のもの |
| `device_id` | `NULL`（派生に端末は無い） |
| `schema_version` / `unit_system` / `crs` | `1` / `'si'` / `'EPSG:4326'` |
| `raw` | **サーバが組んだ JSON の文字列**（下の形）。派生に原文は無いので、作った内容そのものを入れる |
| `payload` | `raw` と同じ内容の `jsonb` |
| `content_hash` | `ingest::content_hash` と同じ作り方（`logical_source` + `event_time` + `raw`） |

`raw` の形（キーの順を固定して直列化する。**同じ滞在は毎回同じ文字列**になり、D3 の「内容が同じなら更新しない」が効く）:

```json
{"start":"…Z","end":"…Z","lat":35.6812,"lon":139.7671,"points_used":38,
 "criteria":{"id":1,"radius_m":100,"min_minutes":10,"gap_minutes":10,"sources":["c01-location"]}}
```

緯度経度は小数 6 桁（約 0.1 m）に丸めて書く —— 丸めないと浮動小数の誤差で同じ滞在が別の文字列になり、
作り直しのたびに前の版が積まれる。

> 採らなかった案: 別の表（`derived.stay`）に置く。一意索引も門も当たらず素直だが、
> 読み出し・削除の印・感度を別に作ることになり、**ST25 / ST26 / ST27 が 2 か所を読む**。

### D2. 登録簿に `s01-stay` を 1 行足し、取り込みの口では断る

移行で `core.source` に `('s01-stay', '滞在', 86400, external_id_kind='record')` を足す。
`external_id_kind` は `'record'`（D3 で記録ごとの識別子を持つため。deep.md C9 を Q1 の答えで変えた）。
`expected_gap_sec` は稼働状況に使われない（`coverage::must_sources()` は NFR-13 の 5 ソースだけを引く。deep.md C11）が、
列が `NOT NULL` なので 1 日を入れる。

**`/ingest` は `logical_source = 's01-stay'` の記録を 400 で断る**（deep.md C12）。
**`origin='derived'` 全体は断らない** —— ST03 の `derived_rebuild_is_not_folded` が `/ingest` 経由の派生を
受け入れる前提で書かれており、断ると `record-envelope` の振る舞いを変える。

### D3（仮）. 識別子は最初に振り、作り直しでは時間の重なりで引き継ぐ

**本人の答え（Q1）は「安定な鍵を与え、区切りが変わっても同じ滞在を指す」。その性質を、選択肢の説明文
（「その日・そのあたりの場所から鍵を計算する」）とは違う形で実装する。**

計算した鍵は 2 か所で性質を破る:
1. **割れると同じ鍵が複数できる。** 半径を下げて 09:00〜12:00 が 3 件に割れると、3 件とも「その日・その場所」
2. **場所の格子の境目で鍵が変わる。** 基準を変えて代表点が数 m 動き、格子をまたぐと別の鍵になり、紐づけが指す先を失う

採る形:
1. 作り直しの範囲（D5）で新しい滞在を計算する
2. 範囲と時間が重なる既存の滞在を集める —— **本人が消したもの（D4）を除き**、読み出しに出ているものと、
   作り直しで吸収されたもの（下の 4）の両方
3. (新しい滞在, 既存の滞在) の組を**時間の重なりの大きい順**に並べ、まだどちらも使われていない組から割り当てる
   （重なりが同じなら、読み出しに出ているほうを先に）。**1 つの既存の識別子は 1 つの新しい滞在にしか渡さない**
   - 割り当てられた新しい滞在は、その既存の行を**更新**する。`raw` が同じなら何もしない。
     違えば、更新の前に前の版を `core.event_version` に積む（`version_no` は続き番号）。吸収の印があれば外す
   - 割り当てられなかった新しい滞在は、新しい UUID を `id` と `external_id` に入れて足す
4. どの新しい滞在にも割り当てられなかった既存の滞在は、**行を消さず**、`deleted_at = now()` と
   `deleted_by = 'rebuild:absorbed'` を付ける。時間の重なりがいちばん大きい新しい滞在（無ければ `NULL`）を
   **吸収の台帳** `core.stay_absorbed(event_id, into_event_id, criteria_id, at)`（追記のみ）に 1 行書く

`external_id` を持たせるのは**一意索引 `event_dedup_hash`（`WHERE external_id IS NULL`）を当てないため**
（選択肢の説明文どおり）。当てたままだと、吸収された滞在と同じ `raw` の滞在が後で作られたとき一意違反で落ちる
（R1 の実測）。`event_dedup_ext` は `(user_id, logical_source, external_id)` の一意で、`id` と同じ値なので衝突しない。

**`deleted_at` を吸収の印に使う理由**: `core.event_live` が `deleted_at IS NULL` で絞っているので、
**滞在を読むすべての経路（ST25 / ST26 / ST27 を含む）から、何もしなくても吸収された滞在が消える**。
新しい列を足してビューを作り直すと `record-envelope`（ST03 が archive 待ち）に触れる。
本人が消した印とは `deleted_by` で分ける（D4）。

**反転条件**: ST17 の最初の紐づけより前なら、引き継ぎの規則はいつでも変えられる（紐づけが 0 件なので失われるものが無い）。
実データで「同じ滞在なのに引き継がれない」例が見つかったら、重なりの計り方（時間だけ → 時間と距離）を変える。
**ST17 の上流はこの D3 を読んでから紐づけの形を決めること。**

> 採らなかった案: 識別子を作り直しのたびに振り直す（紐づけが指す先を失う）/
> 計算した鍵（上の 2 つの理由）/ 吸収された滞在を行ごと消す（`core.event_version` の `event_id` が
> `core.event(id)` を参照し、履歴の行は消せないので、**版を持つ滞在は消せない**。消せても紐づけが指す先を失う）

### D4（仮）. 本人が消した印は、消した滞在の時刻の範囲に掛ける

**`deleted_at IS NOT NULL` かつ `deleted_by` が `'rebuild:'` で始まらない滞在**を「本人が消した滞在」とする。

- 本人が消した滞在は、D3 の割り当ての対象にしない（**行を変えない**）
- 新しく計算した滞在のうち、本人が消した滞在の `[start, end]` と時間が重なるものは、
  `deleted_at = now()` と `deleted_by = 'rebuild:erased-range'` を付けて入れる（捨てずに印を付ける。既定は厳しい側）
- `'rebuild:erased-range'` の滞在は D3 の割り当ての対象にする（同じ時間帯の断片が作り直しのたびに増えないように）。
  重なる本人が消した滞在が無くなることは無い（本人が消した行は作り直しで変えない）ので、印は外れない

**Q2 の答えは「印を何に掛けるか」を開いていた**（時刻の範囲 / 場所 / Q1 の鍵）。時刻の範囲にしたのは、
鍵に掛けると半径を下げて割れた**残りの断片が印を持たずに現れ**、「戻さない」が破れるため。
場所に掛けると、同じ場所の別の日の滞在まで消える。

**反転条件**: 滞在を消す操作は ST22 まで存在しない。ST22 の深掘りで本人が「重なる部分だけを隠す（切り取る）」を
望めば、それまでに変える。**消した滞在が 1 件でもできた後は、掛け方を変えると隠れる範囲が変わる。**

### D5（仮）. 作り直しの範囲と、走らせる契機

**自動（Q6）**: `/ingest` のまとめ送り 1 回を処理し終えた後、`c01-location`（基準の `sources`）の記録を
1 件以上**受け入れた**なら、その記録の日（Asia/Tokyo）ごと・利用者ごとに作り直す。
- 1 件ごとではなく**まとめ送り 1 回につき 1 回**。端末は 5 分ごとに最大 200 件を送る（`collector-android` の
  `SEND_INTERVAL_MS` / `MAX_BATCH`）ので、1 日 288 回の作り直しで済む
- 範囲は **その日の 00:00〜24:00 を、範囲と重なる読み出しに出ている滞在の始まりと終わりまで広げたもの**
  （日付をまたぐ滞在を半分だけ作り直さないため）。位置の記録は広げた範囲から、さらに前後 `gap_minutes` ぶん余分に読む
- **作り直しの失敗は取り込みの応答を変えない。** 位置の記録は 1 件 1 トランザクションで既に確定している（ST03 D3）。
  失敗は `tracing::error!(kind = "stay.rebuild", …)` で残し、滞在の値や座標はログに出さない（製造準備 A-2）。
  次のまとめ送りか、手の作り直しで回復する

**手（Q6 / C10）**: `POST /stays/rebuild`（資格情報が要る）。本文に基準（`radius_m` / `min_minutes` / `gap_minutes`）を
渡せば、基準の台帳に新しい版を足してから作り直す。省けばいまの基準で作り直す。**範囲は全期間**
（位置の記録がある最初の日から最後の日まで、日ごとに D3 を回す）。応答は作り直した日数・前後の滞在の件数・かかった時間。

**反転条件**: 1 日ぶんの作り直しがまとめ送りの応答を目に見えて遅らせたら（`collector-android` の読み取り上限 15 秒に
近づいたら）、応答の後に回す。全期間の作り直しが人が待てる時間を超えたら、期間の指定を足す（deep.md C10）。

### D6（仮）. 「記録が無い」とみなす間隔は 10 分

**隣り合う位置の記録（精度を問わない）の間が `gap_minutes`（既定 10 分）以上なら、そこで滞在を切り、
一覧では「記録なし」の行にする。** 基準の台帳の列なので、作り直しで変えられる。

10 分にした理由: FR-1 の取得間隔は 60 秒で、端末の取りこぼし 1〜2 回で滞在が割れては困る。
最短のとどまり（10 分）より短い欠けを「記録なし」にすると、滞在より細かい欠けが一覧に並ぶ。

**反転条件**: 実機の `c01-location` で、正常に動いているときの取得間隔の分布を測り、
99 パーセンタイルが 10 分を超えるなら広げる（proto の数字は合成データ。deep-review R8）。

### D7. 判定のやり方

利用者ごとに、範囲の位置の記録を出来事の時刻順に 1 本の列にして走査する。

1. `payload` に `lat` / `lon` が無い記録（消去された記録。FR-51 で `payload = '{}'`）は読み飛ばす
2. 前の記録（精度を問わない）との間隔が `gap_minutes` 以上なら、いまの集まりを閉じる（Q7）
3. `acc_m` が `radius_m` より大きい記録は、**集まりに入れず、集まりも閉じない**（Q8）。`acc_m` が無い記録は精度が良いものとして扱う
4. いまの集まりの重心から `radius_m` 以内なら集まりに加え、重心を更新する。外なら集まりを閉じ、この記録から新しい集まりを始める
5. 閉じた集まりの長さ（最初の記録から最後の記録まで）が `min_minutes` 以上なら滞在にする（Q9: 上限は置かない）

距離は正距円筒近似（緯度 1 度 = 111,320 m、経度 1 度 = 111,320 × cos(緯度) m）。数百 m の判定には十分。
**重心が集まりとともに動く**ので、半径を広げると件数が増えることがある（proto の実測で 400 m のとき平日が 6 → 7 件）。
これは判定のやり方の性質で、Risks に書いた。

### D8. S-2 の最小形

`web` に 1 日の滞在の一覧を足す。**S-1（稼働状況）はルート `/` のまま変えない**（ST02 の画面の入口を動かさない）。
一覧は `#/day/YYYY-MM-DD`（省けば今日。Asia/Tokyo）で開き、S-1 と一覧の上端に互いへの行き先を置く。

- 読み出しは `GET /stays?date=YYYY-MM-DD`（資格情報が要る）。**行の並び（滞在・移動・記録なし）はサーバが組んで返す** ——
  「記録なし」を出すには位置の記録の間隔を見る必要があり、画面に位置を 1,440 件送りたくない
- 応答: `{ date, criteria: [{radius_m, min_minutes, gap_minutes}], entries: [{kind: "stay"|"move"|"no-record", start, end, id?}] }`。
  `criteria` はその日に並んだ滞在を作った基準の重複なしの並び
- 行の形は深掘り Q4 の proto の出力のまま: 見出し＝時刻の範囲 / 添える値＝長さ・始まり – 終わり /
  移動の行「移動 42 分」/ 記録なしの行「記録なし 8:20–16:40」（**文字で**移動と区別し、左端の線は補助）/
  一覧の上に「この一覧は 半径 100 m / 10 分 で作った」
- 表面は `web/src/tokens.ts` の確定値を使う（新しい色を足すときは `contrast.ts` の検査を通す）
- 前の日・次の日のボタンと日付の入力。どれも 24×24 CSS px 以上、フォーカスの輪郭を出す
- 読み込み中・読み出しの失敗・滞在 0 件を分ける（ST02 の `Load<T>` と同じ形）

**反転条件**: ST25 が S-2 を入口にし、ソースをまたいだ時刻順の表示を足すときに、ルートと行き先の置き方を決め直す。

### D9. 感度は DB の既定に乗せる

滞在の `sensitivity` には何も書かず、列の既定（`1` = 外部 AI に出してよい）に乗せる（Q3 / PERM-3 ★）。
**「書かない」ことをテストで固定する** —— 実装が「位置由来だから」と厳しい値を書き込むと、
それが判るのは QS-1 に外部 AI が答えられなくなったときになる。

### D10. 基準の台帳と吸収の台帳は追記のみ。移行は 1 本

移行（名前は作成時刻 `YYYYMMDDHHMM_stays.sql`、`.down.sql` を添える）で次を作る:

- `core.stay_criteria(id bigint 自動採番, radius_m integer, min_minutes integer, gap_minutes integer, sources text[], created_at timestamptz)`。
  `CHECK`: `radius_m` 1〜10,000 / `min_minutes` 1〜1,440 / `gap_minutes` 1〜1,440 / `sources` が空でない。
  **最初の行（100 / 10 / 10 / `{c01-location}`）を移行が入れる**。いまの基準は `id` が最大の行
- `core.stay_absorbed(event_id uuid, into_event_id uuid NULL, criteria_id bigint, at timestamptz)`
- どちらも UPDATE / DELETE / TRUNCATE を拒むトリガ（ST03 の `erasure_ledger` と同じ形）
- `core.source` に `s01-stay` を 1 行（D2）

**すべて `IF NOT EXISTS` / `ON CONFLICT DO NOTHING` で当て直せる形にする**（`migrate()` は起動のたびに全版を当てる）。
`crates/server/src/lib.rs` の `MIGRATIONS` 配列の末尾に足す。

## Risks / Trade-offs

- **[半径を広げると件数が増えることがある]**（D7 の重心の移動）→ 判定のやり方の性質として受け入れる。
  proto の実測で 100〜300 m は件数が変わらず、400 m で平日が 6 → 7 件。実データで困ったら、重心ではなく最初の点を
  中心にする案に変える（作り直せば戻る）
- **[重なりが同じ組の割り当てが入力の順に依る]**（D3）→ 重なりが同じなら読み出しに出ている滞在を先にし、
  それでも同じなら始まりの早いほうを先にする。**決定的な順に固定する**（テストで固定）
- **[いま居る滞在は作り直しのたびに終わりが伸び、前の版が積まれる]**（D3 + D5）→ 1 日 288 回・年 10 万行程度。
  履歴は追記のみで消せない（ST03 の門）。多すぎると判ったら、**終わりだけが伸びた更新は版を積まない**に変える
  （版は「区切りが変わった」ことを残すためのもので、伸びた終わりは原文から再計算できる）
- **[吸収の印に `deleted_at` を使うので、`deleted_by` を見ない読み手は本人の削除と区別できない]** →
  滞在の読み出しでは区別する必要が無い（どちらも出さない）。区別が要るのは作り直し（D4）と、ST22 の
  「消したものを戻す」操作だけ。**ST22 の上流はこの D3 / D4 を読むこと**
- **[`gap_minutes` の既定が実機に合わない]**（D6）→ 反転条件のとおり実機の分布で決め直す
- **[位置の記録の読み出しが 1 日 1,440 件 × 288 回]** → `(logical_source, event_time)` の索引が
  `202609112113_source_lifecycle.sql:72` に既にある（利用者で絞るのは索引の後。単一利用者なので行は減らない）。
  **索引は足さない。** tasks 3.1 で `EXPLAIN` を 1 回見て、全表走査になっていたら足す
