# ST16 設計 — 位置から滞在を作り、派生を作り直せる

## Context

D-01 にあるのは端末の位置（`c01-location`。60 秒ごと、`payload` に `lat` / `lon` / `acc_m`）だけで、
滞在は 1 行も無い。`core.event` の `origin` は day one から `'derived'` を持ち、
ST03 の門（`migrations/202609120944_gates.sql:82`）は派生の行の UPDATE / DELETE を素通しにしてある。
一方で一意索引 `event_dedup_hash` には `origin` の述語が無く、**派生にも掛かる**（deep-review R1 の実測）。
動機は `proposal.md` の Why。

深掘りで本人が決めた 9 件は `deep.md`。**ここで決めるのは、その決定を実装に落とすときの技術判断だけ**で、
観測可能な振る舞いは `specs/derived-records/spec.md` と `specs/browsing-views/spec.md` に置いてある。

## Goals / Non-Goals

**Goals**
- `derived-records` を作り、ST17（主観）と ST20（人物）が紐づけ先として滞在を使える土台にする
- 作り直しても、識別子（Q1）と本人が消した判断（Q2）が失われない
- `browsing-views` を前倒しで作り、1 日の滞在の一覧を出す（Q5）

**Non-Goals**
- **紐づけそのもの**（主観・人物を滞在に付ける操作と、吸収されたときに紐づけが吸収先へ移るかどうか）。ST17 / ST20。
  ST16 は「吸収された」事実を残すところまで
- **滞在を消す操作。** ST22。ST16 は「本人が消した時間帯」を読むだけ
- **場所の名前**（ST21）/ **ソースをまたいだ時刻順の表示**（FR-56。ST25）/ **主観と人物の本文の置き場**（ST17 / ST20。
  行の形は `docs/ui-direction.md` ★ 2026-09-13 補足に書いた）
- **一意索引 `event_dedup_hash` を派生から外すこと。** `record-envelope`（ST03 が archive 待ち）の移行に触れる。
  滞在は D3 で `external_id` を持つので当たらない
- **感度の操作。** ST24。滞在は DB の既定に乗るだけ（D9）

## Decisions

### D1. 滞在は `core.event` の 1 行。ソースは `s01-stay`

**`origin='derived'`、`logical_source='s01-stay'` の行として入れる。**
エンベロープ（FR-19〜FR-29）が自動で掛かり、読み出し（`core.event_live`）・削除の印（FR-50）・
感度（PERM-2）を既存のまま使える。§5「扉ではないもの」がテーブルの置き場を移行できると明記している（deep.md C1）。

| 列 | 入れるもの |
|---|---|
| `id` | 滞在の識別子（D3。作り直しで引き継ぐ） |
| `external_id` | `id` と同じ値の文字列（D3） |
| `user_id` | 入力にした位置の記録の `user_id`（利用者ごとに作る） |
| `event_time` | 滞在の始まり（deep.md C7） |
| `tz_offset_min` / `tz_id` | 始まりの位置の記録のもの |
| `device_id` | `NULL`（派生に端末は無い） |
| `schema_version` / `unit_system` / `crs` | `1` / `'si'` / `'EPSG:4326'` |
| `raw` | **サーバが組んだ JSON の文字列**（下の形）。派生に原文は無いので、作った内容そのものを入れる |
| `payload` | `raw` と同じ内容の `jsonb` |
| `content_hash` | `ingest::content_hash` と同じ作り方（`logical_source` + `event_time` + `raw`） |

`raw` の形（キーの順を固定して直列化する。**同じ滞在は毎回同じ文字列**になり、D3 の「内容が同じなら更新しない」が効く）:

```json
{"start":"…Z","end":"…Z","lat":35.6812,"lon":139.7671,"points_used":38,
 "criteria":{"id":1,"radius_m":100,"min_minutes":10,"gap_minutes":10,"sources":["c01-location"]}}
```

緯度経度は小数 6 桁（約 0.1 m）に丸めて書く —— 丸めないと浮動小数の誤差で同じ滞在が別の文字列になり、
作り直しのたびに前の版が積まれる。

> 採らなかった案: 別の表（`derived.stay`）に置く。一意索引も門も当たらず素直だが、
> 読み出し・削除の印・感度を別に作ることになり、**ST25 / ST26 / ST27 が 2 か所を読む**。

### D2（仮）. 登録簿に `s01-stay` を 1 行足す。取り込みの口では断らず、作り直しが上書きする

移行で `core.source` に `('s01-stay', '滞在', 86400, external_id_kind='record')` を足す。
`external_id_kind` は `'record'`（D3 で記録ごとの識別子を持つため。deep.md C9 を Q1 の答えで変えた）。
`expected_gap_sec` は稼働状況に使われない（`coverage::must_sources()` は NFR-13 の 5 ソースだけを引く。deep.md C11）が、
列が `NOT NULL` なので 1 日を入れる。

**`/ingest` で `s01-stay` を断らない**（deep.md C12 を spec-review R18 で覆した）。登録簿にあるソースをコードで断るのは、
正典 `record-envelope` の「登録簿に 1 行足すだけで受け付けられる」を変える MODIFIED で、`record-envelope` は ST03 が
archive 待ちで握っている —— 書けば ST16 自身が `衝突待ち` になる。拒否の種類を新設すると取り込みの契約も変わる（R17）。

代わりに:
- **作り直しの候補（D3）と滞在の読み出し（D8）は `origin='derived'` の `s01-stay` だけを見る。** 取り込みの口から入った
  「派生させた」滞在は候補になり、計算した滞在で置き換わるか吸収される
- 取り込みの口から `origin='collected'` で `s01-stay` を名乗った記録は、滞在として扱わない（凍結されるので作り直しで触れない）。
  `core.event_live` を直に読む経路には現れる —— Risks に書いた

**反転条件**: ST03 の archive 後、偽の滞在が実際に問題になったら（本人の運用で `/ingest` の資格情報を第三者製プラグインに渡すなど）、
「サーバだけが書くソース」の宣言を登録簿の列として `record-envelope` への MODIFIED で足し、取り込みの口で断る。

### D3. 識別子は最初に振り、作り直しでは時間の重なりと距離で引き継ぐ（第 1 回 Q1 / 第 2 回 Q10 / Q11 の決定）

**本人の答え（第 1 回 Q1）は「安定な鍵を与え、区切りが変わっても同じ滞在を指す」。** 選択肢の説明文の形
（「その日・そのあたりの場所から鍵を計算する」）は 2 か所で成り立たない:
1. **割れると同じ鍵が複数できる。** 半径を下げて 09:00〜12:00 が 3 件に割れると、3 件とも「その日・その場所」
2. **場所の格子の境目で鍵が変わる。** 基準を変えて代表点が数 m 動き、格子をまたぐと別の鍵になり、紐づけが指す先を失う

そこで下の形を置いたが、spec-review R11 が「選ばれなかった第 3 選択肢の説明文そのもの（割れたら重なり最大の 1 件だけが継ぐ）」と
指摘したので、**第 2 回 Q10 として本人に返した。本人はこの形を選んだ**（割れた残りは新しい滞在）。距離を見る条件は Q11 で本人が選んだ。

形:
1. 作り直しの範囲（D5）で新しい滞在を計算する
2. 範囲と時間が重なる既存の `origin='derived'` の `s01-stay` を集める —— **本人が消したもの（D4）を除き**、読み出しに出ているもの・
   作り直しで吸収されたもの・消した時間帯に重なる印のもの（D4）を含める
3. **代表点どうしが `radius_m` の 2 倍より離れている組を捨てる**（Q11。基準は作り直しに使う新しい基準の半径）。
   残った (新しい滞在, 既存の滞在) の組を**時間の重なりの大きい順**に並べ、まだどちらも使われていない組から割り当てる。
   重なりが同じなら、読み出しに出ている既存の滞在を先に、それも同じなら始まりの早い既存の滞在を先に（**決定的な順**）。
   **1 つの既存の識別子は 1 つの新しい滞在にしか渡さない**
   - 割り当てられた新しい滞在は、その既存の行を**更新**する。`raw` が同じなら何もしない。違えば、更新の前に前の版を
     `core.event_version` に積む（`version_no` は続き番号。D5 の錠の中で読むので衝突しない）。削除の印は D4 に従って付け外しする
   - 割り当てられなかった新しい滞在は、新しい UUID を `id` と `external_id` に入れて足す
4. どの新しい滞在にも割り当てられなかった既存の滞在は、**行を消さず**、`deleted_at = now()` と
   `deleted_by = 'rebuild:absorbed'` を付ける。時間の重なりがいちばん大きい新しい滞在（無ければ `NULL`）を
   **吸収の台帳** `core.stay_absorbed` に 1 行書く（D10）

**前の版は、終わりだけが伸びた更新でも積む**（spec「区切りが伸びると前の版が残る」。R20）。量は Risks。

`external_id` を持たせるのは**一意索引 `event_dedup_hash`（`WHERE external_id IS NULL`）を当てないため**
（選択肢の説明文どおり）。当てたままだと、吸収された滞在と同じ `raw` の滞在が後で作られたとき一意違反で落ちる
（R1 の実測）。`event_dedup_ext` は `(user_id, logical_source, external_id)` の一意で、`id` と同じ値なので衝突しない。

**`deleted_at` を吸収の印に使う理由**: `core.event_live` が `deleted_at IS NULL` で絞っているので、
**滞在を読むすべての経路（ST25 / ST26 / ST27 を含む）から、何もしなくても吸収された滞在が消える**。
新しい列を足してビューを作り直すと `record-envelope`（ST03 が archive 待ち）に触れる。
本人が消した印とは `deleted_by` で分ける（D4）。

**本人の決定なので下流は変えない。** 距離の「2 倍」と重なりの同点の順は計算し直せば戻るが、変えるなら本人に聞く。
**ST17 の上流はこの D3 を読んでから紐づけの形を決めること**（割れた残りの断片には何も付いていない状態から始まる）。

> 採らなかった案: 識別子を作り直しのたびに振り直す（紐づけが指す先を失う）/ 計算した鍵（上の 2 つの理由）/
> 吸収された滞在を行ごと消す（`core.event_version` の `event_id` が `core.event(id)` を参照し、履歴の行は消せないので、
> **版を持つ滞在は消せない**。消せても紐づけが指す先を失う）

### D4（仮）. 本人が消した印は、消した滞在の時刻の範囲に掛ける。一部だけ重なる滞在は丸ごと隠す（第 2 回 Q12 の決定）

**本人が消した滞在** = `origin='derived'` の `s01-stay` で、`deleted_at IS NOT NULL` かつ
`coalesce(deleted_by, '') NOT LIKE 'rebuild:%'`。**`deleted_by` が `NULL` の削除も本人の削除に数える**
（spec-review R14 の実測: `deleted_by NOT LIKE …` だけだと三値論理で `NULL` が 0 件になり、候補に混ざって更新されうる）。
作り直しが付ける印は `'rebuild:absorbed'`（D3）と `'rebuild:erased-range'`（下）の 2 つだけ。

- 本人が消した滞在は、D3 の割り当ての対象にしない（**行を変えない**）
- 新しく計算した滞在のうち、本人が消した滞在の `[start, end]` と**少しでも**時間が重なるものは、
  `deleted_at` を付け（既に付いていれば据え置き）`deleted_by = 'rebuild:erased-range'` にする（捨てずに印を付ける。既定は厳しい側）
- 重ならなくなった滞在が `'rebuild:erased-range'` の印を持っていれば、**印を外す**（`deleted_at = NULL`, `deleted_by = NULL`）。
  spec「基準を戻して重ならなくなった断片は戻る」（R19）

**区別の約束を design だけに置かない**（R14）: spec の Scenario「削除した者の欄が空の削除も本人が消したものとして扱う」と、
`docs/handoff/ST22.md`（**ST22 は `deleted_by` に `rebuild:` で始まる値を書かない**）に置いた。

**Q2 の答えは「印を何に掛けるか」を開いていた**（時刻の範囲 / 場所 / Q1 の鍵）。時刻の範囲にしたのは、
鍵に掛けると半径を下げて割れた**残りの断片が印を持たずに現れ**、「戻さない」が破れるため。
場所に掛けると、同じ場所の別の日の滞在まで消える。
**一部だけ重なる滞在は丸ごと隠す**（第 2 回 Q12 で本人が選んだ）。**（仮）なのは印を時刻の範囲に掛ける形のほう**（Q2 の答えが開いていた部分）。

**反転条件**: 滞在を消す操作は ST22 まで存在しない。ST22 の深掘りで本人が掛け方（場所に掛けるなど）を変えたいと
望めば、それまでに変える（FR-50 の ★ の「時間帯に作らない」の文面も合わせて改訂する。`docs/handoff/ST22.md` に書いた）。
**消した滞在が 1 件でもできた後は、掛け方を変えると隠れる範囲が変わる。**

### D5（仮）. 作り直しの範囲と、走らせる契機と、錠

**錠**（R16）: 作り直しは**利用者ごとに直列化する**。1 日ぶん（広げた範囲）の作り直しを 1 トランザクションにし、
その先頭で `pg_advisory_xact_lock` を利用者の鍵で取る（`crates/server/src/testdb.rs:35` と同じ手）。
全期間の作り直しは日ごとにトランザクションを分け、日ごとに錠を取り直す（自動の作り直しを長く待たせない）。

**範囲**（R15）: 求められた日の `[00:00, 24:00)`（Asia/Tokyo）から始め、次を**変わらなくなるまで**繰り返して広げる。
1. 範囲の端から `gap_minutes` 以内に始まりか終わりを持つ、読み出しに出ている既存の滞在があれば、その端まで広げる
2. 範囲の端の前後の位置の記録を読み、端をまたいでとどまりが続いている（端の外側 `gap_minutes` 以内に、端の内側の集まりの
   半径以内の位置がある）なら、とどまりが閉じるところまで広げる

**実装での形（下流 2026-09-14）**: 2 は、範囲の前後を「範囲の長さ（最低 1 日）」ぶん広く読んで集まり（最短のとどまりに満たないものも含む）を作り、
範囲の端をまたぐ集まりの始まり・終わりまで端を動かす。読む幅を範囲の長さに合わせて伸ばすので、何日も続くとどまりでも回数は日数に比例しない（64 回で定まらなければ失敗として返す）。
広げた端では集まりが切れているので、最後に `[lo, hi)` だけで判定しても全期間で判定したときと同じ滞在になる。
1 で広げる対象は読み出しに出ている滞在と、消した時間帯で隠れている滞在（`rebuild:erased-range`）。吸収された滞在では広げない。

これで「0 時の前後で別々に届いても日付をまたぐ滞在は 1 件のまま」が成り立つ —— 00:00〜00:04 の塊だけが届いても、
1 の条件で前日の 20:00〜23:59 の滞在まで範囲が広がり、D3 がその識別子を継ぐ。
**tasks 4.1 で、2 回に分けて送る形を DB を使うテストで確かめる**（純粋な関数のテストはこの経路を踏まない）。

**自動（Q6）**: `/ingest` のまとめ送り 1 回を処理し終えた後、基準の `sources` の記録を
1 件以上**受け入れた**なら、その記録の日ごと・利用者ごとに作り直す。
**「受け入れた」には重複（`duplicate: true`）も含める**（下流 2026-09-14）—— 取り込みの応答と同じ意味にそろえる。
重複だけのまとめ送りでも作り直しは走るが、内容が同じなら行も版も増えない（`stay_rebuild_is_idempotent`）。
- 1 件ごとではなく**まとめ送り 1 回につき 1 回**。端末は 5 分ごとに最大 200 件を送る（`collector-android` の
  `SEND_INTERVAL_MS` / `MAX_BATCH`）ので、1 日 288 回の作り直しで済む
- **作り直しの失敗は取り込みの応答を変えない。** 位置の記録は 1 件 1 トランザクションで既に確定している（ST03 D3）。
  失敗は `tracing::error!(kind = "stay.rebuild", day, error)` で残し、**緯度経度と時刻の値はログに出さない**（製造準備 A-2。spec に Scenario がある）。
  次のまとめ送りか、手の作り直しで回復する
- **失敗の起こし方**（テスト用）: 作り直しの関数を差し替えられる形にし、テストでは必ず失敗する関数を入れる。
  **表の権限を剥がす・名前を変えるやり方は使わない** —— テストは開発 DB を共有するので、他のテストの作り直しも落ちる（R21）

**手（Q6 / C10）**: `POST /stays/rebuild`（資格情報が要る）。本文に基準（`radius_m` / `min_minutes` / `gap_minutes`）を
渡し、それがいまの基準と違えば、基準の台帳に新しい版を足してから作り直す。省くか同じ値ならいまの基準で作り直す（R21）。
範囲外の値は 400（D10 の `CHECK` に当てる前にアプリで弾く。当てると 500 になる）。**範囲は全期間**
（その利用者の位置の記録がある最初の日から最後の日まで、日ごとに D3 を回す）。
応答は `{ criteria_id, days, stays_before, stays_after, took_ms }`。

`GET /stays/criteria` は利用者の基準の版を古い順に `{ id, radius_m, min_minutes, gap_minutes, sources, created_at }` で返す（R21）。

**反転条件**: 1 日ぶんの作り直しがまとめ送りの応答を目に見えて遅らせたら（`collector-android` の読み取り上限 15 秒に
近づいたら）、応答の後に回す。全期間の作り直しが人が待てる時間を超えたら、期間の指定を足す（deep.md C10）。

### D6（仮）. 「記録が無い」とみなす間隔は 10 分

**隣り合う位置の記録（精度を問わない）の間が `gap_minutes`（既定 10 分）以上なら、そこで滞在を切り、
一覧では「記録なし」の行にする。** 基準の台帳の列なので、作り直しで変えられる。

10 分にした理由: FR-1 の取得間隔は 60 秒で、端末の取りこぼし 1〜2 回で滞在が割れては困る。
最短のとどまり（10 分）より短い欠けを「記録なし」にすると、滞在より細かい欠けが一覧に並ぶ。

**反転条件**: 実機の `c01-location` で、正常に動いているときの取得間隔の分布を測り、
99 パーセンタイルが 10 分を超えるなら広げる（proto の数字は合成データ。deep-review R8）。

### D7. 判定のやり方

利用者ごとに、範囲の位置の記録を出来事の時刻順に 1 本の列にして走査する。

1. `payload` に `lat` / `lon` が無い記録（消去された記録。FR-51 で `payload = '{}'`）は読み飛ばす
2. 前の記録（精度を問わない）との間隔が `gap_minutes` 以上なら、いまの集まりを閉じる（Q7）
3. `acc_m` が `radius_m` より大きい記録は、**集まりに入れず、集まりも閉じない**（Q8）。`acc_m` が無い記録は精度が良いものとして扱う
4. いまの集まりの重心から `radius_m` 以内なら集まりに加え、重心を更新する。外なら集まりを閉じ、この記録から新しい集まりを始める
5. 閉じた集まりの長さ（最初の記録から最後の記録まで）が `min_minutes` 以上なら滞在にする（Q9: 上限は置かない）

距離は正距円筒近似（緯度 1 度 = 111,320 m、経度 1 度 = 111,320 × cos(緯度) m）。数百 m の判定には十分。
**重心が集まりとともに動く**ので、半径を広げると件数が増えることがある（proto の実測で 400 m のとき平日が 6 → 7 件）。
これは判定のやり方の性質で、Risks に書いた。

### D8（仮）. S-2 の最小形

`web` に 1 日の滞在の一覧を足す。**S-1（稼働状況）はルート `/` のまま変えない**（ST02 の画面の入口を動かさない）。
一覧は `#/day/YYYY-MM-DD`（省けば今日。Asia/Tokyo）で開き、S-1 と一覧の上端に互いへの行き先を置く。
`docs/ui-direction.md` の遷移図は S-2 を入口にしているが、**入口を決め直すのは ST25**（spec に「S-1 の入口を変えない」と書いた）。

- 読み出しは `GET /stays?date=YYYY-MM-DD`（資格情報が要る）。**行の並び（滞在・移動・記録なし）はサーバが組んで返す** ——
  「記録なし」を出すには位置の記録の間隔を見る必要があり、画面に位置を 1,440 件送りたくない
- 応答: `{ date, criteria: [{criteria_id, radius_m, min_minutes}], entries: [{kind: "stay"|"move"|"no-record", start, end, id?, criteria_id?}] }`
- **記録なしの測り方**（R23）: その日の前後 `gap_minutes` ぶんの位置の記録も読み、日の頭と尻の欠けを隣の日を含めた間隔で測る。
  **今日の一覧は、いまの時刻より後を行にしない**（最後の位置からいままでが `gap_minutes` 以上なら、そこまでを記録なしにする）
- 行の形は深掘り Q4 の proto の出力のまま: 見出し＝時刻の範囲 / 添える値＝長さ・始まり – 終わり /
  移動の行「移動 42 分」/ 記録なしの行「記録なし 8:20–16:40」（**文字で**移動と区別し、左端の線は補助）
- **基準の表示**（R24）: proto の描画どおり**一覧の上に 1 行**「この一覧は 半径 100 m / 10 分 で作った」。本人の貼り戻しの
  ラベルは「行に」だが、proto は `badge` を選ぶと上に 1 つ描いていた（本人が見て選んだのはこの描画）。
  **基準が混ざる日だけ**、上にすべての基準を並べ、最初の基準と違う滞在の行にその基準を添える。deep.md Q4 の読み方 3 に書いた。
  **並べる順は新しい版から**（下流 2026-09-14）—— 混ざるのは作り直しの途中か取り込みの口から入った滞在で、
  古い基準の滞在の側に基準を添えるほうが「どれが残り物か」が読める
- 表面は `web/src/tokens.ts` の確定値を使う（新しい色を足すときは `contrast.ts` の検査を通す）
- 前の日・次の日のボタンと日付の入力。どれも 24×24 CSS px 以上、フォーカスの輪郭を出す
- 読み込み中・読み出しの失敗・滞在 0 件を分ける（ST02 の `Load<T>` と同じ形）

**実装での形（下流 2026-09-14）**:
- **移動は「滞在にも記録なしにも入らない時間」**。滞在と滞在の間だけでなく、最初の滞在の前・最後の滞在の後にも出る。
  今日は**最後の位置まで**しか移動を並べない（その先は、まだ記録なしとも移動とも決まっていない）
- 滞在は、その日と**正の長さで**重なるものだけを並べる（前の日の 0:00 ちょうどに終わる滞在は翌日に出さない）
- 時刻は `H:MM`。**見ている日の外の時刻には `M/D` を添え**（`6/30 23:30 – 8:00`）、見ている日の翌日 0:00 ちょうどは `24:00` と書く
- S-1 から一覧への行き先は**見出しと同じ行**に置く。行を増やすと ST02 の「ひとスクロール」の勘定（`one-scroll.test.tsx`）が動く
- 滞在が 0 件の日は「この日の滞在はありません」と文字で出す（記録なしの行は並べたまま）

**反転条件**: ST25 が S-2 を入口にし、ソースをまたいだ時刻順の表示を足すときに、ルートと行き先の置き方を決め直す。
基準が混ざる日が実際には作り直しの途中にしか出ないと分かったら、行に添える表示を落とす。

### D9. 感度は DB の既定に乗せる

滞在の `sensitivity` には何も書かず、列の既定（`1` = 外部 AI に出してよい）に乗せる（Q3 / PERM-3 ★）。
**「書かない」ことをテストで固定する** —— 実装が「位置由来だから」と厳しい値を書き込むと、
それが判るのは QS-1 に外部 AI が答えられなくなったときになる。

### D10. 基準の台帳と吸収の台帳は利用者ごと・追記のみ。移行は 1 本

移行（名前は作成時刻 `YYYYMMDDHHMM_stays.sql`、`.down.sql` を添える）で次を作る:

- `core.stay_criteria(id bigint 自動採番, user_id uuid NOT NULL, radius_m integer, min_minutes integer, gap_minutes integer, sources text[], created_at timestamptz)`。
  `CHECK`: `radius_m` 1〜10,000 / `min_minutes` 1〜1,440 / `gap_minutes` 1〜1,440 / `sources` が空でない。
  **利用者ごと**（FR-29。R12）。**いまの基準は、その利用者の `id` が最大の行。利用者の行が 1 本も無ければ既定（100 / 10 / 10 / `{c01-location}`）**
  —— 移行は行を入れない（利用者の一覧を移行が知らないため）。既定の値はコードの定数 1 か所に置き、最初に基準を変えたとき、
  または最初に作り直したときに、既定の行をその利用者の最初の版として書く
- `core.stay_absorbed(event_id uuid, user_id uuid NOT NULL, into_event_id uuid NULL, criteria_id bigint, at timestamptz)`
- どちらも UPDATE / DELETE / TRUNCATE を拒むトリガ（ST03 の `erasure_ledger` と同じ形）
- `core.source` に `s01-stay` を 1 行（D2）

**テストは利用者で隔離する**（R13）。テストの接続先は開発 DB そのもの（`crates/server/src/testdb.rs:14`）で、
基準の台帳は追記のみなので、テストが基準を変えると消せない。**滞在のテストは `testdb::user()` で利用者を毎回新しく作り、
その利用者の基準だけを変える**。開発 DB の既定の利用者（`00000000-…`）の基準には触らない（tasks 0 の規律）。

**すべて `IF NOT EXISTS` / `ON CONFLICT DO NOTHING` で当て直せる形にする**（`migrate()` は起動のたびに全版を当てる）。

**台帳の錠の関数は自前で持つ**（下流 2026-09-14）。`TRUNCATE` の文トリガに ST03 の `core.reject_truncate()` を使うと、
その関数を落とす `202609120944_gates.down.sql` が依存で当たらなくなる（`tools/check-immutable.sh` が実測で落とした）。
`core.stay_absorbed` の `event_id` / `into_event_id` / `criteria_id` には FK を張る（台帳が指す先を失わない。既定は厳しい側）。
`crates/server/src/lib.rs` の `MIGRATIONS` 配列の末尾に足す。

### D11（仮）. 1 日の一覧のライトの面と文字（下流 2026-09-14）

`docs/ui-direction.md` はライトの確定値を数で持っていない（「ライトでもダークでも成立させる」だけ）。
1 日の一覧は OS の明暗に追従する（NFR-17。取得できないときはダーク）ので、`web/src/tokens.ts` の `SCHEMES` に

ライトの面は playground がライトの面を置く帯（明度 66 以上）の中。4.5:1 とフォーカスの輪郭の 3:1 は `day-view-limits.test.tsx` が値から計算する。

### D12（仮）. 端が触れるだけの時間の重なり（下流 2026-09-14）

時間の重なりを 2 か所で使うが、**端が触れるだけ（重なりの長さ 0）の扱いを分けた**:
- **識別子の引き継ぎ（D3）と吸収先**: 長さが正の重なりだけを「重なり」とする。09:00〜09:30 の既存の滞在は、09:30 に始まる新しい滞在の識別子にならない
- **本人が消した時間帯（D4 / Q12「少しでも重なる」）**: 端が触れるだけでも重なりとし、隠す（既定は厳しい側）

D3 の規則（重なりの大きい順・1 対 1・距離）は本人の決定なので変えていない。ここで決めたのは「重なり 0 を数えるか」だけ。

**反転条件**: 端が触れるだけの滞在に識別子が移らないことで、ST17 / ST20 の紐づけが指す先を失う例が出たら、引き継ぎの側も閉区間にする（紐づけが 0 件のうちは戻せる）。

## Risks / Trade-offs

- **[半径を広げると件数が増えることがある]**（D7 の重心の移動）→ 判定のやり方の性質として受け入れる。
  proto の実測で 100〜300 m は件数が変わらず、400 m で平日が 6 → 7 件。実データで困ったら、重心ではなく最初の点を
  中心にする案に変える（作り直せば戻る）
- **[いま居る滞在は作り直しのたびに終わりが伸び、前の版が積まれる]**（D3 + D5）→ 1 日 288 回・年 10 万行程度。
  履歴は追記のみで消せない（ST03 の門）。**この量は受け入れる**（spec「区切りが伸びると前の版が残る」を正とする。R20）。
  1 行は数百バイトなので年 50 MB 未満
- **[吸収の印に `deleted_at` を使うので、`deleted_by` を見ない読み手は本人の削除と区別できない]** →
  滞在の読み出しでは区別する必要が無い（どちらも出さない）。区別が要るのは作り直し（D4）と、ST22 の
  「消したものを戻す」操作だけ。`docs/handoff/ST22.md` に書いた
- **[取り込みの口から `origin='collected'` で `s01-stay` を名乗った記録は、`core.event_live` を直に読む経路に滞在のような顔で残る]**（D2）→
  滞在の読み出しと作り直しは `origin='derived'` だけを見るので一覧には出ない。資格情報（PERM-10）を持つ呼び出し元しか送れない。
  問題になったら D2 の反転条件
- **[`gap_minutes` の既定が実機に合わない]**（D6）→ 反転条件のとおり実機の分布で決め直す
- **[位置の記録の読み出しが 1 日 1,440 件 × 288 回]** → `(logical_source, event_time)` の索引
  `event_by_source_time` が `202609112113_source_lifecycle.sql:71-72` に既にある（利用者で絞るのは索引の後。単一利用者なので行は減らない）。
  **索引は足さない。** tasks 3.7 で `EXPLAIN` を見る。
  **行の少ない開発 DB の統計では計画器が `event_hash_all`（利用者・ソース・内容の鍵）を選んだ**（下流 2026-09-14 の実測）ので、
  検査は使い捨ての DB に 1 人 14 日ぶん（20,160 件）を入れて `ANALYZE` した後の計画を見る。その統計では `event_by_source_time` に乗る。
  作り直し 1 回は範囲を広げるために前後を広めに読む（D5）ので、実際の読み出しは 1 回あたり数千件になる

## Migration Plan

2. 起動後に `POST /stays/rebuild` を 1 回叩くと、既に溜まっている位置の記録から全期間の滞在ができる
   （確認バッチの手順書に載せる）
3. 戻すときは `.down.sql`（`core.event` の `s01-stay` の行と履歴の行は門で消せないので、
   **滞在の表と登録簿の行は残し、台帳 2 つだけを落とす**と書く。滞在の行は `deleted_by = 'rebuild:rolled-back'` の印を付ける）
