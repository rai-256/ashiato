### Q8. DB はあるのに秘密が無くてインストーラが止まったとき、記録を残したまま戻る出口を作るか（design D10）

- 問い: 走らせ直しで「DB はあるのに設定のファイル（秘密）が無い」に当たったとき、インストーラは何も書き換えずに止まります。そこから記録を残したまま動かし直す出口を、この Story で作りますか。
- 推奨: 作る。`ashiato-setup.exe repair` で、管理者として DB を単独の利用者の形（`postgres --single`）で起こし、役割の合言葉と秘密を作り直して設定に書く（記録は書き換えない）
- 否の根拠: 止まった後に出口が無く（design.md D10「出口…は作らない」）、止まっている間に携帯の未送信が FR-9 の上限（90 日・2 GB）で捨てられ、元に戻す手は DB の置き場を消して入れ直すこと（記録を全部捨てる）だけ（discarded）。出口を作る側は範囲の中で要件を変えずに選べるので、P ではなかった
- 答え: この Story で出口を作る（`ashiato-setup.exe repair`）（本人の選択。推奨と同じ。補足なし。`deep-answers-2.txt`）

### Q9. サービスにした DB のログの行き先と権限（design D17）

- 問い: DB のログを置き場の `logs\db` のファイルに書くとき、DB のサービスのアカウントに書きを付け、ログの収集へ切り替わる前の数行がイベントログに出ることを受け入れますか。
- 推奨: 受け入れる。`logs\db` に `NT SERVICE\ashiato-db:(OI)(CI)M` を足し（D3 の ACL の表を直す）、D17 は D3 に乗ると明記する。イベントログに出るのは起動の最初の数行と `pg_ctl` の知らせだけで、送った文の字面と秘密は出ない —— design の文言を「文の字面と秘密はイベントログに出さない」に合わせる
- 否の根拠: 「権限は置き場と同じ」は D3（仮）の ACL に乗るのに rests_on に無く、その ACL は `logs\db` に DB のサービスの書きを付けない（design.md D3）ので DB が起動しない。また、サービスの PostgreSQL は切り替えより前の出力と `pg_ctl` の出力をイベントログへ書くので、「イベントログに出さない」が字面どおりには成り立たない（exported の境目の読み直し）
- 答え: `logs\db` に DB のサービスの書きを足し、起動の数行がイベントログに出るのは受け入れる（本人の選択。推奨と同じ。補足なし。`deep-answers-2.txt`）

### Q10. `repair` が DB の管理者の役割に入るとき、その役割の名前をどこから知るか（design D28・D1）

- 問い: `repair` は合言葉なしで DB の管理者の役割に入って 3 つの役割の合言葉を替えますが、いまの作り方だと管理者の役割の名前が「インストールを走らせた Windows の利用者の名前」になり、`repair` はそれを知る先がありません。名前をどう決めますか。
- 推奨: DB を作るときに名前を固定する（`initdb -U ashiato`。開発の DB の `tools/db-roles.sh` の既定と同じ）。`repair` もインストールの役割の段も、この名前で入る
- 否の根拠: 一時の `hba_file` と `pg_ident` は管理者の役割の名前を要るのに、D1 の `initdb` は `-U` を渡さず名前が固定されず、D4 の設定の鍵にも無く、`repair` は設定のファイルが無いときに動くので名前を読む先が無い（別の管理者 B の `repair` では B を A の名前の役割に結べない）。名前が引けなければ `repair` は (c) で止まり、出口の無い D10 の状態に戻って携帯の未送信が FR-9 の上限で捨てられる（discarded）。土台の D1・D4・D6 を rests_on に挙げていなかったので、P ではなかった
