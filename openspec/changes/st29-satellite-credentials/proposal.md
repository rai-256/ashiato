## Why

**衛星（読書ログ・家計簿・AI など、本体の外で動くアプリ）を後から気軽につなぐための、最初の 1 歩が無い。**
いま本体が知っている呼び出し元は 2 種類だけ —— 収集アプリと C-02 が共有する合言葉（`API_TOKEN`）と、画面のログイン（ST28）。
共有の合言葉では、どの衛星が書いたか（FR-24）も、どの衛星に何を承認したか（PERM-11）も分けられない（PERM-10 ★ 2026-10-11）。
衛星ごとの資格情報が無いかぎり、後続の書き手の列（ST37）・承認（ST38）・衛星の読み出し（ST45）・AI（ST27）はどれも始められない。

いま作る理由は 2 つ。

1. **衛星が書く名前の形（扉 #30）の期限が、この Story の中に来る。** 名前は記録の 1 行ずつに保存され、衛星が書き始めた後に形を変えると
   全行の書き直しになる（FR-101）。さらに、断った衛星の求めは書き換えられない読み出しの記録に残すので、衛星の識別子の形は
   ST29 で記録に入った時点で固まる（`review/deep.md` R4）
2. **衛星の資格情報を、読み書きの口より先に「何も通さない」形で置く。** 承認（ST38）より先に読める口ができると、
   承認していない種類が外へ出る（扉 #15。既定は厳しい側）。資格情報だけを先に作り、どの口も通さないことを全 route で固定する

## What Changes

深掘りは **第 1 回・8 問**（A 1 / B 6 / 画面 1）。**この文書は推奨の答えで先に書いた**（2026-10-20 の流れ。本人の答えはまだ無い）。
推奨と違う答えが返れば、その問いだけを仕様に写す（`spec --answers`）。聞かずに決めた既定は C1〜C15（`deep.md`）、
独立レビュー（`deep-review`）が足した仮の決定は D1〜D4（`design.md`）。

- **衛星の登録簿を作る**（FR-101 / PERM-8）。衛星は識別子（逆ドメイン風。`dev.example.booklog`）と名前を持つ。
  識別子の形を検査し、`ashiato.` で始まるもの・本体の前置きの形（`c03-` など）で始まるもの・既に登録された識別子を断る（Q1 / C1 / C3）。
  識別子は登録の後に変えられない
- **「外部 AI」（`ashiato.ai-external`）と「ローカル AI」（`ashiato.ai-local`）を最初から登録しておく**（完了の判定 / PERM-14）。
  この 2 つは外せない（Q3）。AI を止めたいときは資格情報を取り消す
- **衛星の名前の形を決める**（Q1。扉 #30）: 衛星が登録する論理ソースと種類の名前は `<衛星の識別子>:<名前>`（`dev.example.booklog:reading`）。
  本体の名前は `:` を含まない（C2）。ST29 では衛星はまだ名前を登録しない（登録の口は ST38 / ST39）が、形はここで決めて正典に置く
- **衛星ごとの資格情報を発行する**（PERM-14）。発行するときにどの衛星のものかを決め、資格情報の名前と画面にその衛星の名前を出す。
  文字列は `ashsat_<衛星の識別子>_<乱数>`（Q4）。本体はハッシュだけを持ち、値は発行の直後に 1 回だけ見せる（C4）。
  1 つの衛星に何本でも発行でき、1 本ずつ取り消せる。取り消した 1 本は行を消さずに取り消しの時刻を付ける（C5 / D1）。
  発行の時刻と最後に使われた時刻を出す（C6）。期限は付けない（Q5）
- **衛星を外せる**（FR-90）。外すと、その衛星の資格情報は次の求めから効かない。外した衛星の行は消さない。
  同じ識別子で登録し直すと、前の衛星の続きになる（Q2。承認は空から、資格情報は新しく。C14）
- **衛星の資格情報では、まだどの口も通らない**（完了の判定 / Q6 / Q7）。資格情報の要らない口（生存確認・ログイン・ログアウト）を除き、
  router のすべての口が衛星の資格情報に 403 を返す。資格情報の要らない口は、衛星の資格情報を付けても付けなくても同じ応答（C8）。
  衛星向けの口はこの Story では置かない（ST42 が版の付いた契約と一緒に置く）
- **断った衛星の求めを読み出しの記録に残す**（C9 / D4）。資格情報の種類に「衛星」を足し、どの衛星の・どの 1 本の資格情報かの識別子を残す。
  取り込みの口に衛星が来たときも残す（C12）
- **衛星の登録・発行・取り消し・外すは、画面のログインでだけできる**（C13）。S-7 設定に「衛星と資格情報」の節を足す（Q8）
- **本体に衛星のコードを読み込む仕組みを持たせない**ことを、依存の検査で機械が固定する（FR-77 / C11）
- **衛星の登録簿を書き出しに入れ、資格情報の表は入れない**（C7）

**BREAKING は無い。** 収集アプリの合言葉と画面のログインで通る口と、その応答は変えない（C10。収集アプリの合言葉の範囲は ST44）。
正典 `record-envelope` の「すべての API 要求は資格情報を要求する」はそのまま成り立つ（衛星の資格情報も呼び出し元を識別できる資格情報で、
資格情報の無い求めは今までどおり 401）。資格情報の要らない口の例外を正典に書く MODIFIED は ST44 が持つ（`docs/audit/2026-10-11-consistency.md` K5）。

## Capabilities

### New Capabilities

- `satellite-platform`: 衛星の登録簿・識別子と名前の形・衛星ごとの資格情報（発行・1 回だけ見せる・取り消し・外す）・
  衛星の資格情報ではまだどの口も通らないこと・本体に衛星のコードを読み込まないこと・S-7 の「衛星と資格情報」の節。
  INDEX の capability 表は ST29 を `satellite-platform` の最初の Story にしている（前倒しは無い）

### Modified Capabilities

- `data-sensitivity`: 「誰がいつ読んだかを、追記のみの読み出しの記録に残す」を MODIFIED。資格情報の種類に「衛星」を足し、
  衛星と 1 本の資格情報の識別子の欄と、403 の結果を足す。「識別子の文字列を持たせない」は記録と利用者の識別子のこととして残す（C9 / D4）
- `data-durability`: 「書き出しは台帳・導出・内部の表と、消したことの痕跡を入れない」を MODIFIED（入らないものに衛星の資格情報を足し、
  zip の中のファイルの一覧に衛星の登録簿を足す）。衛星の登録簿を書き出しに入れる Requirement を ADDED（C7）。
  **INDEX の capability 表の `data-durability` の行に ST29 が無かったので足した** —— 書き出しは分類の無い表があると始まらない（正典）ので、
  表を足す Story が分類を載せる（前例: ST09 の「…書き出しの分類に載る」）。ST33 の Scenario がファイルの一覧を「それ以外のファイルは無い」で
  固定しているので、ファイルを足すには MODIFIED が要る
