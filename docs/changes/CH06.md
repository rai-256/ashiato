# CH06 — 検証のたびにテスト用 DB を作り直す

## 価値

検証の証跡を、CI と同じくいつも空の DB から取る。worktree の DB に溜まった行で server の試験（とくに書き出し）が回ごとに遅くなり、
下流の AI 時間の約半分を食っていた（10/17〜10/24 で 53.5 時間）のを止め、ハーネスの約束（`HARNESS_VERIFY=1` なら repo が溜まった状態を作り直す）を `tools/verify-env.sh` でも守る。
あわせて、Docker の既定のアドレスの空きが尽きた機械でも worktree の DB を立てられるようにする（推奨で先に書いた。第 1 回の答えで確定する）。

## 依頼（逐語）

> ## 依頼
>
> 検証（`scripts/verify-run`）のたびに、その worktree のテスト用 DB を空から作り直す。
>
> ## なぜ（2026-10-25 の調査の実測）
>
> - 手元の `cargo test -p ashiato-server` は 1262 本で 84 分かかり、export 系（`export_job_tests` など）が `書き出しが終わらない`（`wait_idle` の 300 秒）で落ちる。
>   CI（毎回空の DB）では 1386 本が 601 秒で通る。
> - 書き出しは DB 全体を対象にする（例: `export/ledger.rs` の `erased_after` は `core.event` を全件読む）。
>   ところが worktree の DB は作り直されず溜まり続ける（ch03 の DB は `core.event` 22 万行・`core.export_ledger` 115MB）。
> - 同じ worktree・同じ `export_` で、DB を作った直後は 43 秒、その後は 2745 秒・7048 秒（CH03 2.1）。ST41 6.2 は 1424 → 3295 → 4598 → 7881 秒と増えていく。
> - 10/17〜10/24 の server の cargo test の証跡は合計 53.5h（下流の AI 時間の約半分）で、Task の時間の長い裾（3〜13 時間のセッション）の主因になっている。
> - harness2 の `verify-run` は準備（`tools/verify-env.sh`）と検証に `HARNESS_VERIFY=1` を渡す（harness2 README・`scripts/evidence.py` の `VERIFY_FLAG`。
>   「repo は溜まった状態を作り直す」約束）。ashiato2 では `tools/stack.sh` だけがこの印を見て、`tools/verify-env.sh` は見ていない。
>
> ## 完了の判定
>
> - `HARNESS_VERIFY=1` のとき `tools/verify-env.sh` が、この worktree の DB を空から作り直してから役割（`tools/db-roles.sh`）を整える。
>   ほかの worktree の DB には触らない。印が無いときの振る舞い（起動して待つだけ）は変えない。
> - 作り直した直後の DB で、`scripts/verify-run` 経由の `cargo test -p ashiato-server` が通る（移行は `testdb.rs` の初回で当たる）。
> - 溜まった DB（行を足した状態）から `HARNESS_VERIFY=1 tools/verify-env.sh` を呼ぶと、`core.event` が 0 行になることを機械が確かめる検査がある。

## 壊してはいけないもの

- 印（`HARNESS_VERIFY=1`）が無いときの `tools/verify-env.sh`: DB を起動して繋げるまで待ち、役割を整えるだけ。DB の中身に触らない
- CI でない main の checkout の DB（開発用の起動の中身）: 印があっても作り直さない
- ほかの worktree の DB・compose の外のコンテナと volume: 触らない
- 既にある `.env` の合言葉の行（変えると既にある DB に繋がらなくなる）と、CI の合言葉（`$GITHUB_ENV`。CI では `.env` を作らない）
- worktree ごとの port の規則（`tools/ports.sh`）、`tools/stack.sh`・`tools/smoke.sh`・`tools/dev.sh`・`tools/record-env.sh` の振る舞い、試験のコードと移行

## 完了の判定

- `HARNESS_VERIFY=1` のとき `tools/verify-env.sh` が、この worktree の DB を空から作り直してから役割（`tools/db-roles.sh`）を整える。切った接続の数と出所を 1 行出し、作り直せなければ何も消さずに非 0 で終わる。
  CI でない main の checkout では作り直さない。印が無いときの振る舞いは変えない（`tools/check-verify-env-reset.sh` と `--self-test` が rc=0。CI の rust job で走る）
- 作り直した直後の DB で、`scripts/verify-run` 経由の `cargo test -p ashiato-server` が通る（tasks 7.1 の証跡）
- 溜まった DB から `HARNESS_VERIFY=1 tools/verify-env.sh` を呼ぶと `core.event` が 0 行（か無い）になることを、`tools/check-verify-env-reset.sh` が機械で確かめる
- worktree ごとの DB の network が、木ごとに被らない subnet で立つ（`tools/check-ports.sh --self-test`。この worktree の DB が Docker の既定のアドレスの空きに依らずに立つこと —— tasks 1.3 の証跡）。
  消えた worktree の空の network が同じ subnet を塞いでいても立ち、コンテナが繋がっていれば何も消さずに非 0（`tools/check-verify-env-reset.sh` の worktree での証跡）
- 画面も人の操作も変わらないので、確認バッチの「人間の確認待ち」は置かない。archive の判定は上の機械の検査と証跡だけで決まる
