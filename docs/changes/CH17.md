# CH17 — Windows のインストールの試験の 1 周を縮める（台本だけの変更ではビルドし直さない）

## 価値

試験の台本と文書だけを変えた PR の push では、CI が Windows の配布物をビルドし直さず、組み立ての入力が同じ前の配布物でインストールと更新の試験だけを走らせる。
ビルドするときも Rust の依存を組み直さない。ST58 の関門で 1 周が約 1 時間（ビルド 33 分・インストールの試験 17 分）かかり、台本しか変えていない最後の 3 周も
毎回ビルドし直していた。手元の Windows は使わず（並列とコンテナ化を保つ）、CI の Windows の 2 つの job（`package-windows`・`install-windows`）の中で縮める。

深掘り第 1 回（2026-11-17）で本人が、PR ごとに Windows の配布物を組むという要件を改めて使い回しを認め、使い回した配布物の `SOURCE.txt` と印はそれを組んだ commit（同じ PR の前の push の head か main の commit）を指すとした（FR-127 ★ 2026-11-17）。正典 distribution の本文を改めるので、軽い路から通常の路へ移った。

受け皿の依頼 #308（https://github.com/rai-256/ashiato/issues/308）から。

## 本人の言葉

> Windows 環境を直にいじれるようにすると、並列化とかできなくなってしまってコンテナ化した意味が半減する気がする（→ CI の中で縮める案に「はい」）

## 議論で決めたこと（本人の決定。深掘りで聞き直さない）

- **何を**: CI の install-windows が、試験の台本（tools/release/ など）だけが変わった push では、前に作った Windows の配布物を使い回してインストールの試験だけを走らせる。あわせて package-windows の Rust のビルドにキャッシュを効かせる
- **なぜ**: ST58 の関門で 1 周が約 1 時間かかり、13 時間で 12 周した。内訳は package-windows のビルド 33 分・install-windows 17 分で、最後の 3 周は台本しか変えていないのに毎回ビルドし直していた
- **どこまで**: CI（.github/workflows）の Windows の配布物とインストールの試験の job だけ。手元の Windows を試験に使う形にはしない（並列とコンテナ化を保つ）。製品のコードと他の job は変えない

## そのとき考えたこと

手元の Windows を直に触らせる案は、1 台を Story が取り合い並列とコンテナ化の利点が半減するのでやめた。使い回す配布物が本当にその commit のコードから作ったものかは、ビルドの入力の鍵で確かめる必要がある（作るときの深掘りで決める）

## 壊してはいけないもの

- 配る形を壊す変更（`crates/`・`Cargo.*`・`web/`・`migrations/`・組み立ての台本・`ci.yml` など、試験の台本と文書以外の全部）は、その PR の CI で Windows の配布物をビルドし直し、壊れていれば落ちる
- `install-windows` は、配る形と試験の形の 2 つの配布物でインストールと更新の試験を走らせ、走った Scenario を `--list` の全部と突き合わせ、欠けがあれば落ちる（使い回したかどうかに依らない）
- `changes` の job の出し分け（`code` / `windows` / `android` / `stamp` / `deps`）と `tools/release/changes.sh` の判定
- `package-windows` と `package-artifacts` の job の `if:` と、`package-windows` が PR の head の commit を checkout すること（`tools/release/check-guards.sh workflows`）
- `ch14_` の試験の step が最初の `package.sh windows` より前にあること（`tools/check-ci-ch14-step.sh`）
- 成果物の名前（`package-windows-release` / `package-windows-test` / `release-package`）と、ビルドするときの手順（`package.sh windows` と `--test-build`）
- `package-windows` 以外の job・`release.yml`・`nightly.yml`・製品のコード・配布物の作り方（`tools/release/build.sh` / `package.sh`）
- PR の配布物を公開しないこと。正式版・ベータ版・開発版の配布物の `SOURCE.txt` が、自分を組んだ commit を指すこと（使い回すのは PR の CI の Windows の配布物だけ）
- `package-artifacts` の job（深掘り Q2 で変えないと決めた）

## 完了の判定

1. 手元で: `tools/release/windows-build-key.sh --self-test` と `--check-workflow` が spec の Scenario を全部出して rc=0。`tools/release/check-guards.sh workflows`・`--self-test`・`tools/check-ci-ch14-step.sh` が rc=0 のまま（tasks の Task 1・2）
2. この change の PR の CI で: `package-windows` が配布物をビルドし（`ci.yml` が変わったので鍵が新しい）、保存し、`install-windows` がインストールと更新の Scenario を全部走らせて通る
3. 同じ PR の CI を同じ commit でもう一度走らせると（Actions の「Re-run all jobs」）: `package-windows` がビルドの step を飛ばして前の配布物を同じ名前で上げ、`install-windows` が Scenario を全部走らせて通り、`package-windows` の時間が 2. より大きく縮む（目安: 33 分 → 数分）
4. 試験の台本だけを変えた別の commit で: この change の merge の後、試験の台本（`tools/release/install-check.sh` など）だけを変えた PR の CI で（無ければ確認のために台本のコメントだけを変えた一時の PR を作り、確かめたら閉じる）、`package-windows` がビルドを飛ばし、`install-windows` が Scenario を全部走らせて通る
5. Rust のキャッシュ: 2. の run の後に `crates/` を変えてビルドする run で、Rust のキャッシュの step が前の鍵（Rust の版までの前方一致を含む）から戻し、`package-windows` の時間が 2. より縮む
6. 確認バッチの問い: 「4. の run で Windows の配布物のビルドが飛ばされ、インストールの試験は全部走って通っているか。5. の run で Rust のキャッシュが戻ったか（run の画面の `package-windows` の step と `install-windows` の結果）」
