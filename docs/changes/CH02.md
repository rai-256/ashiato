# CH02 — 書き出しの「次の記録」の引きを行数の 2 乗で遅くならないようにする

## 価値

書き出しから除く範囲の判定（`export/excluded.rs` の `overlap_sql`）が「次の記録」を行ごとの相関副問い合わせで引くため、行数の 2 乗で遅くなる
（7.8 万行で 1 本約 84 秒。本物の約 120 万行では書き出しも、設定画面を開くたびの件数の数えも実用にならない）。
これを窓関数の一度読みに替え、行数に対して線形に近い時間で書き出せるようにする。どの記録が除かれるかは、同じ時刻に並んだ記録が除く側へ揃うこと（Q1）のほかは変えない。
（第 1 回の答え 2026-10-21: Q1〜Q4 とも推奨のとおり）

## 依頼（逐語）

> export/excluded.rs の overlap_sql は、幅の終わりを決める「次の記録」を、行ごとの相関副問い合わせ（同じ user_id・logical_source・device_id IS NOT DISTINCT FROM・(event_time, id) > の ORDER BY ... LIMIT 1）で引いている。
> 2026-10-20 に ST09 のテスト用 DB（core.event 約 7.8 万行。c02-window 4 万・c01-location 1 万）で実測したところ、書き出し 1 回の 3 本の問い合わせがそれぞれ約 84 秒かかり、export の試験 1 本が 240 秒、142 本では 2 時間を超えた。実行計画では、副問い合わせが 17,529 回走り、そのたびに event_by_user_source_ingest で約 1.5 万行を読み流していた（1 回 4.6 ms）。
> (user_id, logical_source, device_id, event_time, id) の索引を試しに足しても 147 秒にしかならなかった（IS NOT DISTINCT FROM は索引で絞れない）。DB を作り直すと 1 本 0.9 秒・142 本 9 分に戻ったので、原因は行数に対して 2 乗で伸びる引き方にある。本物の写しは約 120 万行なので、本物のデータでの書き出しも同じ理由で遅いはず。
> 依頼: 次の記録の引きを、ソース・端末ごとの窓関数（lead() over (partition by user_id, logical_source, device_id order by event_time, id)）などの一度読みで済む形に直し、書き出しの結果（どの行が消した時間と重なり除かれるか）を変えない。行数を増やしても時間が線形に近いことを試験か計測で示す。既存の export の試験（ST33・ST09）をすべて通す。

## 壊してはいけないもの

- どの記録・前の版が書き出しから除かれるか（同じ時刻に並んだ記録を除く側へ揃える Q1 のほか）。いまの SQL を試験に残し、まっさらな DB の偽データで新旧を突き合わせて固定する（Q2）
- 写し（書き出しの本体）は `READ ONLY` のトランザクションで、一時表を作らない（ST33 design D5）
- 次の記録は `core.event_live` から引き、削除の印の行を間に挟まない（ST33 design D5・C21）
- 前の版の組の鍵（利用者・ソース・端末）は親の記録から取る（`core.event_version` は端末を持たず、利用者は凍結される）
- 次の記録は緯度経度で絞る前の `core.event_live` の並びで決める（ST33 design D17 の「新しい記録の取り込みは幅を縮める側にだけ働く」を崩さない）
- 除く範囲の式は `excluded.rs` の 1 か所だけ（書き出しの本体・`GET /export/summary`・D17 が同じ断片を使う）。公開の形と呼び出し側は変えない
- 消した滞在が 0 件なら記録の表を読まない・消した時間より後の行は各組の最初の 1 行だけを窓に入れる（Q4）
- 画面・操作・API・書き出しのファイルの形・台帳・移行

## 完了の判定

- 書き出しから除く記録と前の版が、同じ時刻に並んだ記録（Q1）のほかは変わっていない —— いまの SQL を試験に残し、まっさらな DB の偽データで新旧の除く集合を突き合わせる試験が緑（tasks Task 3）。
  同じ時刻の組は、除く側にだけ変わり、差が名指しした id だけである
- 除く範囲の判定が読む行の数が、記録を 4 倍にしても 8 倍未満に収まり、いまの SQL では 8 倍以上になる（tasks Task 4。時間ではなく読んだ行の数で見る）。消した滞在が無ければ記録の表を読まない。窓の枠が 2 乗に戻る形でないことを断片の文字列で固定する
- 書き出しと件数の数えの時間を 1 万・10 万・120 万行、消した滞在あり・無しで測った表が `openspec/changes/ch02-export-next-record-window/design.md` の「計測の記録」に埋まり、
  件数の数え 1 回が 3 秒以上か（ST33 D13 の反転条件）が書いてある（tasks Task 5）。**確認バッチでは、本人がこの表を見て D13 を替える（件数を前回の書き出しの目録から出す）かを決める**（この change では替えない）
- ST33 の export の試験と server の試験が全部通り、ST09 のブランチの export の試験も CH02 の断片の上で通る（tasks Task 6。CH02 の worktree で一時に merge して走らせ、abort で戻す）
- 画面・操作・API・書き出しのファイルの形・移行は変わらない（確認バッチで本人が触って確かめるものは無い）
