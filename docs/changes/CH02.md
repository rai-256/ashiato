# CH02 — 書き出しの「次の記録」の引きを行数の 2 乗で遅くならないようにする

## 価値

export/excluded.rs の overlap_sql は、幅の終わりを決める「次の記録」を、行ごとの相関副問い合わせ（同じ user_id・logical_source・device_id IS NOT DISTINCT FROM・(event_time, id) > の ORDER BY ... LIMIT 1）で引いている。
2026-10-20 に ST09 のテスト用 DB（core.event 約 7.8 万行。c02-window 4 万・c01-location 1 万）で実測したところ、書き出し 1 回の 3 本の問い合わせがそれぞれ約 84 秒かかり、export の試験 1 本が 240 秒、142 本では 2 時間を超えた。実行計画では、副問い合わせが 17,529 回走り、そのたびに event_by_user_source_ingest で約 1.5 万行を読み流していた（1 回 4.6 ms）。
(user_id, logical_source, device_id, event_time, id) の索引を試しに足しても 147 秒にしかならなかった（IS NOT DISTINCT FROM は索引で絞れない）。DB を作り直すと 1 本 0.9 秒・142 本 9 分に戻ったので、原因は行数に対して 2 乗で伸びる引き方にある。本物の写しは約 120 万行なので、本物のデータでの書き出しも同じ理由で遅いはず。
依頼: 次の記録の引きを、ソース・端末ごとの窓関数（lead() over (partition by user_id, logical_source, device_id order by event_time, id)）などの一度読みで済む形に直し、書き出しの結果（どの行が消した時間と重なり除かれるか）を変えない。行数を増やしても時間が線形に近いことを試験か計測で示す。既存の export の試験（ST33・ST09）をすべて通す。
