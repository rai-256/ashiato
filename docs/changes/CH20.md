# CH20 — 配る形の更新の確認を本物の配布元で nightly に確かめる

## 価値

更新の確認（サーバの更新係と PC の収集アプリ）が本物の配布元（GitHub の `rai-256/ashiato` のリリース）と話したときの振る舞いを、毎晩機械が確かめる。
偽の配布元だけを相手にした試験では見えない食い違い（答えの形・大きさ・状態コードの扱い）が起きたら、翌朝までに赤で分かる。
2026-11-19 に本人が見たエラーの原因探しと直しは別の change で行う（深掘り Q1・Q9。推奨で先に書いた。答え待ち）。

## 依頼（逐語）

> ## 何を
> 配る形の更新の確かめ（サーバの更新係 `crates/updater` と PC の収集アプリの `update_check.rs`）が、**本物の配布元**（GitHub の `rai-256/ashiato` の releases）と話したときに正しく振る舞うことを、nightly で 1 日 1 回確かめる。
>
> ## なぜ
> 2026-11-19、本人が配る形をインストールして普通に使ったら、更新の確認がエラーを出し続けた。CI の `install-windows` は ST57 design D18 で更新係の外向きを塞ぎ、試験用の zip は loopback の偽の配布元を相手にする。配る zip で見ているのは「配布元に届かなくてもインストールは終わる」だけで、**本物の配布元との組み合わせは一度も試されていなかった**。
> （参考: 2026-11-19 時点で `rai-256/ashiato` の releases は 0 件。エラーの直し自体は別に行う。この change は「次に同じ種類の食い違いが起きたら機械が気づく」ための検査）
>
> ## どこまで
> - nightly（PR ごとではない。共有の runner の IP で上限 60 回に当たらないよう、1 回の実行で問い合わせは数回まで）
> - 本物の配布元の今の状態（release が 0 件・最新が自分と同じ版・新しい版がある）のどれでも、更新係が「エラー」を記録し続けず、決めた振る舞いになることを判定する
> - 落ちたら nightly が赤になる。PR の CI の D18（外向きを塞ぐ）は変えない
> - 配布元の応答の形が変わったことも拾えるようにする（偽の配布元が本物とずれたら気づく）

## 壊してはいけないもの

- 製品のコード（更新係・PC の収集アプリ・選び方の共有の部品・携帯の収集アプリ・インストーラ・サーバ）は 1 字も変えない（Q9。3 つの食い違いも直さない）
- 部品の問い合わせに資格情報・版・端末の情報を入れないこと。配る組み立ての宛先が定数で、変える口を持たないこと（正典の Scenario をそのまま残す）
- PR ごとの CI は本物の配布元に問い合わせない。`install-windows` は最初のインストールより前に更新係の外向きを塞ぐ（ST57 D18）
- 今の偽の配布元の試験（`st57_once`・`st57_pc_update`・`update-check-install.sh`）と共有の材料（`update-check-vectors.json`・`update-apply-vectors.json`）
- 配る物の組み立てと公開（`nightly.yml`・`release.yml`）と、脆弱性の毎晩の検査（`vulns-nightly.yml`）

## 完了の判定

**archive の判定**（機械）:
- tasks の全項目の検証が PASS（自己試験・配線の検査・手元の流し直しで部品の行（`updater`・`collector`・`collector-dev`）は 3 つの食い違いの 6 行だけが赤・触れないパスの差分が無い）
- PR の CI の `chain` の job が `release-source-check.sh --self-test` と `--check-workflow` を走らせて通る

**確認バッチの問い**（merge の後。本人が見る）: tasks の「人間の確認待ち」の 8.1（最初の毎晩の実行の要約。本物の状態の行・既に分かっている食い違いの 3 つ・それ以外の赤が無いこと・成果物）と、仮の決定 D13・D14（`provisional.jsonl`）
