# CH21 — 確認バッチの前に、その回で足した機能を使ってみる席（/tsukau）で確かめ、違和感を直すか人間に回す

## 価値

## 依頼（逐語）

> ## 何を
> ashiato2 に harness2 の「使ってみる席」（`/tsukau`・`scripts/tsukau.py`。harness2 #272 / PR #276 で入った）の差し込み口を置き、
> 確認バッチの準備から、**その回のバッチで足した機能だけ**を範囲にして、小さい時間と token で毎回呼ぶ。
> **見つけた違和感の候補は、見つけて書くだけで終えず、機械が直すか人間に回す。** 手で好きなときに呼ぶ（`/tsukau`）ときも同じ差し込み口を使う。
>
> ## なぜ
> 2026-11-19、本人が配る形を入れて普通に使ったら、違和感（更新の確認がエラーを出し続ける）がすぐ見つかった（#329）。
> 今の試験はどれも spec の Scenario を 1 つずつ確かめるだけで、「入れて普通に使うとどう見えるか」を見る席が無く、人間が最初の利用者になっている。
> 本人の決定（2026-11-20）: 好きなときに回したいが、毎回簡単な動作確認もしてほしい。毎回やるのは追加機能に限ってよい。
> **やりたいのは違和感を見つけて直したりエスカレーションしたりすること**で、手順書に件数を載せるだけでは足りない（2026-11-20、第 2 版の CH21 の問いを見た本人の指摘）。
>
> ## どこまで
> - 差し込み口: `tools/tsukau/tsukau.json` と env_hook（`up` / `down`）。契約は harness2 の `scripts/tsukau.py` の冒頭と README の「使ってみる席」。
>   相手は画面（web）と PC（Windows Sandbox に配る zip を入れる）。携帯は外（後で足せる作り）
> - 確認バッチの前: その回に入った Story / change が足した機能を範囲にして席を呼ぶ。小さい時間と token
> - **見つけた後の処置**（本人の決定。ふだんのレビューの指摘と同じく「機械が直す」か「人間に回す」）:
>   - 候補が本物かどうかは、見つけた席とは**別の席**が根拠を見て決める（誤検知で無駄に直さない）
>   - そのバッチの Story / change が原因で直し方がはっきりしているもの → 確認バッチの `fix` で直す（人間が「通らなかった」と答えたときと同じ経路）。直した後に席でもう一度確かめる
>   - 直すかどうかが判断になるもの（仕様どおりだが使いにくい、など） → 手順書の問いとして人間に回す
>   - そのバッチと関係ない、前からある違和感 → 受け皿の依頼（ラベル「違和感」の issue）にする
> - 候補の本文を公開の repo に出さない決まりは残す。人間に回すものは手元の手順書に載せ、issue にするときは私的な値を伏せる
> - 席が落ちても・時間切れでも、確認バッチの準備は止めない（警告として手順書に書く）
> - 席の中身（触り方・違和感の候補の書き方）は harness2 側で、席は直さない。直すのは上の処置の経路。処置の経路に harness2（verify グラフ）の変更が要るなら、
>   深掘りでどこまでを ashiato2 に置き、どこからを harness2 の依頼にするかを決める
> - 以前の CH21（ashiato2 だけで席を作る形）と第 2 版（差し込み口と手順書への記載だけの形）は捨てる
