# CH25 — CI の偶発的な赤を直す（gradle の部品の取り置き・時計のテストの許容幅）

## 価値

CI が中身と関係なく赤になる 2 つの原因（gradle の部品を毎回配布元から取り直す・時計の試験の許容幅に用意の時間が入らない）を直し、再実行の手間をなくす。
要件・製品の振る舞い・依存の版は変えない。

## 何を（依頼から）

1. gradle を使う 6 つの job（ci.yml の `build-stamp`・`android`・`android-instrumented`・`package-linux`、nightly.yml と release.yml の `package-linux`）の
   `actions/setup-java` に `cache: gradle` を足す（design D1（仮）・D2（仮））。依頼が挙げた `chain` は gradle を呼ばない（proposal の Impact）
2. `crates/collector-windows/src/clock.rs` の試験の偽の取り込み口が、応答を返す瞬間の時刻にずらしを足して Date を返す。用意の間に 1.5 秒眠る試験で、直す前に落ちることを証跡に残す

## 壊してはいけないもの

- 製品のコード: `clock.rs` の `#[cfg(test)]` より前（`HttpDateClock::now` など）は 1 字も変えない
- 正典の Scenario「PC の時計が進んでいると差が正で残る」「PC の時計が遅れていると差が負で残る」と、その試験の幅（`300_000..301_000 + width`・`-300_000 - width..-299_000 + width`）・関数の名前・印
- 依存の版とロック（`collector-android/` に触れない）。ロックの検査（`tools/check-gradle-locks.sh` とその自己試験）は今と同じ段・同じ順で走り、今と同じに効く
- workflow の、取り置きの指定の外（ほかの段・段の順・job の条件・`on`・`permissions`・ほかの job）。workflow を読む既存の検査（依存の検査の配線・Windows の組み立ての鍵・一時フォルダの配線）が通る

## 完了の判定

1. 用意の間に 1.5 秒眠る時計の試験が、直す前の偽の取り込み口で落ち（証跡に FAIL）、直した後に通る。`clock::tests::clock_reference` の試験が全部通り、5 本を 300 回続けて走らせても落ちない（tasks 1.1・1.2・1.4）
2. 製品のコードが base のままで、2 つの Scenario の試験の幅と印が字面のまま（tasks 1.3）
3. gradle を使う 6 つの job が `cache: gradle` を持ち、workflow はそれ以外 base のまま、`collector-android/` も base のまま。workflow を読む既存の検査とロックの検査が通る（tasks 2.1〜2.3）
4. 触ったファイルが予定のパス（`lane.json`）とこの change の中だけ（tasks 3.1）
5. 確認バッチの問い（tasks 4.1）: 「この PR の CI で gradle の job が緑で、setup-java の段に取り置きの復元の試みと保存の行が出ているか」・「merge の後の PR で android の job に `Cache restored` が出たか（観測できなければ、そう答える）」

## 残るもの

- 取り置きは鍵（`*.gradle*` などの hash）が変わった最初の run と、main が保存する前の PR では効かない。その run は今と同じく配布元から取る
- 6 つの job が同じ鍵を使うので、先に保存した job が使わない部品は取り置きに無い（design D1 の代償と反転条件）

## 依頼（逐語）

> CI が中身と関係なく落ちる 2 つの原因を直す。要件は変えない。
>
> ## 1. Gradle の部品を CI で取り置く（キャッシュ）
>
> 何が嫌か: android・エミュレータ・package-linux・chain など gradle を使う job が、Maven から部品を取れずに落ちる（2 日で 4 回）。毎回、人か機械が再実行している。
>
> 原因: `.github/workflows/ci.yml` の gradle を使う job は、部品のキャッシュを持たない（`setup-java` に cache の指定が無く、gradle のキャッシュもどこにも無い）。毎回数百個を Maven Central などから取り直すので、配布元が一瞬おかしいだけで落ちる。
> 実例: run 44684479094 の android（job 136115495058）。`Could not find org.ow2.asm:asm:9.8`・`commons-io:commons-io:2.16.1` など実在する部品が「無い」と返り、`Did not resolve ... dependency lock state` で落ちた。再実行では通った。
>
> どこまで: gradle を使う全 job で、部品を CI のキャッシュから取る形にする（`setup-java` の `cache: gradle` か `gradle/actions/setup-gradle`。どちらにするかは作るときに決める）。ロックの検査（`tools/check-gradle-locks.sh`）が今と同じに効くこと。依存の版は変えない。
>
> ## 2. 時計のテストの許容幅の穴を塞ぐ
>
> 何が嫌か: `crates/collector-windows/src/clock.rs` の `clock_reference_pc_behind_gives_negative_difference` が、CI の Windows で時々落ちる（run 44684479094 の collector-windows-runtime、`skew=-298996 width=4`）。
>
> 原因（テストの誤り。製品のコードは正しい）: `skew_against` は最初に「今 ± 5 分」を決めて偽のサーバ（`fake_ingest`）に固定の Date を返させ、その後にサーバの起動と `HttpDateClock::new`（通信の部品の用意）をしてから問い合わせる。許容幅は問い合わせの時間（`width`）しか含まず、その前の用意の数ミリ秒が入らない。Date は秒で切り捨てられて最大 999ms ずれるので、切り捨てが 999ms 近い回に用意の数ミリ秒で幅を外れる（1 回あたりおよそ 0.5〜1%）。進んでいる側の `clock_reference_pc_ahead...`（`skew_against(Utc::now() - 5分)`）も同じ穴を持つ。
>
> どこまで: 偽のサーバが**返す瞬間の時刻**にずらし（± 5 分）を足して Date を返すなど、用意の時間が誤差に入らない形にする。両方向のテストを直す。テストが確かめていること（差の符号と大きさ・幅の扱い）は弱めない。製品のコード（`HttpDateClock::now`）は変えない。
