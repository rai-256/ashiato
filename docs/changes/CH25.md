# CH25 — CI の偶発的な赤を直す（gradle の部品の取り置き・時計のテストの許容幅）

## 価値

CI が中身と関係なく落ちる 2 つの原因を直す。要件は変えない。

## 1. Gradle の部品を CI で取り置く（キャッシュ）

何が嫌か: android・エミュレータ・package-linux・chain など gradle を使う job が、Maven から部品を取れずに落ちる（2 日で 4 回）。毎回、人か機械が再実行している。

原因: `.github/workflows/ci.yml` の gradle を使う job は、部品のキャッシュを持たない（`setup-java` に cache の指定が無く、gradle のキャッシュもどこにも無い）。毎回数百個を Maven Central などから取り直すので、配布元が一瞬おかしいだけで落ちる。
実例: run 44684479094 の android（job 136115495058）。`Could not find org.ow2.asm:asm:9.8`・`commons-io:commons-io:2.16.1` など実在する部品が「無い」と返り、`Did not resolve ... dependency lock state` で落ちた。再実行では通った。

どこまで: gradle を使う全 job で、部品を CI のキャッシュから取る形にする（`setup-java` の `cache: gradle` か `gradle/actions/setup-gradle`。どちらにするかは作るときに決める）。ロックの検査（`tools/check-gradle-locks.sh`）が今と同じに効くこと。依存の版は変えない。

## 2. 時計のテストの許容幅の穴を塞ぐ

何が嫌か: `crates/collector-windows/src/clock.rs` の `clock_reference_pc_behind_gives_negative_difference` が、CI の Windows で時々落ちる（run 44684479094 の collector-windows-runtime、`skew=-298996 width=4`）。

原因（テストの誤り。製品のコードは正しい）: `skew_against` は最初に「今 ± 5 分」を決めて偽のサーバ（`fake_ingest`）に固定の Date を返させ、その後にサーバの起動と `HttpDateClock::new`（通信の部品の用意）をしてから問い合わせる。許容幅は問い合わせの時間（`width`）しか含まず、その前の用意の数ミリ秒が入らない。Date は秒で切り捨てられて最大 999ms ずれるので、切り捨てが 999ms 近い回に用意の数ミリ秒で幅を外れる（1 回あたりおよそ 0.5〜1%）。進んでいる側の `clock_reference_pc_ahead...`（`skew_against(Utc::now() - 5分)`）も同じ穴を持つ。

どこまで: 偽のサーバが**返す瞬間の時刻**にずらし（± 5 分）を足して Date を返すなど、用意の時間が誤差に入らない形にする。両方向のテストを直す。テストが確かめていること（差の符号と大きさ・幅の扱い）は弱めない。製品のコード（`HttpDateClock::now`）は変えない。
