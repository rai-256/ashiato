# CH24 — zip の部品を 2 から 9 に上げ、例外の表の理由を事実に合わせる

## 価値

重大の勧告を事実と違う理由（「互換範囲外の修正版待ち」。直った版はもう出ている）で外したままにしない。Rust の zip を直った版（9 系）に上げ、
例外の表から zip の行を消す。サーバと PC の収集アプリが zip を読む・書く振る舞いは変えない。

受け皿の依頼 #338（https://github.com/rai-256/ashiato/issues/338）から。

## 議論で決めたこと（本人の決定。深掘りで聞き直さない）

- **何を**: Rust の zip を 2.6.1 から直った版（9.0.5 以上）に上げ、osv-scanner.toml の GHSA-m665-v7pm-7grj・GHSA-q7v9-x93c-xqv3・GHSA-8hxf-qr8p-62x4 の例外を外す
- **なぜ**: 例外の理由は「上げる予定: 互換範囲外の修正版待ち」だが、直った版は既に出ていて、残っているのは 2 → 9 の大きな上げの作業だけ。今の使われ方（PC の収集アプリの更新は展開の前に sha256 の指紋を照合・サーバは本人の Takeout の zip をディスクへ展開せずに読む）ではすぐには困らないが、重大の勧告を事実と違う理由で外したままにしない
- **どこまで**: zip を使う 4 か所（crates/server の archive/open.rs・export/dump.rs・export/ledger.rs、crates/collector-windows の update_apply.rs）を新しい版に合わせ、振る舞いは変えない。書き出しの AES の zip が今と同じに読めることを確かめる。上げきれないときは、例外の理由を事実（「上げる予定: 2 → 9 の上げの作業が残る」）に直して期限を 90 日以内に置く

## 壊してはいけないもの

- **書き出し**（サーバ。`export/dump.rs`）: どの項目も AES-256 で暗号化し、中身は deflate、注記は `ashiato-export <id>`。合言葉が無い・違うと読めない。
  **前の版（zip 2.6.1）で書いて手元に残っている書き出しの zip も、上げた後の版で同じに読める**（台帳の照合 `export/ledger.rs` も注記を読む）
- **Takeout の書庫の取り込み**（サーバ。`archive/open.rs`）: ディスクへ展開せずに読む・ディレクトリの項目を飛ばす・読めない zip を `broken_zip` として台帳に残す
- **PC の収集アプリの更新の展開**（`update_apply.rs`）: 指紋（sha256）を照合してから展開する・道の外を指す項目を断る（`enclosed_name`）・Unix の権限を写す。
  zip の部品の `extract` に置き換えない（手書きの展開のまま）
- 読める圧縮の方式を今より狭めない（zip の部品の既定の features のまま）
- 試験の Scenario の印・試験の名前・1 行の assert の期待値（新しい版の API に合わせる直しだけ）
- 例外の表の zip 以外の行・ほかの依存の版（`Cargo.lock` で zip に引かれて変わるもの以外）
- API・送信の契約・移行・画面

## 完了の判定

1. `Cargo.lock` の zip が 1 つの版だけで、9.0.5 以上である。サーバと PC の収集アプリが zip の既定の features で組み立つ（tasks 2.1）
2. 上げる前の版（zip 2.6.1）で書いた書き出しの zip を試験に埋め込み、上げた後の版で全項目が同じ中身で読め、AES の形（強さ・実の圧縮方式）が同じ（tasks 1.1・2.2。埋め込んだ commit の `Cargo.lock` が zip 2.6.1 であることを機械が見る）
3. 書き出し・Takeout の取り込み・PC の更新の既存の試験が、上げた後に全部通り、印・名前・期待値が base から減っていない（tasks 2.2〜2.4）
4. 例外の表から zip の行（GHSA-m665-v7pm-7grj・GHSA-q7v9-x93c-xqv3・GHSA-8hxf-qr8p-62x4 と、同じ zip の RUSTSEC-2026-0367・0368・0369・0429）が消え、
   PR の脆弱性の検査（`tools/check-vulns.sh --base`）が rc=0、許諾と更新係の依存の境界の検査が rc=0（tasks 3.1・3.2）
5. 触ったファイルが `lane.json` の予定のパスとこの change の中だけ（tasks 4.1）
6. 上げきれなかったとき（Task 2 が予定のパスの中で通らない）は、1〜4 を満たさない。その場合は本人の決めた代わり（7 行の理由を
   `上げる予定: 2 → 9 の上げの作業が残る` に直し、期限を 90 日以内に置く）を、計画の直しとして人間に返す（tasks の Global Constraints）
7. 確認バッチの問い: 「CH24 の PR の証跡で、1.1 の埋め込みが zip 2.6.1 の commit で入り、2.2 で上げた後の版が同じ中身で読めているか。PR の Windows の CI（`runtime_windows`・Windows 向けの clippy）が通っているか」。
   画面や操作は変わらないので、人間の確認待ちの項目は無い
