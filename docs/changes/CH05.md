# CH05 — 試験の DB が打ち切った run の残りで膨れないようにする

## 価値

（第 1 回の深掘りの推奨の答えで先に書いた。答えが推奨と違えば record と spec が直す）

各 worktree のテスト用 DB に積もった試験の残りで、後の試験が遅くなって下流が止まることを、人も agent も気づかないうちに機械が戻す。
膨れた `ashiato` database は検証の準備が作り直し（使っている途中なら見送る）、試験を途中で殺しても次の回の後に残りが無いことを台本と CI が確かめる。
残りを積まない試験の足場そのものは CH04 が持ち、CH05 はその上に積む（Q1）。

以下は依頼の内訳（逐語の正本は「依頼（逐語）」）。完了の条件は Q6 の推奨で量の形に書き直した。

### 何が起きたか（2026-10-24 実測）

worktree ごとのテスト用 DB（`ashiato2-<id>-db-1`）が、打ち切った・殺された `cargo test` の run が残した行で膨れ、後の試験が数百倍遅くなって下流が止まった。

- ST29: DB に体積試験の行（user ごとに 20001 件・計 16 万件超）。`cargo test -p ashiato-server export_` が `test result` まで届かず、fix round を 5 回使い切った。DB を作り直すと 557 秒で通った
- ST23: DB が 223MB。`stay_` の通しに 3701 秒かかり、`export_status_erased_count_is_recounted_after_a_stay_is_absorbed` が 300 秒の待ちを超えて落ちた。lock timeout・権限のエラーも出た。DB を作り直すと `stay_` 114 本が 15.69 秒、その 1 本は 1.12 秒で通った
- CH03 も 179MB（作り直す前の 1 MB 前後と比べて）

体積の行を入れる試験は `deletion_tests.rs` `stay_tests.rs` `places_tests.rs` `export_excluded_tests.rs` `export_file_tests.rs` `archive_flow_tests.rs` など。試験が途中で殺されると（時間切れ・SIGTERM・agent の打ち切り）後片付けが走らず、行がそのまま残る。

### 依頼（両方やる）

1. **試験の後片付けを、途中で殺されても残らない形にする。** 例: 体積の行を共有の `ashiato` DB に入れず、試験ごとの使い捨ての database（`testdb.rs` に既にある `st16_tmp_*` 型の仕組みなど）に閉じる。あるいは、次に走る試験が前の run の残りを片付ける。殺された run の残りが次の run の速さに影響しないことを、機械で確かめる試験を置く
2. **worktree のテスト用 DB を定期的に（あるいは膨れたら）作り直す。** 作り直しの手順は `tools/db.sh down -v` → `tools/db.sh up -d --wait db` → `tools/db-roles.sh`。いつ作り直すか（大きさの閾値・下流の Task の開始前など）は機械が決める。走っている試験がある DB は作り直さない（使っている途中で壊さない）
   - ハーネス（harness2）の側が要るなら、その部分は申し送りにしてよい

### 完了の条件（Q6 の推奨で書き直した。依頼の文は「依頼（逐語）」に残る）

- 体積の試験を途中で殺した後でも、次の `cargo test` の後に殺した回の database が残らず、`ashiato` の行数が殺す前と同じで、大きさが 1 MiB を超えて増えない（速さを決める量で見る。秒数は記録するだけ。大きさの許しは、触らない database でも統計などで少し動くため）
- 膨れた DB を機械が見つけて作り直す道がある（人間や agent が気づいて手で作り直さなくてよい）

依頼の作り直しの手順（`down -v` → `up` → `db-roles`）は採らず、中の `ashiato` database だけを作り直す（Q4。ネットワークの割り当てが尽きた機械で、コンテナごと立て直すと DB を取り直せないことがある）。

## 壊してはいけないもの

（第 1 回の深掘りの推奨の答えで先に書いた。CH04 の「壊してはいけないもの」を引き継ぐ）

- CH04 が決めた試験の足場: `testdb` の形（`pool()`・`app_pool()`・`url()`）・回の database・試験ごとの database・次の回の初めの片付け・`tools/check-test-db-growth.sh`（CH05 は変えない）
- 消せない表の書き換え禁止のトリガ（外さない・無効にしない・`session_replication_role` を変えない）
- 試験の期待値（assert）・`// Scenario:` の印・試験の名前と本数
- `tests/server_startup.rs`・縦串（`tools/smoke.sh`）・開発用の起動（`tools/dev.sh`）が `ashiato` database を使い、使う前に自分で移行を当てること
- `ashiato` に繋いでいる接続（起きているサーバ・確認バッチの画面）—— 作り直しは接続を切らない。接続があれば見送る
- main の checkout と確認バッチ（`-verify`）の DB の中身 —— 作り直さない（Q5）
- `tools/ports.sh` の port の値と規則（作業ツリーの種類を出す変数を足すだけ）
- 既存の 4 つの台本（smoke・stack・check-immutable・check-panic-log）の `down -v`（Q7。見送りを当てない）
- DB のコンテナ・ネットワーク・volume（作り直しは中の database だけ。Q4。使われていない資源の片付けは別の change へ申し送る。Q7）

## 完了の判定

（第 1 回の深掘りの推奨の答えで先に書いた）

- 作り直しの判定: 閾値（既定 64 MiB）を超えた database を作り直し、閾値以下・main と確認バッチの作業ツリー・走っている回・回の作成の途中・接続がある（判定の後に繋いだものも）ときは作り直さず、
  作り直した database に移行を当て直せる（`tools/test-db-rebuild.sh --self-test` が rc=0。tasks 1.3）。作業ツリーの種類の規則が `tools/ports.sh` にあり、port もそこから決まる（`tools/check-ports.sh --self-test` が rc=0。tasks 1.2）
- 検証の準備が膨れた `ashiato` を作り直し、その後も所有者で `ashiato` に繋げる。DB に問えなければ検証の準備が落ちる（`tools/test-db-rebuild.sh --verify-env-check` が rc=0。tasks 2.2）
- 体積の行を入れる途中と、確定した後の 2 時点で殺した回の database が次の回の後に残らず、`ashiato` の行数が同じで大きさが 1 MiB を超えて増えない。探りが眠っている間の作り直しは「走っている回」で見送る（`tools/check-test-db-killed.sh` が rc=0。tasks 4.2）。
  CH04 の片付けを外すと同じ台本が rc=1 で落ちる（tasks 4.3）。次の回の秒数は design の「計測の記録」にある（合否にしない）
- `tools/check-test-db-killed.sh --self-test` が rc=0 で、CI の rust job が 3 つの検査を走らせる（tasks 4.1・5.1）
- 画面・操作・API・移行・製品のコードは変わらない（確認バッチで本人が触って確かめるものは無い）

archive の判定: 上の検査が揃い、CH05 の commit が触ったファイルが許したもの（新しい 2 つの台本・`tools/verify-env.sh`・`tools/ports.sh`・探りの試験と `lib.rs` の 1 行・ci.yml・文書）だけで（tasks 6.2）、
server の試験の全体が作り直した `ashiato` の上で通り（tasks 6.3）、`openspec validate ch05-test-db-bloat --strict` と `python3 scripts/check_scenarios.py . ch05-test-db-bloat` が rc=0。
