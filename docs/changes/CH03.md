# CH03 — テストの一時ファイルの後始末

## 価値

テストが /tmp に一時ファイル・ディレクトリを作って消さず、16G の tmpfs（/tmp）を満杯にした（2026-10-23 実測。df 100%）。
満杯のあいだ、並走する Story / change の検証（CH02 の export 試験など）が「空きなし」で落ち、原因の切り分けに時間を取られた。

実測の内訳（/tmp の直下、名前の頭で集計）:
- `ashiato-export*`（ashiato-export-file / -tamper / -late など）約 6.2G … crates/server の export の試験
- `seg<数字>` 264 個・約 4.7G … collector-android の `SegmentStoreTest`（`Files.createTempDirectory("seg")`、消していない）
- そのほか `outbox*` 5145 個・`st09-media*` 2219 個・`st06-usage*` 936 個・`heartbeat*` 789 個・`clock*`・`counters*`・`legacy*` など
  （件数は多いが小さい。同じ漏れ方）
- 共通の形: Rust は `std::env::temp_dir().join(format!("ashiato-…-{uuid}"))` を作って消さない（archive_tests / archive_flow_tests ほか）。
  Kotlin は `Files.createTempDirectory(...)` を作って `@After` で消さない

依頼:
1. テストが作る一時ファイル・ディレクトリを、テストの終わりに（失敗しても）消える作りにする。
   Rust は落ちても消える仕組み（例: tempfile の TempDir の drop）、Kotlin は JUnit の TemporaryFolder か @After での削除。
   どの手段にするかは決めてよい。
2. 再発を機械で止める: 手書きの `std::env::temp_dir()` / `Files.createTempDirectory` / `createTempFile` を、テストのコードで使ったら
   落ちる検査（tools/check-*.sh と CI）を足す。エラーの文言に「何を使えばよいか」を書く。
3. テストを一通り走らせた前後で /tmp に残るものが増えないことを、検証のコマンドで確かめる。

触らない: テストが確かめている振る舞いそのもの（期待値・Scenario の印）は変えない。製品のコード（export.rs など）の置き場の決め方も変えない。
