# CH26 — 夜間の脆弱性検査の 4 件を片付ける（chrono・libsqlite3-sys・rustix・同梱の PostgreSQL 17.12）

## 価値

夜間の脆弱性検査が 2026-11-19 から毎晩赤のままだと、新しい勧告が出ても赤に埋もれて気づけない。挙がった 4 件（#334〜#337）を、互換の範囲で上げるか、当たる使い方を確かめた理由つきの例外にして、検査を緑に戻す。
配る物の同梱の PostgreSQL は 17.12 にし、既に入っている DB をそのまま使える。要件と製品の振る舞いは変えない。

| issue | 処置（`openspec/changes/ch26-nightly-vulns-cleanup/design.md`） |
|---|---|
| #336 rustix 1.1.5 | `Cargo.lock` だけで 1.1.6 以上へ（D1） |
| #335 libsqlite3-sys 0.30.1 | 直る版は rusqlite 0.41（互換の範囲の外）。例外の表に `届かない:`（D2（仮）） |
| #334 chrono 0.4.45 | 保守終了で直る版が無い。例外の表に `届かない:`。90 日で切れてまた知らせる（D3（仮）） |
| #337 PostgreSQL 17.6-1 | `pgsql.lock` を 17.12-1 に（D4）。17.6 の DB の置き場を 17.12 が使い、戻しても使え、17.12 の退避を 17.6 が戻せることを Linux で走らせて確かめる（D5）。Windows の配布物どうしの更新と戻しは、lock を変える PR だけ CI が前の lock（17.6-1）の zip を組んで Windows の runner で通す（D5・D7（仮）〜D9（仮）。`deep.md` の R2。第 1 回の合意で本人が A → C に変えた） |

## 何を（依頼のまま）
- #334 chrono 0.4.45（RUSTSEC-2026-0543）
- #335 libsqlite3-sys 0.30.1（RUSTSEC-2026-0459、重大度 6.8）
- #336 rustix 1.1.5（RUSTSEC-2026-0486）
- #337 同梱の PostgreSQL 17.6 → 17.12（EDB の zip あり、公開日 2026-11-12）

## 壊してはいけないもの

1. 製品のコードと振る舞い: `crates/**/src`・`collector-android`・`web`・移行・API と送信の契約に触れない。Rust の試験と clippy が今のまま通る（rustix を上げても依存の木のほかの所は動かない）
2. 同梱の PostgreSQL の大きい版は 17 のまま。DB の置き場（`db\17`）・実行ファイルの一覧・許諾の文の置き場は変わらない（`tools/check-pg-major.sh` が通る）
3. 17.6 で使っていた DB の置き場を、17.12 が作り直さず・移さずに同じ中身で使い、17.6 に戻しても使える。17.12 で取った退避を 17.6 が戻せる（PostgreSQL の部分を Linux で機械が確かめ、Windows の配布物どうしの 17.6 → 17.12 の更新と戻しは、lock を変える PR だけ CI が前の lock の zip を組んで `tools/release/update-apply-install.sh` で通す —— 本人の決定 R2、第 1 回の合意で C に変えた。本人の PC の移行はこの change で扱わない（ST64））
4. 例外の表のほかの行・検査の台本（`tools/check-*.sh`）を変えない。CI と workflow は、`pgsql.lock` を変える PR だけ前の lock で古い側の試験用の zip を組んで更新と戻しを通す所だけを足し、lock を変えない PR の組み立てと試験は今のまま（本人の決定 R2 = C）。例外の行は今の形（`届かない: ` で始まる理由・90 日以内の期限）で足す
5. ブラウザの履歴を読む PC の収集アプリの SQLite（rusqlite 0.32・libsqlite3-sys 0.30）は今のまま

## 完了の判定

1. `tools/check-vulns.sh` と `tools/check-vulns.sh nightly <置き場>` が rc=0 で（nightly は材料を書かない）、`RUSTSEC-2026-0486`・`RUSTSEC-2026-0459`・`RUSTSEC-2026-0543` を出さない（tasks 1.2・1.3）
2. `Cargo.lock` で動いた `(name, version)` の組は rustix（1.1.5 → 1.1.6 以上）だけ。例外の表の既にある行は中身ごと残り、足した行は `RUSTSEC-2026-0459` と `RUSTSEC-2026-0543`（と別名で出た libsqlite3-sys の ID）だけで、`届かない: ` の理由と 90 日以内の期限を持つ。足した行は PR 本文の「例外の表で足した・変えた行」に載る（tasks 1.1〜1.3）
3. `tools/release/pgsql.lock` が 17.12-1 を指し、`tools/release/pgsql.sh fetch` が sha256 を照合して通り、`slim` が lock の実行ファイルと DLL を全部写せて、lock の DLL の一覧が 17.12-1 の zip の実行ファイルから辿れる DLL と一致し、大きい版・実行ファイル・許諾の置き場が変わらず、`tools/check-pg-minor.sh` と `tools/check-pg-major.sh` が rc=0（tasks 2.1・2.2）
4. 17.6 → 17.12 → 17.6 の置き場の入れ替えで中身が同じで、17.12 の退避を 17.6 が戻せる（`check-ch26.sh minor-swap` rc=0。tasks 3.1）。`cargo test --workspace` と clippy が rc=0（tasks 5.2）
5. 触ったファイルが予定のパス（`Cargo.lock`・`osv-scanner.toml`・`tools/release/pgsql.lock`・`tools/release/pgsql-prev-lock.sh`・`.github/workflows/ci.yml`・`docs/release.md`・`docs/changes/CH26.md`・この change の中）だけ（tasks 5.4）
6. `tools/release/pgsql-prev-lock.sh --self-test` と `check-workflow` が rc=0 で、`chain` の job がその 2 つを走らせ、`docs/release.md` の「PostgreSQL の小さい版を上げる PR」の節が CI の通し方を書く（tasks 4.1〜4.3）。例外の 2 行（D2（仮）・D3（仮））と CI の決め方（D7（仮）〜D9（仮））と、CI が更新の後に動いている PostgreSQL の版を見ないこと（D10（仮））は、確認バッチの仮の決定の一覧で本人が見る（本人の PC で更新を確かめる問いは置かない。本人の決定 R2 = C）
7. #334〜#337 は、merge の後に夜間の検査（`vulns-nightly.yml`）が緑で走ったのを本人が見て閉じる（夜間の検査は勧告が消えても issue を閉じない。`tools/check-vulns-issues.py`）。確認バッチの問い: 「merge の後の夜間の検査が緑で、#334〜#337 を閉じたか」
8. この change の PR の CI が緑（Windows の runner でしか走らないので、Task の手元の検証ではなく PR の CI が見る。merge gate は CI の緑を要る）。lock を変えた PR では、古い側の zip が 17.6-1・新しい側が 17.12-1 でなければ `package-windows` が落ちる（design D7・D8）ので、緑は `install-windows` の `tools/release/update-apply-install.sh` の Scenario 群がその 2 つの zip の更新と戻しで通ったことを含む

## 依頼（逐語）

> 夜間の脆弱性検査（vulns-nightly）が 11-19 から毎晩赤で、見つけた 4 件の issue に誰も手を付けていない。4 件を片付ける。要件は変えない。

> ## 何を
> - #334 chrono 0.4.45（RUSTSEC-2026-0543）
> - #335 libsqlite3-sys 0.30.1（RUSTSEC-2026-0459、重大度 6.8）
> - #336 rustix 1.1.5（RUSTSEC-2026-0486）

> ## なぜ
> 夜間の検査が毎晩赤のままだと、新しい脆弱性が出ても赤に埋もれて気づけない。配る物に既知の脆弱性を残さない。
>
> ## どこまで
> - 依存は互換の範囲で上げる。上げられないものは AGENTS.md の「依存の脆弱性」の規則どおり、例外の表に `届かない: <理由>` か `上げる予定: <見込み>` と 90 日以内の期限で書き、PR 本文に一覧を載せる。勧告が実際に当たる使い方かも確かめて理由に書く
> - PostgreSQL は同梱の minor を 17.12 に上げる（配る zip・インストーラ・確かめの台本が持つ版と検査値をそろえる）。major は変えない。既に入っている PC で minor の更新が既存の DB をそのまま使えることを確かめる
> - 終わったら tools/check-vulns.sh nightly と tools/check-pg-minor.sh が通り、#334〜#337 を閉じる
> - 走っている CH24（zip の部品を上げる）と触る所が重なるなら、衝突しないように合わせる
