# CH04 — 試験用 DB に溜まるデータで試験が遅くなるのを止める

## 価値

試験が入れたデータで後の試験が遅くなり、並走する Story と change の 1 段が数時間かかることを止める。試験は回ごとの database に書き、書き出しの試験は試験ごとの database で走り、
前の回の分は次の回の始まりに database ごと消える（消せない表のトリガには触らない）。詰まった問い合わせは数十分待たずに落ち、残りが積もらないことを台本と CI が確かめる。
製品の書き出しの除く範囲の判定も、使った年数の 2 乗で遅くならないようにする（CH02 の後に残った、候補の行 × 消した時間の入れ子を取る。直したかは読んだ行の数で確かめる）。

（第 1 回の深掘りの答え（2026-10-24。Q1〜Q4 とも推奨のまま）のとおり）

以下は依頼の内訳（逐語の正本は「依頼（逐語）」）。

server の試験（cargo test -p ashiato-server）が、試験で入れたデータを試験用 DB に残し続ける。そのせいで試験が回を追うごとに遅くなり、並走する Story / change の 1 段が数時間かかっている（2026-10-24 実測）。

実測（2026-10-24 10:30 頃）:
- 各 worktree の試験用 DB（`ashiato2-<id>-db-1`。port は worktree ごとに分かれていて、取り合いは無い）の `event` の行数: st23 16.6 万・st29 16.7 万・st41 18.3 万・ch03 14.2 万・verify 4.3 万。立てたばかりの st33 は 217。
- 書き出しの問い合わせ（`crates/server/src/export/excluded.rs` の `WITH erased_spans AS MATERIALIZED (...)`）が 1 本 8 分走っていた（st23 の DB の `pg_stat_activity`）。同じ形の問い合わせが 1 つの DB で 17 本同時に走り、postgres のプロセスが 1 本あたり CPU 50〜100% を食っていた。機械の負荷は 16 コアに対して 36。
- その結果、ST29 の Task 7 の implement が 3.3 時間、ST41 の Task 6 の fixer が 2.9 時間かかった。agent は `export_` の試験の 1 本が数分かかる（`has been running for over 60 seconds`）のを待ち続けた。しびれを切らした ST23 の agent が範囲を絞らない pkill を打ち、他の Story の agent を殺した（pkill の方は harness2 側で別に止める）。

依頼:
1. 試験が入れたデータで、後の試験（同じ回の他の試験も、次の回も）が遅くならないようにする。手段（試験ごとに DB / schema を分ける、試験の終わりに消す、問い合わせの範囲を試験のデータに絞る、索引を足す など）は深掘りで決める。
   ただし、DB の書き換え禁止のトリガ（消せない記録）を試験のために外す・緩めることはしない。消せない表のデータの後始末が要るなら、どう扱うかを深掘りで問う。
2. `export/excluded.rs` の問い合わせが、データ量に対して素直な速さか確かめる。行数に対して二乗で遅くなるなら、製品でも同じ形で遅くなる。その場合は製品のコードの不具合として直す（試験の都合だけでは片付けない）。
3. 再発を機械で止める: 試験を一通り走らせた前後で試験用 DB の行数が増え続けないこと、または server の試験の全体が決めた時間内に終わることを、検証のコマンドか CI で確かめる。

触らない: 試験が確かめている振る舞いそのもの（期待値・Scenario の印）。本物の PostgreSQL で試す方針（`testdb.rs` の「偽物に差し替えない」）。worktree ごとの port の割り当て。

## 壊してはいけないもの

（第 1 回の深掘りの答え（2026-10-24。Q1〜Q4 とも推奨のまま）で決まった）

- 試験の期待値（assert）・`// Scenario:` の印・試験の名前・試験の本数（減らさない。tasks 10.2 が機械で見る）
- 本物の PostgreSQL で試すこと（`testdb.rs` の「偽物に差し替えない」）と、worktree ごとの port の割り当て（`tools/ports.sh`）
- 消せない表の書き換え禁止のトリガ（外さない・無効にしない・`session_replication_role` を変えない。回の database でも断ることを tasks 1.2 が見る）
- 書き出しが除く記録と前の版（1 件も変えない。CH02 の後の式を試験に残して突き合わせる。tasks 8.2）。除く範囲を利用者で絞らないこと（ST33 Q7）。件数の数え方（ST33 D13）
- `tests/server_startup.rs`・縦串（`tools/smoke.sh`）・開発用の起動（`tools/dev.sh`）が `ashiato` database を使うこと
- `testdb::pool()`・`app_pool()`・`url()` の形（走っている st09・st13 が `testdb.rs` に足した関数が rebase の後も通る）
- 各 worktree の `ashiato` に積もった今のデータと、使われていない Docker の volume（この change では消さない。Q4）

## 完了の判定

（第 1 回の深掘りの答え（2026-10-24。Q1〜Q4 とも推奨のまま）で決まった）

- 同じ worktree で server の試験の全体を 2 回続けて走らせ、どちらも通り、前の回の database が残らず、残るのは最後の回のテンプレートと回の database だけ
  （`tools/check-test-db-growth.sh -p ashiato-server` が rc=0。tasks 7.2）。2 回目の全体の時間が 1 回目と同じ桁（design の「計測の記録」）
- 試験の足場の繋ぎ先が回の database で、`ashiato` に試験の記録が入らない・書き出しの試験が他の試験の消した滞在を判定しない・試験ごとの database が通っても panic しても消える・
  持ち主のいない回の database が次の回で消え、走っている回のものは接続が 0 本でも消えない、の試験が緑（tasks 1.2・2.2・3.2・5.2）
- 1 本の問い合わせが上限（既定 60 秒）を超えると試験が落ちる試験が緑（tasks 4.2）。書き出しの試験のファイルが回の database を取ると `--lint` が落とす（tasks 6.2）
- `tools/check-test-db-growth.sh --self-test` と `--lint` が rc=0 で、CI の rust job がこの台本を走らせる（tasks 6.2・7.3）
- 書き出しの除く範囲の判定: 直した式が直す前の式と同じ記録と前の版を除き、記録と消した滞在を一緒に 4 倍にして消した時間を読む量が直した式で 8 倍未満・直す前の式で 8 倍以上（tasks 8.2・8.3）。
  (30 万, 25)・(60 万, 50)・(120 万, 100) の書き出しと件数の数えの時間が、直す前と後の両方で design の「計測の記録」にある（tasks 9.2。時間は合否にしない —— 今の量では入れ子が線形の部分に埋もれる）
- 画面・操作・API・移行は変わらない（確認バッチで本人が触って確かめるものは無い）。製品で変わるのは書き出しの除く範囲の判定の速さだけで、書き出しの中身は変わらない

archive の判定: 上の検査が揃い、試験の期待値・`Scenario:` の印・試験の本数が `origin/main` から減っておらず（tasks 10.2）、`tests/server_startup.rs`・`tools/smoke.sh`・`tools/dev.sh` に差分が無く（tasks 10.3）、`openspec validate ch04-test-db-growth --strict` と `python3 scripts/check_scenarios.py . ch04-test-db-growth` が rc=0。
