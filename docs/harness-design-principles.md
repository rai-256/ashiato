# AI 開発ハーネスの設計原則

この文書は、このリポジトリの AI 開発ハーネスを追加・変更・削除するときの最上位の判断基準である。
個別の工程、関門、コマンド、Skill の仕様は定めない。それらの現在の運用は
[`flow-gates.md`](flow-gates.md)、OpenSpec、LangGraph のグラフと各実装を正典とする。

## 目的

人間が目的、方針、優先順位、要求、制約、リスク許容度、重要な設計判断、UX / Product 判断に集中できるようにする。
日常的な実装、検証、レビュー、修正、再試行、証跡収集、コマンド実行、状態遷移は、可能な限り AI と機械的な制御に委ねる。

ハーネスは、LangGraph を基盤に AI によるソフトウェア開発を自律的かつ安全に進めるための、薄いオーケストレーション層である。ハーネス自体を高機能な独自開発プラットフォームにすることは目的ではない。

> LangGraph と信頼できる既存資産を最大限に利用し、独自実装と LLM による状態管理を最小化する。人間は目的・方針・重要判断に集中し、日常的な実装・検証・反復は AI と機械的な制御に任せる。ハーネスは薄く、理解可能で、壊れたときに安全に止まるオーケストレーション層であり続ける。

## 原則

### 1. LangGraph をオーケストレーションの基盤にする

workflow、状態遷移、分岐、retry、stop、executor 間の接続は、原則として LangGraph 上で表現する。LangGraph と重複する独自 workflow engine は作らない。shell、Python、CLI は、原則として LangGraph から呼ぶ薄い実行部品に留める。

### 2. 単純さを既定にする

同じ目的を満たすなら、より単純な設計を選ぶ。新しい state、abstraction、configuration、adapter、exception、metadata、gate、agent、document を増やす前に、既存の仕組みを修正するだけで足りないかを確かめる。特殊ケースのために正常系を複雑化しない。

### 3. 自作は最後、再利用は最初にする

新しい機能が必要になったら、まず信頼できる既存資産を調べる。採用の優先順位は次のとおりとする。

1. Claude Code / Codex などの標準機能
2. LangGraph / LangChain の標準機能
3. 公式 Skill / MCP / Plugin
4. 信頼でき、保守され、利用実績のある OSS
5. GitHub Actions、lint、test、review tool などの既存エコシステム
6. このプロジェクトに既にある機能
7. 独自実装

既存手段で要求を十分に満たせるなら、それを採用する。独自 Skill、agent、workflow、protocol は、既存手段では要求を満たせないことを確認してから作る。外部資産は少なくとも、出所の信頼性、継続した保守、実装または挙動を確認できること、一定の利用実績、このハーネスとの責務の適合を確認して採用する。

### 4. 人間を最も有用な上位の仕事に置く

人間に聞く価値の低い質問をなくす。人間は Why / What、Product Vision、目的、方針、優先順位、要求、制約、リスク許容度、大きなアーキテクチャ判断、UX / Product 判断、AI だけでは解消できない本質的な曖昧さを扱う。

「人間への質問をゼロにする」ことは目標にしない。実装、lint、test、通常のレビュー、修正、retry、command execution、evidence 収集、state transition、定型的な技術判断は、可能な限り AI と機械的制御に任せる。

### 5. 機械で決められることを LLM に決めさせない

exit code、test 結果、Git 状態、file の存在、current Story / Task、state transition、timeout、retry 条件など、決定的に判定できるものはプログラム側で判定する。LLM に「実質 PASS とみなしてよいか」のような裁定をさせない。

LLM は、要件解釈、設計、実装、原因分析、semantic review、trade-off 判断など、意味理解が必要な仕事に使う。

### 6. LLM を workflow engine にしない

controller に、現在地、次の行動、Task の完了、retry、次の node を、長い文脈から毎回推論させない。これらは LangGraph とハーネスの責務である。LLM には、できるだけ局所的で明確な Task を渡す。

### 7. happy path を短く保つ

通常の Task は、概念的に次の経路で完結することを目指す。

```
Task → fresh executor → implement → verify → review → PASS → next
```

例外のために基本経路を複雑にしない。

### 8. fail closed にする

必須の検証が成功していなければ、完了扱いにしない。

```
verification success → complete
otherwise            → incomplete / stop / retry
```

古い証跡、推測、LLM の裁量だけで失敗を PASS に変換しない。

### 9. scope を明確に区別する

少なくとも Task、Story、Integration / Repository の scope を区別する。Story の実行中に、まだ統合されていない別 Story の責任を持たせない。一方、最終 integration では repository 全体の整合性を確認する。必要性が実証されていない gate や scope は増やさない。

### 10. executor 固有事情を上位へ漏らさない

Codex / Claude などの executor 固有事情は adapter など適切な境界に閉じ込める。上位の LangGraph からは、`execute`、`verify`、`review` のような共通操作として見える形を保つ。sandbox、CLI option、特定 device などの事情を上位 flow へ拡散させない。

### 11. 例外を足す前に境界を疑う

問題が起きたとき、「このケースだけ特別扱いする」仕組みを足す前に、input、command、責務境界、既存抽象化が誤っていないかを確かめる。

### 12. 抽象化より再利用を先にする

一度だけ起きた問題をすぐ一般化しない。小さく直接解決し、同じ構造が複数箇所で繰り返されてから共通化を検討する。不要な先行抽象化を避ける。

### 13. 複雑性の予算を持つ

新しい仕組みを採用する前に、増える state、config、exception、独自 code、LLM が読む context、人間が理解すべき概念、debugging surface を見積もる。追加の価値より複雑性が大きければ採用しない。可能なら、何かを追加するときに既存の何かを削れないかも検討する。

### 14. ハーネス自身を目的にしない

目的はハーネスを作ることではなく、良いソフトウェアを AI で効率よく作ることである。プロダクト開発よりハーネスの維持・開発に多くの労力が必要になる状態を避ける。「ハーネス改善のためのハーネス改善」が増えたら、設計を再評価する。

## 非目標

このハーネスは、次を目指さない。

- 独自 AI 開発プラットフォームを作ること
- LangGraph を置き換えること
- 既存 Skill や既存ツールを理由なく再実装すること
- あらゆる失敗ケースを事前にモデル化すること
- 人間を完全に排除すること
- LLM にすべての状態管理を任せること
- すべての技術判断をルール化すること
- 完璧な自律性のために過剰な複雑性を許容すること

## この文書の使い方

ハーネスの変更を検討するときは、まずこの原則に照らして「既存資産の利用で足りるか」「状態・例外・人間の判断を増やさずに済むか」「LangGraph と実行部品の責務境界が保たれるか」「検証失敗時に安全に止まるか」を確認する。

この文書は設計上の判断基準であり、現行実装がすべての原則を満たすと宣言するものではない。既存実装との適合性の棚卸しや変更は、別の作業として扱う。
