## 1. プロジェクト概要

### 1.1 背景 — 何がしたいのか

本人の言葉を逐語で置く。

- 目的は「**全記録を AI に読ませ、自分についてメタ分析し、理解を深め、行動し、幸せになること**」
- 原体験は「**自分が何が好きか**を分析しようとしたが、自分の記憶や分析能力だけでは限られ、時間もかかった」
- 分析の先に欲しいものは「**自己理解として納得したいが一番**。済んでいれば今後の意思決定がスムーズになる」
- 忘れて困るものは「**過去の出来事＋そのとき自分がどう感じたか**」および「**断片的な事実**」の両方
- 1 年後の姿は「データをもとに自己認識を深め、分析して意思決定ができる」。意思決定の具体例は
  **旅行・買い物・遊び**（転職などの大きな判断は 1 年後の目標ではない）
- 自作を選んだ決め手は「求めるものが無い」もあるが「**どちらかというと作ること自体が楽しい**」

**成功の定義**（本人の言葉そのまま。判定方法は NFR-13 / NFR-14）:

1. **1 年間データが途切れずに収集され続けている**
2. **AI に質問して満足のいく答えが返ってくる（十分なコンテキストを渡せている）**

### 1.2 解決する問題

- 既存サービスへの不満は「**記録がめんどくさい**」「**AI に接続するのが手間**」
- 現状は「**Google マップ履歴のみを月 2 回程度**」。YouTube や画像は稀。
  他は散らばって管理しきれていない。まず「まとめるところ」から始めたい
- データ所有・可搬性を最優先にする理由は「**漏洩リスクだけ。過去に嫌な経験は無い**」

### 1.3 システム構成（記号の定義）

| 記号 | 何か | 動く場所 |
|---|---|---|
| D-01 | 正統データストア。全記録の単一の情報源 | 自宅 PC（PostgreSQL） |
| D-02 | メディア原本の格納庫 | 自宅 PC（ファイルシステム） |
| S-01 | バックエンド。API・取り込み・プラグイン基盤・バックアップ | 自宅 PC |
| C-01 | 収集アプリ（携帯端末） | Android |
| C-02 | 収集アプリ（PC） | Windows |
| C-03 | 取り込み器。書庫の解析とアカウント系の定期取得 | 自宅 PC（S-01 内） |
| V-01 | ビュー。稼働状況・タイムライン・主観入力・検索 | PC / 携帯端末 |
| A-01 | MCP サーバ。AI からの問い合わせ口 | 自宅 PC（S-01 内） |
| P-xx | プラグイン。データの入口と出口を足す | S-01 に登録 |

**衛星アプリ（旅行実績・ランキング・分析・地図）は本システムの範囲外**。本体の第一の消費者は
AI（A-01 経由）と衛星アプリである、というのが本人の位置づけ。

### 1.4 中核となる設計思想

1. **単一の正統データストア。** 全記録を D-01 に集約し、全アプリがそこを読み書きする
2. **ローカルファースト。** データは自宅 PC に置き、外部からは Tailscale 網内でのみ届く。
   BaaS を避ける理由は漏洩懸念（1.2 の逐語）
3. **収集は受動的・ゼロ負担。** ただし **Google 系のみ 2 か月に 1 回の手作業を例外として認める**
   （NFR-12。理由は §5 の外部世界の主張 EXT-A / EXT-B）
4. **記録し損ねたものは後から足せない。** 列（記録する枠）は day one で決める。値は後から入れ直せる
5. **本体と衛星アプリの分離。** 本体は収集・蓄積・最低限のビューまで

## 2. ターゲットユーザー

- **利用者は本人 1 名のみ。** 権限は分かれない（PERM-1）
- 個人開発。週 15 時間（NFR-11）
- プラグインの書き手は「**将来的に第三者も**」（本人の言葉）。第三者製プラグインは
  データを読む側になりうるため、権限の既定を最も厳しい側に置く（PERM-8 / FR-62〜FR-64）

## 3. 機能要件

### 3.1 コア機能（Must Have）

#### 収集 — 携帯端末（C-01）

- **FR-1**: WHEN C-01 が位置取得の契機（60 秒間隔）に達する THE SYSTEM SHALL
  緯度・経度・水平精度・端末時刻・端末識別子を含む記録を 1 件生成する。
- **FR-2**: WHEN C-01 がアプリ利用の取得契機（**30 分間隔**）に達する THE SYSTEM SHALL
  前回取得以降のアプリ利用イベントを取得して記録を生成する。
  ★ 2026-09-18 訂正（ST06 の深掘り Q6）。**未確認だった保持期間が一次情報で取れた** ——
  AOSP の `UsageStatsDatabase.prune()` は 生のイベント（`queryEvents` が読む日ごとの箱）を **10 日**、
  週ごとの集計を 4 週、月ごとを 6 か月、年ごとを **2 年** で捨てる。
  間隔は保持の側から自由になったので、**NFR-1 を「出来事の時刻から」と読んでも収まる 30 分**にした
  （1 時間だと送信の間隔 5 分を足して最大 65 分になり、NFR-1 の読み方次第で外れる）。
  従来の `[NEEDS CLARIFICATION]` はこの事実で解消した。
- **FR-84**: WHEN C-01 のアプリ利用の収集を始める THE SYSTEM SHALL
  取得元がその時点で保持している**過去の利用の集計**（粒度ごとの、アプリごとの合計利用時間）を
  取得して記録を生成する。
  ★ 2026-09-18 追加（ST06 の深掘り Q5）。**集計だけは導入前 2 年ぶんが取得元に残っており、
  取らなければ日が経つごとに消える** —— 生のイベントは 10 日しか残らないので、集計を
  イベントから作り直すことはできない（FR-2 の訂正で挙げた保持期間）。
  粗い（いつ・どの順で が無く、アプリごとの合計時間だけ）が、成功条件 2 と
  QS-7 / QS-10 が求める「過去の厚み」は他のどこにも無い。
  取得元は**アンインストール済みのアプリの過去を削る**ので、取れるのは
  その時点で端末に入っているアプリについてだけ。
- **FR-85**: IF アプリ利用の取得の窓の始まりが、取得元がその時点で保持している範囲より前にある THEN
  THE SYSTEM SHALL その期間を「取得元に残っていなかった」として記録する。
  ★ 2026-09-18 追加。ST06 の深掘り Q4 の決定。
  扉 #14 が求める「データが無い日の意味」は、携帯端末では生存信号（FR-78）と
  受け手側の検知（FR-80）の 2 つで担われるが、**どちらも「収集は生きていたか」しか見ない**。
  アプリ利用は取得元（OS）が 10 日で消すので、**収集が生きていて生存信号も届いているのに
  イベントだけが取れない**形が起きる —— そのとき受け手には「使っていなかった」（②）と
  区別がつかない。その事実は**取りに行った瞬間にしか分からず**、過ぎれば端末にも残らない。
  FR-82（PC が止まっていた期間を C-02 が残す）と同じ型の、第 3 の担い手にあたる。
- **FR-3**: WHEN 端末に新しい写真が保存される THE SYSTEM SHALL
  撮影日時・位置・機種・内容ハッシュを含む記録を 1 件生成する。
- **FR-4**: WHEN FR-3 の記録が生成される THE SYSTEM SHALL その写真の原本を D-02 へ転送する。
- **FR-5**: WHEN 端末に新しい動画が保存される THE SYSTEM SHALL
  撮影日時・位置・長さ・内容ハッシュを含む記録を 1 件生成する。
- **FR-6**: IF メディアが動画である THEN THE SYSTEM SHALL その原本を D-02 へ転送しない。
  根拠は NFR-6（動画を含めると年 50 GB を超え、NFR-9 のバックアップ設計が成立しない）。
- **FR-7**: WHEN C-01 が基準時刻との同期の契機（1 時間間隔）に達する THE SYSTEM SHALL
  端末時刻と基準時刻の差（ミリ秒）と測定時刻を含む測定記録を 1 件生成する。
- **FR-8**: WHILE C-01 に送れていない記録がある THE SYSTEM SHALL
  その記録を端末内に、**端末に積んでから 90 日**かつ 2 GB を上限として保持する。
  ★ 2026-09-14 訂正（「S-01 に到達できない間」→「送れていない記録」、「90 日分」→「端末に積んでから 90 日」）。
  ST04 の深掘り Q1 / Q4 の決定。**到達できても送れない未送信がある**（合言葉の不一致・サーバ側の失敗・
  登録簿に無いソース・設定が揃っていない。ST03 はこれらを「捨てずに再び送る」とした）ので、
  上限を到達できない間だけにかけると、断られ続ける未送信が端末の空きを食い尽くし、**その後の新しい記録が取れない**。
  上限は送れない理由を問わずにかける（送信の結果を理由に捨てないという FR-10 の決定とは独立に働く）。
  90 日を出来事の時刻から数えると、過去の写真をまとめて積んだ瞬間（ST09）に全部が上限を超えるので、積んでから数える。
  **端末の時計の前進が単調時計と食い違うとき（時計が飛んだとき）は、90 日の側では捨てない**（2 GB の側だけが端末を守る）。
- **FR-9**: IF 端末内の保持が 90 日または 2 GB を超える THEN THE SYSTEM SHALL
  最も古い記録から破棄し、破棄した期間と件数を稼働記録（FR-33）に残す。
  ★ 2026-09-14 追加。ST04 の深掘り（Q5 / C5 / C8 / C9 / C12）の決定。
  (1) 破棄の報告は**どの端末が・なぜ捨てたか**（上限 / 置き場に書けなかった / 置き場の行が壊れていた）を持ち、
  生存信号（FR-78）と同じく書き換えない。**上限を超えた以外の理由で端末から失われた記録も、同じ報告で残す** ——
  残さないと扉 #14 の「バッファから破棄されたのか」が、その経路だけ区別できない。
  (2) 件数は**捨てる時点で細かい時間ごとに数える**（取得は一様でないので、範囲と総件数からは日ごとの件数を割り戻せない）。
  (3) 上限の **7 日前に、端末で 1 回だけ知らせる**。常駐通知の文言には未送信の日数を出す ——
  途絶の通知（FR-35）は S-01 が出すので、自宅 PC が止まっている間は鳴らない。
- **FR-10**: WHEN C-01 が S-01 に到達できる THE SYSTEM SHALL 未送信の記録を送信する。
  **恒久的に断られた記録（400）は未送信から取り除いて捨て、捨てた事実を残す。**
  ★ 2026-09-11 追加。ST03 の深掘り Q4 / Q5 の決定。断られた記録を未送信に残すと
  5 分ごとに送られ続け、**200 件たまると新しい記録が送られなくなる**（実測）——
  1 件の恒久的な失敗が後続を永久に止める。
  **溜まった未送信は、溜まっているうちは続けて送る。**
  ★ 2026-09-14 補強。ST04 の深掘り Q6 の決定。一定の間隔で少しずつ送る形（ST01 の design D9）のままだと、
  90 日ぶんに約 55 時間かかり、その間に生まれる新しい記録が NFR-1 の 1 時間を超える。
  溜まっていないときの送り方は変えない。
- **FR-11**: WHEN C-01 が初回起動する THE SYSTEM SHALL 健康データの履歴読み取り権限を要求する。
  健康データの収集そのものは Should（FR-73）だが、**権限の宣言はこの時点で行う**
  —— 宣言していない期間の 30 日より前は永久に読めない（§5 の EXT-C）。

#### 収集 — PC（C-02）

- **FR-12**: WHEN アプリ名・ウィンドウ題名・URL のいずれかが変化する THE SYSTEM SHALL
  その時点の情報を含む記録を 1 件生成する。
  **URL はアドレスバーに見えている文字列をそのまま**（クエリもフラグメントも落とさずに）記録する。
  **アプリ名と URL の変化は必ず 1 件生成し、ウィンドウ題名だけの変化には最小の滞留時間を置く。**
  ★ 2026-09-12 訂正（URL の粒度と、題名だけの変化の間引きを追加）。ST07 の深掘り Q4 / Q6 の決定。
  URL を切り詰めると、落とした部分は**後から作れない** —— ブラウザ履歴（FR-13）は
  「いつ訪問したか」であって「その瞬間どれを前景に置いていたか」ではないので、埋め戻せない。
  題名だけの変化を間引くのは容量（NFR-5）のため。**題名が秒単位で変わり続けるアプリ**
  （動画プレイヤーの再生位置・端末の実行中コマンド・進捗表示）は**それ 1 本で 1 時間 3,600 件**で、
  2 時間の視聴だけで 1 日ぶんの枠を超える（実測の概算: 1 行 ≒ 891 B、ウィンドウに使える枠は
  **1 日 5,990〜15,200 件**、通常の切り替えは 1 日 1,500〜3,000 件）。
  **アプリと URL を間引かないのは、5 秒未満しか前景に無かったアプリを落とすと
  「使っていない」と読めてしまう**ため。滞留時間の値は、間引く対象を題名だけに限る限り可逆。
- **FR-13**: WHEN C-02 がブラウザ履歴の取得契機（24 時間間隔）に達する THE SYSTEM SHALL
  前回取得以降の履歴を取得して記録を生成する。
  **「前回取得以降」は訪問時刻で切らない** —— 前回の取得の後に履歴に入った訪問（同期で古い訪問時刻のまま入るものを含む）と、
  送った後で値が変わった訪問を指す。
  **対象は PC で見つかったブラウザの全プロファイル**とし、**訪問 1 件ごとに 1 件**を、
  **訪問ごとの識別子**を持たせて生成する。同じ訪問の題名や滞在時間が後から書き換わっていれば、
  **新しい行を作らず更新し、前の版を残す**（FR-22）。
  **一度取った訪問がブラウザの履歴から消えていたら、「消えた」事実を記録として残す**（消えた訪問の記録は消さない）。
  ★ 2026-09-15 訂正（対象の範囲・訪問ごとの識別子・消えた事実を追加）。ST08 の深掘り Q1 / Q2 / Q3 の決定。
  **Chrome 系は 90 日を過ぎた履歴を手元の DB から削除する**（EXT-E の注記）ので、取らなかったブラウザ・
  プロファイルの履歴は後から作れない。題名（`urls.title`）と滞在時間は履歴 DB の中で後から書き換わるので、
  原文の文字列で同一を判定すると読み直すたびに行が増える —— 見分け方は 1 行でも入った後に変えると
  既存の行と対応が切れる。訪問の番号は全期間の削除で振り直されるので、**番号だけを識別子にしない**。
  「消えた」事実は次の取得で比べた時にしか分からず、比べなかった期間の削除は後から特定できない。
  ブラウザで消した訪問を D-01 でも消したことにするか（FR-50）は、残した事実を材料に後から決める。
- **FR-81**: WHILE C-02 が動作している THE SYSTEM SHALL 入力が無い状態への出入り
  （離席・画面ロック・スリープと、そこからの復帰）を、その時刻とともに記録する。
  ★ 2026-09-12 追加。ST07 の深掘り Q7 の決定。
  FR-12 だけだと、ウィンドウの滞在時間は「次の変化までの差」でしか出せないので、
  **席を離れていた時間が「そのアプリを見ていた時間」に混ざる**。混ざったまま溜めると、
  「見ていた」のか「離席」なのかは**後から一切区別できない**。
  成功条件 2 の QS-7（いちばん時間を使ったアプリは何か）が直接これに乗る。
  何分で離席とみなすかの閾値は、出入りの時刻が残っていれば後から計算し直せる（可逆）。
- **FR-82**: WHEN C-02 が起動する THE SYSTEM SHALL 前回の停止から今回の起動までの期間を
  「PC が止まっていた」として記録する。
  ★ 2026-09-12 追加。ST07 の深掘り Q1 の決定。
  扉 #14 が求める「データが無い日の意味」は、携帯端末では生存信号（FR-78）と
  受け手側の検知（FR-80）の 2 つで担われるが、**PC ではその両方が電源とともに消える**。
  記録も生存信号も無い日は途絶（FR-80）になるので、**PC を開かなかった日が、
  本物の故障とまったく同じ形で 1 年の格子に並ぶ**（実測: 想定間隔 6 時間は近傍の判定で
  0.25 日になり、同じ日しか近傍にならない。`crates/server/src/coverage.rs`）。
  前回の停止時刻を知っているのは **C-02 自身が書き残した印だけ**で、
  残さなかった期間は後から作れない（Windows のイベントログは既定の大きさで巡回して消える）。
  この期間を「意図的な停止」（FR-34）に混ぜない —— 混ぜると後から見分けられなくなる。
- **FR-83**: WHERE 収集から除外する対象が登録されている THE SYSTEM SHALL
  その対象の本文（アプリ名・ウィンドウ題名・URL）を記録せず、**除外した事実と件数を残す**。
  ★ 2026-09-12 追加。ST07 の深掘り Q5 の決定。
  パスワード管理ソフトのウィンドウ題名には開いている項目の名前（サービス名・アカウント名）が載り、
  シークレットウィンドウは「残らないこと」を期待して開くもの。
  **除外した事実を残さないと、その時間帯の「記録が無い」が「PC を触っていなかった」のか
  「除外された」のかを永久に区別できない** —— 扉 #14 が作った区別を自分で壊す。
  除外リストは空で始めてよい（登録が 1 件も無ければ何も除外されない）。

#### 取り込み（C-03）

- **FR-14**: WHEN 取り込み待ち置き場にエクスポートの書庫が置かれる THE SYSTEM SHALL
  その内容を解析して記録を生成する。
  **書庫には、Takeout の書庫（zip）と、端末から書き出したマップのタイムライン（1 本の JSON）の両方を含む。**
  **読み終えた書庫のうち、読んだ製品のファイルは写しを残す**（既定。設定で残さない側にできる）。
  **置き場にある本人のファイルは消さない。**
  **Takeout の書庫の中身は、形の確認の印を置くまで格納しない**（書庫の台帳と写しには残し、印を置いたら写しから読み直す）。
  ★ 2026-09-15 追加（第 2 回）。ST12 の深掘り 第 2 回 Q10 の決定。書庫の中身を振り分ける論理ソースは格納した時点で書き換えられないので、
  振り分けの規則（マイアクティビティの製品の名前・中の YouTube の項目）が本物の書庫で外れていると、既に入った行は直せない。
  ★ 2026-09-15 追加。ST12 の深掘り Q1 / Q2 / Q3 の決定。マップのタイムラインはいまは Takeout に入らず、
  端末の設定から書き出す（§5 の EXT-M）ので、「書庫」を zip に限ると位置の履歴の経路が無くなる。
  Takeout の書庫は約 7 日で失効しダウンロードは 5 回まで（EXT-B）なので、**手元の書庫を消すと、
  記録にならなかった部分（読み飛ばした項目・解析器の不具合で落とした項目）は二度と取れない** ——

#### 成功の判定

- **NFR-13**: 成功条件 1 の判定 —— Must のソース（位置・アプリ利用・写真・ウィンドウ・
  ブラウザ履歴）を**主語で 2 つに仕分け**、それぞれの達成日を数える。
  **5 ソースすべてが、分母の 95 % 以上**であることを達成とする。
  - **端末が主語**（位置）: **記録が 1 件以上ある日**
  - **利用が主語**（アプリ利用・写真・ウィンドウ・ブラウザ履歴）:
    **取得できる状態の生存信号（FR-78）があった日**
  - ★ 2026-09-18 訂正（ST06 の深掘り Q2）。**アプリ利用を「端末が主語」から「利用が主語」へ移した。**
    位置は 60 秒のタイマーが本人の操作と無関係に記録を作るが、**アプリ利用はそうではない** ——
    携帯を触らなければイベントは生まれない。写真・ウィンドウ・ブラウザ履歴と同じ性質のものを
    位置と同じ列に入れていた。365 日の 95 % は 18 日しか落とせないので、
    携帯を置いて出た日・寝込んだ日がそのまま未達成として数えられていた。
  - **PC 上の C-02 が集めるソース（ウィンドウ・ブラウザ履歴）だけは、
    生存信号が 1 件でも届いた日を分母とし**、そのうち取得できる状態だった日を分子とする。
    **PC の電源が入っていなかった日は、分母にも分子にも入れない**（FR-82 が残す期間で判る）。
  - 数える期間は、**そのソースの収集開始日（FR-79）から 365 日**とする
    （5 ソースの窓はそれぞれ別の日に始まる）。365 日を待たない途中経過は
    「収集開始日から今日まで」を分母にして同じ式で出す。
  - **合否は 5 ソースすべての窓が閉じた日に確定する。** それまでは**暫定**として示す。
  - 収集開始日が遡れば（FR-79）**窓の起点も遡る**。
    **変えないのは判定式**（割合・主語の仕分け・窓の長さ）であって、入力ではない。
  - 日の区切りは **`Asia/Tokyo` に固定**する。
  - 分母から除くのは、FR-34 で記録された意図的な停止のうち **1 日を丸ごと覆うもの**だけ。

    （1 ソースでも落ちれば未達。どのソースが落ちたかが残る）。
  - 分母は**ソースごとに違う**（収集開始日が違うため。FR-79）。
    365 日フルに動いたソースの線は 347 日（= 365 × 0.95）にあたり、
    **「350 日」は 365 日フル稼働時のおおよその目安**として読む。
  ★ 2026-09-10 訂正（1 回目。従来は「日単位で記録が 1 件以上ある日を数え」を全 Must ソースに
  一律で当て、「意図的な停止期間は分母から除く」とだけ書いていた）。ST02 の深掘り Q2 / Q3 / Q4。
  一律に当てると**写真が正常動作時から未達で固定される** —— 写真は FR-3（新しい写真が保存された
  ときに 1 件）であって、毎日届くはずのものではないので、撮らなかった日が未達に積み上がる。
  **旧プロジェクトが同じ問題を実測で踏んでいる**（旧 ashiato の `requirements.md:765`、2026-09-01 の追記で
  Takeout 経路と週次取得のアカウント系を対象外にしている）。

  分母がぶれる**ため。停止を「1 日を丸ごと覆うもの」に限るのは、時刻範囲の停止（FR-34）を
  部分的に除き始めると分母が日でなくなるため。
  ★ 2026-09-10 再訂正（2 回目。独立レビューが 1 回目の書き方に 3 つの穴を見つけた）。
  ST02 の深掘り 第 4 回 Q7 / Q8 / Q9 の決定。
  (1) **写真だけを切り出したのが狭すぎた** —— ウィンドウ（FR-12 = 変化したとき）と

  全画面に AAA を課さない理由は、1 画面に 20 件前後の行が並ぶ想定（§4 の件数）で
  全行に 44 px を課すと 1 画面に収まらなくなるため。**主表現が何になるかには依存しない。**
- **NFR-23**: **意味を担う非テキスト**（状態を表す面の色・明度など）は、
  隣り合うものとのコントラスト比を **3:1 以上**とする。
  出所: WCAG 2.2 SC 1.4.11 Non-text Contrast / Level AA（§5 の EXT-J）。
  ★ 2026-09-11 追加。ST02 の深掘り 第 5 回 Q21 の決定が**この基準を根拠に選ばれた**のに、
  要件の側に対応する行が無かった（独立レビュー 2 巡目の R10）。
  NFR-18（4.5:1）は**文字**に掛かる条項（SC 1.4.3）で、**面には掛からない** ——
  稼働状況の格子のセルは文字でも文字画像でもないので、NFR-18 では守れない。
  この要件が「格子が担える段数」を決める ——
  7 段を隣接 3:1 で並べると 3^6 = 729:1 が要るが、sRGB の理論最大は 21:1 で成り立たない。
  3 段なら 3:1 × 3:1 = 9:1 で収まる（FR-54 の補強を参照）。
- **NFR-22**: キーボードで操作できる画面は、フォーカスの位置が見える状態を持つ。
  出所: WCAG 2.2 SC 2.4.7 Focus Visible / Level AA（§5 の EXT-I）。
  2026-09-08 の `ui-review` が「要件に無い」と指摘して見つけた抜け。
  NFR-18（1.4.3）でも NFR-19（2.5.8）でも代替できない別条項である。
- **NFR-21**: 原色・派手な配色・角張った四角を用いない。
  出所: 本人の逐語「原色ギラギラなのとか、派手なのとか、ガチガチすぎるのとか
  （角張った四角とか）」（旧 ashiato の `discussions/20260724_ライフログソフトウェアの概要説明.md`）。
  **この要件は数値を持たない**（本人が数値で言っていないため）。運用上の具体値
  （彩度の上限・角の最小半径）は `docs/ui-direction.md` が方向として持つ。

### 商用化の方針（2026-09-08 決定）

- **本体（S-01 / C-01 / C-02 / V-01 / D-01）は AGPL-3.0 で公開する。**
  選んだ理由: 改造版を隠したまま配られるのを防げる唯一の OSS ライセンスで、かつ
  **このプロジェクトでは追加コストがゼロ**（プラグインが別プロセスなので、
  同一プロセスの派生物問題が起きない）。GPL-3.0 との差はネットワーク越しの利用に及ぶかどうかで、
  いま選ばないと後から足せない
- **他人からの貢献は CLA（許諾型）の下でのみ受け付ける。** 取らずに受け入れると、
  その時点でデュアルライセンス（自分だけ商用ライセンスを売る）の道が閉じる。**遡って取れない**
- **衛星アプリとプラグインは有料でよい。** 別プロセスで HTTP の API 越しにやり取りするため、
  本体の派生物にならない（FR-77 がこれを要件として固定する）
- **本体を公開する = 配布が発生する。** 依存ライブラリのライセンスが実際に効くようになるので、
  機械検査を CI に置く（`docs/production-prep.md` の C）
- **PostGIS は引き続き採らない。** 従来は「自宅運用では配布が発生しないので扉ではない」としていたが、
  **配布するなら配布は発生する**。判断は変わらないが理由が変わった（GPLv2+ と AGPL-3.0 の
  両立可否を検討するより、素の座標計算に留めるほうが安い）

  ★ 2026-09-08 変更: 従来ここには「商用化・第三者への配布は範囲外」と書いていたが、
