ashiato ライセンスの地図

本体・衛星アプリ・友人との共同開発で、誰のコードがどの条件で配られるかを並べ、決めることを順番に置いたページです。2026-10-09 時点のリポジトリの事実をもとにしています。

法律の助言ではありません。仕組みと選択肢の整理です。特に L3（V-02 の共同開発の取り決め）は、お金が動く前に専門家に一度見てもらう価値があります。

誰のコードが、どの条件か

本体 AGPL-3.0

  • S-01 サーバ・D-01 のスキーマ
  • 収集アプリ C-01 / C-02
  • 画面 V-01・MCP（A-01）
  • 貢献は CLA を通してだけ受け入れる
HTTP API ／ 別プロセス

衛星アプリ 自由に決められる

  • V-02 旅行（友人と共同）
  • 読書・家計簿・睡眠など
  • 有料・非公開でもよい
  • 本体の派生物にならないことが前提

境界に置くもの 未決

  • API の定義（OpenAPI の docs/openapi.json）・封筒の型・クライアントの SDK
  • 衛星の作り手が自分のコードに取り込むものなので、ここを AGPL にすると衛星まで AGPL になりうる

論点

L1

衛星が本体の派生物にならない条件

ほぼ決着

AGPL の義務が及ぶのは、本体と「1 つのプログラム」とみなされるものです。別プロセスでネットワーク越しに話すだけなら、ふつうは別のプログラムとして扱われます。FR-77 がこれを要件として固定しています。

崩れる場合
本体の内部のデータ構造をそのままやり取りするほど密につながると、1 つのプログラムとみなされる余地が出ます（FSF の FAQ の立場）。DB を直接読む衛星もこの方向です。
守り方
衛星には公開した汎用の API だけを使わせる。画面用の内部 API（/stays/* など）を衛星の契約にしない。監査の「汎用の読み出し API」「API の版管理」と同じ作業で守れます。
L2

SDK・API 定義・型をどの条件で出すか

未決

衛星の作り手は、API の定義から型を生成したり、SDK をアプリに組み込んだりします。これが AGPL だと、組み込んだ衛星も AGPL で公開する義務を負う可能性があります。有料の衛星という方針と衝突します。

選択肢
(a) Apache-2.0（特許の許諾が付く）
(b) MIT（最も短い）
(c) AGPL のまま（衛星も公開を強いる）
推奨
(a) Apache-2.0。docs/openapi.json と、将来の SDK のフォルダにだけ別の LICENSE を置く。本体のコードは AGPL のまま。自分が全部の著作権を持っているいまなら、ファイル 1 枚で済みます。
急ぎ度
友人が V-02 で API を使い始める前。後から緩めることはできますが、それまで友人は条件が分からないまま作ることになります。
L3

V-02 の著作権（友人との共同開発）

最優先

2 人で一緒に書いたコードは、日本の著作権法では共同著作物になりえます（2 条 1 項 12 号）。共同著作物の権利は、全員の合意がないと使えません（65 条）。有料で売る、ライセンスを変える、片方が抜けた後も続ける、のどれにも相手の同意が要ります。著作者人格権は譲れない（59 条）ので、「行使しない」という合意で扱います。

起きやすいこと
取り決めないまま書き始め、後で「売りたい／売りたくない」「抜けたい」で止まる。書いた後に合意を取るのは、書く前よりずっと難しくなります。
選択肢
(a) 共有のまま、収益配分・意思決定・離脱時の扱いを書面で決める
(b) 片方に権利を集め（譲渡か独占的な許諾）、もう片方には収益配分で報いる
(c) V-02 をオープンソースにする（売るなら別の価値で売る）
推奨
友人がコードを書く前に、(a) か (b) を短い書面にする。最低限決めるのは「誰が権利を持つか・収益の分け方・抜けたらどうするか・人格権を行使しないこと」の 4 つ。
失われるもの
合意なしで書き進めた分は、後から一方的には使えなくなる可能性があります。
L4

友人が本体に手を入れるとき

仕組みはある

友人が V-02 のために本体（S-01 など）を直して PR を出すことは起こりえます。docs/CLA.md があるので、PR 本文の 1 行で同意を取れます。

注意
DCO（「自分が書いた」と署名するだけの方式）では足りません。DCO は AGPL で出す権利しか確認しないので、デュアルライセンスの道が閉じます。CLA の 1 行を毎回確かめることです。
推奨
友人の最初の PR の前に CONTRIBUTING.md を一緒に読む。機械で止めたいなら、CI で PR 本文の同意の行を検査する（いまは無い）。
L5

友人が自分の本体を動かすとき

義務は小さい

友人は「別の D-01 を持つ別の利用者」という想定です。公開されている本体をそのまま動かすだけなら、友人に特別な義務はありません。

義務が出る場合
友人が本体を改造して、他人にネットワーク越しに使わせる場合だけ、その相手に改造後のソースを出す義務が生じます（AGPL 13 条）。自分 1 人で使うなら実質的に関係ありません。
L6

商用ライセンスを売る道を残すには

穴が 2 つ

本体を AGPL 以外の条件で売る（デュアルライセンス）には、本体のすべての部分について自分が別条件で許諾できなければなりません。CLA はそのための仕組みですが、依存ライブラリにも同じことが言えます。

穴 1
check-licenses.sh は「AGPL で配れるか」を見ています。許可一覧に AGPL-3.0-only が入っているので、AGPL の依存が入っても通ります。AGPL では配れても、その依存がある限り商用ライセンスでは売れません。いま該当する依存があるかは確かめていません。
穴 2
Android の依存は検査の対象外です。play-services-location（プロプライエタリ）を AGPL のアプリに入れて配れるかが未決のままです。リポジトリは既に公開されています。
推奨
検査を 2 段にする。「AGPL で配れるか」に加えて、「商用ライセンスでも配れるか」（コピーレフトの依存を警告）を見る。Android は公開版の配布の前に D15 を決める。
L7

データはライセンスの外にある

方針は決まった

ライセンスが決めるのはコードの扱いです。衛星が読む記録（位置や家計簿の中身）は、利用者が衛星に何を許したかで決まります。これはスマホの権限のような承認の仕組みで扱う、と 2026-10-09 に決めました（許可された情報は持ち出してよい）。

残ること
V-02 が友人どうしで旅程を共有するために共有のサーバを持つなら、その運営者（あなたか友人）は他人の位置を預かる立場になります。そのときはライセンスではなく、プライバシーポリシーと利用規約が要ります。

決める順番

  1. L3 V-02 の取り決め：友人がコードを書く前。4 項目（権利の持ち主・収益配分・離脱時・人格権）。取り返せない
  2. L2 SDK と API 定義のライセンス：友人が API を使い始める前。推奨は Apache-2.0 で、ファイル 1 枚。
  3. L4 友人の PR の扱い：最初の PR の前。CLA の 1 行を確かめる。
  4. L6 依存の検査を 2 段に：商用ライセンスを売る前ならいつでもよいが、依存は増えるほど洗い直しが重くなります。
  5. L6 Android の D15：公開版の配布の前。

このうち要件に書くのは L2（境界に置くもののライセンス）と L3 の存在だけです。取り決めの中身は友人との間の話なので、リポジトリには置きません。

用語

AGPL-3.0
改造して配るときと、改造してネットワーク越しに使わせるときに、ソースの公開を求めるライセンス。
派生物
本体を元に作られ、本体と一体とみなされるもの。AGPL の義務が及ぶ。
許諾型
MIT や Apache-2.0。表示さえすれば、非公開・有料の製品に組み込んでよい。
デュアルライセンス
同じコードを、公開版は AGPL、ソースを出せない相手には有料の別条件、の 2 通りで出すこと。
CLA
貢献者がプロジェクトに広い許諾を与える同意書。ashiato のものは著作権を譲らない許諾型。
DCO
「自分が書いたものをプロジェクトのライセンスで出す」と署名するだけの方式。別条件での許諾は含まない。
共同著作物
2 人以上で作り、各人の寄与を分けて使えない著作物。権利は全員の合意で使う。
