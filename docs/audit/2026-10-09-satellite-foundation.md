# 監査: 「ashiato は衛星アプリの基盤が主」という前提と、いまの要件・Story・実装のズレ（2026-10-09）

`/requirements` の改訂の入力。本人の前提（2026-10-08）:

- ashiato は**衛星アプリを作るための基盤が主**。AI が問うのも衛星の 1 つ（MCP か直接か未決）
- 衛星は用途特化の小さなアプリ。core.* を変えず、S-01 の HTTP API 越しにつながる。交換可能
- 最初の衛星 V-02 旅行アプリは友人（外部協力者）と作る。書き込みは位置・場所ドメインのみ
- 拡張性の合否: 読書ログ・家計簿・睡眠デバイスを机上で想定し、core.* の変更ゼロ

出所: 3 本の独立した読み取り（ST21 / requirements.md 全文 / Story 36 本と実装済みの契約）。旧 ashiato は `~/dev/ashiato/docs/requirements.md` と比較した。

## 2. 要件の矛盾（書き換えが要る）

- **§1.1 目的・成功の定義**: AI が目的、成功は 2 条件。基盤が主・AI は衛星の 1 つ、に書き換える（本人の逐語なので本人が書く）。拡張性の合否（3 種の机上テスト）を成功条件 3 にする案
- **§1.3 / §1.4-5**: 「衛星は範囲外」「本体は収集・蓄積・最低限のビューまで」→ 衛星向けの契約を本体の責務に
- **§1.3 A-01「S-01 内」/ FR-59「本体に同梱」**: AI を衛星とするなら FR-77 とずれる。(a) 本体内の特権経路 (b) 公開 API 越しの衛星 (c) DB 直読み（旧が撤回した直 SQL と同じ問題）
- **§範囲外**: 衛星の行と「V-02 は記載しない」の 2 行
- **扉ではないもの「C-02 と S-01 の信頼境界は本システムが決めない」**: 外部が作る衛星には成り立たない
- **PERM-1「権限は分かれない」**: 「人は 1 名、アプリごとに権限が分かれる」へ
- **FR-62〜65 / PERM-8 / FR-77**: 「プラグイン」と「衛星」を統合するか

## 4. 机上テスト（core.* を変えずに入るか）

**行は 4 種とも入る**（登録簿に 1 行 = DML、`raw` に原文、`payload` に構造）。重複排除（`external_id_kind`）と版の履歴（`core.event_version`）もそのまま使える。弱いところ:

| ドメイン | 弱いところ |
|---|---|
| 読書ログ | 「本」の台帳が無い。感想の感度を送り手が指定できない |
| 家計簿 | 通貨の欄が無い（payload で持つ）。集計は jsonb 全走査。カテゴリの台帳が無い。金銭の感度の既定 |
| 睡眠デバイス | **区間の終わりの列が無い**（滞在も `payload.end`）。日の境界が `Asia/Tokyo` 固定（`coverage.rs:14`）。Health Connect（ST34）と重複 |
| V-02 旅行 | 旅程という「器」の置き場が無い。書き込みを位置・場所に限れない。海外で日の境界がずれる |

**合否の分かれ目**: 「器」（本・旅程・カテゴリ・人物・場所）。ST19（属性の種類）と ST21（`core.place`）が**ドメインごとに専用の表を足す前例**を作っており、ST20（人物）も同じ型で予定されている。このままでは衛星が増えるたびに core.* が増える。汎用の「実体の台帳」（種類＋識別子＋名前の追記台帳）を 1 つ持てるかどうか。

### 追加の答え（2026-10-09 第 2 回）

- **V-02 は今決めない。** 作るときに別途考える。ashiato は個人での開発予定（ライセンスの L3・L5 は保留）
- 問い 4 **V-02 の記載**: 衛星の**例として置く程度**でよい。権限の仕組みを入れ、承認されればどんなドメインでも触ってよい（→ 問い 6 は「ドメインを固定しない。承認で決まる」に解消）
- 問い 7 **器**: 推奨を採る（衛星が持ち込むモノは汎用の台帳、本体自身が扱う場所・人物は専用の表も可）。デメリットを確認したい
- 問い 8 **衛星専用データ**: 基本は衛星が持つ。ただし**衛星が送ってきたら D-01 に取っておく**（積読の順番なども価値があるかもしれない）
- AI の既定（C）: 衛星が書き換えられるのは**自分が書いた行だけ**。本人や他の衛星の行を変えるのは別の権限。場所の座標の変更は「直す / 移った（いつから）」を契約で必須にする（U5）

### 追加の答え（2026-10-11 第 3 回）感度と承認

- **承認が主、感度は記録ごとの「出さない」だけに縮める**（C 案）。扉 #15（PERM-2〜9）の前提を変える
  - 承認: 衛星ごとに「種類 × 読む / 書く」。既定は何も許可しない。承認画面で持ち出しの有無も見せる
  - AI も衛星: 「ローカル AI」「外部 AI」を最初から入っている 2 つの衛星にし、PERM-3〜6 の既定をその初期の許可へ移す
  - 記録ごとの除外: 既存の `sensitivity` 列で「どこにも出さない」の印。どの承認より優先
  - 種類をまたぐデータの例外は当面「写真の位置」1 つ（PERM-6）

### 追加の答え（2026-10-11 第 4 回）残りの論点

- **承認を取り消したとき**: 承認画面に「取り消しても戻らない」と明記するだけ（→ PERM-12）
- **誰が何を読んだかの記録**: 「いるか怪しいですが、一旦入れておきますか」（→ PERM-13・扉 #27）
- **外部 AI とローカル AI の見分け**: 「出来る範囲で良いです」。資格情報の発行時に用途を選ばせて名前に出す（→ PERM-14）
- それ以外は推奨を採る: 種類の一覧（FR-88）・衛星の更新は増えた分だけ承認し直す（FR-62）・API の版（FR-89）・
  自宅 PC が止まっている間は衛星が溜める（§5）・本人の削除は持ち出された写しに及ばない（PERM-12）
