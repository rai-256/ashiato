# ST61 — main の製品が変わるたびに版番号が自動で進む

## 価値

本人として、版を上げる操作をせずに、main に merge するたびに次の番号の組み立てができてほしい。なぜなら、版を手で上げる決まりは重くて使われず、同じ 0.1.0 で中身の違う物ができて、直した版をインストーラが入れられなかったから（2026-11-19。依頼 #352）。

## 満たす要件（requirements.md から逐語）

> - **FR-134**: WHEN main の commit が CI を通り、前の番号を付けた commit から製品（文書・仕様以外）が変わっている THE SYSTEM SHALL main に commit を積まずに、その commit に版番号を 1 つ進めた組み立てを作る。
>   ★ 2026-11-21 追加。依頼 #352。**右の数字（PATCH）と真ん中の数字（MINOR）は機械が決め、左の数字（MAJOR）だけ本人が手で決める**（NFR-25）。
>   同じ番号で中身の違う組み立てを作らない（2026-11-19 の事故の根）。番号は 1 列に並び、正式版・ベータ版・開発版の意味を持たない（FR-104）。
>   **新しい形の番号は、今の形で既に使った番号（0.1.0・0.1.1）より大きいところから始める**（本人の PC の 0.1.x より新しいと比べられるように。FR-117・FR-137）。
>   ★ 2026-11-23 閉じる。ST61 の深掘り Q3（`openspec/changes/st61-auto-version-bump/deep.md`。推奨のまま）。旧い未決「真ん中の数字（MINOR）をいつ上げるか（Story が入ったら、など）」は、**前の番号から間に確認バッチの merge があれば真ん中を上げ（右は 0 に戻す）、無ければ右を上げる**で閉じた
>   ★ 2026-11-21 補足。整合の確認 `docs/audit/2026-11-21-version-labels-consistency.md` の C4。**今の携帯の versionCode の式（`MAJOR×1,000,000 + MINOR×10,000 + PATCH×100 + 末尾`）は PATCH を 99 までしか持てない**。main への merge は 2026-10-21〜11-21 の 30 日で 110 回あり、merge ごとに PATCH を進めると 1 か月ほどで携帯の組み立てが落ちる。

> - **FR-104**: THE SYSTEM SHALL S-01（V-01 を含む）・C-01・C-02 を、同じ版番号を付けた 1 つのリリースとして配布元に置く。
>   版番号は MAJOR.MINOR.PATCH で、**どの組み立てかだけを表し、チャンネル（正式版・ベータ版・開発版）の意味を持たない**（番号の進め方は FR-134、チャンネルは札 —— FR-105。NFR-25）。配布元の既定は実装上の既定として `docs/production-prep.md` に置く（事業者の名前を要件に縛らない —— PERM-7 と同じ理由）。
>   **版をそろえても、部品ごとに更新する時期はずれる**（S-01 の更新は手動・FR-114）ので、食い違いは FR-124 / FR-125 / FR-130 が受ける。

> - **NFR-25**: 版番号は、一般向けの配布までは **0.x** とし、一般向けの配布の最初の正式版を **1.0** とする。
>   ★ 2026-10-25 追加。配布と更新の深掘り Q10（推奨と同じ側）。0.x は「形が変わりうる」の合図として読まれる。
>   ★ 2026-11-03 訂正。整合の確認（`docs/audit/2026-11-03-native-postgres-consistency.md`）の C10。旧い本文は「一般向けの配布（§5「配布の方針」の S-01 の配り方の選び直し）まで」。配り方の選び直しは 2026-11-03 に済んだが、一般向けの配布はまだなので、合図を「一般向けの配布」だけにした

>   「最初の正式版」は、最初に正式版の札を付けた番号を指す（印 `v*` はやめた。FR-105）。ベータ版の `-beta.N` は付けない（FR-104）

## 高リスクの印（機械）

- `tools/lanes.json` の `risky` に当たる予定パス: `tools/release/**`
- GO で人間が外せる。外した回答は agreement.json に残る。

## 壊してはいけないもの

- 3 つの部品（サーバ・PC の収集アプリ・携帯の収集アプリ）が同じ版番号を持つこと（FR-104）
- 組み立ての印（`<版番号>+<commit>`）と記録ごとの部品の版（FR-122・FR-123）・更新の履歴（FR-121）
- 携帯の versionCode が版をまたいで減らないこと（Android の上書き更新）
- 今の正式版・開発版の組み立て（札の形ができるまでの間も CI が緑のまま）

## 完了の判定

- 製品（文書・仕様以外）に触れる変更が main に merge され、その commit の CI が通ると、main に commit が増えずに、前の番号より 1 つ進んだ番号の組み立て（サーバ・PC・携帯）ができる（文書だけの merge には番号を付けず、CI が取り消された merge の中身は次の番号に入る）
- 同じ番号で中身の違う組み立てはできない（PR の組み立ては自分の番号を持たない）
- 左の数字は本人が決めた値のまま、真ん中と右の数字は機械が決める。携帯の組み立ては 1 年分の merge の番号でも落ちない
