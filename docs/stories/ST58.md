# ST58 — 更新を入れ、移行が失敗したら自動で戻る

## 価値

本人として、「更新あり」を押して新しい版を入れ、移行が失敗しても放っておけば前の版で動き続けてほしい。なぜなら、サーバの更新は移行を伴い、失敗したまま止まると、その間の記録がサーバに入らないから。

## 満たす要件（requirements.md から逐語）

> - **FR-114**: WHEN 利用者が「更新あり」を押す THE SYSTEM SHALL 新しい版を落とし、入れる操作（Android のインストール画面・Windows のインストーラ・S-01 の更新の手順）を開く。
>   **入れるのは本人**（Q6）。S-01 の更新も手動で始める。自動で入れる設定は後で足す（本人の言葉:「一旦は後者で、いずれ自動アップデートに関する設定を入れます」）。
>   Android は直配布なので、アプリの中から入れる画面を開くには「提供元不明のアプリ」の許可が要る。
>   ★ 2026-10-25 補足。整合の確認（`docs/audit/2026-10-25-consistency.md`）の K1。C-02 からインストーラを開くと、いまの `tools/check-no-time-server.sh`（子プロセスは `w32tm` / `wevtutil` だけ）が落とす。
>   正典が求めるのは「時刻を問い合わせる経路が無い」ことだけなので、この要件の Story が検査の許可の形にインストーラの起動を足す

> - **FR-119**: IF 更新の中で移行が失敗する THEN THE SYSTEM SHALL 移行の前の退避（FR-66 とは別。`ashiato-server migrate` が当てる前に毎回取る）から D-01 を戻し、前の版の S-01 で起動し直す。
>   ★ Q9。更新の間 S-01 は止まっていて、新しい記録は収集アプリの手元に溜まる（FR-10）ので、戻して消える記録は無い。

> - **FR-120**: WHEN FR-119 で戻す THE SYSTEM SHALL 戻したこと・失敗した版・失敗の理由を利用者に知らせる。

## 壊してはいけないもの

- 移行の前の自動の退避と、その置き場（Windows のフォルダ。ST55）
- 時刻サーバを問い合わせない検査（`tools/check-no-time-server.sh`。PC の子プロセスは `w32tm` / `wevtutil` だけ。インストーラの起動を許可の形に足す）
- 未送信の保持（更新の間は収集アプリの手元に溜まる）

## 完了の判定

- 「更新あり」を押すと、携帯は Android のインストール画面、PC はインストーラ、サーバは更新の手順が開き、入れるのは本人
- サーバの更新で移行が失敗すると、退避から DB が戻り、前の版で起動し直して、戻したこと・失敗した版・理由が知らされる
- 更新の前後で記録が 1 件も失われない（溜まった未送信は更新の後に入る）
