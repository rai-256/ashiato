# ST13 — ソースの取り方と取得の間隔を登録簿で持ち、定期取得の枠を置く

## 価値

本人として、取れるものは自動で取ってほしい。なぜなら、既存サービスへの不満が「記録がめんどくさい」だったから。

## 満たす要件（requirements.md から逐語）

> - **FR-15**: WHEN C-03 が各ソースに登録された取得契機に達する THE SYSTEM SHALL
>   そのソースの新着を取得して記録を生成する。取得間隔はソースごとに登録簿が持つ。
>   **いま要件の中に、API で定期取得できるアカウント系のソースは無い**（Data Portability API は日本で提供されず（§5 の EXT-N）、テストの OAuth は 7 日で切れる。
>   ST13 の `premises.md`）。C-03 は定期取得の枠と取り込み器の見回りの間隔だけを持ち、後のソースは登録簿に 1 行足して乗る。
>   **ソースごとの取り方と取得の間隔は登録簿が持ち、画面からは変えない。** サーバが回す取得（取り込み器の見回り・定期取得）は登録簿の間隔に従い、
>   端末と PC の取得の間隔（FR-1 / FR-2 / FR-13）は端末が決め、登録簿はそれを写して見せる。
> …（続きは requirements.md）

> - **NFR-3**: Takeout 系のソースには遅延の目標値を置かない。構造的に 2 か月周期のため
>   （§5 の EXT-B）。代わりに取り込み済み最終日（FR-16 / FR-55）で状態を見せる。

> - **NFR-12**: 収集に要する手作業は、**Google 系のみ 2 か月に 1 回**まで許容する。
>   他のすべてのソースは手作業を要さない。根拠は §5 の EXT-A / EXT-B。
>   ★ 2026-09-15 補足。ST12 の深掘り Q7 / Q8 の決定。**Google 系の手作業には、端末でマップのタイムラインを書き出し、
>   網の外に出ない手段（Tailscale のファイル送信・USB など）で自宅 PC の置き場へ運ぶことを含む**（2 か月ごと。EXT-M）。
>   Google の推定した訪問と移動手段は C-01 の位置からは作れないので、書き出さなかった期間は端末から消えれば戻らない。
>   クラウドのドライブを経由しないのは、位置の全履歴の写しが外へ出るため。運ぶ仕組みはシステムが作らない。

## 壊してはいけないもの

- ST12 の取り込み経路と最終日の表示
- ST02 / ST12 の稼働状況の画面（Must の 5 ソースがひとスクロール以内に見えること。直近に置いた書庫の箱の高さを除いて数える）

## 完了の判定

- ソースごとの取り方と取得の間隔を登録簿が持ち、サーバが回す取得（取り込み器の見回り・定期取得の枠）がその間隔で走る。取り方と間隔は稼働状況の格子に読むだけで見える
- Google 系については、2 か月に 1 回の手作業以外に操作が要らない
