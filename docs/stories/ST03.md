# ST03 — 同じ記録を何度送っても増えない

## 価値

本人として、端末が再送しても記録が二重にならないでほしい。なぜなら、後から「重複か本当に 2 回起きたか」を区別する手段が無いから。

## 満たす要件（requirements.md から逐語）

> - **FR-22**: WHEN 同一の記録が再び届く THE SYSTEM SHALL 既存の記録を更新し、新しい行を作らない。
>   同一かどうかは**利用者ごと・ソースごとに、2 段で**判定する ——
>   **外部サービス上の識別子があればそれで、無ければ内容ハッシュで**。
>   同じ内容でも外部サービス上の識別子が違えば、**別の記録として新しい行を作る**。
>   収集側が生成した識別子（FR-21）は判定に使わず、同じ識別子で内容が違えば 400 で断る。
>   更新するときは**前の版を履歴に残す**（FR-18 / FR-30）。
> …（続きは requirements.md）

> - **FR-23**: THE SYSTEM SHALL 外部サービス由来の記録に、その外部サービス上の識別子を持たせる。
>   登録簿は**その識別子が「記録ごと」か「対象ごと」か**を宣言し、「記録ごと」と宣言された
>   ソースからの記録が識別子を欠けば 400 で断る。**書き忘れたときは「記録ごと」に倒す**。
>   **対象ごとの識別子（動画 ID など）は別の列に持ち、重複の判定には使わない** ——
>   記録ごとの識別子とは別物で、同じ対象の記録を後から集めるために持つ。
>   識別子を返す記録と返さない記録が混ざるソースは、**論理ソースを分けて登録する**。
> …（続きは requirements.md）

## 触れる扉（requirements.md §5 から逐語）

> 12. **外部サービス上の識別子を持つか** — 決めるもの: 記録の有無
>     決着状態: 決定済（持つ。これが無いと同一物の更新を追えない）
>     ★ 2026-09-11 補足（ST03 の深掘り Q13 / Q18 / Q24）。**「記録ごとの識別子」と
>     「対象ごとの識別子」は別物**で、別の列に持つ。同一物の更新を追えるのは前者だけ。
> …（続きは requirements.md）

## 壊してはいけないもの

- ST01 の書き込み経路
- ST01 が固定した冪等キーの期待値（利用者識別子は索引にだけ足し、鍵の中身は変えない。深掘り Q15）

## 完了の判定

- 同じ記録を 3 回送っても D-01 の行数が増えない（端末 / 記録ごとの外部識別子 / 対象ごとの外部識別子の 3 クラスとも）
- 外部サービス側で内容が更新された記録を再取得すると、行が増えず既存行が更新され、前の版が履歴に残る。**対象ごとの識別子しか持たないソースは対象外**（そのクラスでは更新が行を増やす。深掘り Q25）
- 本人が消した記録は、同じ内容が別の外部識別子で届いても入らない（深掘り Q19）
- 履歴を残さない書き換えと、台帳を残さない消去を、DB が拒む（深掘り Q10 / Q23）
