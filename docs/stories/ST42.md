# ST42 — 衛星向けの API の契約を、版を付けて読める形で公開する

## 価値

衛星の作り手として、何をどう呼べばよいかを契約から知り、本体が更新されても自分の衛星が黙って壊れないようにしたい。なぜなら、衛星は本体と別に作られて別に更新され、壊れている間に書くはずだった記録は取れないから。

## 満たす要件（requirements.md から逐語）

> - **FR-89**: THE SYSTEM SHALL 衛星が使う API に版を付け、同じ版の中では既存の衛星を壊す変更をしない。
>   ★ 2026-10-11 追加。衛星の基盤の監査（`docs/audit/2026-10-09-satellite-foundation.md`）§3。衛星は本体と別に作られて別に更新されるので、
>   本体の更新で衛星が黙って壊れると、衛星が書くはずだった記録が取れない。
>   壊す変更かどうかは、版ごとの衛星向けの API 契約（FR-103。内部の口の `docs/openapi.json` ではない）の差分を機械で見て判定する。

> - **FR-95**: WHEN 衛星が使う API の壊す変更を新しい版として出す THE SYSTEM SHALL 前の版を 6 か月以上並べて動かす。
>   ★ 2026-10-11 追加。6 か月は推奨を採った仮の値（変えても失うものは無い。並べる期間を延ばすだけ）。

> - **FR-103**: THE SYSTEM SHALL 衛星が使う API の契約（口・型・記録の封筒の形・資格情報の渡し方・版）を、本体の収集アプリと画面だけが使う口の契約と分けて、
>   リポジトリの中のブラウザで読めるページとして公開する。
>   ★ 2026-10-11 追加。本人の決定（「はい、それで良いので進めてください」）。いまの `docs/openapi.json` は本体の収集アプリと画面の口だけを持ち、
>   資格情報の渡し方（securitySchemes）も版も無く、リポジトリにファイルが置いてあるだけだった。内部の口は本体の都合で変えてよいが、
>   衛星の作り手が頼る契約は版を付けて守る（FR-89）ので、2 つを分けないと内部の口の変更がすべて衛星への壊す変更に数えられる。
>   ★ 2026-10-11 独立レビューの指摘で、資格情報の渡し方と版を本文に入れた。置き場（リポジトリの中のページ）は AI の仮置き（リポジトリは公開なので外の作り手も読める。変えても失うものは無い）。

## 触れる扉（requirements.md §5 から逐語）

> 31. **衛星向けの API の契約と SDK のライセンス** — 決めるもの: 値
>     決着状態: 決定済（2026-10-11。Apache-2.0。本体は AGPL-3.0 のまま）——

>     関与要件: FR-103

## 壊してはいけないもの

- ST01 の API 契約（docs/openapi.json）と、それを見る検査（tools/check-openapi.sh）
- ST29 の衛星の資格情報

## 完了の判定

- 衛星向けの契約が、本体の内部の口の契約とは別に生成され、Apache-2.0 を宣言し、資格情報の渡し方を含む
- 衛星向けの契約がリポジトリの中のブラウザで読めるページになっている
- 契約に版が付き、同じ版の中で既存の衛星を壊す変更を入れると CI が落ちる（内部の口の変更では落ちない）
- 衛星の資格情報で受ける口が内部の契約に載っていると CI が落ちる。壊す変更を新しい版として出すと前の版も並んで動く
