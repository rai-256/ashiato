# 表面の作り直し playground のレビュー

HTML は描画していない。`docs/ui-surface-playground.html` の `<script>` を Node の `vm` にそのまま読み込み
（末尾の `init()` だけ外した）、`buildTones` / `evaluate` / `sizes` / `varsFor` を**中身を書き換えずに**呼んで値を出した。
比の式は playground の `lum` / `cr`（342〜361 行）をそのまま使っており、`web/src/contrast.ts` と同じ式であることも読み比べた。
突き合わせた実物は `web/src/tokens.ts`・`DayView.tsx`・`CoverageGrid.tsx`・`AchievementPanel.tsx`・`App.tsx`・`MasterView.tsx`・

## 先に結論

- **作成側の「165,888 通り × ライト・ダークで違反 0 件」は格子の目が粗いために出た数字で、可動域の中には NFR-18 を割る状態がある**（USR-1）。
  主の色相 54〜86°・面の色み 35% 以上で、ダークのいちばん明るい面が明るさ 36 に届くと、文字 5 種がどれも **4.12:1** まで落ちる。
  格子の色相は 45° 刻み（0, 45, 90 …）なので、黄の帯（54〜86°）を挟んで通り過ぎていた。整数値を一様に 100,000 通り選んで走らせると、655 件の割れが出た
- **作る表 → CSS 変数 → 測る対の筋は、文字については通っている。** `varsFor` は `T` の全キーをそのまま CSS 変数にしていて（517 行）、
  `.pv` の CSS は色を `var()` からしか取っていない（影の黒だけが例外）。文字の組は全部、重複を除いた面の全段に対して測っている。
  UIR-13 / 38 / 61 と同じ型（描く色が測る対から漏れる）は**文字では再発していない**。
  ただ、**描いた形と測った形がずれている**ところが 2 つ残っている。格子のセルは 3px の隙間を空けて `s1` の上に描いているのに、
  セルどうしが接しているものとして測っている（USR-3）。`line` は表にあるのに測っておらず、そのうえで意味を担う「その他」のセルの縁取りに使っている（USR-4）
- **9/8 の preset は `tokens.ts` と今の web を再現していない**（USR-2）。地と面の明るさ（ダーク 12/18/24、ライト 96/91/86）と文字の明るさ（92/72、14/30）は合っている。
  一方で、文字の彩度（12% と 30%）、フォーカスの輪（アクセント色 2px と本文色 3px）、本文の大きさ（15px と 16px）、行の角（15px と 8px）、
  格子を置く面（`s1` と `surface2`）が違う。「9/8 から変えたものだけ」を出す prompt は、この差を「変えていない」として扱う
- **骨格の 5 項目（時系列・リスト・1 行＝滞在・その場で開く・主役＝場所の名前）はコントロールになっておらず、固定されている。**
  ただ、上部の帯（ブランド名と全画面への導線とログアウトを 1 本に並べたもの）と稼働状況の凡例は今の web に無い構造で、
  「色の量＝はっきり」はこの帯があるものとして塗る（USR-6）

### 成り立っているもの（直すときに壊さないように）

## 観点ごとの結果

### 1. 軸が実際に動くか

`state` の 22 キーは全部、`buildTones` / `surfaceLs` / `varsFor` / `mark` / `sizes` のどれかで読まれていて、書き込んだだけで使われない軸は無かった。
色相・彩度・大きさの直書きは、開示済みの運用値（注意色の `seek(8, 50, …)`（433 行）、文字の彩度の上限 `Math.min(st.surfSat, 12)`（425 行））を除くと見つからなかった。指摘は次のとおり。

- USR-15: 「面が浮く」のときの「面の段差（ライト）」は、`100 - lightG` を超えた分が効かない（friendly では 5〜10 の範囲が丸ごと効かない）
- USR-3 / USR-4: 作る表 → 描く → 測るの 3 か所のうち、格子と `line` の 2 か所で描く側と測る側がずれている
- USR-1 の原因の 1 つは、総当たりの格子が色相を 45° 刻みでしか取っていないこと。差し色の色相（`sparkHue`）も色の軸なのに、走査では `accHue` と同じ値に固定されている（875 行）

### 2. 要件との整合

- USR-1（高）: 可動域の中で NFR-18 が割れる。警告は「この組み合わせは選べない」と出るが、実際には選べる（713 行）
- USR-3（中）: NFR-23 を「隣どうし」で測っているが、描くとセルの隣は面 `s1` になる
- USR-13（低）: NFR-19 の実測は `[data-t]` しか数えていない。18×18px のラジオが数から外れている
- USR-18（低）: NFR-17 の「満たす / 割れている」を NFR-18 の結果で出している。`ui-direction.md` の下限の表に NFR-23 の行が無い
- 要件に無い値を自前で立てていないか: **立てた値は全部「運用値（要件ではない）」として開示されている**（267〜280 行）。
  前回の型（UIR-18/44: 要件に無い閾値を黙って置く）は再発していない。強いて言えば、フォーカスの輪の 3:1 は NFR-22 が求めていない値だが、それも出所を書いて開示してある

### 3. 文脈の網羅

- ライト・ダーク: 両方ある（既定は「両方」、340 行）。S-1 は今の web ではダークしか無い（`App.tsx` は `SURFACE` / `TEXT` を直に使っている）ので、ライトの S-1 は新しく作る範囲になる（USR-20）

- 画面: 3 枚（S-2 1 日の滞在 / S-1 稼働状況 / S-6 マスタ管理）で、情報の性質が違うものが揃っている。S-8 ログインは無い（USR-20）
- 状態: **読み込み中と、最長・最多が無い**（USR-9）。9/8 版の playground には両方あった（UIR-32/46/47 で足したもの）

### 4. 一貫性

- USR-2（高）: 9/8 preset と `tokens.ts` / 今の web がずれている

- 空・エラー・読み込み中: USR-9（中）。読み込み中が無い
- 一番長い・一番多い: USR-9 / USR-8。場所の名前は最長でも「そば処 まつ川」で、滞在は 6 件どまり

## 指摘一覧

### USR-1 — 色相が黄（54〜86°）で面の色みが 35% 以上のとき、ダークの文字が 4.12:1 まで落ちる（NFR-18 が割れる）。総当たりの格子はこれを踏まない
- 重さ: **高**
- 観点: 1, 2
- 根拠:
  - `docs/ui-surface-playground.html:396` `const DARK_TOP = 36`。これはダークのいちばん明るい面の**明るさ（L）**の上限で、相対輝度の上限ではない
  - `:400` で段差を詰めると、`darkG + (n-1)*step` がちょうど 36 に届く
  - `:429〜433` で文字 5 種を `seek(..., toward=+1)` で白へ寄せても、白（`[0,0,100]`）と `hsl(60 40% 36%)` の比は **4.121:1** で 4.5 に届かない。
    このとき `seek` は `ok:false` のまま返る（372 行）
  - 割れる帯（Node で 1° ずつ計算）: 面の色み 40% なら色相 **54〜86°**、35% なら **58〜68°**。30% 以下では割れない。
    明るさを 34 以下に抑えれば、色み 40% でも全ての色相で割れない
  - 最小の再現: `hue:60, surfSat:40, darkG:24, steps:3, stepDark:6`（それ以外は 9/8 のまま）→ 面 24 / 30 / 36、
    本文・控えめ・アクセント・差し色・注意が「面 2」の上でどれも 4.12:1
  - 総当たり（`sweep`、865〜869 行）の格子は `hue: [0,45,90,…]`・`surfSat: [0,20,40]` で、45° は 4.978:1、90° は 4.542:1 と両隣が通るので、
    帯の中を 1 点も踏まない。可動域の整数値を一様に選んで 100,000 通り走らせると、**割れた対は 655 件**（全部ダークの文字。あるのは `本文/控えめ/アクセント/差し色/注意 × 面 2・面 3` だけ）。
    明るさにかかわる 5 軸（hue / surfSat / darkG / steps / stepDark）だけを一様に選ぶと、ダークの状態の約 0.15% が割れる
  - 警告の文は「この組み合わせは選べない」（713 行）だが、スライダーは制限されておらず、実際には選べる
- 何が起きるか: 「黄みの暖かい地」（7/24 の形容詞「暖かい」の側。preset「温かく静か」は色相 34°）を探して色相を 60° 前後・色みを強めに振ると、
  ダークの最も明るい面（3〜4 段のときのボタン・入力欄の面）の上の文字が全部 4.5:1 を割る。prompt の「守る下限」には
  「いまダーク最小 4.12:1」と出るだけで、本人がそのままコピーしうる。作成側の「違反 0 件」をもとに「全状態で満たす」と記録すると、事実と違う記録が残る
- 直し方の案: `DARK_TOP` を明るさの定数で持つのをやめ、**白との比が 4.5 を割らない輝度（相対輝度 ≤ 0.1833）**から、その色相と彩度ごとに上限の明るさを解いて決める
  （`surfaceLs` の中で二分探索すれば 1 か所で済む）。あわせて、総当たりの色相を 1°（少なくとも 5°）刻みにする

### USR-3 — 格子のセルを隙間 3px で `s1` の上に描いているのに、NFR-23 はセルどうしが接しているものとして測っている
- 重さ: 中
- 観点: 1, 2
- 根拠:
  - 描く側: `.pv .wk{display:flex;gap:3px; …}`（150 行）で、セルの間に節の面（`.sec` = `s1`、145 行）が 3px 見える。「その他」のセルは `box-shadow:inset 0 0 0 1px var(--line)`（154 行）で縁を取る
  - 測る側: `P` にあるのは「記録あり ↔ 動いていた」と「動いていた ↔ その他」の 2 組だけ（484〜485 行）。セルと `s1` の組は無い
  - 実際にセルと隣り合う色（`s1`）との比（Node で計算）: 9/8 のダークで「動いていた」2.68:1・「その他」1.44:1、ライトで 2.81:1・1.08:1。
    friendly のダークで 2.72:1、morning のダークで 2.76:1。**preset の中にも 3:1 を割るものがある**
  - 実物も同じ形をしている（`CoverageGrid.tsx:139` が `gap: 2`、面は surface2 で、セルとの比は 1.88 / 2.07 / 7.89:1）。tokens.ts の 3.89 / 3.81:1 もセルどうしで測った値
- 何が起きるか: WCAG 1.4.11 の「隣り合う色」を字句どおりに読めば、隙間を空けた格子では節の面が隣になり、表に出ている「満たす」が描いた絵と食い違う。
  playground が自分で掲げている「描く色と測る色を別々の場所で決めない」（10〜12 行）の、形の側の割れにあたる
- 直し方の案: どちらで測るかを決めて揃える。(a) 隙間を 0 にしてセルを接させる（今の測り方が字句どおりになる）か、
  (b) 隙間を残すなら、セルと `s1` の組を `P` に足し、満たせない「その他」は縁（`line`）の側で 3:1 を取る。どちらにするかは実物の格子にも及ぶので、本人か ST02 の判断が要る

### USR-4 — `line` は表 `T` にあって CSS 変数になるが、測る対に入っていない。意味を担う「その他」のセルと凡例の縁にも使われている
- 重さ: 中
- 観点: 1, 2
- 根拠: `line`（463 行）は `T` に入り（466 行）、`--line` / `--bd` / `--bdt` / `--hline` として描かれる（517、523、527〜528 行）。`P`（474〜489 行）には `line` を含む組が無い。
  「その他」のセル（154 行）と凡例の見本（612 行）は、地や面とほぼ同じ色なので縁取りの `line` だけで見えている。
  「その他」と `line` の比は 9/8 のライトで 1.45:1、friendly のライトで 1.20:1、hut のライトで 1.22:1。凡例の「その他」は地（`g`）の上にあり、`c0` と `g` の比は 1.00〜1.16:1

### USR-5 — 9/8 では 1 本だった色相と彩度を 3 本ずつに分けたのに、prompt は変えた軸のことしか言わない。どの色相がどこに残るかが伝わらない
