# ST54 への申し送り

## st51-update-history premises 9 — 同じ PC に並べた C-02 の端末識別子を分ける

- C-02 の端末識別子は環境変数 `ASHIATO_DEVICE_ID`（設定の値。`crates/collector-windows/src/config.rs:123`）。正式版と開発版を同じ PC に並べたとき、同じ値になりうる
- ST51 は収集アプリの版の変化を、端末・部品ごとに生存信号の版を並べて導く（`core.collector_version_change`）。並べた 2 つの C-02 が同じ端末識別子で交互に信号を送ると、
  版が行き来したように見える（生存信号の行と版は残るので、識別子を分ければ読み口は出し直せる）
- 並べる仕組みを作る ST54 で、並べた C-02 が別の端末識別子を持つようにする
- 出所: `openspec/changes/st51-update-history/premises.md` の 9・C10

## ST52 Q4・Q11 — 開発版に携帯の APK を足し、開発版の鍵を作る（整合の確認 `docs/audit/2026-11-01-st52-door34-consistency.md` の C1）

- ST52 の深掘りで、開発版（`nightly`）に携帯の APK を入れ始めるのは **ST54 から**になった（Q4。本人が推奨と違う側を選んだ）。ST52 の開発版のリリースには S-01 と C-02 だけが並ぶ
- 開発版の C-01 は識別子 `dev.ashiato.collector.dev`（扉 34）で、**正式版と別の鍵**で署名する（Q11）。鍵は開発版の Environment に置き、控えは USB に 1 部（扉 34 ★ 2026-11-01・`docs/production-prep.md` の A-3）
- 開発版の鍵は一度配ると替えられない（替えると開発版を入れた携帯は消して入れ直し、手元の未送信が消える）。ST54 で鍵を作る前に、形（ST52 の design D3（仮）の RSA 4096・25 年以上）と作る手順（ST52 の `docs/release.md`）を確かめる
- ST52 が用意するもの（ST52 の design D23（仮））: gradle の `.dev`（`-dev.` の版番号のときだけ）・`tools/release/sign-apk.sh` の開発版の側と取り違えの止め・`tools/release/make-key.sh dev`・配布物の名前 `ashiato-collector-dev-<版番号>.apk`（どれも使い捨ての鍵で確かめただけ）と、鍵を置かない Environment `nightly`（枝 `main`）。
  ST54 がやるもの: 開発版の鍵を作って `nightly` に Secrets と指紋の変数 `ASHIATO_CERT_SHA256` を置く・`nightly.yml` に携帯の APK の組み立てと署名を足す・`tools/release/check-artifacts.sh --channel nightly` の期待を 4 つに戻す（FR-104 ★ 2026-11-01 の例外を外す）。
  正典 `distribution` の「印（タグ）の名前で、3 つのチャンネルに分けて配る」「開発版は、幹にその日の変更があった日だけ作り直す」を MODIFIED で書き直し、「ST54 まで」の例外の文と Scenario（`開発版の配布物の検査は、携帯の APK を除く 3 つで通る`・`開発版の置き場に携帯の APK があれば、検査は落ちてその名前を示す`・`開発版の作り直しの workflow は、ST54 まで携帯の APK を組む手順を持たない`）を外す（開発版も 4 つ）
- ST54 の完了の判定には、いまは開発版のリリースに携帯の APK が並ぶこと・開発版の鍵で署名されていることが無い。足すかは ST54 の上流で決める
- 出所: `openspec/changes/st52-release-channels/deep.md` の Q4・Q11、`docs/requirements.md` の扉 34・FR-104 の ★ 2026-11-01

## ST52 R11 — 開発版 DB の食い違いを確認する

R11 は、名前を変えた・消した移行が main に入ると、開発版サーバの台帳が知らない版になって `Ahead` となり、起動も移行も止まることを示している。移行の中身だけを変えた場合は警告にとどまり、移行を当て直さないため、開発版 DB の形が黙って main とずれる。ST54 では、nightly の DB の扱いにこの不整合を検出して原因を記録し、無理に DB を書き換えず次の版で直す手順を組み込む。

また、nightly の印を毎日動かす方式では、別の clone で `git fetch --tags` を実行したときに既存の nightly 印を上書きできず rc=1 になる（DB の食い違いが原因ではない）。印を動かさない設計と、nightly の DB の更新手順を ST54 で合わせて決める。

出所: `openspec/changes/st52-release-channels/review/deep.md` R11（移行の名前変更・削除では起動が止まり、中身の変更では形がずれる。nightly の印を動かすと `git fetch --tags` が rc=1 になりうる点）。

## ST52 code_verify R26 — 開発版の署名は、開発版の鍵の指紋を受け取らないと署名しない

`tools/release/sign-apk.sh <apk> dev <出力>` は、渡された鍵の証明書の指紋を `ASHIATO_EXPECT_DEV_CERT_SHA256` と比べ、
無いか違えば署名しない（識別子とチャンネルが合っていて鍵だけを取り違えたときに、開発版の APK を正式な鍵で配らない。正式版の側は `ASHIATO_EXPECT_CERT_SHA256`）。
ST54 で `nightly.yml` に署名を足すときは、`nightly` の変数に置く開発版の指紋をこの名前で `sign-apk.sh` に渡す。

出所: `openspec/changes/st52-release-channels/review/code.md` R26。

## ST53 との合わせ目（整合の確認 `docs/audit/2026-11-03-st53-st54-consistency.md` の C2・C3・C4）

ST53（許諾の同梱）と ST54 の上流は別々に合意して main に入った。どちらが先に下流へ入っても、後の側がここに当たる。

- **C2 開発版の鍵の守り**: ST53 の GO 資料は「ST54 の上流はまだ無い」として、`nightly` の Environment（開発版の鍵）と ST53 が絞るエージェントの資格情報（design D3: Contents と Workflows の書き）の関係を見ていない。ST54 の上流もここは見ていない。
  `nightly` は main からの実行に開き、承認者が付かないので、エージェントの資格情報で main に入れた変更が開発版の鍵を読めるかを、**開発版の鍵を作って `nightly` に置く前に**確かめる（読めるなら、置く前に本人に問う。開発版の鍵は替えると開発版を入れた携帯の未送信が消える）
- **C3 `docs/release.md` の節の番号**: `docs/requirements.md` の FR-108 ★ は `docs/release.md` の「§7」（本人の環境を移す）を番号で指す。ST54 の Task 11.1 が release.md に節を足すときは §7 より前に入れて番号をずらさないか、ずらすなら FR-108 の参照を節の名前「本人の環境を移す」に直す（ST53 の Task 10.2 も同じ制約を `docs/handoff/ST53.md` に持つ）
- **C4 ST53 が先に main に入っていたとき**:
  (a) 新しく足すソースの許諾の表示は ST53 の式 `AGPL-3.0-only WITH AdditionRef-ashiato-play-services`（`check-spdx.sh` が落とす）
  (b) `check-artifacts.sh --self-test` の開発版の偽の配布物にも許諾の 3 点と `SOURCE.txt` を入れる
  (c) `draft.sh --channel nightly` は、`nightly.yml` の run が組んだ commit を checkout した手元の木で走らせる（`LICENSE` を手元の木と比べるため）
  (d) 開発版の鍵の Secrets の節は、release.md の「エージェントの資格情報」の節より後に置く（ST53 の Task 10.2 の検証が、`ASHIATO_SIGNING_KEYSTORE_B64` が最初に出る行の順を見る）

出所: `docs/audit/2026-11-03-st53-st54-consistency.md` の C2・C3・C4。
