## st21-place-registry Q4 — S-2 の見出しを場所の名前にするのは、ST21・ST22・ST25 の archive 後の fix/

- 何を: S-2（1 日の一覧）の滞在の行の見出しを、時刻の範囲から**その滞在が当たる場所の名前**にする（`docs/ui-direction.md` が S-2 の主役を「場所の名前」にしている）
- 決まったこと（ST21 の深掘り Q4。本人が推奨と同じ側を選んだ）: **ST21 も ST25 も見出しを触らない。** ST21・ST22・ST25 の 3 本が archive された後に `fix/<slug>` の小さな change で変える。担当は見つけた側（ST21）
- 使うもの: 滞在がどの場所かは ST21 の照合（`crates/server/src/places.rs` の `assign`。FR-48 ★）で、読み出すたびに計算する。**滞在には書き込まない**（FR-48 ★）。
  どの場所にも当たらない滞在の見出しは時刻の範囲のまま（名前の無い居た所に名前を付けるのは S-6）
- 気をつけること: ST25 の上流は「行の見出しは時刻の範囲（場所の名前は ST21 まで無い）」を前提に深掘りしている（`st25-day-timeline/deep-questions.json` Q1 の context）。
  その前提は変えなくてよい。見出しの幅・切り詰め・同じ場所が続く行の扱いは `fix/` の側で決める（S-2 の Requirement の MODIFIED になる）
- 起こす係（st21-place-registry review/spec.md R14）: ST21 の下流が PR 本文の「後続」にこの `fix/` を挙げる（ST21 tasks 11.1）。
  **ST25 の下流は PR 前に handoff を読んだとき（2 回目）、ST21・ST22 が archive 済みなら ST25 の PR 本文の「後続」にもこの `fix/` を挙げる** ——
  3 本目の archive が済んだ時点で、その `fix/` の issue が立っているようにするため（ST25 の tasks には足さない）
- 根拠: openspec/changes/st21-place-registry/deep.md Q4、review/deep.md R1、review/spec.md R14、design.md D19

## st08-browser-history Q8 — URL と題名の無い訪問が `c02-browser-history` に入る（2026-10-12 の整合の確認 C3）

- 何を: ST08 の深掘り第 4 回 Q8（2026-10-05。FR-13 ★）で、**URL の行が無い訪問は捨てず、`url` と `title` の欄を省いた `visit` として入る**ことになった
  （`docs/collector-contract.md` の C-02 の履歴の節。時刻・遷移・滞在時間は持つ）
- 気をつけること: ST25 の design は「どちらにも `url`・`title`・`browser`・`at` はある」（design.md:16 / :80）を前提に、
  `c02-browser-history` の訪問を `(event_time, url)` で畳み（D4）、ブラウザの要約を「訪問の多い URL のドメインの上位 3 つ」、中身を「題名とドメイン」で出す。
  URL の無い訪問について、次を下流で決める（表示は計算し直せるので、ST25 の tasks には戻さない）:
  - 畳み方: SQL の `NULL` は `=` では一致せず、`GROUP BY` / `DISTINCT` では 1 つにまとまる。URL の無い訪問どうしを畳むか
  - 数え方: 件数には数え、ドメインの上位からは外すか
  - 行の出し方: 題名もドメインも無い行に何を出すか
  - 二重: URL 付きで送った訪問が後で URL の行を失うと、URL 無しの 2 件目が別の識別子で入る（`docs/handoff/ST08.md` の R66）。`(event_time, url)` では畳まれない
- 根拠: docs/audit/2026-10-12-consistency.md C3、openspec/changes/st08-browser-history/deep.md Q8、design.md D2 / D6 / D10
