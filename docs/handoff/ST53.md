### ST52 IMP-01 —— 印を push できる人が、main を通さずに正式な鍵を読めるかもしれない（重大・後の Story で扱う）
- 問題: 正式な鍵の置き場（Environment release）は印の名前 v* だけを見て開く。main の祖先かどうかは workflow の中の判定が確かめ、印の作成を止める規則は無い（ルールセットは削除と付け替えだけ、pre-push は feat/st* の枝だけ）。印の push で走る workflow が印の commit の定義なら、main に入っていない commit で書き換えた workflow に v* の印を打つと、その workflow が正式な鍵を読める。鍵が外に出ると、配った APK の更新を他人が作れる。D21（仮）が main に開かない理由（AI が書いた変更から鍵を読ませない）と同じ経路が、印の側に残る。 本人が鍵を置く手順（docs/release.md。D19）は Environment と Secrets を置く工程をルールセットより前に並べ、そのルールセットは印の作成に効かない。「ルールセットが無ければ公開しない」の判定も、書き換えられる同じ workflow の中にある。
- 残るリスク: 本物の鍵を Environment に置いた時から、印の作成を限るまで、この経路が開く
- 影響の範囲: 正式な鍵と、それで署名する携帯の APK
- 暫定の手当て: ST52 は本物の鍵を作らず、確かめは使い捨ての鍵と下書きのリリースで行う（D22（仮））。本物の鍵を置くのは最初の印を打つ前で、ST53 の後（この Story の仕様で手当てする）
- いま進めて安全な理由: ST52 の間は Environment に本物の鍵が無いので、読まれて困る値が無い
- 責任者: 本人（ST53 の深掘りで答える）
- 解決の時期: ST53 の上流の合意まで
- 参照元: openspec/changes/st52-release-channels/go.json の impact.findings[IMP-01]・agreement.json（2026-11-01T12:47:34Z・答え deep-answers-2.txt）
- 引き受け方: ST53 の GO 資料（go.json の impact.findings）に `from: ST52/IMP-01` の IMP を置き、ST53 で人間が判断する（go_brief が見る）。この塊は機械が書く —— 手で直すと merge gate が止める

## ST52 Task 11 — 最初の印と開発版の公開

ST52 の手順は [`docs/release.md`](../release.md) にある。最初の印と開発版の公開は、ST53 の確認が終わった後に本人が始める。`ASHIATO_NIGHTLY_PUBLISH=on` を設定するまでは nightly を公開しない。正式な鍵を置く前に、`release` Environment が tag `v*` だけ、`nightly` Environment が branch `main` だけを対象にし、印の削除・付け替えを拒むルールセットを確認する。

ST52 の完了判定で残るものは、使い捨ての鍵による署名手順と下書きのリリースで確かめる。本物の印の公開、正式な鍵での署名、本人のサーバの切り替えは ST53 の確認で見る（Q13 / D22）。
