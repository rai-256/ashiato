## st12-archive-ingestion R25 — 記録・台帳・ソース別台帳がトランザクションで括られていない

- **何を**: `crates/server/src/archive/worker.rs` の読み手は、記録 n 件 → 台帳の `read` 行 →
  `archive_ledger_source` を**別々の自動コミット**で書く。途中で DB が落ちると、
  `read` の行だけがコミット済みで残る（追記のみトリガなので直せない）。
  design D11 は最終日を台帳からのみ導くので、**記録は入っているのに画面が永久に「まだ無い」**。
  既読判定（`scan.rs`）に当たるので読み直しもされない
- **なぜ ST12 で直さないか**: 括り直すと `PgSink` が持つ格納関門の境界（ST03 の本人の決定）に触る。
  ST12 の R24 の直し（読み手が処理の前に台帳を引く）で**発生の条件は狭まった**
- **根拠**: `openspec/changes/st12-archive-ingestion/review/code.md` R25

## st12-archive-ingestion R28 — MyActivity の見分けが先頭 1 件の `titleUrl` に依存

- **何を**: `crates/server/src/archive/classify.rs` は配列の**先頭項目**が `titleUrl` を持たないと
  `None` を返す。本物の `MyActivity.json` には `titleUrl` を持たない項目が混ざるので、
  並び次第でファイルごと「読まなかったファイル」として黙って落ちる
- **なぜ ST12 で直さないか**: 見分けの規則は design D3（仮）そのもので、その反転条件は
  「実物の書庫で形が表と違うとき」。**H.1 で本物の `MyActivity.json` を見てから**直すのが安い
  （合成の想像で規則を広げると別の誤判定を作る）
- **根拠**: 同 R28

## st12-archive-ingestion R32 — 移行前ロケーション履歴の読めない項目が数にも場所にも残らない

- **何を**: `crates/server/src/archive/legacy.rs` の `filter_map` が時刻を読めない項目を黙って落とし、
  `worker.rs` は**返った**件数しか数えないので、読めなかった件数・場所が台帳に残らない
  （spec「読めなかった項目の件数と場所を台帳に残す」）。YouTube 側は正しく数えている
- **なぜ ST12 で直さないか**: 解析器が「落とした件数」を返す形に変える必要があり、
  R28 と同じく実物の形を見てからのほうが安い（どの欄が欠けるのが正常か分からないと、
  正常な項目まで「読めなかった」に数える）
- **根拠**: 同 R32

## st12-archive-ingestion R34 — 置き場の片方が読めないともう片方も走査されない

- **何を**: `crates/server/src/archive/scan.rs` は 2 つの置き場を `?` で直列に読むので、
  専用フォルダが無いだけでダウンロードのフォルダも走らない。既定は相対パスで、作る処理も無い
- **なぜ ST12 で直さないか**: 片方ずつ走らせると「2 つの置き場をどちらも読めた走査の回数」
  （spec の生存信号の成功回数）の定義に触る。いまは `blockers` に読めない置き場が出るので**気づける**
- **根拠**: 同 R34

## st12-archive-ingestion R35 — 登録簿が利用者で分かれていない

- **何を**: `core.source` は `user_id` 列を持つが ST12 が入れる 11 行は全部 NULL。
  `retire_legacy_sources` は利用者で絞らず全員の退役日を動かし、`archives_status_for` の
  sources クエリは他人の `c03-myactivity-*` を返す（**表示名から他人がどの製品を置いたかが分かる**）
- **なぜ ST12 で直さないか**: 登録簿を利用者で分けるのは `core.source` を共有している**全 Story の前提**
  （`coverage.rs` の `must_sources()` も `testdb::source` も利用者を持たない）。ST12 だけで変えると
  他の Story の判定が割れる。**いまの運用は単独の利用者**（`ASHIATO_ARCHIVE_USER_ID` が 1 つ）なので実害は出ていない
- **根拠**: 同 R35

## st12-archive-ingestion R37〜R46 — 中程度のものまとめ

- **何を**:
  - M1 `reparse_path` が書庫の sha256 で `archive_file` を引くが、`record_copy` が入れるのは
    中のファイルのハッシュ。鍵が一致しないので「解析器の版が上がったら読み直す」に実体が無い
    （ST12 の R22 の直しで、**確認待ちの読み直しだけは** `archive_sha256` 列で辿れるようにした）
  - M2 同じ zip を 2 回読み、同じ JSON を 4〜5 回解く
  - M3 `hash_file` が書庫全体をメモリに載せる
  - M4 `archives_status_for` の sources クエリが直積で、索引 `archive_ledger_source_latest` がどこからも使われない
  - M5 `unreadable_at` / `skipped_file_count` / `archive_sighting.first_seen_at` を読む経路が無い
    （design D7 の「名前から取れなければ置き場で最初に見つけた時刻」が満たされていない）
  - M6 `already_read_ledger_id` に参照制約が無く、自己結合に利用者条件も無い
  - M7 `consecutive_failures` を 0 に戻す経路が無い（ダウンロードのフォルダのファイルは移動しないので残る）
  - M8 `.json` の I/O 失敗を `unsupported_format` と呼ぶ（本人が「形が対応していない」と誤読する）
  - M9 移行の guard に `relnamespace` の条件が無い
  - M10 新規 DB と旧 DB で `archive_pending_shape.shape` の DEFAULT が食い違う
- **なぜ ST12 で直さないか**: M1〜M4 は **design D17（仮）と同じ「実データの規模が分かってから」**の領域。
  M5〜M10 はこの PR で触った範囲の外か、H.1 の後に形が変わる見込みのもの
- **根拠**: 同 R37〜R46
