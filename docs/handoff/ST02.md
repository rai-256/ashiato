ST03（`st03-idempotent-ingest`）の上流が ST02 へ返した 5 件のうち、**4 件はすでに ST02 に

## st03-idempotent-ingest R-e — 更新だけが届いた日を稼働記録でどう数えるか

- **何を**: ST03 が外部サービス由来の更新の経路を開けたので、稼働記録の正典
  「**新しく入った記録だけを数える**」に穴が開く —— 更新だけが届いた日は
  `core.coverage.event_count` が 0 のまま増えない
- **ST03 側でどうしたか**: 正典どおり**更新は 0 件として数える**。ただし
  **その日の行そのものは立てる**（「その日は収集が動いていた」は更新の到着でも真）。
  `crates/server/src/lib.rs` の `ingest_one`（`i32::from(row.is_some())`）
- **いまどう見えるか**: `coverage.rs:568-578` が「① 記録あり」を `core.event` から
  `count(*)` で引いているので、**更新だけが届いた日も「① 記録あり」になる**
  （出来事の時刻がその日にある限り）。画面は倒れない
- **なぜ今入れないか**: 数え方の正典は `collection-coverage`（ST02）が持つ。
  ST03 が変えると **NFR-13 の分子が動く**（成功条件 1 の合否に触る）
- **いつ・どこで**: ST02 の merge 後、必要なら `fix/coverage-count-updates` で。
  **数え方を変えるなら本人に問う** —— 達成日数が動くので `premise` の型
- **根拠**: `openspec/changes/st03-idempotent-ingest/tasks.md` 13.2 (e) /
  `openspec/changes/st03-idempotent-ingest/deep.md`「あわせて、`lib.rs:224` は稼働記録の件数に
  『新しく入った行だけ』を足すので、Q1 の更新で入った再取得は 0 件として数えられる」

## st03-idempotent-ingest R-g — `core.coverage` に削除・切り詰めの門が無い

- **何を**: `core.coverage` / `core.coverage_span` に `UPDATE` / `DELETE` / `TRUNCATE` の門を置く
  （`core.reject_truncate()` は ST03 が作ったので、`TRUNCATE` は 2 行で足せる）
- **なぜ**: `crates/server/src/lib.rs` のコメント自身が「**その日の稼働記録は二度と戻らない**
  （引き直す経路が無い）」と書いている帳簿に、門が 1 つも無い。実測で
  `TRUNCATE core.coverage` が rc=0 で通る
- **なぜ ST03 で入れないか**: `core.coverage` は `collection-coverage` の表で、門を置くと
  **ST02 のコードとテストが何をしてよいかが変わる**（実際 ST03 のテストは
  `DELETE FROM core.coverage` を使っている）。他の capability の表に錠を掛けるのは、
  その capability の spec が決めること
- **いつ・どこで**: ST02 の merge 後に `fix/coverage-gates` で。担当は見つけた側（ST03）
- **根拠**: `openspec/changes/st03-idempotent-ingest/review/code.md` の R100 / MEDIUM-17

## st03-idempotent-ingest R-k — 更新が日をまたぐと `event_count` が旧日に残る

- **何を**: 外部サービス由来の更新は `event_time` を書き換えられるので、
  **旧日の `core.coverage.event_count` が +1 されたまま残り、新日には 0 の行が立つ**
- **いまどう見えるか**: 状態の出どころが `core.event` の `count(*)` に移っている
  （`coverage.rs:568-578`）ので**画面は倒れない**。倒れるのは
  `core.coverage.event_count` を実数として読む経路だけ
- **なぜ ST03 で入れないか**: 数え方の正典は `collection-coverage` が持つ。R-e と同じ理由
- **推奨**: `core.coverage.event_count` の doc に「状態の出どころではない。
  更新で出来事の時刻が動くと実態と一致しないことがある」を明記する
- **根拠**: 実装レビュー MEDIUM-11（`openspec/changes/st03-idempotent-ingest/review/code.md`）

## st07-active-window R10 — NFR-13 の分母から「PC が止まっていた日」を外す

- **何を**: `crates/server/src/coverage.rs` の `Subject::Usage` の数え方を、
  **C-02 が集める 2 ソース（`c02-window` / `c02-browser-history`）だけ**
  「生存信号が 1 件でも届いた日を分母、うち取得できる状態だった日を分子」に変える。
  写真（`c01-photo`）は現状のまま（常時稼働の C-01 が集めるので条件が違う）。
  `openspec/specs/collection-coverage/spec.md` の
  「成功条件 1 の達成日はソースの主語で分けて数える」に delta が要る
- **なぜ今入れないか**: `collection-coverage` は ST02 の capability で、**ST07 は持っていない**
  （`docs/stories/INDEX.md` の表）。ST02 は merge 済み・archive 前で凍結されており、
  走っている Story へ差し戻すと往復が生まれる（実測: ST02 と ST03 が 12 時間で 5 往復）
- **いつ・どこで**: ST02 の archive 後に `fix/nfr13-c02-denominator` で。担当は見つけた側（ST07）
- **根拠**: `openspec/changes/st07-active-window/review/deep.md` R10 /
  `openspec/changes/st07-active-window/deep.md` Q2。
  要件本文（`docs/requirements.md` の NFR-13）は **2026-09-12 に訂正済み**（4 回目の ★）
- **ST07 の実装はこれを待たない**: FR-82（PC が止まっていた期間を記録として残す）さえ入れば、
  数え方は後から引き直せる。ST07 が止まる理由にはならない

### 事実（ST07 の深掘りで判った）

NFR-13 の訂正 2 回目 (1) は「PC を開かない日は記録 0 件になる」を**生存信号で塞いだつもり**だったが、
**生存信号も電源とともに消える**ので塞がっていなかった。「利用が主語」の 3 ソースのうち、
写真を集めるのは常時稼働の C-01、ウィンドウとブラウザ履歴を集めるのは PC 上の C-02 で、
**同じ式に乗るという前提が事実と違っていた。**

そのままだと 95 %（= 未達成でよいのは年 18 日まで）は、収集の稼働ではなく
**本人が PC を何日開いたか**を測る式になる。

---

> **R-e / R-k（ST03）と R10（ST07）は、どれも `NFR-13` の数え方に触る。**
> `fix/` で拾うときは 3 件まとめて見ること —— 分子（更新だけが届いた日を数えるか。R-e）と
> 分母（PC が止まっていた日を外すか。R10）を別々に動かすと、

> R10 は**要件本文の訂正が済んでいる**（`★ 2026-09-12`。ST07 の深掘り Q2 で本人が決めた）ので、
> 残っているのは実装だけ。

## st07-active-window R38 — PC を開かなかった日に「① 記録あり」が立ちうる

- **何を**: ST07 の C-02 は、前景の変化のほかに **`idle`（離席の出入り）/ `powered-off`（PC が止まっていた期間）/
  `excluded`（除外した件数）/ `clock-skew`（時計のずれ）** を同じ `core.event`（`c02-window`）に書く
  （`docs/collector-contract.md` §C-02）。`coverage.rs` の「① 記録あり」は `core.event` の行の有無で引くので、
  **PC を開かなかった日でも、翌朝の起動で書かれた `powered-off` の区間（`event_time` は前夜）や、
  離席の区間を閉じた記録がその日に落ちれば「① 記録あり」になる**
- **なぜ今入れないか**: 数え方の正典は `collection-coverage`（ST02）が持つ。ST02 は凍結中
- **いつ・どこで**: ST02 の archive 後、`fix/nfr13-c02-denominator`（上の R10）と同じ change で。
  `payload->>'kind'` で種類を見て、**前景の変化（`foreground`）だけを「記録あり」に数える**か、
  種類ごとの意味（`powered-off` は ⑦ 相当など）を決める。**達成日数が動くので本人に問う**（`premise` の型）
- **ST07 の実装はこれを待たない**: 記録には種類が載っているので、数え方は後から引き直せる
- **根拠**: `openspec/changes/st07-active-window/review/code.md` R38（pr-test-analyzer の指摘を写したもの）



## st12-archive-ingestion R11 — 空白の日の「途絶」の判定が、正典と実装で読みが違う

- **何を**: 正典（`collection-coverage` の「ソース × 日 の状態は 8 つのいずれかに決まる」）の (8) は「**直前の**記録・生存信号からの経過が想定間隔を超えていれば途絶」だが、
  実装（`crates/server/src/coverage.rs:806-813` の判定）は「**前か後ろ**に想定間隔以内の活動があれば『動いていた・記録なし』」と読んでいる
- **いつ差が出るか**: 記録の間に想定間隔を超える空きがあり、その後ろにまた記録があるとき。Must の 5 本（想定間隔 6〜24 時間）では日の単位でほとんど差が出ないが、
  **書庫のソース（想定間隔 60 日。ST12）では、視聴しなかった 2〜3 か月の後半が、正典では途絶・実装では動いていた・記録なし**になる
- **なぜ今入れないか**: ST02 は archive 済みで、判定は ST02 の本人の決定。ST12 は判定を変えない（design D13）
- **いつ・どこで**: ST12 の下流が書庫のソースの格子を出す前後で、`fix/coverage-outage-rule` の小さな change で。**正典と実装のどちらに揃えるかは本人に問う**（格子の見え方が変わる。`premise` の型）
- **根拠**: `openspec/changes/st12-archive-ingestion/review/deep-r2.md` R11
