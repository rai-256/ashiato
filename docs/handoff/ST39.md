# ST39 への申し送り

ST39（衛星が記録を書き、自分の書いたものだけを直せる）は、この申し送りを書いた時点（2026-10-12）では上流が始まっていない。
**差し戻しではない** —— 書き出し（ST33）が決めた数え方と、ST39 が決める印の形が噛み合うように置いておく。

## docs/audit/2026-10-12-st33-consistency.md C11 — 衛星が付けた削除の印を、書き出しの「後に消した記録の件数」に数えるか

- 何を: ST33 の書き出しの画面は「この書き出しの後に消した記録が N 件あります」を出す。数え方は design D17（仮）で、本人の削除を
  `deleted_by IS NULL OR deleted_by NOT LIKE 'rebuild:%'`（`Mark::of` と同じ読み方）で読む。FR-64 ★ 2026-10-11 で衛星も自分の書いた記録に削除の印を付けられるので、
  その `deleted_by` が `rebuild:` でなければ、本人が消したものとして数える
- どうする: 衛星の削除の印の `deleted_by` の形を決めるときに、ST33 の D17 の読み方から外すか（文は「本人が消した」）、含めて文を「消した」に変えるかを決め、
  試験を 1 本置く（衛星が消した記録が `erased_after` に入るか入らないか）
- 失われるもの: 無い（件数の文だけ。書き出しから除く判定は書き手を問わない）

## st41-event-end-time R3 — 外部の識別子を持たない送り手は、幅のある出来事を終わってから送る

- 何を: ST41 は同じ記録かどうかの鍵（内容のハッシュ）に終わりの時刻を混ぜない（ST41 の深掘り Q7・design D7）。外部の識別子のある記録は、
  終わりだけが違う到着も更新として前の版を残して入る（進行中を終わりなしで送り、終わったら同じ識別子で終わりつきを送る）。
  外部の識別子の無い記録の終わりだけが違う到着は畳まれ、後から来た終わりは捨てられる（応答は `duplicate: true` の受理なので、送り手からは見えない）
- どうする: 衛星の書き込みの契約（FR-64 / FR-99）に、「進行中の出来事を送るなら外部の識別子を付ける。付けない送り手は終わってから送る」を書く。
  衛星の種類の登録で、幅のある出来事を書く種類に記録ごとの外部識別子を求めるかを決める
- 失われるもの: 契約に書かないと、外部の識別子を持たない衛星が送った進行中の記録の終わりが黙って捨てられる（`loss: discarded`。ST41 の Q7 の推奨の側で失うもの）

## st41-event-end-time R5 — 始まりの側のずれとタイムゾーンの値を検査していない（既存の穴）

- 何を: ST41 は終わりのずれ（−1,439〜1,439 分）とタイムゾーン（空でない・U+0000 を含まない）を取り込み口で検査する（design D2）。始まりの側の
  `tz_offset_min` / `tz_id` には同じ検査が無い（`ingest.rs` の `validate` に無く、`core.event.tz_offset_min` に CHECK も無い。`lib.rs` の主張と場所の記録の検査の注記）。
  範囲外のずれは受理された顔で格納され、読み出しで時刻に直せない
- どうする: 衛星の記録にも FR-20 を課す（FR-99）ときに、始まりの側にも同じ検査を足すか決める。収集アプリ（ST01 の送信契約）の送る値が範囲内であることを確かめてから足す
- 失われるもの: 無い（足すまでの間、範囲外の値が入りうるだけ。断る側に倒すと、その 1 件を失う）

## st41-event-end-time R9 — 1 日の並びに衛星のソースを足すなら、終わりを列から読み、重なった日すべてに出す

- 何を: ST41 の深掘り Q4 の推奨は「日の区切りは Asia/Tokyo のまま、件数は始まりの日に 1 件、『その日に何があったか』は重なった日すべてに出す」。
  ST41 は稼働記録の件数と `GET /events` の期間の重なりでこれを満たすが、1 日の並び（`day_records.rs` の許可リスト）には終わりを列に持つソースが無いので触っていない（ST41 design D12（仮））
- どうする: 衛星のソース（睡眠・読書など）を 1 日の並びの許可リストに足すときに、その `Span` を終わりの列 → 内容の鍵の順で読み、日をまたぐ記録を重なった日すべてに出す
  （browsing-views の「区間を持つ記録は、その区間がその日と重なれば、始まりがその日の外でも返す」と同じ扱い）。試験を 1 本置く
- 失われるもの: 無い（表示だけ。記録は始まりと終わりの時刻のまま残る）

## st29-satellite-credentials R1 — 衛星が書く論理ソースの名前を、ST29 の名前の形で検査する

- **何を**: ST29 は衛星が登録する論理ソースと種類の名前の形を `<衛星の識別子>:<名前の部分>`（名前の部分は英小文字・数字・`-` の 1〜64 文字）と決め（深掘り Q1・扉 #30）、
  形の判定（`satellite.rs` の `name_owner`）を本体の 1 か所に置く（ST29 の tasks 2.1。この申し送りを書いた時点では未着手）。ST29 には名前を登録する口が無いので、口での検査は無い
- **ST39 で書き込みの口を作るとき**: `:` を含む論理ソースは、`:` より前の識別子の衛星だけが書ける（`name_owner` で判定し、ほかの衛星の識別子を前置した名前・形に合わない `:` つきの名前は断る）。
  本体の論理ソース（`:` の無い名前。場所の `s01-place` など）への書き込みは名前で断らず、FR-64 の種類の承認と FR-98 が決める（ST39 の完了の判定 3 は衛星が場所の座標を変えることを前提にする）。
  Scenario を置く（「衛星は自分の識別子を前置した論理ソースに書ける」「ほかの衛星の識別子を前置した名前の記録は断られる」「場所を承認された衛星は『直す』を付けて場所の座標を変えられる」）。
  整合の確認（`docs/audit/2026-10-24-st29-consistency.md`）C1 で絞った
- **失われるもの**: 無い（ST39 より前に衛星が書く口は無い）。口ができた後に検査を足すと、それまでに書かれた形の違う名前は全行の書き直しになる（FR-101）
- **根拠**: openspec/changes/st29-satellite-credentials/review/spec.md R1 / specs/satellite-platform/spec.md「衛星が登録する名前は、衛星の識別子を前置した形をとる」
