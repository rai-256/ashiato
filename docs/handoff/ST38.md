# ST38 への申し送り

ST38（衛星ごとに、読む種類と書く種類を承認できる）は、この申し送りを書いた時点（2026-10-11）では上流が始まっていない。
**差し戻しではない** —— 宛先だった Story の前提が消えたので、残っていた問いを新しい宛先へ移す。

## st12-archive-ingestion の「後続へ送るもの」— 検索・視聴の履歴を外部 AI に出してよいか

- 何を: 検索・視聴の履歴（YouTube の検索と視聴・マイアクティビティ・Takeout の Chrome の履歴）を、「外部 AI」の衛星に最初から承認するかを、
  **本人に問う**（`kind: irreversible` / `loss: exported`）。要件 FR-88 の表は、決まるまで「未決（承認しない）」に置いている
- なぜ: ST12 の深掘りは「検索語を持つソースと Chrome の履歴の既定の感度を問う」を ST24 へ送った（`openspec/changes/st12-archive-ingestion/deep.md` の
  「後続へ送るもの」）。2026-10-11 の要件の改訂で感度は承認に置き換わり、ST24 は記録ごとの「出さない」の印だけになったので、宛先が消えていた。
  承認を作るのは ST38 で、外部 AI の経路（ST27）ができた後に変えると、出た分は戻らない
- 気をつけること:
  - 本人は ST07 で、検索語を含む URL（PC の Chrome の履歴）を外部 AI に出してよい側に置いている（PERM-3 の 2026-09-12 の補足）。比べて問う
  - Takeout の Chrome の履歴には、同期された携帯の閲覧と、PC の履歴の表示範囲（90 日）より古い分が入る（ST12 の deep の (3)）
  - 要件 FR-88 の表と ★（NEEDS CLARIFICATION）は、`make_story.py` の引用では表の 1 行目までしか Story に写らない。原文を読む
- 根拠: openspec/changes/st12-archive-ingestion/deep.md / docs/requirements.md FR-88 / docs/audit/2026-10-11-consistency.md C11

## docs/audit/2026-10-12-st17-consistency.md C6 — ST17 の論理ソース `s01-feeling` を種類「主観」に属させる

- **何を**: ST17 は登録簿に `('s01-feeling', '主観', 86400, 'none')` を足す（design D1。2026-10-07。FR-102 より前）。FR-102 は全論理ソースをどれか 1 つの種類に属させる

- **根拠**: docs/audit/2026-10-12-st17-consistency.md C6 / openspec/changes/st17-daily-feeling/design.md D1 / docs/requirements.md FR-102

## docs/audit/2026-10-12-st33-consistency.md C8 — 登録の宣言に「緯度経度を持つか・幅の読み方」を足す（書き出しが読む）

- 何を: ST33 の書き出しは、本人が消した滞在の時間と重なる緯度経度つきの行を除く。緯度経度を持たないソースと幅の読み方は Rust の定数
  （`export::NO_COORD_SOURCES` / `SPAN_RULES`）で、載っていないソースは「緯度経度を持つ・次の記録まで」とみなす。衛星が登録するソース（FR-61 / NFR-24。本体のコードを変えない）は
  定数に載る経路が無く、書く間隔が長いので幅が日の単位になり、その間に本人が消した滞在が 1 つあれば記録ごと書き出しから落ち続ける
- どうする: 種類と登録の宣言（FR-62）に「緯度経度を持つか」「幅の読み方（終わりの列 / 長さ / 時刻 1 点）」を足し、ST33 の判定が定数の代わりに宣言を読む。
  **宣言の無いソースは今の既定（除く側）のまま**（緩めると消した場面の緯度経度が出て戻らない）
- 失われるもの: 無い（除き過ぎの側。書き出し直せば戻る）。ST43 の衛星の試験に「消した滞在のある期間に書いた衛星の記録が書き出しに入る」を 1 本置くと落ちる

## 2026-10-12-st12-consistency.md C1 — 検索・視聴の履歴の原文が、その時いた位置（`locationInfos`）を持つことがある

- 何を: 書庫のマイアクティビティ・YouTube の視聴と検索の項目は、原文（`raw`）に `locationInfos`（その時に端末がいた位置）を持つことがあり、
  地図の製品の項目は URL に座標を持つ。FR-88 の★は「種類をまたぐデータは当面『写真の位置』1 つだけ」と置くので、**位置を承認せず
  検索・視聴の履歴を承認した衛星に、原文ごと座標が渡る**。写真の撮影地と同じく抜くか、種類を割るかを、承認の表を決める深掘りで本人に問う
  （`kind: irreversible` / `loss: exported`）。ST45（読み出しの門）は、決まった扱いを `locationInfos` を持つ項目の試験で確かめる
- なぜ ST12 で直さないか: ST12 は原文を捨てない・欄を外さない（design D22-b）。読み出しの門はまだ無く、初期の承認の表では起きないので、いま外へ出ているものは無い
- 根拠: `docs/audit/2026-10-12-st12-consistency.md` の C1。本物の Takeout（2026-10-12 の確認バッチ）で `locationInfos` を持つ項目 13 件、URL にだけ座標を持つ項目 約 1.5 万件

## st09-media-capture R21 — ST09 が足したメディアの論理ソースの種類（FR-88 / FR-102）

- **何を**: ST09 は論理ソースを 4 つにした（`c01-photo` / `c01-screenshot` / `c01-image` / `c01-video`）。登録簿に種類の欄がまだ無い（ST38 が作る）ので、ST09 は欄を作らず
  （欄を作ると ST38 の承認の器を先に決めることになる。st09 の design D19）、割当てだけをここに送る:
  - `c01-photo` → 写真 / `c01-image` → 写真（FR-88 の★ 2026-10-17。整合の確認 2026-10-17-st09 の C11）/ `c01-screenshot` → スクリーンショット / `c01-video` → 動画
  - 撮影位置（解析した値の `lat` / `lon`・原文の EXIF の GPS の欄・動画の入れ物の位置・D-02 の原本の EXIF）は「写真の位置」の種類として、**渡すときに抜く**（記録は割らない。FR-88 の★ 2026-10-17 / st09 の deep.md C16）
- **ST38 で種類の欄を作るとき**: 上の割当てで 4 つの行を埋め、「各ソースがどの種類に属するか」の Scenario を置く（st09 の deep.md「spec の段へ渡すもの」が求めたもの）
- **それまで**: 承認の門が無いので、種類で絞る読み出しは無い。**失われるもの（A）は無い**（種類は後から割れる。FR-88 の★ 2026-10-11）
- **根拠**: openspec/changes/st09-media-capture/review/spec.md R21 / design.md D19 / docs/requirements.md FR-88・FR-102

## st29-satellite-credentials C14 — 外して登録し直した衛星の承認は空から

- **何を**: ST29 は、外した衛星と同じ識別子で登録し直すと、同じ衛星の行（番号が同じ）を外していない状態に戻す（ST29 の深掘り Q2。前の衛星の続き）。
  前の資格情報は戻さない。**承認も戻さず、何も承認していない状態から始める**（PERM-8 / ST29 の deep.md C14）
- **ST38 で承認を作るとき**: 衛星を外したときに、その衛星の承認をすべて取り消す（行を消すか取り消しの時刻を付けるかは ST38 が決める）。
  「外して登録し直した衛星は、どの種類も承認していない」の Scenario を置く（同じ番号の衛星なので、外したときに取り消していないと前の承認が生き返る）
- **それまで**: 承認が無いので、生き返るものは無い。失われるもの（A）は無い
- **根拠**: openspec/changes/st29-satellite-credentials/deep.md C14 / specs/satellite-platform/spec.md「資格情報を 1 本ずつ取り消せ、衛星を外すとその衛星の資格情報が全部止まる」
