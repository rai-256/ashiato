# ST14 への申し送り

## st06-app-usage R6 — NFR-13 の主語の仕分けを、要件だけでなく正典と実装にも反映する

- **何を**: NFR-13 の「端末が主語（位置・アプリ利用）は記録が 1 件以上ある日」という仕分けは、
  要件（`docs/requirements.md`）だけでなく **受け手側の正典**（`openspec/specs/collection-coverage/spec.md`）と
  **実装の定数**（`crates/server/src/coverage.rs` の `DEVICE_SUBJECT`）にも書かれている。
  ST06 の深掘り Q2 がこの仕分けを動かした場合、**要件だけが直り、正典と定数が古いまま残る**
- **なぜ今入れないか**: `collection-coverage` は ST12（下流）が走っている capability。
  走っている Story へ差し戻すと往復が生まれる（ST02 ↔ ST03 で 12 時間 5 往復の実測がある）
- **同じ型の事故が既に 1 件ある**: ST07 が NFR-13 に「PC 上の C-02 が集める 2 ソースだけは、
  生存信号が 1 件でも届いた日を分母とする」を足したが、`collection-coverage` の spec にその但し書きが無い
  （ST07 の spec delta は `desktop-collection` だけ。`openspec/changes/archive/2026-09-14-st07-active-window/specs/`）。
  **要件を直して正典を直し忘れる**のは、この capability で繰り返し出ている型
- **いつ・どこで**: ST12 の archive 後。ST14 の上流で `collection-coverage` の `MODIFIED` に畳む
- **根拠**: `openspec/changes/st06-app-usage/review/deep.md` R6

## st06-app-usage R5 — 「取りに行ったが取得元に無かった期間」を格子に出す

- **何を**: ST06 の深掘り Q4 で、端末が「取りに行ったが OS にイベントが残っていなかった期間」を
  記録として残すことになった場合、**受け手がそれを稼働状況の格子にどう出すか**が未定
- **なぜ今入れないか**: 同上（`collection-coverage` は ST12 が走行中）。
  ST06 は**端末の側で閉じる形**（`c01-app-usage` の記録 1 件として残す）だけを決め、
  `/drops` の理由を増やす形は取らない —— それは `collection-coverage` の変更にあたる
- **畳むまでの現状（これを知らずに着手しないこと）**: ST06 は gap の記録の**出来事の時刻を期間の終わり**
  （＝見込みの保持の下限）に置く。受け手は `event_time` の `Asia/Tokyo` の日で稼働記録を積み
  （`crates/server/src/lib.rs`）、`coverage.rs` の `decide()` は `event_count > 0` ならその日を
  ①「記録あり」と返すので、**「取れなかった」と主張する 1 件が、その日を①に塗る**。
  さらに `coverage.rs` の `DEVICE_SUBJECT` に `c01-app-usage` が残っている間は、
  NFR-13 の達成日も 1 日増える（上の R6 と同じ着地点で消える）。
  **ST06 の側でこれ以上閉じる手は無い** —— 受け手の判定は `collection-coverage` の領分
- **いつ・どこで**: ST12 の archive 後。ST14 は「収集が途切れたら気づける」Story なので、
  「収集は生きているが取得元に届かない」区間はそこで畳むのが安い
- **根拠**: `openspec/changes/st06-app-usage/review/deep.md` R5、
  `openspec/changes/st06-app-usage/review/spec.md` R2、`deep-questions.json` の Q4

## st05-clock-skew R6 — PC の時計の測定記録（`c02-window` の `kind = clock-skew`）が、その日を ① に塗る

- **何を**: PC 側の収集は 1 時間ごとに時計のずれの測定記録を `c02-window` の `kind = clock-skew` として 1 件残す（ST07 から）。
  ST05 で、**基準が 1 つも取れない契機にも**取れなかった印の付いた 1 件を残すようになった（FR-7 ★ 2026-09-15）。
  `coverage.rs` の `decide()` は `event_count > 0` を生存信号の `capturable` より先に見るので、PC が動いていた日は
  窓が読めなかった日（③）も記録の無い日（②）も、**すべて ① 記録あり に塗られる**
- **既にある性質**: ST07 も取り込み口に届く日は毎時 1 件入れていた（同じ機械の構成ではいつも届く）。ST05 はそれを「届かない日」にも広げる
- **なぜ ST05 で閉じないか**: 稼働状況の数え方は `collection-coverage`（ST12 が走行中）の領分。ST05 は `c02-window` のまま残した
  （`openspec/changes/st05-clock-skew/design.md` の D12（仮）。過去の測定記録が `c02-window` にあり、PC の送信がソースを 2 本持つ形は ST08 が作っている最中）
- **畳み方の候補**: 日の状態の数えから `payload.kind = 'clock-skew'` の記録を除く（ST06 R5 の「取れなかったと主張する 1 件」と同じ着地点で畳める）。
  除けないと判断したら、ST05 の D12 の反転条件（PC の測定記録を `c02-clock` へ移す。新しい記録だけ）を使う
- **NFR-13 の達成日には効かない**: `c02-window` は `USAGE_SUBJECT`（生存信号が来た日を分母にする）
- **いつ・どこで**: ST12 の archive 後。ST14 の上流で `collection-coverage` の `MODIFIED` に畳む
- **根拠**: `openspec/changes/st05-clock-skew/review/spec.md` R6

## st25-day-timeline Q5 — 稼働状況（S-1）が OS の明暗に追従しない（NFR-17）

- **何を**: 稼働状況の画面はダーク固定で、NFR-17（OS の明暗に追従。取れなければダーク）を満たしていない。
  `web/src/App.tsx` / `CoverageGrid.tsx` / `AchievementPanel.tsx` は `SURFACE`（ダークの値）を直に使い、`useScheme` を読まない
  （1 日の画面 `DayView.tsx` とマスタ管理 `MasterView.tsx` は追従する）
- **なぜ ST25 でやらないか**: ST25 の深掘り Q5 で本人が「ST25 は自分の画面（1 日の画面）だけ。稼働状況は ST14 へ」と選んだ。
  `docs/stories/INDEX.md` の訂正（2026-09-15、ST19）「画面の下限は画面を持つ Story が自分の画面について満たす」に揃え、
  ST02 の proposal の「NFR-17〜22 は ST25 が代表して持つ」は採らない。稼働状況は `collection-coverage` の capability で、
  ST12 の下流が走っている（同じ capability を 2 本が同時に触らない）
- **ST25 の後に目立つこと**: ST25 でルートを今日の 1 日の画面にし、稼働状況は `#/coverage` へ移る（Q4）。
  OS がライトのとき、1 日の画面（明るい）→ 稼働状況（暗い）と移るたびに明暗が入れ替わる
- **いつ・どこで**: ST14 の上流で `collection-coverage` に NFR-17 の要件を足す（ST14 の `satisfies` に NFR-17 を足すかは ST14 の上流で決める）
- **根拠**: `openspec/changes/st25-day-timeline/deep.md` Q5、`deep-answers-1.txt`
