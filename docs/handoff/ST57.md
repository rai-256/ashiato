## FR-112 の改訂の整合の確認（`docs/audit/2026-11-11-st57-fr112-consistency.md`）

深掘り第 2 回 Q11（入れ替えた収集アプリは切り方を示すまで問い合わせない）で FR-112 に ★ 2026-11-11 を足した後の食い違い。次の spec 段（`spec --answers Q11`）で D23 を書き直すときに一緒に直す。残れば下流の入口で読む。

- **C2 示すまでの間を 7 日に数えない**: 示すまで止めている間も確認は「有効」なので、7 日の Requirement のままだと、入れ替えた携帯は画面を開いて示した瞬間に「更新を確かめられていない（最後に確かめた —）」を並べうる。入れ替えた部品の 7 日の起点は「切り方を示した時」にし、Scenario を足す（PC: 送り先を 30 日前に設定・トーストが `Err` を返してから `Ok` → `update-stale` は出ない。携帯も同じ形）
- **K1 携帯の「示せた」の判断**: `SetupNotifier.canPost()` は private で、送り先の設定のチャンネル（`setup`）の重要度を見る。そのまま使うと、チャンネル `update` だけを切った人を「示せた」と数え、Q11 が防ぐ「見ないままの問い合わせ」が起きる。許可・`areNotificationsEnabled()`・**チャンネル `update` の**重要度で判断する（チャンネルを引数に取る 1 か所の関数にする）。Robolectric で `update` だけを `IMPORTANCE_NONE` にして問い合わせ 0 件の Scenario
- **K2 PC の「示せた」の判断**: `windows` 0.62 の `ToastNotifier::Setting()`（`DisabledForApplication` / `DisabledForUser`）を `Show` の前に読めば、通知を切っている人を「示せない」に数えられ、FR-112 の ★ が残す損（通知を切っていても `Ok`）の一部を消せる見込み。本物の Windows で切った状態の値はまだ確かめていない（確かめてから採る。集中モードは `Setting` に出ない）
