## st22-record-deletion R2 — 書き出しは削除済みの記録を出さない（ST22 の不可逆の担保の半分）

- 何を: 書き出し（NFR-16 / FR-66 系）が記録を読むとき、**素の `core.event` ではなく削除済みを除いた読み出し**（`core.event_live`、
  履歴は `core.event_version_live`）を読む。出す側に回すなら、**本人に問う**（`kind: irreversible` / `loss: exported`）
- なぜ: ST22 の深掘り Q1 は `loss: exported` の問いで、本人は「滞在を消すと、その時間の位置の記録も消す」を選んだ。
  その理由は**書き出しができたときに、消した場面の緯度経度が外へ出て戻らないから**（`openspec/changes/st22-record-deletion/deep.md` Q1）。
  ST22 は「消したことにする」までしかできず、**外へ出さないことの担保は ST33 が持つ**。
  一度出たファイルは回収できないので、ここは「後から直せばよい」型ではない
- 気をつけること:
  - 削除済みの行は**消えていない**（ST22 は論理削除。本文は残っている）。素のテーブルを読む実装は、何もしなくても消した場面を出す
  - 消した記録には**連鎖で消えた位置**（`user:cascade`）と**後から届いて印が付いた位置**（`user:late`）も含まれる（ST22 の design D4）
  - 削除の台帳（`core.deletion_ledger`）と消去の台帳（`core.erasure_ledger`）は記録ではない（FR-50）。書き出しに含めるかは ST33 が決める
  - 稼働状況は削除済みも数える（ST22 の深掘り Q3。本人の決定）ので、「記録の件数」と「稼働状況の件数」は一致しない
- 根拠: openspec/changes/st22-record-deletion/deep.md Q1 / review/deep.md R5 / review/spec.md R2 / proposal.md の Impact

## 2026-10-11 の整合の確認 — 書き出しの対象に、衛星の基盤で増える器を入れる

- 何を: 書き出し（NFR-16「D-01 の全記録は、外部の道具で読める形式に書き出せる」）の対象に、要件の改訂（2026-10-11。衛星の基盤）で
  増える次の 4 つを入れる。**モノの台帳**（FR-86）・**衛星の保管場所**（FR-87）・**書き手の列**（FR-24。どのソース・どの端末・どの衛星が書いたか）・
  **記録ごとの「出さない」の印**（PERM-2）
- なぜ: ST33 の完了の判定は「全記録を書き出し」だが、台帳と衛星の保管場所は記録（`core.event`）ではなく、書き手と印は封筒にまだ無い欄。
  NFR-16 の「全記録」にこれらが入るかを、要件も Story もどこにも書いていない。黙って「記録だけ」を書き出すと、
  衛星が持ち込んだモノ・衛星の都合のデータ・誰が書いたか・本人が付けた「出さない」が、書き出しから抜け落ちる
- 気をつけること:
  - 4 つとも器はまだ無い。作るのは衛星の基盤の Story（/stories で立てる）で、ST33 の上流は**その Story の後に**形を確かめる
    ★ 2026-10-12 訂正（`docs/audit/2026-10-12-st33-consistency.md` C5）: ST33 は layer 3、器を作る ST40 / ST46 は layer 6 で、ST33 の上流は「その Story の後」にならない。
    **器を作る Story（台帳 ST40・保管場所 ST46・書き手の列 ST37・印 ST24）が、ST33 の分類（design D8 の `export::CATALOG`）に自分の表と列を足す**。
    D8 / D9 の検査が、列や表を足した時点で分類を求めるので黙っては落ちない。INDEX の `data-durability` に ST24 / ST40 / ST46 を足した（C6）
  - 「出さない」の印は**衛星に出さない**の印で、本人の書き出しから外す印ではない（PERM-15 は衛星への返却だけを止める）。文面どおりに読めば、印の付いた記録も書き出し、印そのものも書き出す。別の扱いにするなら ST33 の深掘りで本人に問う
  - 印は**親の記録に従う**（PERM-2★。履歴の前の版と消去の台帳は自分の印を持たない）。書き出しでも親と束ねて出す
  - 上の R2（削除済みを出さない）とは独立した話
- 根拠: docs/requirements.md の NFR-16 / FR-24 / FR-86 / FR-87 / PERM-2 / PERM-15（いずれも 2026-10-11 の版）/ 2026-10-11 の整合の確認（C33）

### C1 — 主観の記録 `s01-feeling`（ST17）を、緯度経度を持たない側と幅の読み方に置く

- 何を: design D5a(1) の `NO_COORD_SOURCES` と D5b の `SPAN_RULES` に `s01-feeling` が無い。一覧に無いソースは「緯度経度を持つ・次の記録まで」の既定で、
  消した滞在に付けた気分と、消した滞在のある日の「日」の記録が書き出しから除かれる。ST17 の spec（`subjective-log` の spec:507）は「書き出しからは見える（Q10）」を前提にしている
- どうする: ST17 が先に archive されていれば、ST33 の下流が `s01-feeling` を `NO_COORD_SOURCES` に置き、幅は紐づけ先（`target`）で読む。ST33 が先なら ST17 の下流が足す（`docs/handoff/ST17.md`）。
  `core.source` の全ソースが「緯度経度を持つ / 持たない」と「幅の読み方」のどちらかに明示で置かれていることを試験にすると、どちらの順でも漏れが名前つきで落ちる
- 失われるもの: 無い（除き過ぎの側。書き出し直せば戻る）

### C3 — 書き出しの置き場とフォルダを 0700、ファイルを 0600 で作る

- 何を: design D3 に権限の文が無い。Linux の代わりの場所（`$HOME/.local/share`）は既定の umask だと同じ PC の別の利用者が読める。
  main は同じ「全記録の写し」である移行前の退避を 0700 / 0600 で作っている（`crates/server/src/migrate_backup.rs:138` `:150`、試験は `:239-248`）
- どうする: 同じ形で作り、unix で mode を確かめる試験を 1 本置く。Windows は利用者のプロファイルの既定の ACL に任せる（`%LOCALAPPDATA%`）。design に D<n>（仮）として書く
- 本人への問い Q9（同じ PC の衛星が書き出しを読めるか）の答えに依らず要る（別の利用者への備えで、Q9 は同じ利用者で動く衛星の話）
- → 2026-10-13: spec「全記録を自宅 PC の決まったフォルダに書き出せる」の Unix の権限の文と Scenario、design D3、deep.md の C25、tasks 2.1 に入れた。Q9 で書き出しは 1 つの zip になったので「フォルダ」はファイル 1 つ（置き場は 0700）
